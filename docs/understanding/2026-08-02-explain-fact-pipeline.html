엑셀과 워드는 정말 같은 말을 하고 있을까?
— ContentCompare가 문서를 대조하는 두 가지 방법

엑셀 표에 "충전환경온도는 -5도에서 55도"라고 적혀 있는데, 워드 문서에는 뭐라고 적혀 있을까요? 같은 말일까요, 아니면 누군가 옮겨 적다가 숫자를 실수한 걸까요? 이 이야기는 그걸 컴퓨터가 대신 확인해주는 프로그램, ContentCompare가 지금까지 어떻게 일해왔는지와 앞으로 어떻게 더 똑똑해지려는지에 대한 이야기입니다.

Section 1 · Background

이야기의 배경

큰 회사에서 새 제품을 만들 때는 문서가 정말 많이 생깁니다. 제품의 규격(예: "이 배터리는 영하 5도에서 55도 사이에서만 충전해야 안전하다")을 적어둔 엑셀 표가 하나 있고, 그걸 풀어서 설명하는 워드 문서가 있고, 회의에서 발표할 PPT도 있습니다.

문제는, 이 문서들을 사람이 한 땀 한 땀 손으로 옮겨 적는다는 거예요. 사람은 실수를 합니다. 엑셀에는 분명히 "-5도"라고 적혀 있는데, 워드 문서를 쓰던 사람이 깜빡하고 "5도"라고 적으면? 아무도 눈치채지 못한 채 회의 자료가 나가버릴 수도 있어요.

ContentCompare는 이 실수를 컴퓨터가 대신 잡아주는 프로그램입니다. 엑셀을 "기준"으로 놓고, 워드나 PPT 같은 다른 문서들과 항목 하나하나를 대조해서 같다 / 다르다 / 잘 모르겠다 세 가지 중 하나로 표시해주고, "어디에 그렇게 적혀 있길래 그렇게 판단했는지" 증거까지 같이 보여줍니다. 사람이 다시 한번 눈으로 확인하기 쉽도록요.

📌 잠깐! 이 저장소 안에는 방법이 두 가지 있어요
지금 이 프로젝트 안에는 문서를 대조하는 완전히 다른 두 가지 방법이 나란히 들어있습니다. 하나는 이미 완성돼서 실제로 쓰이고 있는 "RAG 방식"이고, 다른 하나는 지금 한창 새로 만들고 있는 "Fact 방식"입니다. 둘 다 목적지(정확한 대조)는 같지만, 가는 길이 완전히 다릅니다. 이 이야기는 두 길이 어떻게 다른지, 그리고 왜 새 길을 만들고 있는지를 설명합니다.

1) 지금 쓰이고 있는 방법 — "도서관 사서" 방식 (RAG)

이 방법을 사람에 비유하면 이렇습니다. 도서관에 정말 많은 책(워드/PPT 문서 조각들)이 꽂혀 있어요. 엑셀의 한 행을 "질문 쪽지"로 만들어서 사서에게 건네주면, 사서는 그 질문과 가장 관련 있어 보이는 페이지 10장 정도를 뽑아옵니다. 그러면 심사위원이 그 10장만 딱 보고 "네, 같은 내용이네요" 또는 "아니요, 다르네요"라고 판단합니다.

"사서가 후보를 찾는다"는 게 정확히는 두 가지 방법을 합친 거예요.

  • 뜻으로 찾기 (임베딩) — 모든 문장을 숫자 목록(벡터)으로 바꿔서, 비슷한 뜻을 가진 문장은 숫자 목록도 비슷하게 만듭니다. "매출액은 1,200억원이다"와 "작년 매출 1200억"은 단어가 다르지만 뜻이 비슷하니까 숫자 목록도 가깝게 나옵니다.
  • 낱말로 찾기 (BM25) — 옛날부터 쓰던 검색엔진 방식으로, 정확히 같은 단어가 들어있는지를 봅니다. 제품 이름이나 숫자처럼 "정확히 똑같아야 의미 있는" 것들을 잘 잡아냅니다.
  • 두 리스트 합치기 (RRF) — 뜻으로 찾은 순위표와 낱말로 찾은 순위표를 합쳐서 최종 후보를 뽑습니다.
  • 골고루 뽑기 (MMR) — 후보 10개가 전부 비슷비슷한 문장이면 손해니까, 서로 다른 위치에서 온 후보들이 섞이도록 골고루 뽑습니다.

2) 지금 진행 상황

새 방식(Fact 방식)은 아직 완성되지 않았습니다. 아래는 지금까지 어디까지 만들어졌는지를 보여주는 표예요 (docs/FACT_PIPELINE_PLAN.md 기준).

단계하는 일상태
F0문서에서 있는 그대로의 정보(글자·표·위치) 꺼내기완료
F1이 문서가 대충 뭘 말하는 문서인지, 표의 각 열이 무슨 뜻인지 AI가 추측완료
F2엑셀의 각 행을 깔끔한 형태로 정리 (레코드)완료
F3레코드/문단을 "사실 카드"(Fact)로 바꾸기 — 오늘의 주인공구현 완료, 실전 검증 대기
F3.5진짜 문서로 제대로 되는지 확인 + 정답지 만들기시작 전
F4사실 카드가 틀리지 않았는지 검사하고 고치기시작 전
F5사실 카드끼리 짝지어서 같다/다르다 비교하기시작 전
F6최종 리포트 + 옛날 방식과 성능 비교시작 전

이 글은 F0~F3, 즉 "사실 카드를 만드는 부분까지"를 중심으로 설명합니다. 아직 카드끼리 비교하는 부분(F5)은 만들어지지 않았다는 걸 기억해두세요 — 지금은 "재료를 깨끗하게 다듬는 단계"까지 온 거예요.

Section 2 · Intuition

핵심 아이디어

도서관 사서 방식의 함정

도서관 사서 비유로 돌아가 볼게요. 사서가 정말 유능해도, 딱 하나 약점이 있습니다. 애초에 사서가 후보로 뽑아오지 못하면, 심사위원은 그 내용을 아예 볼 수조차 없다는 거예요. 심사위원은 "본 것"만 판단할 수 있지, "못 본 것"은 판단할 수 없습니다.

다음 상황을 상상해봐요.

기준.xlsx (엑셀, 한 행)
항목하한치상한치
충전환경온도-555
설명.docx (워드, 두 문단)
3번째 문단: "충전환경온도는 배터리 보호를 위해 엄격히 관리되는 항목이다."
4번째 문단: "관리 범위는 -5~55℃이며, 이를 벗어나면 충전을 중단한다."

사람이 읽으면 "아, 3번째 문단과 4번째 문단을 같이 읽으면 엑셀이랑 똑같은 말이구나!"라고 바로 압니다. 그런데 RAG 방식은 문단 하나하나를 따로따로 도서관에 꽂아둡니다. "충전환경온도"라는 이름만 있는 3번째 문단은 엑셀 행과 뜻이 비슷해 보이지만 정작 숫자가 없고, 숫자만 있는 4번째 문단은 "충전환경온도"라는 이름이 없어서 검색에 안 걸릴 수도 있어요. 둘 다 후보 10위 안에 못 들면, 심사위원은 이 사실 자체를 못 보고 "모르겠다" 또는 "못 찾음"이라고 답할 수 있습니다 — 실제로는 맞는 내용인데도요!

⚠️ RAG 방식이 조용히 실패하는 경우들
  • 긴 문단을 800자 단위로 뚝 잘라버려서, 앞부분과 뒷부분이 서로 다른 조각이 되어버림
  • 같은 사실이 두 문단(또는 표+각주, 도형+발표자 노트)에 나뉘어 적혀 있으면 둘 다 애매하게 걸림
  • 표현이 너무 달라서(약어, 영어, 다른 용어) 사서가 아예 못 찾음
  • 후보를 10개까지만 보여주기로 정해놔서, 진짜 정답이 11등이면 영원히 못 봄

중요한 건, 이 실패가 조용히 일어난다는 점이에요. 시스템은 그냥 "모르겠다"고 답할 뿐, "제가 사서 단계에서 후보를 놓쳤어요"라고 알려주지 않습니다. 그래서 사람이 결과만 보면 "진짜 다른 내용이라서 그런지, 시스템이 못 찾아서 그런지" 구분하기 어렵습니다.

새 방식의 아이디어 — "먼저 사실 카드부터 만들어두자"

Fact 방식은 완전히 다르게 접근합니다. "일단 후보를 찾고 그 안에서 비교하자"가 아니라, "문서를 통째로 미리 읽고, 그 안에 있는 사실들을 전부 깔끔한 카드로 만들어두자"는 아이디어입니다. 나중에 비교할 때는 이 카드끼리 짝지으면 되니까, 애매하게 후보를 놓칠 걱정이 줄어듭니다.

레고 설명서를 만드는 것과 비슷해요. 완성된 레고 성 사진 한 장을 던져주는 대신,

  1. 부품을 종류별로 나누고 (F0: 원본 그대로 꺼내기)
  2. 이 상자가 대충 "성 만들기 세트"인지 "자동차 세트"인지 파악하고 (F1: 문서 프로파일)
  3. 부품 하나하나에 이름표를 붙이고 (F2: 엑셀 행 정리)
  4. "이 조립품은 무엇이고, 어떤 특징(색깔·크기)을 갖는다"는 카드를 만드는 것 (F3: 사실 카드 만들기)

과 같습니다. 앞서 나온 예시라면, 워드 문서의 3번째 문단과 4번째 문단은 하나로 합쳐져서 이런 카드가 됩니다.

📇 충전환경온도
하한치 (lower_limit)-5 ℃
상한치 (upper_limit)55 ℃
근거: "관리 범위는 -5~55℃이며, 이를 벗어나면..." · 출처: 설명.docx 3~4번째 문단

엑셀의 해당 행도 똑같은 모양의 카드로 바뀝니다. 이제 두 카드는 "충전환경온도"라는 같은 이름표를 달고, 같은 모양(하한치/상한치)의 값을 갖고 있으니 훨씬 쉽고 정확하게 짝지어 비교할 수 있습니다 — 이 짝짓기 단계(F5)는 아직 만들어지지 않았지만, "카드가 준비돼 있으면 비교가 쉬워진다"는 게 핵심 논리입니다.

그런데, AI가 카드를 지어내면 어떡하죠?

아주 좋은 의심이에요. AI(LLM)는 가끔 그럴싸하게 "거짓말"을 합니다(이걸 할루시네이션이라고 불러요). 카드를 만드는 걸 AI에게 맡기면, AI가 원본에 없는 값을 지어내서 카드에 적어버릴 위험이 있습니다. 새 방식은 이 위험을 막기 위해 두 가지 규칙을 강하게 적용합니다.

✅ 규칙 1 — 엑셀은 AI를 아예 안 씁니다

엑셀 행은 F2 단계에서 이미 한 번 깔끔하게 정리됐기 때문에, 그걸 카드로 바꾸는 F3 단계는 AI 호출이 0번입니다. 그냥 정해진 규칙대로 코드가 옮겨 적습니다. AI가 관여하지 않으니 지어낼 수도 없습니다.

✅ 규칙 2 — 워드/PPT는 "증거 검사"를 통과해야 함

워드/PPT는 AI가 카드를 만들긴 하지만, AI가 "이 카드는 [문단3], [문단4]를 근거로 했어요"라고 답하면, 코드가 진짜로 그런 문단이 존재하는지 대조합니다. 존재하지 않는 근거를 댄 카드는 그 자리에서 통째로 버려집니다.

이게 왜 "맞는 접근"이라고 볼 수 있을까요? 세 가지 이유로 정리할 수 있습니다.

기준도서관 사서 방식 (RAG)사실 카드 방식 (Fact)
흩어진 내용 문단이 따로따로 검색되어 놓칠 수 있음 관련된 조각(본문+각주, 도형+발표자 노트)을 한 그룹으로 묶어서 AI에게 한 번에 보여줌
표현이 다른 경우 "하한치"와 "Lower"를 다른 말로 인식할 수 있음 정해진 사전(semantic_role)으로 "하한치=Lower=최소값"을 같은 의미로 미리 통일
AI가 지어내는 문제 후보 10개 안에서 판단하지만, 판단 자체가 근거 검증 없이 신뢰됨 근거 문단 id가 실제로 존재하는지 코드가 매번 대조·검증, 실패하면 카드 폐기
디버깅(문제 원인 찾기) 중간 과정이 로그에만 남아 추적이 어려움 모든 단계 결과가 파일(JSON)로 저장되어 사람이 직접 열어볼 수 있음
💡 정리
RAG 방식은 "필요할 때마다 빠르게 찾아서 비교"하는 방법이라 빠르고 저렴하지만, 검색이 실패하면 조용히 틀립니다. Fact 방식은 "미리 모든 사실을 정리해서 깔끔한 카드로 만들어두고, 그 카드가 진짜인지 매번 검증"하는 방법이라 느리고 손이 더 가지만, 흩어진 정보를 놓치지 않고 AI의 거짓말도 걸러낼 수 있습니다. 정확도가 훨씬 중요한 "규격 대조" 작업에는 이 방향이 더 안전한 선택입니다.

참고로 워드/PPT 문서는 F1의 "문서 프로파일"까지만 거치고, F2(레코드 정리)는 건너뛰고 바로 F3에서 문단·도형을 사실 카드로 바꿉니다. 반면 엑셀은 F1의 "열 의미 추측"과 F2 레코드 정리를 거친 뒤, F3에서는 AI 없이 규칙 변환만 합니다.

F0 — 있는 그대로 꺼내기

가장 먼저 할 일은 "문서를 있는 그대로, 해석 없이" 꺼내는 것입니다. 셀 주소, 병합 여부, 슬라이드 번호, 도형 id 같은 물리적 사실만 physical_raw.json에 담고, 이를 조금 압축한 compact_raw.json도 만듭니다. 실제로 저장된 예시를 보면 이렇게 생겼습니다. 

// artifacts/기준_xlsx/document_profile.json 근처 데이터의 원천이 되는
// compact_raw 의 표 구조 예시 (요약)
{
  "doc_type": "excel",
  "sheets": {
    "실적": {
      "rows": [
        ["제품명", "연도", "매출액", "직원수"],
        ["A제품", 2023, "1,200억원", "500명"]
      ]
    }
  }
}

아직 AI는 한 번도 등장하지 않았습니다. F0은 100% 코드입니다.

F1 — "이 문서 대충 뭐야?" 물어보기

이제 처음으로 AI에게 물어봅니다. profiler.py의 profile_document()가 문서 전체를 보여주고 "이 문서의 목적이 뭐고, 어떤 표/문단 구조를 갖고 있어?"라고 묻습니다. 실제로 저장된 결과입니다. 

// artifacts/기준_xlsx/document_profile.json
{
  "doc_type": "excel",
  "main_purpose": "제품별 연도별 매출액 및 직원수 실적 기록",
  "main_structures": [{
    "kind": "table",
    "location": "sheet=실적 / A1:D4",
    "purpose": "제품별 성과 지표(매출, 인원) 데이터 목록",
    "row_grain_hint": "특정 제품의 특정 연도 실적 정보"
  }],
  "confidence": 1.0
}

엑셀이라면 한 걸음 더 나아가서, schema_inducer.py가 "이 열은 무슨 의미야?"를 물어봅니다. 이때 등장하는 게 semantic_role(의미 역할)이라는 사전입니다. "하한치", "Lower", "최소값"처럼 표현은 달라도 뜻이 같은 것들을 미리 정의된 카테고리로 묶어줍니다. 

// contentcompare/fact/semantic_roles.py (개념 요약)
ROLE_SYNONYMS = {
    "quantitative_lower_bound": ["하한치", "하한값", "최소값", "min", "lower", "lsl"],
    "quantitative_target":      ["중심치", "기준값", "target", "nominal", "typ"],
    "quantitative_upper_bound": ["상한치", "최대값", "max", "upper", "usl"],
    ...
}

그 결과로 나온 열 의미 사전이 아래처럼 저장됩니다.

// artifacts/기준_xlsx/column_schema.json
{
  "columns": [
    {"column": "A", "field_name": "제품명", "semantic_role": "entity_name"},
    {"column": "C", "field_name": "매출액", "semantic_role": "quantitative_target"},
    {"column": "D", "field_name": "직원수", "semantic_role": "quantitative_target"}
  ]
}
🛡️ 안전장치 하나
AI가 semantic_role로 아무 단어나 마음대로 지어낼 수는 없습니다. normalize_role()이라는 코드가 항상 결과를 검사해서, 정해진 목록(하한치/중심치/상한치/이름/단위/기타 등)에 없는 값이 오면 무조건 "unknown"으로 바꿔버립니다. AI의 창의력이 시스템을 망가뜨리지 못하게 막는 장치예요.

F2 — 엑셀 행을 카드 재료로 다듬기

엑셀 행 하나하나를 record_normalizer.py가 정리합니다. 한 번에 30행씩 묶어서 AI에게 보여주고, "제품명·상한치·하한치 같은 속성들을 뽑아서 정리해줘"라고 요청합니다. 

// F2 가 만드는 Record 하나의 예시
{
  "record_id": "row-2",
  "entity": {"display_name": "충전환경온도"},
  "attributes": {
    "lower_limit": {"value": -5, "unit": "℃"},
    "upper_limit": {"value": 55, "unit": "℃"}
  },
  "source": {"sheet": "실적", "row": 2, "cell_range": "D2:E2"},
  "evidence_text": "충전환경온도 -5 55"
}
🛡️ 안전장치 — 좌표는 AI에게 안 맡깁니다
AI에게는 딱 "몇 번째 행이야?"만 물어봅니다. sheet(시트 이름)나 cell_range(정확한 셀 범위)는 코드가 원본을 다시 확인해서 직접 계산합니다. AI가 "D2:E2"라고 잘못 우겨도 무시되고, 코드가 실제로 그 행에 어떤 셀이 있었는지 보고 다시 계산한 값으로 항상 덮어씁니다.

또 하나 재밌는 장치는 이어달리기(carry-over)예요. 엑셀에서 "대분류" 열은 보통 첫 행에만 적히고 아래 행들은 비어있잖아요? 30행씩 나눠서 AI에게 보여주다 보면, 딱 그 경계에서 잘리면 대분류를 잃어버릴 수 있습니다. 그래서 각 배치가 끝날 때마다 "지금까지 확정된 분류는 이거야"라는 메모를 다음 배치에 같이 넘겨줘서 끊기지 않게 합니다.

F3 — 진짜 사실 카드(Fact) 만들기 — 핵심 단계

드디어 카드를 만드는 단계입니다. 여기서 엑셀과 워드/PPT의 길이 완전히 갈립니다.

엑셀 → Fact : AI 없이, 규칙만으로

F2에서 이미 정리를 끝냈기 때문에, F3은 그냥 형식만 바꿔주는 "번역 작업"입니다. 코드가 직접 처리하고 AI를 부르지 않습니다. 

// contentcompare/fact/fact_extractor.py (개념 요약)
def _facts_from_records(records):
    facts = []
    for rec in records.items:
        f = Fact(
            fact_id=f"fact-{rec.record_id}",          # 코드가 직접 정함
            entity_name=rec.entity.display_name,
            attributes=dict(rec.attributes),            # 있는 그대로 복사
            source={"doc_type": "excel", **rec.source.to_dict()},
        )
        facts.append(f)
    return FactSet(items=facts)

AI 호출이 0번이니 비용도 0원, 지어낼 위험도 0%입니다. F2가 이미 "의미를 이해해서 정리"하는 어려운 일을 끝냈기 때문에, F3에서는 그저 자리만 옮겨 담으면 됩니다.

워드/PPT → Fact : AI가 만들지만, 코드가 검사함

워드 문단이나 PPT 도형은 애초에 표처럼 깔끔하지 않아서 AI의 도움이 필요합니다. fact_extractor.py는 관련 있어 보이는 조각들을 하나의 묶음으로 만든 뒤 AI에게 보여줍니다. 특히 PPT는 같은 슬라이드의 도형들 + 그 슬라이드의 발표자 노트를 하나의 묶음으로 만듭니다 — 앞서 본 "본문과 각주가 나뉘어 있는" 문제를 이렇게 해결합니다. 

// AI에게 보내는 입력의 느낌 (각 조각에 id가 붙어있음)
[p001_s001] "충전환경온도"
[p001_s002] "-5~55℃, 중심치 25℃"
[s1-notes]  "0.1C, 4.55V 조건 기준"

// AI가 돌려주는 답
{
  "entity_name": "충전환경온도",
  "attributes": {
    "lower_limit": {"value": -5, "unit": "℃"},
    "upper_limit": {"value": 55, "unit": "℃"},
    "target_value": {"value": 25, "unit": "℃"}
  },
  "evidence_text": "-5~55℃, 중심치 25℃",
  "source_ids": ["p001_s001", "p001_s002", "s1-notes"]
}

여기서 가장 중요한 부분이 나옵니다. AI가 source_ids로 어떤 조각을 근거로 삼았는지 답하면, 코드는 곧바로 "그 id가 진짜로 이 묶음 안에 있었나?"를 확인합니다. 

// contentcompare/fact/fact_extractor.py (개념 요약)
batch_ids = {u["id"] for u in batch}          # 실제로 AI에게 보여준 조각 id 들
valid_ids = [i for i in raw.get("source_ids", []) if i in batch_ids]

if not valid_ids:
    continue   # 근거가 전부 가짜면 이 카드는 통째로 버림!

fact.source = build_source_from(valid_ids)     # 진짜 id로만 출처를 다시 구성
✅ 실제 테스트로 확인된 동작
이 프로젝트의 테스트 코드(tests/test_fact_extractor.py)에는 이런 상황이 그대로 들어있습니다. AI가 ["p1", "p99"]를 근거로 댔는데 p99는 실제로 존재하지 않는 조각이었다면 → 결과 카드에는 p1만 남습니다. 만약 AI가 댄 근거가 전부 가짜라면 → 그 카드 자체가 사라집니다. "그럴듯하지만 근거 없는 카드"가 최종 결과에 살아남지 못하게 코드가 매번 검사하는 거예요.

이렇게 만들어진 Fact는 fact_id, source, search_text 이 세 가지 값을 AI가 뭐라고 답했든 상관없이 항상 코드가 새로 계산해서 덮어씁니다. AI는 "무슨 사실이 있는지, 값이 얼마인지"만 책임지고, "이 카드의 정체를 증명하는 껍데기 정보"는 전부 코드 몫입니다. 이게 지금까지(F0~F3) 만들어진 새 방식의 핵심이며, 다음 단계(F4 검증, F5 카드 짝짓기)를 위한 튼튼한 재료가 됩니다.

🔮 앞으로 만들 것 (아직 없음)
  • F4 — 카드 안의 숫자가 말이 되는지(하한치가 상한치보다 커버리진 않았는지 등) 코드로 한 번 더 검사하고, 이상하면 AI에게 "다시 만들어봐"라고 시키는 반복 교정
  • F5 — 드디어 카드끼리 짝짓기! 엑셀 카드와 워드/PPT 카드 중 같은 이름표를 가진 것끼리 묶어서 속성 값을 대조하고 같음/다름/모름을 판정
  • F6 — 사람이 보기 좋은 리포트로 만들고, 옛날 방식(RAG)과 실제로 어느 쪽이 더 정확한지 같은 문서로 비교 실험
