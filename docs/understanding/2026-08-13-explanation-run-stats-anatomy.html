1. 배경 — 왜 통계를 남기는가

1.1 아주 깊은 배경 (아는 분은 1.2 로)

ContentCompare 는 엑셀 규격표(기준)의 항목들을 워드·PPT 문서(대상)와 대조해 "같음 / 다름 / 대상에 없음 / 판단보류"를 판정합니다. 어려운 점은 두 문서가 같은 내용을 전혀 다른 모양으로 적는다는 것입니다 — 한쪽은 표의 셀, 다른 쪽은 문장, 심지어 언어가 다릅니다.

그래서 문서를 fact 라는 공통 형태로 정규화합니다. fact 하나는 "무엇에 대한 주장인가(entity_name)" + "값과 단위(attributes)" + "근거 원문(evidence_text)" + "출처 좌표(source)" 입니다.

📌 이 시스템의 제1 목표는 정확도가 아니라 검수 가능성이다 LLM 은 그럴듯하게 틀립니다. 그래서 판정마다 양쪽 원문과 좌표를 함께 싣고, 중간 산출물을 전부 디스크에 남기며, 계측(통계)을 집요하게 남깁니다. 프로젝트 규칙에도 이렇게 적혀 있습니다 — "오판·누락 추적이 목적이므로 이 계측을 제거하지 말 것." 통계는 장식이 아니라 이 시스템이 스스로를 의심하는 방식입니다.

1.2 숫자는 세 곳에서 나온다

헷갈림의 절반은 "이 키가 어느 단계에서 만들어졌나"를 모르는 데서 옵니다. 출처는 셋입니다.

블록만드는 곳세는 대상
concept: {...} concept_builder.py:338 후보 쌍 — (기준 fact × 대상 fact) 조합
fast_path_rate 등 게이트 지표 review_router.py:86 gate_stats() 비교 — (기준 fact × 대상 문서)
comparisons, decided_by_llm, llm_calls pipeline.py:212 같은 비교 단위 + LLM 호출 수
⚠️ 단위가 다르다 — 쌍 500 과 비교 100 은 같은 것을 세지 않는다 concept 블록의 500 은 후보 쌍이고, comparisons 의 100 은 비교입니다. 비교 하나에 후보 쌍이 최대 concept_recall_top_k(기본 5)개 달리므로 100 × 5 = 500 입니다. 이 둘을 같은 축에 놓고 비율을 내면 아무 의미가 없습니다.
질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

2. 용어 사전 — 숫자를 읽기 전에

아래 아홉 개만 알면 모든 숫자가 읽힙니다. 각 용어에는 왜 그렇게 만들었는지의 배경을 붙였습니다 — 배경을 모르면 숫자를 봐도 무엇을 조여야 할지 알 수 없기 때문입니다.

🔢 임베딩  recall (후보 검색)
문장을 숫자 벡터로 바꿔 "가까운 것"을 찾는 단계입니다. 파라미터는 두 개 — concept_recall_top_k(기준 항목당 몇 개까지 볼까, 기본 5)와 concept_recall_min(최소 유사도, 기본 0.3).

배경: min_score 0.3 은 임계값이 아니라 계산량 제한입니다. 설정 주석에도 "판정 아님 — 계산량 제한"이라고 못 박혀 있습니다. 한↔영 문서에서는 아무 관계 없는 쌍도 코사인 0.5~0.6 이 나오기 때문에, 0.3 으로는 사실상 아무것도 걸러지지 않습니다. 그래서 recall 은 거의 항상 5칸을 꽉 채웁니다.
🤖 LLM  개념 그래프(F7) — same_as / differs_by / unknown
"이 둘을 비교해도 되는가"만 답하는 단계입니다. 값이 같은지는 보지 않습니다. same_as 로 이어지지 않으면 아예 비교하지 않습니다.

배경: 예전에는 유사도 점수에 임계값을 걸었는데, 실측에서 정답 최저 0.697 vs 오매칭 최고 0.700 으로 두 분포가 겹쳤습니다. 코사인 점수는 "무관함"을 표현할 수 없다는 뜻이죠. 그래서 점수는 후보를 좁히는 데만 쓰고, 판정은 그래프 조회로 바꿨습니다.
👤 사람  온톨로지 승격 — pairs_from_ontology, pairs_by_code
knowledge/ontology.yaml 에 사람이 "이 둘은 같다"를 적어두면 LLM 을 건너뛰고 영구 적용됩니다. 정규화한 이름이 완전히 같은 경우도 코드가 바로 확정합니다(pairs_by_code).

배경: 번역어·약칭은 aliases: 로 묶어야 합니다. differs_by 목록에 번역어를 직접 나열하면 동의어까지 "다르다"로 선언되어 반대 효과가 납니다.
⚙️ 코드  ComparisonProbe — 코드 판정까지만 끝낸 중간 상태
compare_code() 가 만들고, LLM 을 절대 부르지 않습니다(테스트로 고정). code_result 는 match/mismatch/missing/ None 넷입니다.

배경: None 과 "unknown" 은 다릅니다 — None 은 코드가 판단을 포기했다는 뜻이고 unknown 은 최종 판정 라벨입니다. 둘을 합치면 "코드가 못 정한 것"과 "사람이 봐야 하는 것"이 섞입니다.
⚙️ 코드  Acceptance Gate 와 review_reasons
probe 를 채점해 검토 사유를 붙입니다. 사유가 하나도 없으면 "안전하게 확정 가능". 사유는 7종: code_missing, code_mismatch, code_unknown, low_confidence, partial_attribute_coverage, duplicate_entity_facts, invalid_evidence.

배경: 게이트는 탐지가 아니라 라우팅입니다. "후보가 2건 이상이다" 같은 셀 수 있는 사실만 확인하고 "어느 후보가 맞는가"는 판단하지 않습니다. 이 경계를 흐리면 게이트가 또 하나의 축약된 판정기가 됩니다.
⚙️ 코드  attribute_coverage — 커버리지
기준 fact 의 속성 중 대상 fact 에서 대응된 비율입니다.

배경: 코드의 값 대조는 공통 속성만 봅니다. 그래서 기준에 속성이 셋 있고 대상에 하나뿐이어도, 그 하나가 같으면 match 가 됩니다. 이 구멍을 수치로 드러내려고 만든 지표입니다. 분모는 기준 fact 의 전체 속성입니다.
Fast Path 와 shadow / enforce
사유가 없는 비교는 LLM 없이 즉시 확정 — 이것이 fast path 입니다. fast_path.enforce: false(기본)면 게이트는 채점만 하고 판정을 바꾸지 않습니다(shadow 모드).

배경: 이 단계는 비용을 줄이지 않고 늘립니다. 지금도 코드 match 는 LLM 을 안 부르므로, 게이트를 켜는 효과는 조용히 확정되던 판정을 LLM 으로 보내는 것입니다. 그래서 기본이 shadow 이고, unsafe_match_rate 가 "켜면 얼마나 늘어나는가"를 미리 알려줍니다.
🤖 LLM  decided_by 와 예산
판정 주체가 code 였는지 llm 이었는지 남깁니다. 개념 단계의 LLM 호출은 max_llm_calls_per_concept(기본 30)로 제한되고, 한 번에 concept_batch_pairs(기본 20)쌍씩 묶어 묻습니다.

배경: 예산이 끝나면 남은 쌍은 판정 없이 잘리고 budget_exhausted_pairs 에 기록됩니다. 이 값이 0 이 아닌데 모르고 넘어가면 "전부 대상에 없음"으로만 보입니다.
⚙️ 코드  needs_review → low_confidence
후보에 붙는 깃발인데, 생산자에 따라 뜻이 다릅니다. 개념 그래프 경로에서는 "이 연결을 LLM 이 만들었는가"를 뜻합니다(점수 경계가 아닙니다).

배경: 아직 아무도 확인하지 않은 연결 위에서 코드가 값을 단정하면 위험하므로, LLM 이 한 번 더 보게 합니다. 코드·온톨로지가 확정한 연결은 False 입니다.
질문 메모 아홉 용어 중 아직 흐릿한 것이 있으면 적어보세요.

4. 가장 중요한 것: 분모가 셋이다

이 통계를 오독하는 가장 흔한 이유는, 모든 비율이 100 을 분모로 쓴다고 가정하기 때문입니다. 실제로는 지표마다 분모가 다르고, 그것은 의도된 설계입니다.

분모 = 100
전체 비교
fast_path_rate
secondary_review_rate
result_changed_count
code_overridden_count
분모 = 24
후보가 있던 비교
mean_attribute_coverage
(initial_result == missing 76건 제외 — 커버리지가 낮은 게 아니라 잴 대상이 없기 때문)
분모 = 2
코드 match
unsafe_match_rate
(코드가 match 라고 한 건만. 이 실행에선 단 2건)
⚠️ 전환 비용은 enforce_new_llm_count 로 볼 것 — 아래 정정

코드로 보면 분모의 차이가 명확합니다.

total = len(comparisons)                                    # 100
safe  = sum(1 for c in comparisons if c.safe_to_finalize)   # 0

code_match = [c for c in comparisons if c.initial_result == MATCH]   # 2건
unsafe     = sum(1 for c in code_match if not c.safe_to_finalize)    # 2건

measured = [c for c in comparisons if c.initial_result != MISSING]   # 24건

return {
  "fast_path_rate":       round(safe / total, 4),                       # 0/100  = 0.0
  "secondary_review_rate": round(1 - safe / total, 4),                  # 1.0
  "unsafe_match_rate":     round(unsafe / len(code_match), 4),          # 2/2    = 1.0
  "mean_attribute_coverage": round(sum(c.attribute_coverage
                                       for c in measured) / len(measured), 4),  # 0.1278
}
⚠️ 그래서 unsafe_match_rate: 1.0 은 "100% 위험"이 아니다 분모가 2 입니다. "코드가 의견을 낸 두 건이 둘 다 검토 대상이 됐다"는 뜻일 뿐이죠. 비율이 아니라 분모의 크기를 먼저 보세요.
🔧 정정 (2026-08-13) — unsafe_match_rate 는 전환 비용이 아니다 이 페이지의 초판은 이 값을 "enforce 를 켜면 늘어날 LLM 호출 비율"로 설명했습니다. 그렇게 읽으면 안 됩니다. 게이트 사유 셋(low_confidence · code_unknown · duplicate_entity_facts)은 finalize() 가 이미 LLM 으로 보내는 조건과 같은 사실을 가리키므로, 켜도 호출이 늘지 않습니다.

그래서 enforce_new_llm_count / enforce_new_llm_rate 가 추가됐습니다 (커밋 4993933) — 정말로 새로 늘어나는 호출만 셉니다. 실측에서 unsafe_match_rate 0.88 이 실제 순증가 10%를 3.5배 부풀렸습니다 (unsafe 7건 중 5건은 이미 LLM 경로였음).
질문 메모 분모가 왜 지표마다 달라야 하는지 등, 궁금한 점을 적어보세요.

rejected_evidence / rejected_differs_by확인 필요 LLM 의 same_as 제안을 코드가 거부한 수(인용 실패 / 모순). 과차단의 흔적
🔍 differs_by 454 는 문제인가? 그 자체로는 정상입니다. recall 은 "가장 가까운 5개"를 무조건 채우므로, 대상 문서에 없는 항목이라도 엉뚱한 후보 5개가 붙습니다. 예를 들어 기준의 고객 표준 버전 에는 Rated charging voltage(0.596), Rated capacity(0.551) … 가 후보로 붙는데, 이들을 differs_by 로 막는 것은 정답입니다.

문제는 정답 쌍까지 막혔을 때입니다. 실제로 이 저장소 산출물에서 최대충전전류 ↔ Maximum charging current 가 recall 1위(0.691)였는데 same_as 제안이 거부되어 unknown 으로 떨어진 사례가 있습니다.

5.3 검토 사유 (review_reasons)

막대의 회색 배경은 그 사유가 붙을 수 있는 최대치(=분모)입니다. 첫 줄만 분모가 100 이고 나머지는 24 라는 점을 눈으로 확인해 보세요.

사유이 실행에서의 해석
code_missing 76 후보가 하나도 없음. 단독 반환이라 다른 사유와 절대 겹치지 않는다 (evaluate() 가 return [CODE_MISSING] 로 즉시 끝냄). 왜 단독인가: 함께 평가하면 모든 missing 에 "커버리지 0"과 "대상 fact 없음"이 따라붙어 사유 통계가 온통 partial_coverage 로 보이면서 진짜 원인을 덮는다
low_confidence 24/24 후보가 있는 전건. pairs_by_code: 0 이 원인 — 모든 개념 연결을 LLM 이 만들었으므로 needs_review=True. 한↔영 문서쌍에서는 정상
partial_attribute_coverage 23/24 커버리지 1.0 인 비교가 단 1건. 아래 code_unknown 과 같은 뿌리
code_unknown 22/24 코드가 판단 포기. 공통 속성 키가 없거나 단위 등가를 모름
duplicate_entity_facts 8/24 후보가 2건 이상. 1:N 판정 문제가 실제로 8건 발생 중 (현재 candidates[0] 으로 조용히 확정됨)

5.4 mean_attribute_coverage 0.1278 을 그림으로

기준 fact 하나가 속성을 여러 개 갖고, 대상 fact 는 보통 하나만 갖습니다. 코드는 공통 키만 보므로 이런 그림이 됩니다.

기준(엑셀) fact — 속성 8개
target_value ✓lower_limitupper_limit unitconditiontolerancenoterank
대상(워드) fact — 속성 1개
target_value ✓
커버리지 = 대응된 1 ÷ 기준 전체 8 = 0.125  ≈  실측 평균 0.1278
🚨 커버리지가 0 이면 코드는 아예 판단을 포기한다 공통 키가 하나도 없으면 코드는 _compare_single_attributes() 로 넘어가는데, 이 함수는 양쪽 모두 속성이 하나뿐일 때만 작동합니다. 기준이 속성 8개를 가지면 즉시 None 을 돌려주고, 그것이 code_unknown 22건입니다.

즉 code_unknown 22 와 partial_attribute_coverage 23 은 두 개의 문제가 아니라 하나의 문제입니다 — 양쪽 fact 의 속성 키 어휘가 갈렸다.
질문 메모 커버리지·사유 해석에서 궁금한 점을 적어보세요.

6. 검산 — 숫자들은 서로 맞물린다

좋은 계측의 조건은 서로 독립적으로 세어진 숫자들이 맞아떨어지는 것입니다. 이 실행의 값들은 네 갈래로 검산됩니다. 하나라도 어긋나면 계측 자체를 의심해야 합니다.

검산식결과
후보 쌍 총량comparisons 100 × top_k 5 = 500 = pairs_considered ✔
LLM 호출 수500 ÷ concept_batch_pairs 20 = 25 = llm_calls ✔
비교의 분해code_missing 76 + 후보 있는 24 = 100 = comparisons ✔
same_as 간선의 분배 후보 1건짜리 16 + 후보 2건짜리 8×2 = 32 = same_as ✔
(8 = duplicate_entity_facts)

네 번째 검산이 특히 예쁩니다. same_as 는 개념 그래프가 센 간선 수이고 duplicate_entity_facts 는 게이트가 센 비교 수인데, 서로 다른 모듈이 센 두 숫자가 32 = 16 + 8×2 로 정확히 맞습니다.

✅ 그래서 총 건수를 몰라도 역산할 수 있다 처음에 comparisons 값을 몰랐을 때도 pairs 500 ÷ top_k 5 = 100 으로 총 건수를 맞힐 수 있었습니다. 계측이 서로 맞물려 있으면 일부만 봐도 전체를 복원할 수 있다는 것이 이런 설계의 실질적 이득입니다.
질문 메모 검산이 안 맞는 경우가 있다면 어떤 뜻일지 등, 적어보세요.

7. 흔한 오해 세 가지

오해 ① "candidate_pairs.json 에는 후보가 다 있는데 왜 code_missing 인가?"

가장 많이 걸리는 함정입니다. 두 파일이 다른 단계를 기록합니다. 

candidate_pairs.json  →  ① recall 단계의 순위표
                          kept:true 는 "개념 판정에 올라갔다"는 뜻이지
                          "비교 후보가 됐다"가 아니다

code_missing          →  ③ 개념 판정을 통과한 뒤 남은 후보의 수

F5 가 쓰는 후보는 ConceptMatcher.search() 가 만드는데, 이 함수는 유사도를 아예 보지 않고 개념 그래프의 same_as 파트너만 가져옵니다. 

def search(self, ref):
    out = []
    for member in self.graph.partners(self.reference_doc, ref.fact_id, self.target_doc):
        ...            # same_as 로 이어진 멤버만. 없으면 빈 리스트 → missing

실제 데이터로 보면 이렇습니다.

[고객 표준 버전] → spec_en.docx      ← recall 은 5칸을 꽉 채웠다
   0.596  Rated charging voltage      kept:true  cut_by:""   → differs_by
   0.551  Rated capacity              kept:true  cut_by:""   → differs_by
   0.550  Nominal capacity            kept:true  cut_by:""   → differs_by
   0.535  Standard charging current   kept:true  cut_by:""   → differs_by
   0.534  Nominal voltage             kept:true  cut_by:""   → differs_by
                                                  → same_as 0건 → code_missing

후보 다섯이 전부 무관한 항목이므로 이 경우 차단은 정답입니다. 워드 문서에 "고객 표준 버전"이 없으니 ⚪ 대상에 없음 이 맞습니다.

오해 ② "unsafe_match_rate 1.0 이니 코드 판정을 못 믿겠다"

분모가 2 입니다(§4). 이 지표는 코드 match 가 충분히 쌓였을 때만 의미가 있습니다. 지금은 분모가 너무 작아 노이즈입니다.

오해 ③ "사유 합계가 153 인데 비교는 100건이라 이상하다"

한 비교에 사유가 여러 개 붙을 수 있습니다. 후보가 있는 24건에는 보통 low_confidence + partial_attribute_coverage + code_unknown 이 동시에 붙습니다. 그래서 합계는 비교 수를 넘습니다. 

76 + 24 + 23 + 22 + 8 = 153  >  100

단, code_missing 76 만은 단독이라 겹치지 않는다
→ 나머지 77개 사유가 24건에 몰려 있다 (건당 평균 3.2개)
질문 메모 세 오해 외에 헷갈렸던 지점이 있으면 적어보세요.

8. 그래서 무엇을 해야 하는가

⚠️ 게이트 지표는 지금 포화라 아무것도 알려주지 못한다 100건 전부에 사유가 붙어 fast_path_rate 0 입니다. 전부 검토 대상이라는 것은 아무것도 구분하지 못한다는 뜻이죠. 게이트 손잡이(enforce)를 만질 게 아니라 상류 두 곳을 봐야 합니다.

진단 1 — 76건의 차단이 정당한가 (LLM 호출 0)

python scripts/why_missing.py --all

missing 의 원인은 여섯 가지이고 조치가 각각 다릅니다 — ①recall 실패 ②LLM 미판정 ③근거 게이트 강등 ④F3 추출 누락 ⑤의도된 차단 ⑥F5 LLM 판정. 이 도구가 산출물만으로 갈라줍니다. 함께 볼 것은 rejected_differs_by 와 rejected_evidence — 과차단의 흔적입니다. 번역어 쌍이 막혀 있으면 knowledge/ontology.yaml 에 aliases: 로 묶어 승격하면 됩니다.

진단 2 — 속성 키 어휘가 갈렸는가 (LLM 호출 0)

python - <<'PY'
import json, io, glob, collections
for p in glob.glob('artifacts/*/facts.json'):
    d = json.load(io.open(p, encoding='utf-8'))
    facts = d['facts'] if isinstance(d, dict) and 'facts' in d else d
    n = collections.Counter(len(f.get('attributes') or {}) for f in facts)
    keys = collections.Counter(k for f in facts for k in (f.get('attributes') or {}))
    print('==', p, '| fact', len(facts))
    print('   속성 개수 분포:', dict(sorted(n.items())))
    print('   키 상위:', keys.most_common(10))
PY

확인할 것은 두 가지 — 기준 fact 의 속성 개수(8 근처면 위 그림대로), 그리고 양쪽 키 이름이 겹치는가. 기준은 F1 이 정한 semantic_role 어휘(lower_limit, target_value …)로 정규화되는데, 대상(워드/PPT)은 F1·F2 를 건너뛰고 LLM 이 블록에서 바로 뽑기 때문에 키 이름이 자유롭게 나옵니다. 여기서 갈리면 커버리지가 구조적으로 0 이 됩니다.

우선순위

  1. 진단 2 먼저. 표본이 24건으로 작고 원인이 산출물에 그대로 드러나 있어 몇 분이면 확정됩니다. 여기가 문제면 연결에 성공한 24건조차 비교가 안 되고 있다는 뜻이라 파급이 큽니다.
  2. 진단 1. 76건 중 과차단이 얼마인지에 따라 온톨로지 보강으로 회수 가능한 양이 정해집니다.
  3. duplicate_entity_facts 8건 — 설계만 끝난 1:N 판정 구현.
  4. llm_calls 25 / 예산 30 — 문서가 조금만 커져도 예산이 터집니다. max_llm_calls_per_concept 를 올려두세요.
