1. 배경 — 짝을 찾는다는 것

1-1. 이 프로그램이 하는 일 알면 건너뛰기

이미 안다면 1-2 로 건너뛰세요.

기준 문서(엑셀)와 대상 문서(워드·PPT)가 있습니다. 둘이 같은 말을 하는지 확인해야 해요.

그런데 그냥 비교할 수가 없습니다. 기준에는 “충전환경온도” 라고 쓰여 있는데 대상에는 “Charging Ambient Temperature” 라고 쓰여 있을 수도 있거든요. 글자만 보면 완전히 다른 말입니다.

그래서 먼저 짝을 찾아야 합니다. “기준의 이 항목은 대상의 저 항목과 짝이겠구나” 하고요. 그게 F7 개념 판정 단계이고, 그 앞에 후보 고르기 가 있습니다.

1-2. 임베딩 — 문장을 좌표로 바꾸기

컴퓨터는 “충전환경온도”와 “Charging Ambient Temperature”가 같은 뜻인지 모릅니다. 글자가 다르니까요. 그래서 문장을 숫자 목록으로 바꿉니다. 이걸 임베딩이라고 해요.

📖 임베딩이 뭐예요? — 지도 좌표라고 생각하세요

지도에서 서울은 (37.5, 127.0), 부산은 (35.1, 129.0) 입니다. 숫자 두 개로 위치가 정해지죠. 그리고 숫자가 가까우면 실제로도 가깝습니다.

임베딩도 똑같습니다. 다만 숫자가 2개가 아니라 1,024개이고, 지도가 아니라 “뜻의 지도” 입니다. 뜻이 비슷한 문장끼리 가까운 자리에 놓입니다.

⚠️ 이 좌표를 얻으려면 서버에 물어봐야 합니다 좌표는 우리 컴퓨터가 계산하지 못합니다. 문장을 사내 서버로 보내면 서버가 1,024개의 숫자를 돌려줍니다. 즉 임베딩 = 인터넷 왕복 1회 입니다. 이 사실이 이 글 전체의 핵심입니다.
질문 메모 임베딩이나 “1,024개 숫자”가 아직 애매하면 여기 적어보세요.

2. 982는 어떻게 나온 숫자인가

로그의 982 는 마법의 숫자가 아닙니다. 아주 단순한 곱셈입니다.

그리고 로그의 마지막 줄, “LLM 위임 980건” 은 이런 뜻입니다:

💬 “LLM 위임 980건” 을 우리말로 풀면 “후보 982건 중 2건은 이름이 똑같아서 코드가 이미 확정했습니다. 나머지 980건은 앞으로 LLM 에게 물어볼 예정입니다.”

예정입니다. 실적이 아닙니다. 이 로그가 찍힌 시점에 LLM 은 아직 한 번도 안 불렸습니다.
질문 메모 “예정과 실적”의 차이 — 로그를 읽을 때 헷갈렸던 점이 있으면 여기 적어두세요.
질문 메모 “왜 10건씩인가?”, “이름이 똑같은 게 왜 2개뿐인가?” 같은 질문을 적어보세요.

3. 10분 — 우체국에 98번 다녀오기

자, 이제 98이라는 숫자를 손에 쥐었습니다. 10분은 597초입니다.

597초 ÷ 98번 ≈ 건당 6.1초

문장 하나를 좌표로 바꾸는 데 6초가 걸렸습니다. 왜 이렇게 오래 걸릴까요? 이유가 두 개 겹쳐 있습니다.

3-1. 느린 이유 ① — 편지를 한 통씩 부친다

편지 98통을 부쳐야 한다고 해봅시다. 두 가지 방법이 있죠.

⚠️ 왜 대상은 한 번에, 기준은 한 통씩인가 대상 문서의 fact 들은 미리 다 알고 있으니까 한꺼번에 보낼 수 있습니다. 기준 항목은 for 반복문 안에서 하나씩 꺼내며 처리하는 구조라, 그 자리에서는 “지금 이 하나”밖에 손에 없습니다. 코드 모양이 그대로 통신 횟수가 된 것이죠.
질문 메모 “왕복 1번에 6초”가 잘 안 믿기거나, 배치로 묶는 게 왜 그렇게 큰 차이인지 궁금하면 적어보세요.

3-2. 느린 이유 ② — 갈 때마다 수첩을 통째로 베낀다

여기서 두 번째 문제가 겹칩니다. 우리 프로그램에는 주소 수첩이 있습니다. 같은 문장을 또 물어보지 않으려고, 한 번 받은 좌표를 파일에 적어두는 거예요. 좋은 아이디어입니다. 그런데 적는 방식이 문제입니다.

🚨 이것이 9GB 메모리의 정체이기도 합니다 이 수첩은 프로그램이 시작할 때 통째로 메모리에 올라옵니다. 그리고 실행이 끝나도 파일에 남아서, 다음 실행에 더 커진 채로 다시 올라옵니다.

실측한 숫자: 수첩 항목 1개 = RAM 32.8 KB. 항목이 30만 개가 되면 9.8 GB 입니다.
🤔 왜 32.8 KB나 되나 — 숫자 하나가 24바이트짜리 “상자”라서 파이썬에서 숫자 하나는 그냥 8바이트가 아니라 24바이트짜리 객체입니다. 1,024개면 24 KB, 거기에 목록이 그 상자들을 가리키는 화살표 8 KB 가 더해져 약 32 KB.
전용 숫자 배열(numpy float32)을 썼다면 4 KB 였을 겁니다 — 8배 낭비입니다.
질문 메모 “왜 매번 전체를 다시 쓰지?”, “한 줄만 덧붙이면 안 되나?” 같은 질문을 적어보세요.

4. 코드 — 딱 두 줄이 만든 10분

10분의 원인은 서로 다른 파일에 있는 두 줄이 만났기 때문입니다. 따로 보면 둘 다 멀쩡해 보입니다.

줄 하나 — “기준 항목 하나씩 임베딩”

# contentcompare/fact/fact_matcher.py:151-153
def _embed_scores(self, ref: Fact) -> list[float]:
    query = _normalize(self.embedder.embed([fact_text(ref)], kind="query")[0])
    #                                       ↑ 리스트에 딱 1개
    return [_dot(query, vec) for vec in (self._vectors or [])]

embed() 는 리스트를 받는 함수입니다. 여러 개를 한 번에 보낼 수 있어요. 그런데 여기서는 항상 1개짜리 리스트를 줍니다. 그리고 이 함수가 기준 항목마다 한 번씩, 즉 98번 불립니다.

줄 둘 — “미스가 나면 수첩 전체 저장”

# contentcompare/similarity/cache.py:110-131
def embed(self, texts, *, kind="passage"):
    self._load()                       # ← 수첩 전체를 메모리로 (첫 호출)
    ...
    if misses:                          # 수첩에 없는 문장이 있으면
        fresh = self._embedder.embed(...)   # 서버에 물어보고
        ...
        self._dirty = True
        self._save()                   # ← 수첩 **전체**를 디스크에 다시 씀

그리고 _save() 안은 이렇습니다: 

# cache.py:76-95 (요약)
def _save(self):
    fd, tmp = tempfile.mkstemp(...)        # 새 임시 파일을 만들고
    with os.fdopen(fd, "w") as f:
        json.dump(self._cache, f)      # ← 수첩 전체를 거기에 쏟아붓고
    _replace_with_retry(tmp, path)          # 원래 파일과 바꿔치기

📖 이런 걸 뭐라고 부르나 — “N+1 문제” 한 번에 가져올 수 있는 것을 N번 나눠 가져오는 패턴을 데이터베이스 세계에서 N+1 문제라고 부릅니다. 아주 흔하고, 아주 잘 숨습니다 — 코드만 읽으면 “한 번 요청하네” 로 보이고, 몇 번 불리는지는 다른 파일에 있기 때문입니다.
질문 메모 코드 두 줄이나 “N+1 문제”에 대해 궁금한 점을 적어보세요.

5. 어떻게 고치나

지금 당장 (설정만 바꾸기)

  cache_dir: ""     # 수첩을 아예 안 쓴다 → 재작성 98회가 사라짐

수첩을 끄면 같은 문장을 또 물어보게 되지만, 재작성 98회가 통째로 사라집니다. 지금 상태에서는 수첩이 도움보다 짐입니다. 

# 이미 커진 수첩 비우기

제대로 고치기 — 순서대로

#고칠 것효과난이도
1 기준 항목 98개를 한 번에 임베딩
반복문 앞에서 미리 다 모아서 한 번 요청		 왕복 98회 → 1회
10분 → 수 초		 중
2 수첩 저장을 실행 끝에 한 번만 재작성 98회 → 1회 하

그런데 그 뒤에는 뭐가 기다리나

10분을 수 초로 줄여도 끝이 아닙니다. 16:33:22.5 부터 시작되는 2단계가 남아 있어요.
