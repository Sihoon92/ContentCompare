fact 엔진의 LLM 사용 지점 —
무엇을 넣고 무엇을 받는가

문서 파일이 판정으로 바뀌기까지, LLM 이 개입하는 여섯 자리를 실제 입출력 데이터로 따라갑니다. 그리고 왜 이렇게 나누면 비교를 잘하게 되는지, 온톨로지는 그 안에서 무슨 일을 하는지 설명합니다.

ContentCompare · --engine fact · 2026-08-05
이 페이지의 모든 예시는 저장소에 남아 있는 실제 산출물입니다 — 기준 자표준문서.xlsx, 대상 자표준_규격서.docx · 자표준_발표.pptx (artifacts/ 폴더).

이 페이지 사용법 읽다가 막히는 곳이 있으면 「질문 메모」 상자에 그대로 적어두세요. 타이핑하는 즉시 이 브라우저에 자동 저장되고(localStorage), 맨 아래 질문 저장 버튼을 누르면 질문이 박힌 HTML 사본이 다운로드됩니다. 그 파일로 docs/understanding/ 의 원본을 덮어쓴 뒤 Claude 에게 "이 페이지 질문에 답해줘"라고 하면 같은 자리에 답이 채워집니다.

1.배경 ① — 아주 처음부터: 문서 비교가 왜 어려운가

이미 이 프로젝트를 아는 분은 2장으로 건너뛰어도 됩니다. 이 절은 "문서 두 개를 대조한다"는 일이 왜 어려운지 처음부터 설명합니다.

회사에는 같은 사실이 여러 문서에 흩어져 적힙니다. 엑셀 규격서에 정격충전전압 4.55 라는 셀이 있고, Word 규격서에는 "정격 충전 전압은 4.55V 이다." 라는 문장이 있고, 발표 PPT 에는 "정격 충전 4.55V" 라는 도형 텍스트가 있습니다. 셋이 서로 맞는지 사람이 눈으로 대조하는 일은 지루하고, 지루한 일은 틀립니다.

이걸 자동화하려 하면 곧바로 세 가지 벽에 부딪힙니다.

  • 형식이 다르다. 엑셀은 격자, Word 는 문단, PPT 는 도형입니다. 같은 사실인데 담긴 그릇이 다릅니다.
  • 표현이 다르다. 정격충전전압 / 정격 충전 전압 / Rated charge voltage 는 문자열로는 전혀 다릅니다.
  • 비슷한데 다른 것이 있다. 1개월저장온도 와 표준환경온도 는 둘 다 "온도"라서 말도 비슷하고 뜻도 비슷해 보이지만, 비교하면 안 되는 서로 다른 규격입니다.

앞의 두 벽은 익숙한 해법이 있습니다. 문장을 숫자 벡터로 바꿔(임베딩) 가까운 것끼리 붙이면 표현 차이를 넘을 수 있고, LLM 에게 "이 둘이 같은 말이냐"고 물으면 형식 차이도 넘습니다. 문제는 세 번째 벽입니다. 이 페이지의 절반은 결국 세 번째 벽을 어떻게 넘었는가에 관한 이야기입니다.

용어 fact — 이 프로젝트가 문서에서 뽑아내는 최소 단위. "무엇에 대한(entity_name) 어떤 값(attributes)이며, 근거는 이 문장(evidence_text)이고, 출처는 여기 (source)"라는 네 조각으로 이루어진 JSON 객체입니다. 문서 종류가 무엇이든 결국 이 모양이 됩니다.
질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

2.배경 ② — fact 엔진의 지도와 LLM 여섯 자리

ContentCompare 에는 두 개의 엔진이 있습니다. 기존 RAG 엔진은 문서를 잘게 쪼개 검색으로 후보를 찾고 LLM 에게 "같냐"고 묻습니다. 새 fact 엔진(--engine fact)은 접근이 다릅니다. 문서를 먼저 사실의 목록으로 정규화한 뒤, 사실끼리 대조합니다.

그 흐름 전체를 한 장으로 보면 이렇습니다. 색이 곧 누가 그 일을 하는가입니다 — 코드는 결정적이고 공짜이며 항상 같은 답을 내고, LLM은 유연하지만 비싸고 흔들리며, 임베딩은 순위만 매길 뿐 판정하지 않습니다.

이 그림에서 가장 먼저 눈에 띄어야 할 것은 보라색이 생각보다 적다는 사실입니다. 흔히 "LLM 으로 문서를 비교한다"고 하면 문서 두 개를 통째로 넣고 답을 받는 그림을 떠올리지만, 여기서 LLM 은 여섯 개의 좁은 구멍으로만 들어옵니다. 그리고 각 구멍마다 무엇을 넣고 무엇을 받는지가 JSON 스키마로 못 박혀 있습니다.

설계 원칙 파일을 LLM 에 통째로 주지 않는다. 코드가 먼저 문서에서 해석 없이 관찰 가능한 물리 정보 (셀 주소, 병합 범위, 굵은 글씨, 블록 순서)만 뽑아 compact_raw 를 만들고, LLM 은 그것을 보고 구조를 추론합니다. 그래서 각 단계의 입력과 출력이 파일로 남고, 틀렸을 때 어느 단계에서 틀렸는지 짚을 수 있습니다.
질문 메모 위 흐름도에서 헷갈리는 단계가 있으면 적어보세요.

3.직관 — 세 개의 아이디어

세부로 들어가기 전에, 이 설계를 떠받치는 생각 세 개를 먼저 봅니다. 나머지는 전부 이 셋의 귀결입니다.

아이디어 ① — 다른 그릇을 같은 모양으로 옮긴다

엑셀 행, Word 문장, PPT 도형은 생김새가 전혀 다릅니다. 이것들을 직접 비교하려 들면 비교 로직이 문서 종류의 곱만큼 늘어납니다. 대신 전부 같은 카드로 옮긴 뒤 카드끼리만 비교하면, 비교 로직은 하나면 됩니다.

질문 메모 fact 카드의 필드 중 역할이 애매한 게 있나요?

아이디어 ② — "무엇에 대한 것인가"와 "값이 같은가"를 분리한다

이것이 세 번째 벽을 넘는 방법입니다. 처음에는 자연스럽게 임베딩 유사도로 짝을 지었습니다. 그런데 실측을 해보니 이런 결과가 나왔습니다.

문제는 임계값 선정 실패가 아닙니다. 코사인 점수에는 "무관함"을 뜻하는 지점이 없습니다. 0.61 과 0.77 은 정도의 차이일 뿐, "이 둘은 다른 항목이다"라는 부정 판정을 표현하는 수단이 아닙니다. 게다가 점수 스케일은 임베딩 모델마다 달라서, 0.65 라는 임계는 모델을 바꾸면 사실상 "전부 통과"가 됩니다.

그래서 질문을 둘로 쪼갰습니다.

단계묻는 것누가 답하나
F7 개념 그래프 이 둘을 비교해도 되는가 LLM 연결 제안 + 코드 차단 집행
F5 값 대조 값이 같은가 코드 확정 + LLM 애매한 것만

쪼개고 나면 유사도의 역할이 확 줄어듭니다. 이제 임베딩은 판정하지 않고, LLM 에게 검토시킬 후보 쌍을 좁히는 recall 용도로만 남습니다. 판정에서 빠졌으니 임계값을 느슨하게(기본 0.3) 잡아도 안전합니다 — 틀려도 손해가 작습니다. 낮게 잡으면 LLM 호출이 늘고, 높게 잡으면 후보가 안 만들어져 missing 이 될 뿐입니다. 최적값을 고를 필요가 사라진 것이 이 분리의 진짜 이득입니다.

질문 메모 "유사도로는 부정 판정을 못 한다"는 논지에서 걸리는 점이 있나요?

아이디어 ③ — 권한을 비대칭으로 준다

두 종류의 실수는 값이 다릅니다. 틀린 연결(무관한 두 항목을 이어놓고 "값이 다르다"고 보고)은 사람을 잘못된 수정으로 유도합니다 — 멀쩡한 문서를 고치게 만듭니다. 반면 놓친 연결은 missing 으로 남아 검토 목록에 오르고, 사람이 보면 끝납니다. 손해가 비대칭이므로 권한도 비대칭으로 줍니다.

과대평가 금지 근거 인용 게이트가 실제로 막는 것은 "원문에 없는 문구를 지어내는 것"과 값 하나만 던지는 퇴화한 인용뿐입니다. LLM 이 양쪽에서 실제로 존재하는 문구를 골라 인용하면, 두 fact 가 무관해도 이 게이트는 통과합니다. 즉 이 검사는 "주장의 출처가 실재하는가"만 보증하지 "주장이 옳은가"는 보증하지 않습니다. 잘못된 연결을 실제로 막는 것은 (a) 프롬프트 규약, (b) 승격된 differs_by, (c) LLM 이 만든 연결 위에서는 값 판정도 LLM 이 한 번 더 보게 하는 needs_review 입니다.
질문 메모 권한 비대칭 / 근거 게이트의 한계에 대해 궁금한 점.

4.LLM 입출력 카탈로그 ①~④ — 문서를 fact 로

이제 여섯 개의 구멍을 하나씩 들여다봅니다. 각 단계마다 무엇을 넣고 무엇을 받는지를 실제 데이터로 보이겠습니다. 먼저 문서 하나를 fact 목록으로 바꾸는 네 자리입니다. 이 단계들은 문서마다 독립적으로 돌기 때문에, 한 문서가 실패해도 나머지는 계속 처리됩니다.

먼저: 코드가 만드는 입력 — compact_raw

코드 F0 · raw → compact

COM 으로 문서를 열어 해석 없이 물리 정보만 뽑습니다. 서식이 곧 구조 힌트이므로 병합 범위와 굵은 글씨를 그대로 남기는 것이 중요합니다.

{"doc_type":"excel","file_name":"자표준문서.xlsx",
 "sheets":[{
   "sheet_name":"데이터","used_range":"B1:P22","n_rows":22,"n_cols":15,
   "merged_cells":[{"range":"D1:E1","value":"항목"},
                   {"range":"F1:H1","value":"정량규격"},
                   {"range":"K1:K2","value":"단위"}],
   "bold_cells":["B1","C1","D1","F1","I1","D2","E2","F2","G2","H2"],
   "rows":[
     {"r":1,"cells":{"B":"순번","C":"항목구분","D":"항목","F":"정량규격","K":"단위"}},
     {"r":2,"cells":{"D":"중분류","E":"소분류","F":"하한치","G":"중심치","H":"상한치"}},
     {"r":3,"cells":{"B":10.0,"C":"기본사양","E":"고객 표준 버전",
                     "J":"배터리승인규격 ver 4.7\nSEC Req. ver.4.7"}},
     {"r":6,"cells":{"B":40.0,"C":"기본사양","E":"정격충전전압","G":4.55}}
   ]}]}

F1:H1 이 "정량규격"으로 병합돼 있고 2행에 "하한치/중심치/상한치"가 있다는 사실 — 여기에 이 표가 2행짜리 멀티헤더라는 단서가 전부 들어 있습니다. LLM 은 이 단서를 읽습니다.

① Document Profiler — 이 문서는 무엇을 하는 문서인가

LLM ① fact/profiler.py · 문서당 1회 · 모든 문서 종류

입력
system: "당신은 문서 구조 분석가입니다.
  내용을 지어내지 말고, 확신이 없으면
  confidence 를 낮게 주세요. …"

user: compact_raw 전체
      (6000자로 잘라서 넣음)
출력 → document_profile.json
{"doc_type":"excel",
 "main_purpose":"배터리 관련 제품의 기술
   사양 및 환경 조건에 대한 정량/정성
   규격 정의서",
 "main_structures":[
   {"kind":"table",
    "location":"sheet=데이터 / B1:P22",
    "row_grain_hint":"각 행은 특정 항목에
      대한 사양 정보를 나타냄"}],
 "confidence":0.95}

이 한 줄(main_purpose)은 버려지지 않습니다. 뒤의 fact 추출 프롬프트와 개념 판정 프롬프트에 "[문서 분야]" 맥락으로 재사용됩니다. "배터리 규격서"라는 걸 아는 상태에서 판단하는 것과 모르는 상태에서 판단하는 것은 다르기 때문입니다.

② Schema Inducer — 열의 의미를 뽑는다 (엑셀 전용)

LLM ② fact/schema_inducer.py · 시트당 1회

입력
시트 이름: 데이터
크기: 약 22행 x 15열
병합 셀(헤더 힌트): [D1:E1=항목, …]
굵은 셀(헤더 후보): [B1,C1,D1,F1,…]
어휘 힌트(코드 추정, 참고용):
  {"하한치":"quantitative_lower_bound", …}

[상위 행]
행 1: {"B":"순번","D":"항목","F":"정량규격"…}
행 2: {"D":"중분류","E":"소분류",
       "F":"하한치","G":"중심치","H":"상한치"}
행 3: {"B":10.0,"E":"고객 표준 버전", …}
출력 → table_profile.json + column_schema.json
{"header_structure":{
   "header_start_row":1,"header_rows":2,
   "data_start_row":3},
 "row_grain":{"primary_entity_columns":["D","E"]},
 "columns":[
  {"column":"B","field_name":"순번",
   "semantic_role":"metadata"},
  {"column":"E","field_name":"소분류",
   "semantic_role":"entity_subcategory"},
  {"column":"F","field_name":"정량규격",
   "semantic_role":"quantitative_lower_bound",
   "raw_header":["정량규격","하한치"]},
  {"column":"G","field_name":"중심치",
   "semantic_role":"quantitative_target"},
  {"column":"H","field_name":"상한치",
   "semantic_role":"quantitative_upper_bound"}]}
여기가 핵심 아이디어 고정하는 것은 어휘가 아니라 계약이다. 문서마다 열 이름은 제각각(정량규격, Min, 하한, Lower…)이지만, LLM 에게 고정된 10종 어휘(entity_name, quantitative_lower_bound, unit, metadata …) 중에서만 고르게 하면, 이후 코드는 문서 종류를 몰라도 처리할 수 있습니다. LLM 이 하는 일은 "이 문서 특유의 것 → 우리 공통 계약"으로 번역하는 것뿐입니다.

주의할 점: 프롬프트는 "모든 열이 같은 값인 행(예: '대외비')은 배너이므로 헤더가 아니다" 같은 판별 기준을 명시합니다. LLM 에게 "알아서 잘 해봐"가 아니라, 사람이 아는 규칙을 말로 적어주는 것입니다.

질문 메모 semantic_role 어휘 설계에 대해 궁금한 점.

③ Record Normalizer — 행을 레코드로 (엑셀 전용)

LLM ③ fact/record_normalizer.py · 행 배치당 1회

입력
[행 의미] 배터리 제품의 기술 사양 및 환경
  조건에 대한 개별 항목별 규격 정보
[열 스키마(열 → 역할)]
- E열: 소분류 → entity_subcategory
- F열: 정량규격 → quantitative_lower_bound
- G열: 중심치 → quantitative_target
- K열: 단위 → unit
[직전까지 확정된 분류]
  category=기본사양, subcategory=C001D001
[데이터 행]
행 6: {"B":40.0,"C":"기본사양",

[id] 를 붙이는 이유는 추적성입니다. LLM 은 source_ids 에 자기가 근거로 삼은 블록 id 만 적어야 하고, 코드는 그 id 가 실제로 입력에 있었는지 확인할 수 있습니다. "흩어진 서술(본문 + 스피커노트)이 같은 대상이면 하나의 fact 로 병합하라"는 지시도 여기 들어갑니다 — PPT 는 도형과 노트에 정보가 쪼개져 있는 일이 흔하기 때문입니다.

코드 F4a · Rule Validator

뽑힌 fact 의 evidence_text 토큰이 원문에 80% 이상 실재하는지 검사합니다. 실패한 fact 는 버리지 않고 저신뢰(low_confidence)로 표시합니다. 나중에 F5 가 "코드가 단독 판정하면 안 되는 것"으로 취급해 LLM 에게 한 번 더 보여줍니다.

여기까지가 문서 하나의 여정입니다. 실측에서는 엑셀 20건, Word 11건, PPT 12건의 fact 가 나왔고, 형식이 전혀 달랐던 세 문서가 같은 모양의 카드 43장이 됐습니다. 이제 카드끼리 붙일 차례입니다.

질문 메모 추출 단계(①~④)에서 궁금한 점을 적어보세요.

5.LLM 입출력 카탈로그 ⑤ — 개념 판정, 그리고 그 앞뒤의 코드

F7 개념 그래프는 네 단계인데, LLM 은 그중 세 번째에서만 씁니다. 앞뒤로 코드가 감싸고 있는 구조를 먼저 보세요 — LLM 이 받는 일감의 양과 형태를 앞의 코드가 결정하고, LLM 이 낸 답의 효력을 뒤의 코드가 결정합니다.

임베딩 F7-1 · 후보 쌍 생성 (concept_builder.candidate_pairs)

기준 20건 × 대상 23건을 전부 물으면 460쌍입니다. 임베딩 코사인으로 상위만 남겨 65쌍으로 줄입니다. 다시 강조하면, 이건 판정이 아니라 계산량 제한입니다. 그래서 임계값이 concept_recall_min: 0.3 처럼 느슨해도 됩니다.

다만 여기에 구멍이 하나 있고, 코드가 그것을 메웁니다: 온톨로지가 아는 쌍은 유사도와 무관하게 무조건 후보에 추가합니다(_augment_with_ontology). 이유는 7장에서 설명합니다.

사람 + 코드 F7-2 · 확정 (resolve_known)

65쌍 중 17쌍이 LLM 없이 끝납니다. 우선순위는 온톨로지(사람) > 이름 완전일치(코드) 입니다 — 사람이 "이 둘은 다르다"고 확정했으면 이름이 같아도 잇지 않습니다.

{"relation":"same_as",
 "left":{"doc":"자표준문서.xlsx","fact_id":"fact-row-4"},
 "right":{"doc":"자표준_규격서.docx","fact_id":"fact-word-7"},
 "reason":"정규화 항목명이 동일합니다: 공칭용량",
 "decided_by":"code","recall_score":1.0}

실측 내역: 온톨로지 4쌍 + 이름 완전일치 13쌍. 남은 48쌍이 LLM 에게 갑니다.

프롬프트의 가장 중요한 한 줄 "값이 다른 것은 differs_by 의 근거가 아닙니다."
-10~70 과 -10~60 을 보고 "값이 다르니 다른 항목"이라고 추론하면, 우리가 찾으려던 불일치가 판단 재료로 소비돼 영원히 발견되지 않습니다. 개념 판정 단계에서는 "이 항목이 무엇에 대한 것인지"만 보게 합니다. 값의 차이는 결과이지 재료가 아닙니다.

또 하나: axis("측정조건", "물리량", "산정방식"…)는 정해진 목록이 없습니다. LLM 이 문서 도메인에 맞게 직접 이름을 짓습니다. 배터리 규격에서는 (물리량/측정조건)이 구분 축이지만, 계약서라면 (의무주체/기한), 재무라면 (계정과목/기간/연결범위)일 것입니다. 코드는 이 문자열을 해석하지 않습니다 — 엣지 종류(same_as/differs_by)만 보고 집행하므로, 도메인이 바뀌어도 코드는 그대로입니다.

코드 F7-4 · 조립 (concept_assembler.assemble)

코드가 위상만 보고 집행합니다. 순서가 중요합니다.

  1. 근거 검증 — LLM 이 제안한 same_as 만 검사합니다. 인용문 토큰의 80% 가 원문에 실재해야 하고 최소 3토큰이어야 합니다. 실패하면 unknown 으로 강등하되 버리지 않습니다.
  2. 병합 — Union-Find 로 same_as 를 이어 개념 노드를 만듭니다. 사람이 승격한 것(promoted)을 먼저 적용합니다.
  3. 차단 집행 — 합쳤을 때 differs_by 로 이어진 두 fact 가 한 개념이 되면 거부합니다.

강등할 때 사유를 앞에 붙이는 디테일이 있습니다.

"[거부됨: 근거 인용이 원문에 없음] 거부된 주장: 둘 다 SEC Req. ver.4.7 을 가리킨다"

LLM 이 쓴 그럴듯한 사유만 리포트에 실리면, 사람이 그걸 읽고 "아 맞네" 하며 온톨로지로 승격시켜 게이트를 사람 손으로 우회시킬 수 있기 때문입니다. 원문 사유는 검수를 위해 보존하되, 거부됐다는 사실이 먼저 보이게 합니다.

질문 메모 개념 판정 프롬프트나 그래프 조립 순서에서 궁금한 점.

6.LLM 입출력 카탈로그 ⑥ — 값 대조, 코드가 먼저 손대는 이유

개념 그래프가 "비교해도 된다"고 한 쌍에 대해서만 값을 대조합니다. 판정 규칙은 하나뿐입니다.

판정 규칙 (전부) 두 fact 의 개념이 same_as 로 이어져 있지 않으면 비교하지 않는다.
임계값 없음, 슬롯 어휘 없음, 도메인 사전 없음. "연결이 없으면 없는 것"이 기본값입니다.

그리고 대조 자체는 코드가 먼저 합니다. fact 를 {value, unit} 으로 정규화한 이유가 바로 "값 비교는 코드가 한다"였으니, 이건 설계의 일관된 귀결입니다.

코드가 단독 확정하는 경우 — LLM 0회

match 값이 같음 — 그런데 속성 이름이 다릅니다

기준  공칭용량   lower_limit  = 1150.0  (단위 없음)   ← 엑셀 F열('하한치')에 적혀 있었음
대상  공칭용량   target_value = 1150    mAh          ← Word 표에서 추출

→ match  "값이 일치합니다(1150.0). 속성 이름은 다르지만(lower_limit / target_value)
          양쪽 모두 이 항목의 단일 값입니다."

기준 엑셀이 공칭용량을 하필 '하한치' 열에 적어서 키가 어긋난 실제 사례입니다. 코드는 "양쪽 다 속성이 하나뿐이면 키 이름 차이를 무시한다"는 규칙으로 이걸 넘깁니다 — 속성이 하나뿐인 fact 는 "이 항목의 값은 X"라는 뜻이고, 키 이름은 원본 표의 열 위치에서 왔을 뿐이기 때문입니다.

단, 예외가 있습니다. lower_limit vs upper_limit 은 의미가 정반대라 값이 같아도 같은 주장이 아니므로 코드가 단정하지 않습니다.

mismatch 값이 다름

기준  공칭전압   target_value = 3.89
대상  공칭전압   target_value = 3.85 V

→ mismatch ["target_value"]  "값이 다릅니다: target_value(기준 3.89 vs 대상 3.85V)"

한쪽만 단위가 있는 경우는 호환으로 봅니다 — 실측 20 fact 중 16개가 기준 문서의 단위 열이 통째로 비어 있었고, 그때 값이 같으면 같다고 보는 것이 사람의 판단과 일치했기 때문입니다.

missing 후보 없음 — 사유가 경로마다 다릅니다

개념 경로에서 missing 은 "유사도가 임계에 못 미쳤다"가 아니라 "왜 비교하지 않았는지"입니다. ConceptMatcher.explain_missing() 이 이 문장을 만듭니다.

"개념이 같다고 판정되지 않아 비교하지 않았습니다(개념 그래프에 이 항목과 이어진 대상 fact 가 없습니다).
 다른 개념으로 차단된 후보: '표준환경온도'(측정조건 이(가) 다름) — 저장 조건과 상시 환경 조건은 다른 규격"

문구가 틀리면 사용자는 F7 에서 쓰이지도 않는 match_min_score 를 조정하러 갑니다. 사유는 사람을 어디로 보내는지를 결정하므로, 매칭 전략이 자기 사유를 직접 만들게 했습니다.

코드가 손을 떼는 경우 — 그때만 LLM ⑥

다음 중 하나라도 걸리면 코드는 판단을 포기하고 넘깁니다.

  • 공통 속성이 없음 (양쪽 다 속성이 하나뿐인 경우 제외)
  • 사전에 없는 단위 — _UNIT_ALIASES 는 ℃/도씨/degc, %/rh%, V/볼트, mA/A, mAh/Ah 정도만 담고 있고, 추측으로 부풀리지 않습니다. 사전을 넓히면 잘못된 등가 판정이 늘기 때문입니다.
  • 십진 배수 관계 — 1495 vs 1.495A. mA↔A 접두어 차이의 전형적 흔적이라 '다르다'고 단정하지 않습니다.
  • 문자열이 다름 — 문자열은 같을 때만 코드가 단정합니다. "배터리승인규격 ver 4.7 SEC Req. ver.4.7" vs "SEC Req. ver.4.7" 은 문자열이 달라도 같은 규격을 가리키기 때문입니다.
  • 근거가 불안정 — F4a 저신뢰 fact이거나, 그 연결을 LLM 이 만든 경우(needs_review).

프롬프트가 강제하는 태도 "확신이 없으면 match/mismatch 로 단정하지 말고 unknown 을 쓰세요. 틀린 단정보다 보류가 낫습니다."
그리고 "기준의 단위가 비어 있으면 대상 단위를 근거로 단위를 추측하지 마세요" — 값이 배수 관계라 단위에 따라 답이 달라진다면 그건 unknown 입니다. LLM 호출이 실패하거나 예산이 끝나도 결과를 버리지 않고 unknown 으로 남깁니다.
질문 메모 코드/LLM 분담 경계에서 애매하게 느껴지는 케이스가 있나요?

7.온톨로지의 역할

지금까지 LLM 이 판단한 것들은 실행할 때마다 조금씩 흔들릴 수 있습니다. 온톨로지는 그 흔들림을 사람이 확인한 지점부터 고정하는 장치입니다. 같은 knowledge/ 폴더에 있지만 *.md(도메인 지식)와는 성격이 다릅니다.

knowledge/*.mdknowledge/ontology.yaml
형태자연어 설명 ("매출과 Revenue는 같은 항목")항목명 쌍 → 관계
쓰임프롬프트에 참고자료로 주입LLM 을 건너뛰고 코드가 직접 적용
효력LLM 이 참고할 수도, 안 할 수도강제

실제 파일은 이렇게 짧습니다.

same_as:
  - names: ["고객 표준 버전", "문서 기준 규격"]
    reason: "둘 다 SEC Req. ver.4.7 을 가리킨다 (2026-08-03 실측 확인)"

differs_by:
  - names: ["1개월저장온도", "표준환경온도"]
    axis: "측정조건"
    reason: "저장 조건과 상시 환경 조건은 다른 규격"
  - names: ["평가환경온도", "평가 환경 습도"]
    axis: "물리량"
    reason: "온도와 습도"
  - names: ["충전환경온도", "정격 충전 전압"]
    axis: "물리량"
    reason: "온도와 전압"

3장의 "정답과 오답이 겹친다"는 그래프를 다시 떠올려 보세요. 거기 있던 오답 셋이 그대로 이 파일에 등록돼 있습니다. 한 번 확인한 오판은 다시 반복되지 않습니다.

온톨로지가 하는 네 가지 일

① recall 을 건너뛴다 — 가장 중요한 하나

직관적으로는 "온톨로지는 임베딩이 찾아온 후보에 관계를 붙여주는 사전"일 것 같습니다. 그런데 그렇게 만들면 정작 가장 필요한 쌍에 효력이 없습니다.

같은 구멍이 하나 더 있습니다. FactMatcher.search() 는 이름 완전일치를 찾으면 조기 종료합니다 — 그러면 그 기준 fact 에 대해 다른 후보가 아예 안 만들어집니다. 온톨로지 보강은 이 구멍도 같이 메웁니다.

② LLM 을 건너뛴다 — 재현성과 비용

승격된 쌍은 decided_by: "ontology", promoted: true 로 확정됩니다. LLM 이 그날 기분에 따라 다르게 답할 여지가 사라집니다. 실측 65쌍 중 4쌍이 여기서 처리됐습니다.

③ 차단이 연결을 이긴다

우선순위는 온톨로지(사람) > 이름 완전일치(코드) > LLM 입니다. 파일을 로드할 때도 same_as 를 먼저 넣고 differs_by 로 덮어씁니다. 사람이 "이 둘은 다르다"고 했으면 이름이 같아도, LLM 이 잇자고 해도 병합되지 않습니다.

④ LLM 판단의 일관성 기준선

ontology.summary() 가 개념 판정 프롬프트에 [이미 확정된 관계 — 일관되게 판단하세요] 블록으로 들어갑니다(5장 입력 예시 참고). 등록되지 않은 새로운 쌍도 사람이 정한 기준과 같은 결로 판단하도록 유도합니다.

운영 루프 — 쓸수록 결정적으로 수렴한다

한 줄 요약 온톨로지는 쓸수록 LLM 의존이 줄고 판정이 결정적으로 수렴하는 장치입니다. 처음엔 LLM 이 대부분을 판단하지만, 사람이 검토한 결과가 쌓일수록 그 문서군에 대해서는 코드가 재현 가능하게 판정하게 됩니다.
질문 메모 온톨로지 운영(무엇을 승격할지, 언제 위험한지)에 대해 궁금한 점.

8.코드 워크스루 — 어디를 고치면 무엇이 바뀌나

지금까지의 이야기가 실제로 어느 파일에 들어 있는지 정리합니다. 모두 contentcompare/fact/ 아래입니다.

파일역할고치면 바뀌는 것
pipeline.py코드 전체 오케스트레이션. _process_one_safe() 가 문서 단위 예외를 격리하고, finally 에서 계측(run_stats.json)을 반드시 남깁니다.
prompts.pyLLM 여섯 개 프롬프트가 전부 여기 모여 있습니다. 판정 태도를 바꾸려면 여기입니다. 각 프롬프트에는 버전 상수(PROFILER_VERSION 등)가 붙어 있어, 바꾸면 캐시가 자동 무효화됩니다.
llm_stage.py코드 모든 LLM 호출의 공통 관문. JSON 파싱(코드펜스에 관대) + 1회 재시도 + 호출 예산 강제. calls / retries / parse_failures 계측이 여기서 나옵니다.
semantic_roles.py어휘 ②Schema Inducer 가 고를 수 있는 10종 역할 어휘. 새 도메인에 새 역할이 필요하면 여기.
fact_matcher.py임베딩 FactMatcher=recall 전용, ConceptMatcher=개념 그래프 조회. explain_missing() 이 missing 사유 문구를 만듭니다.
concept_builder.py혼합 F7-1~3. candidate_pairs(recall+온톨로지 보강) → resolve_known(코드 확정) → judge_pairs(LLM 배치).
concept_assembler.py코드 F7-4. 근거 검증(EVIDENCE_MIN_COVERAGE=0.8, EVIDENCE_MIN_TOKENS=3), Union-Find 병합, differs_by 차단 집행, 강등 사유 라벨.
fact_comparator.py혼합 F5. _decide_by_code() 가 코드 확정, 실패하면 _decide_by_llm(). 단위 사전 _UNIT_ALIASES 와 십진 배수 판정도 여기.
ontology.py사람 knowledge/ontology.yaml 로더. 파일이 없으면 조용히 빈 온톨로지로 시작하되 로그는 반드시 남깁니다 — 경로 오타로 재현성 장치가 소리 없이 사라지는 걸 막기 위해서입니다.
validator.py코드 F4a fact 검증 + 개념 그래프 검증. evidence_coverage() 는 F4a 와 F7-4 가 함께 씁니다.

두 개의 되돌리기 스위치

fact:
  use_concept_graph: true      # false → F7 을 끄고 옛 유사도 매칭으로 롤백
  compare_use_llm: true        # false → LLM 판정 없이 코드만. 애매하면 전부 unknown
  concept_recall_top_k: 5      # recall 폭 (판정 아님)
  concept_recall_min: 0.3      # recall 임계 (판정 아님 — 느슨해도 안전)
  concept_batch_pairs: 20      # 한 번의 LLM 호출에 넣을 쌍 수
  max_llm_calls_per_concept: 30
  ontology_path: knowledge/ontology.yaml
헷갈리기 쉬운 설정 match_min_score / match_review_score / match_top_k 는 F7 경로에서 쓰이지 않습니다. use_concept_graph: false 로 롤백했을 때만 동작합니다. 개념 경로에서 missing 이 많다고 이 값을 만지면 아무 일도 일어나지 않습니다 — 그래서 missing 사유 문구를 경로별로 다르게 만든 것입니다(6장).

계측 — 이 파이프라인이 자기 자신에 대해 남기는 기록

모든 단계가 artifacts/<문서>/<단계>.json 으로 남고, 거기에 더해 계측 파일이 둘 있습니다. 

artifacts/자표준문서_xlsx/
  physical_raw.json      ← F0 물리정보
  compact_raw.json       ← F0 압축본 (= ①의 입력)
  document_profile.json  ← ①의 출력
  table_profile.json     ← ②의 출력 (1/2)
  column_schema.json     ← ②의 출력 (2/2)
  records.json           ← ③의 출력
  facts.json             ← ④의 출력
  validation_report.json ← F4a
  concept_graph.json     ← F7 전체 (기준 문서에만)
  comparison_result.json ← F5 전체 (기준 문서에만)
  run_stats.json         ← 계측: LLM 호출/재시도/파싱실패, 드롭 사유, 블록 커버리지

decided_by 필드(code / llm / ontology)가 판정마다 붙어 있어서, "LLM 이 실제로 어디서 필요한가"를 수치로 확인할 수 있습니다. 실측 위임률은 20% 였습니다. 이 계측은 장식이 아니라 오판·누락 추적의 유일한 단서이므로 제거하지 않는 것이 이 프로젝트의 규약입니다.

질문 메모 어떤 동작을 바꾸려면 어디를 봐야 할지 헷갈리는 게 있나요?

9.왜 잘 되는가, 그리고 무엇을 못 하는가

잘 되는 이유 여섯 가지

원리효과
파일을 LLM 에 통째로 안 준다 물리정보 → 구조해석 → 값추출로 쪼개져, 어느 단계에서 틀렸는지 파일로 짚을 수 있습니다.
이질적 문서를 같은 모양으로 엑셀 행 / Word 문장 / PPT 도형이 전부 같은 fact 카드가 되어, 형식 차이가 비교 로직에서 사라집니다.
"무엇인가"와 "같은가"를 분리 유사도가 원리적으로 못 푸는 부정 판정을 개념 그래프가 담당. 임계값 튜닝이 판정에서 빠집니다.
값 비교는 코드가 {value, unit} 정규화의 목적. 재현성 100%, 비용 0, LLM 은 진짜 애매한 20%만.
권한 비대칭 + 근거 인용 지어낸 연결을 코드가 강등. 모든 판정에 양측 원문이 나란히 실려 사람이 검수할 수 있습니다.
확신 없으면 unknown 틀린 단정보다 보류. 실패·예산초과도 조용히 사라지지 않고 '검토 필요'로 사람에게 갑니다.

못 하는 것 — 정직하게

  • 근거 게이트는 "옳음"을 보증하지 않습니다. LLM 이 양쪽에서 실재하는 문구를 골라 무관한 fact 를 이으면 통과합니다(3장 경고 참고). 이걸 실제로 막는 건 프롬프트 규약, 승격된 differs_by, 그리고 needs_review 재검토입니다.
  • 한글 토큰이 bigram 으로 부풀려집니다. 그래서 EVIDENCE_MIN_TOKENS=3 은 "퇴화한 인용(값 하나만 던지기)을 막는 바닥"이지 강한 검사가 아닙니다.
  • 추출 자체가 틀리면 그 아래는 전부 틀립니다. ②가 헤더를 잘못 잡으면 ③④⑤⑥이 아무리 정확해도 소용없습니다. 그래서 각 단계 산출물이 파일로 남는 것이 중요합니다.
  • F4b(LLM 교정 루프)는 아직 없습니다. JSON 준수도가 실측에서 양호해 우선순위가 낮았고, 실패 분포를 보고 설계해야 사변이 되지 않기 때문입니다.
  • Ollama 함정. 컨텍스트가 모자라면 오류가 아니라 빈 응답이 옵니다. fact 프롬프트는 기본 num_ctx(4096)를 쉽게 넘으므로 16384 이상을 권장합니다.
질문 메모 한계 중 실제로 부딪힐 것 같은 게 있나요?

답을 클릭하면 정오와 해설이 나옵니다. 헷갈리면 해당 장을 다시 보세요.

Q1. F7 개념 그래프 경로에서 임베딩 코사인 유사도는 어떤 역할을 하는가?

Q2. LLM 이 두 fact 를 same_as 로 이으면서 인용한 left_text 가 해당 fact 의 원문에 존재하지 않는 문구였다. 코드는 어떻게 처리하는가?

Q4. knowledge/ontology.yaml 에 등록된 쌍은 임베딩 recall 결과와 독립적으로 후보 목록에 추가된다. 왜 이렇게 만들었는가?

Q5. 개념 판정 프롬프트는 "값이 다른 것은 differs_by 의 근거가 아니다" 라고 못 박는다. 이 규칙이 없으면 무슨 일이 생기는가?
