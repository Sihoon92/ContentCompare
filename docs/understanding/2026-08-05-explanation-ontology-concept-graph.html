엑셀에 적힌 1개월저장온도와 워드에 적힌 표준환경온도는 닮았습니다. 임베딩은 이 둘에 0.61 점을 줬고, 정말 같은 항목인 다른 쌍에는 0.77 점을 줬습니다. 그렇다면 임계값을 0.7 로 두면 될까요? 이 글은 그 질문 자체가 틀렸다는 것에서 출발해, 그 대신 무엇을 만들었는지를 실제 실행 데이터로 끝까지 따라갑니다.

이 글을 읽는 법

중간중간 “질문 메모” 상자가 있습니다. 읽다가 막히는 지점이 있으면 그 자리에 바로 적어 두세요. 타이핑하는 즉시 브라우저에 자동 저장되고, 맨 아래 질문 저장 버튼을 누르면 질문이 박혀 있는 사본이 다운로드됩니다. 그 파일을 docs/understanding/ 의 원본 자리에 덮어쓴 뒤 Claude 에게 “질문에 답해줘”라고 하면, 같은 페이지에 답이 채워집니다.

1.1 풀려는 문제

회사에는 같은 사실이 여러 문서에 흩어져 적힙니다. 스펙 원본은 엑셀에 있고, 고객에게 보내는 규격서는 워드이며, 리뷰용 발표자료는 파워포인트입니다. 누군가 엑셀의 숫자를 고쳤는데 워드를 안 고쳤다면? 사람이 눈으로 대조하면 몇 시간이 걸리고, 그마저도 빠뜨립니다.

ContentCompare 는 기준 문서(엑셀) 한 개와 대상 문서 N 개를 받아, 기준의 각 항목이 대상에도 같은 값으로 적혀 있는지 판정합니다. 이 글에서 계속 쓸 실제 문서 세 개는 이렇습니다.

1.2 fact 카드 — 문서를 “주장”으로 쪼갠다

문서를 통째로 LLM 에 던지지 않습니다. 대신 각 문서를 먼저 fact 라는 작은 카드들로 쪼갭니다. 카드 하나는 “무엇에 대해(entity_name) 어떤 값을(attributes) 주장하며, 그 근거 원문은 이것(evidence_text)”이라는 한 덩어리입니다.

artifacts/자표준문서_xlsx/facts.json — 실제 값
{
  "fact_id": "fact-row-20",
  "fact_type": "quantitative_spec",
  "entity_name": "1개월저장온도",
  "attributes": {
    "lower_limit":  {"value": -10.0, "unit": ""},
    "target_value": {"value":  35.0, "unit": ""},
    "upper_limit":  {"value":  80.0, "unit": ""}
  },
  "search_text": "1개월저장온도 기본사양 C001D001 -10.0 35.0 80.0",
  "source": {"doc_type": "excel", "sheet": "데이터", "row": 20, "cell_range": "E20:H20"},
  "evidence_text": "-10.0, 35.0, 80.0",
  "confidence": 1.0
}

이 형태가 중요합니다. 값이 {value, unit} 으로 정규화돼 있으므로 값 비교는 코드가 결정적으로 할 수 있습니다. LLM 은 “3.89 와 3.85 중 뭐가 큰가”를 고민할 필요가 없습니다. 그건 파이썬이 훨씬 잘합니다.

1.3 그런데 어느 카드끼리 비교해야 하지?

여기가 진짜 문제입니다. 엑셀 카드 20 장, 워드 카드 11 장. 어느 엑셀 카드가 어느 워드 카드와 짝인지 아무도 알려주지 않습니다. 이름이 같으면 쉽지만(공칭용량 ↔ 공칭용량), 대개는 다릅니다:

  • 고객 표준 버전(엑셀) ↔ 문서 기준 규격(워드) — 같은 것, 이름이 완전히 다름
  • 표준환경온도(엑셀) ↔ Standard ambient temperature(PPT) — 같은 것, 언어가 다름
  • 1개월저장온도(엑셀) ↔ 표준환경온도(워드) — 다른 것, 그런데 닮았음

전통적인 답은 임베딩입니다. 문장을 수백 차원의 좌표(벡터)로 바꿔 주는 모델이 있는데, 뜻이 비슷한 문장일수록 좌표가 가깝습니다. 두 좌표의 각도를 재면 0~1 사이의 코사인 유사도 점수가 나옵니다. “점수가 높으면 짝”이라고 보는 것이 F7 이전의 방식이었습니다.

2. 배경 ② — F7 이전에는 어떻게 짝을 찾았나

쓰이는 도구 세 가지 — 잘하는 일이 서로 다르다
🔢 임베딩  임베딩
하는 일문장 → 숫자 목록으로 바꿔 '뜻이 가까운 정도'를 잰다
실제 예표준환경온도 ↔ Standard ambient temperature = 0.7492
잘하는 것글자가 달라도 뜻이 비슷하면 찾아낸다. 언어를 넘는다.
못하는 것'무관하다'를 말하지 못한다. 정답 최저 0.697 vs 오답 최고 0.700 으로 분포가 겹친다.
⚙️ 코드  BM25
하는 일겹치는 낱말이 얼마나 되는지 센다 (검색엔진의 고전 방식)
실제 예'공칭전압' 이 양쪽에 그대로 있으면 높은 점수
잘하는 것빠르고 공짜다. 임베딩 백엔드가 없을 때 폴백으로 쓴다.
못하는 것한↔영은 원리적으로 불가능하다. 낱말이 안 겹치니까.
🤖 LLM  LLM (채팅)
하는 일사람처럼 읽고 판단한다
실제 예'둘 다 공칭전압을 가리킵니다' → same_as
잘하는 것표현이 달라도, 문장에 파묻혀 있어도 이해한다.
못하는 것느리고 비싸고, 가끔 그럴듯한 거짓말을 한다. 그래서 인용을 요구한다.
셋 다 만능이 아니다. 그래서 순서가 중요하다 — 싼 도구로 먼저 좁히고, 비싼 도구는 정말 애매한 것에만 쓴다.

FactMatcher(contentcompare/fact/fact_matcher.py)가 그 일을 했습니다. 지금도 코드에 그대로 남아 있고, 3 단 전략이었습니다.

3. 문제 — 유사도는 “다르다”를 말할 수 없다

2026-08-03 라이브 실행(임베딩 모델 bge-m3, 엑셀 20 fact ↔ 워드 11 fact)의 실측 결과입니다. 이름이 완전히 같았던 10 건은 전부 정확했습니다. 문제는 임베딩으로 넘어간 4 건이었고, 그중 3 건이 애초에 비교하면 안 되는 쌍이었습니다.

기준 항목 (엑셀)임베딩 1위 (워드)점수사람이 보는 진실
고객 표준 버전문서 기준 규격0.7656✅ 같은 개념
평가환경온도표준환경온도0.6944❌ 다른 개념
충전환경온도정격 충전 전압0.6551❌ 다른 개념
1개월저장온도표준환경온도0.6084❌ 다른 개념

0.6944(오답)와 0.7656(정답) 사이에 선을 그으면 이번엔 맞습니다. 하지만 entity_name 만 임베딩해 봐도 정답 0.87~0.97 대 오답 0.61~0.87 로 여전히 겹쳤습니다. 다른 문서, 다른 모델을 쓰면 그 선은 또 옮겨야 합니다. 실제로 match_min_score = 0.65 는 bge-m3 전용 숫자였고, 코사인 절대 스케일이 다른 모델(multilingual-e5-large 등)에서는 사실상 “전부 통과”가 됩니다.

이 문제의 본질

임계값 선정에 실패한 것이 아닙니다. 코사인 점수에는 “무관함”을 뜻하는 지점이 없습니다. 0.61 과 0.77 은 정도의 차이일 뿐, “이 둘은 다른 항목이다”라는 부정 판정을 표현하는 수단이 아닙니다. 임계값이라는 도구는 이 질문에 원리적으로 답할 수 없습니다.

그리고 이 실패는 조용하지 않습니다. 1개월저장온도(-10~80℃)가 표준환경온도(21~29℃)와 짝지어지면 리포트에는 “값이 다릅니다”가 찍힙니다. 사람은 그걸 보고 멀쩡한 문서를 고치러 갑니다. 틀린 연결은 사람을 잘못된 수정으로 유도합니다.

질문 메모 “유사도로는 원리적으로 안 된다”는 주장이 납득되나요? 반례가 떠오르면 적어보세요.

4. 직관 — 온톨로지란 무엇인가

짝을 정하는 세 갈래 길 — 검문소는 한 곳에만 있다
③번 길에만 검문소가 있는 이유: ①은 코드가 글자를 직접 맞춰 본 것이고 ②는 사람이 확정한 것이라 지어냈을 걱정이 없다. 검문소는 'AI 가 지어냈는가'만 막는 장치다.

“온톨로지”는 거창하게 들리지만, 여기서 쓰는 뜻은 아주 좁고 구체적입니다.

정의

온톨로지 = “무엇과 무엇이 같은 것인가”를 적어 둔 그래프.
· 노드(개념) — 같은 것을 말하는 fact 들의 묶음
· 엣지(관계) — 두 fact 사이의 관계. 딱 세 종류뿐입니다: same_as(같은 개념) · differs_by(다른 개념) · unknown(모르겠음)

점수가 아니라 연결입니다. 그리고 연결에는 “정도”가 없습니다. 있거나, 없거나, 모르거나. 바로 그래서 유사도가 못 하던 부정 판정을 할 수 있습니다.

4.1 실제로 만들어진 개념 노드 하나

아래는 실행이 만든 concept_graph.json 의 노드 c-0013 입니다. 세 문서의 fact 세 개가 하나의 개념으로 묶였습니다.

c-0013 · label: 표준환경온도
표준환경온도 자표준문서.xlsx · fact-row-15 · E15:H15 21.0 / 25.0 / 29.0
표준환경온도 자표준_규격서.docx · fact-word-11 표준환경온도, 21 ~ 29 (중심 25), ℃
Standard ambient temperature 자표준_발표.pptx · fact-ppt-5 21 - 29 degC (target 25 degC)

한글 이름 두 개는 코드가 이름 완전일치로 이었고, 영어 이름은 LLM이 “두 항목 모두 ‘표준환경온도’를 의미합니다”라며 이었습니다. 셋이 한 노드에 들어갔다는 사실이 곧 “이 세 문서가 같은 것을 말하고 있다”는 표현입니다.

4.2 판정 규칙은 딱 하나

유일한 규칙

두 fact 의 개념이 same_as 로 이어져 있지 않으면 비교하지 않는다.

임계값 없음. 점수 없음. 도메인 사전 없음. “연결이 없으면 없는 것”이 기본값입니다.

그러면 differs_by 는 왜 필요할까요? 판정에는 필수가 아닙니다. 두 가지 다른 일을 합니다. (a) 사람에게 왜 비교하지 않았는지 설명하고, (b) 사람이 그것을 승격하면 다음 실행부터 같은 쌍을 다시 판단하지 않게 막습니다.

4.3 고정하는 것은 어휘가 아니라 계약

설계 초안은 항목명을 슬롯으로 쪼개려 했습니다 — (물리량 / 측정조건 / 한정). 배터리 스펙에서는 잘 통합니다. 평가환경온도(물리량=온도)와 평가 환경 습도 (물리량=습도)는 슬롯이 갈리니까요.

그런데 이 슬롯 목록은 배터리 스펙 20 행에서 귀납한 것이지 일반 원리가 아닙니다. 계약서라면 축이 (의무주체 / 기한 / 산정방식)일 테고, 재무제표라면 (계정과목 / 기간 / 연결범위)일 겁니다. 슬롯 목록을 코드에 박으면 도메인이 바뀔 때마다 코드를 고쳐야 합니다.

그래서 결론이 뒤집혔습니다. 슬롯이라는 형태가 중요했던 게 아니라, “두 개념이 어느 축에서 갈라지는지 명시할 수단이 있었다”가 중요했던 겁니다. 그렇다면 고정할 것은 어휘가 아니라 형식입니다.

❌ 어휘를 고정하면

AXES = ["물리량", "측정조건", "한정"]

if left.물리량 != right.물리량:
    return "다른 개념"

계약서를 넣는 순간 코드를 고쳐야 한다.

✅ 계약만 고정하면

{"relation": "differs_by",
 "axis": "측정조건",     ← LLM 이 지음
 "reason": "..."}

if edge.relation != SAME_AS:
    return "비교하지 않음"

코드는 axis 문자열을 읽지 않는다. 도메인이 바뀌어도 그대로.

같은 코드 경로가 다른 분야에서 어떻게 동작하는지 보면 분명해집니다(아래 계약서·재무 행은 가상 예시):

분야기준 항목대상 항목LLM 이 만들 엣지
배터리 (실측)1개월저장온도표준환경온도differs_by axis=측정조건
배터리 (실측)고객 표준 버전문서 기준 규격same_as
계약서 (가상)지체상금율지연배상금 상한differs_by axis=산정방식
재무 (가상)2024 3분기 매출(연결)2024 연간 매출(별도)differs_by axis=기간·연결범위

선례가 이미 있습니다 — F1 Schema Inducer 는 문서마다 다른 컬럼 의미 (semantic_role)를 LLM 이 유도하고 코드는 그것을 규칙으로 소비합니다. 개념 그래프는 같은 패턴의 확장입니다.

4.4 권한은 비대칭 — 연결은 LLM, 차단은 코드

LLM 에게 판정을 맡기면 재현성이 걱정됩니다. 그런데 이 문제에는 손해의 비대칭이 있습니다.

  • 틀린 연결(무관한 쌍을 “값이 다름”으로 보고) → 사람이 멀쩡한 문서를 고치러 간다. 피해가 크다.
  • 놓친 연결(같은 항목인데 “대상에 없음”) → 검토 목록에 남고 사람이 확인하면 된다. 피해가 작다.

손해가 비대칭이므로 권한도 비대칭으로 줬습니다.

과대평가 금지

인용 검증 게이트가 실제로 막는 것은 “원문에 없는 문구를 지어내는 것”뿐입니다. LLM 이 양쪽 원문에서 실재하는 문구를 골라 인용하면, 두 fact 가 서로 무관해도 게이트는 통과합니다. 즉 이 게이트는 “주장의 출처가 실재하는가”를 보증할 뿐 “주장이 옳은가”를 보증하지 않습니다. 잘못된 연결을 실제로 막는 것은 (a) LLM 의 판단 자체, (b) 승격된 differs_by, (c) 하류의 needs_review 입니다.

4.5 사람이 확정한 것은 영구히 남는다

LLM 이 매번 다른 그래프를 만들면 어떡하나? 이 질문의 답이 knowledge/ontology.yaml 입니다. 실행이 만든 concept_graph.json 을 사람이 검토해, 확실한 것만 이 파일로 승격합니다. 여기 있는 쌍은 다음 실행부터 LLM 에 묻지 않습니다.

knowledge/ontology.yaml — 현재 실제 내용 전체
aliases:                       # 같은 개념의 여러 표기(번역어·약칭)
  - ["표준환경온도", "Standard ambient temperature"]
  - ["평가환경습도", "Evaluation ambient humidity"]
  - ["정격충전전압", "Rated charging voltage"]

same_as:
  - names: ["고객 표준 버전", "문서 기준 규격"]
    reason: "둘 다 SEC Req. ver.4.7 을 가리킨다 (2026-08-03 실측 확인)"

differs_by:
  - names: ["1개월저장온도", "표준환경온도"]
    axis: "측정조건"
    reason: "저장 조건과 상시 환경 조건은 다른 규격"
  - names: ["평가환경온도", "평가 환경 습도"]
    axis: "물리량"
    reason: "온도와 습도"
  - names: ["충전환경온도", "정격 충전 전압"]
    axis: "물리량"
    reason: "온도와 전압"

3장의 표를 다시 보세요. 오매칭 3 쌍이 그대로 differs_by 로, 정답 1 쌍이 same_as 로 들어와 있습니다. 사람이 한 번 고친 오판은 영구히 재발하지 않습니다. 그리고 실행을 거듭할수록 LLM 이 새로 판단할 몫이 줄어들어 재현성이 올라갑니다.

키는 fact_id 가 아니라 정규화된 항목명입니다(공백·기호 무시 — “고객 표준 버전” == “고객표준버전”). fact_id 는 실행마다 바뀌므로 쓸 수 없습니다.

번역어는 aliases 로 (2026-08-05 추가)

differs_by 의 names 에 번역어를 그냥 나열하면 안 됩니다 — 로더가 목록 안 모든 쌍에 같은 관계를 부여하므로 ["1개월저장온도", "표준환경온도", "Standard ambient temperature"] 는 뒤 둘 (동의어)까지 “다르다”로 선언합니다. aliases 로 묶으면 관계 entry 가 그룹 간 쌍만 만들고 그룹 내부는 건너뛰므로, 1개월저장온도 ↔ Standard ambient temperature 차단이 자동으로 따라옵니다.

다만 온톨로지는 사람이 승격한 뒤에만 효과가 있습니다. 처음 보는 외국어 문서는 여전히 구제하지 못합니다 — 재발 방지 장치이지 첫 실행 대책이 아닙니다.

질문 메모 “계약만 고정” · “권한 비대칭” · “승격” 중 더 파고들고 싶은 게 있나요?

5. LLM 은 무엇을 하고, 코드는 무엇을 하는가

이 시스템에서 LLM 은 만능 판정자가 아닙니다. 딱 네 곳에서만 일하고, 나머지는 전부 코드가 결정적으로 처리합니다.

단계누가하는 일
F0 raw 추출코드파일 → 관찰 가능한 물리 정보(셀 주소, 병합, 도형 좌표). 해석 없음.
F1 문서 프로파일LLM“이 문서는 무엇에 대한 것인가”(main_purpose) 추론
F2 스키마 유도LLM엑셀 컬럼의 의미(semantic_role) 유도
F3 fact 추출LLM문서 → fact 카드. 값은 {value, unit} 으로 정규화
F7-1 후보 쌍 생성임베딩검토할 쌍을 좁힌다 (판정 아님)
F7-2 온톨로지 조회사람 + 코드승격된 관계는 그대로 채택하고 LLM 을 건너뛴다
F7-3 개념 관계 유도LLM“이 둘을 비교해도 되는가”만 판정 + 원문 인용
F7-4 조립·검증코드인용 검증 · same_as 병합 · 모순 강등

5.1 개념 판정 프롬프트의 5 원칙

F7-3 에서 LLM 에게 주는 지시(CONCEPT_SYSTEM)는 짧습니다. 핵심만 옮기면:

contentcompare/fact/prompts.py — CONCEPT_SYSTEM (발췌)
당신은 서로 다른 문서의 두 항목이 **같은 것을 가리키는지** 판정하는 검토자입니다.
값이 같은지는 다른 단계가 판단합니다. 당신은 "이 둘을 비교해도 되는가"만 답합니다.

원칙:
1. **값이 다른 것은 differs_by 의 근거가 아닙니다.** "21~29 와 -10~80 은 값이 다르니
   다른 항목"이라고 추론하지 마세요. 값의 차이는 우리가 찾으려는 결과이지 판단 재료가
   아닙니다. 항목이 **무엇에 대한 것인지**만 보세요.
2. "same_as" 를 쓰려면 양쪽에서 **원문을 그대로 인용**해야 합니다(left_text/right_text).
   인용할 원문이 없으면 same_as 를 쓸 수 없습니다.
3. 확신이 없으면 "unknown" 을 쓰세요. 틀린 연결은 사람을 잘못된 수정으로 유도하지만,
   놓친 연결은 검토 목록에 남아 확인됩니다.
4. 주어진 쌍마다 정확히 하나의 판정을 내고, 쌍의 id 를 그대로 옮기세요.
원칙 1 이 없으면 시스템이 무너진다

“21~29 와 -10~80 은 값이 다르니 다른 개념”이라는 추론을 허용하면, 우리가 찾으려는 정상적인 불일치를 개념 층이 통째로 삼켜버립니다. 값이 어긋난 항목은 differs_by 로 차단돼 리포트에 “대상에 없음”으로 나오고, 정작 값이 같은 항목만 비교됩니다. 도구가 자기 목적을 스스로 지워버리는 셈입니다.

7.2 대상 ① — 자표준_규격서.docx (Word)

케이스 A — 코드가 잇고, 코드가 값을 확정하다 불일치

공칭전압 fact-row-7 · B7:O7 target_value = 3.89 (단위 없음)
same_as decided_by: code
정규화 이름 동일: 공칭전압
공칭전압 fact-word-4 · w_b007 target_value = 3.85 V

이름이 같으니 코드가 즉시 이었습니다(LLM 호출 0). 그 다음 값 대조도 코드가 했습니다 — 공통 속성 target_value 가 있고 값이 다릅니다. 

"result": "mismatch",
"mismatch_attributes": ["target_value"],
"match_method": "concept",  "decided_by": "code",
"reason": "값이 다릅니다: target_value(기준 3.89 vs 대상 3.85V)"

이것이 우리가 찾으려던 것입니다. 엑셀은 3.89 V, 워드는 3.85 V. 누군가 한쪽만 고쳤습니다.

케이스 B — 코드가 잇고, LLM 이 단위를 판단하다 일치

최대충전전류 fact-row-12 target_value = 1495.0 (단위 없음)
same_as decided_by: code
최대 충전 전류 fact-word-5 upper_limit = 1.495 A

연결은 코드가 했지만 값 대조는 코드가 포기했습니다. 속성 이름도 다르고 (target_value vs upper_limit), 한쪽엔 단위가 없으며, 1495 ≠ 1.495 입니다. _UNIT_ALIASES 사전에 “단위 없음 ↔ A” 같은 조합은 없습니다 — 그리고 사전에 없는 조합을 코드가 추측하지 않는 것이 규칙입니다. 그래서 LLM 으로 갔습니다. 

"result": "match",  "decided_by": "llm",
"reason": "기준의 1495.0과 후보의 1.495 A는 단위(A)를 고려했을 때
           실질적으로 동일한 값을 나타냅니다."

케이스 C — 사람이 미리 차단해 둔 쌍 대상에 없음

2026-08-03 실행에서 충전환경온도(엑셀)는 정격 충전 전압(워드)과 0.6551 로 이어져 “값이 다릅니다”가 나왔습니다. 지금은 이렇습니다:

충전환경온도 fact-row-17 -5.0 / 35.0 / 85.0
differs_by 축: 물리량 · 온도와 전압
decided_by: ontology · promoted ✓
정격 충전 전압 fact-word-2 target_value = 4.55 V

임베딩은 여전히 이 쌍을 후보로 올립니다(recall_score: 0.6551 이 엣지에 기록돼 있습니다). 하지만 온톨로지가 먼저 답을 갖고 있으므로 LLM 에게 묻지도 않고 차단됩니다. 개념이 이어지지 않으니 ConceptMatcher.search() 는 빈 리스트를 돌려주고, 결과는 “대상에 없음”입니다.

중요한 차이

“대상에 없음”은 틀린 답이 아닙니다. 워드 규격서에는 실제로 충전환경온도가 적혀 있지 않습니다. 예전 방식은 이것을 “값이 다름”이라는 거짓 경보로 보고했고, 지금은 “여기엔 없다”는 사실로 보고합니다.

7.3 대상 ② — 자표준_발표.pptx (PPT)

케이스 D — LLM 만이 할 수 있는 연결 (교차언어) 일치

표준환경온도 fact-row-15 21.0 / 25.0 / 29.0
same_as decided_by: llm · recall 0.7508
“두 항목 모두 ‘표준환경온도’를 의미합니다”
Standard ambient temperature fact-ppt-5 21 - 29 degC (target 25 degC)

이름 완전일치로는 절대 못 잇고, BM25(단어 겹침)로도 못 잇습니다. 임베딩이 후보로 올려 주고 LLM 이 “같다”고 판정한 뒤, 코드가 양쪽 인용이 원문에 실재하는지 확인해 통과시켰습니다. 세 도구가 각자 할 수 있는 일만 한 결과입니다.

다만 이 연결은 decided_by: llm 이므로 needs_review = True 입니다. 그래서 값 대조도 LLM 이 한 번 더 봤고, 리포트 사유에 “(근거 신뢰도가 낮아 검토 대상입니다.)”가 붙었습니다. 사람이 이 쌍을 ontology.yaml 에 승격하면 그 비용이 사라집니다.

케이스 E — 진짜 불일치를 잡아내다 불일치

3개월저장온도 fact-row-21 -10.0 / 35.0 / 70.0
same_as decided_by: llm
“상한값 표기만 다를 뿐 동일한 조건”
3개월 저장 조건 fact-ppt-8 -10 ~ 60℃ (기준 35℃)

LLM 이 개념 층에서 “값이 달라도 같은 항목”이라고 정확히 판단한 덕분에(원칙 1!), 값 대조 단계에서 진짜 불일치가 드러났습니다: 

"result": "mismatch",  "mismatch_attributes": ["upper_limit"],
"reason": "기준 문서의 상한값(70.0)과 대상 문서의 상한값(60 ℃)이 서로 다릅니다."

만약 개념 판정 LLM 이 “70 과 60 은 다르니 다른 항목”이라고 했다면, 이 쌍은 차단돼 대상에 없음이 됐을 것이고, 발표자료의 오타를 영영 못 찾았을 것입니다.

케이스 F — 같은 “온도”라도 조건이 다르면 대상에 없음

평가환경습도 fact-row-16 33.0 / 43.0 / 53.0
differs_by 축: 물리량 · 온도와 습도
decided_by: ontology · promoted ✓
평가환경온도 fact-ppt-4 21 / 24 / 28 ℃

이름이 한 글자만 다르고(“온도”/“습도”) 임베딩 점수는 0.6270 이었습니다. 사람이 승격해 둔 differs_by 가 이 쌍을 영구히 막습니다. 그리고 PPT 의 평가환경온도는 엑셀의 평가환경온도(fact-row-19)와 이름 완전일치로 제대로 이어져 일치 판정을 받았습니다.

케이스 G — 판정하지 못한 쌍은 사람에게 검토 필요

실행에서 unknown 으로 남은 엣지가 2 건 있었습니다.

기준 항목대상 항목사유(엣지 원문)
공칭전압 (fact-row-7)충전 규격 상세조건 (fact-ppt-12)LLM 응답에 이 쌍이 없었습니다

첫 번째는 LLM 이 배치 응답에서 그 쌍을 빠뜨린 경우입니다. 쌍을 잃어버리지 않고 unknown 으로 남겨 리포트의 “⚠ 검토 필요” 표에 올립니다. 사람이 확인해 ontology.yaml 에 적으면 다음 실행부터 다시 묻지 않습니다.

같은 내용이 concept_validation.json 에도 concept_unknown_pair(severity: warn) 2 건으로 남아 있습니다. 이 계측은 오판 추적이 목적이므로 제거하지 않습니다.

8.1 엣지는 왜 개념이 아니라 fact 쌍을 가리키는가

직관적으로는 “개념 A ↔ 개념 B” 로 엣지를 걸고 싶습니다. 하지만 concept_id 는 병합의 결과라 실행마다 바뀝니다. 반면 엣지가 담은 인용문은 특정 fact 두 개에 대한 주장입니다. 원인을 결과로 키잉하면 인용 검증도, 사람이 읽는 것도 어려워집니다.

contentcompare/fact/concept_models.py
@dataclass
class ConceptEdge:
    """두 fact 사이의 관계 주장."""
    relation: str          # same_as | differs_by | unknown
    left: FactRef          # (doc, fact_id)
    right: FactRef
    axis: str = ""         # LLM 이 짓는 이름 — 코드는 읽지 않는다
    left_text: str = ""    # 근거 인용(원문 그대로)
    right_text: str = ""
    decided_by: str = BY_LLM   # code | ontology | llm | ""(BY_NONE)
    promoted: bool = False
    recall_score: float = 0.0  # 판정에 쓰지 않고 진단용으로만 남긴다
    rejected_by: str = ""      # evidence | differs_by

노드는 엣지에서 파생됩니다. BY_NONE(빈 문자열)이 따로 있는 것도 이유가 있습니다 — LLM 을 아예 쓰지 않아 판정하지 않은 쌍까지 llm 으로 기록하면 위임률 통계가 거짓이 됩니다.

8.4 조립 — 인용 검증 · 병합 · 강등

인용 검증은 LLM 이 제안한 same_as 에만 적용합니다. 사람 승격과 코드 완전일치는 LLM 의 주장이 아니라 지어낼 수 없기 때문입니다.

여기 있던 가장 심각한 버그

처음 구현에서는 검증이 decided_by 를 보지 않고 모든 same_as 에 걸렸습니다. 그런데 온톨로지 확정 엣지는 인용문이 비어 있습니다(사람은 항목명 쌍만 적으니까). 결과: 사람이 승격한 연결이 100% unknown 으로 강등됐습니다. 이 기능의 재현성 장치 전체가 죽어 있었던 겁니다. 각 단계의 단위 테스트는 전부 통과했고 — 결함이 두 태스크의 경계에 있었기 때문에 end-to-end 회귀 테스트만이 그 지점을 지나갔습니다 (커밋 1520007).

contentcompare/fact/concept_assembler.py
EVIDENCE_MIN_COVERAGE = 0.8   # 인용 토큰의 80% 가 원문에 있어야 한다
EVIDENCE_MIN_TOKENS   = 3     # 풍부한 원문에서 한 조각만 떼어내는 '부분 인용'을 막는 바닥

def verify_evidence(edge, left, right) -> bool:
    for claim, fact in ((edge.left_text, left), (edge.right_text, right)):
        if not (claim or "").strip():                               return False
        source = set(tokenize(f"{fact.evidence_text} {fact.search_text} {fact.entity_name}"))
        if evidence_coverage(claim, source) < EVIDENCE_MIN_COVERAGE: return False
        if not _quote_long_enough(claim, fact):                      return False
    return True

def _quote_long_enough(claim, fact) -> bool:
    """원문 전체를 인용했으면 하한을 면제한다."""
    tokens = set(tokenize(claim))
    if len(tokens) >= EVIDENCE_MIN_TOKENS:
        return True
    return bool(tokens) and tokens == set(tokenize(fact.evidence_text))
2026-08-05 수정 — 하한이 막는 것은 “짧은 인용”이 아니라 “부분 인용”

처음 구현은 하한을 무조건 적용했습니다. 그런데 엑셀 단일값 행의 원문은 "1150.0" — 토큰이 하나뿐이라 3토큰을 인용할 방법이 없습니다. 게이트가 달성 불가능한 조건을 요구하고 있었던 겁니다.

이것을 드러낸 것은 영어 대상 문서였습니다. 언어가 다르면 이름 완전일치가 0건이라 모든 연결이 LLM 경로로 몰리고, 그제서야 이 게이트가 전면에 걸립니다 — 한국어에서는 같은 행들이 decided_by=code 라 검증을 건너뛰어 가려져 있었습니다. 수정 전 실측에서 LLM 이 정확히 인용한 same_as 10건이 전부 강등돼 실제 불일치(공칭전압 3.89 vs 3.85V)를 놓쳤습니다.

면제해도 부분 인용은 계속 막힙니다 — Nominal capacity, 1150, mAh 에서 1150 만 인용하면 토큰 집합이 원문과 달라 면제 대상이 아닙니다. 회귀는 tests/test_concept_regression_en.py.

병합은 union-find 입니다. 그리고 승격된 엣지를 먼저 적용합니다 (sorted(same_edges, key=lambda e: not e.promoted)). 병합 결과가 differs_by 로 연결된 두 노드를 하나로 만들면 그 병합을 거부하고 해당 same_as 를 강등합니다. 

def blocked(a: str, b: str) -> bool:
    """a·b 를 합치면 differs_by 로 연결된 두 fact 가 한 개념이 되는가."""
    for d in blockers:
        if {find(d.left.key), find(d.right.key)} == {a, b}:
            return True
    return False

9. 이 방식이 해결하지 못하는 것

설계 문서 §12 와 라이브 리포트에 그대로 적혀 있는 한계입니다. 숨기지 않는 편이 낫습니다 — 리포트를 믿을 수 있는 범위를 아는 것이 리포트의 값어치이기 때문입니다.

① 인용 검증은 “출처의 실재”만 보증한다

LLM 이 양쪽 원문에서 실재하는 문구를 골라 인용하면 두 fact 가 무관해도 게이트는 통과합니다. 잘못된 연결을 실제로 막는 것은 LLM 의 판단, 승격된 differs_by, 그리고 하류의 needs_review 입니다. 한글 3 글자 이상 토큰은 bigram 으로 부풀려지므로 EVIDENCE_MIN_TOKENS=3 도 강한 검사가 아닙니다.

①-b 단일값 fact 는 자신을 구별할 수단이 없다

원문이 "1150" 뿐인 fact 는 인용으로 자기를 특정할 방법이 없어 아무 1150 과도 이어질 수 있습니다. 실측(영어 문서)에서 실제로 공칭용량 ↔ Rated capacity 와 정격용량 ↔ Nominal capacity 가 교차 병합되어 네 fact 가 한 개념이 됐습니다. 값이 모두 1150 이라 판정은 바뀌지 않았지만, 값이 달랐다면 엉뚱한 쌍을 비교했을 것입니다. 이름 완전일치가 앵커 역할을 하는 같은 언어 문서에서는 일어나지 않습니다 — 이것이 게이트 면제(위 §8.4)의 대가이고, 방어선은 needs_review 와 사람의 승격입니다.

② fact 추출 단계에서 빠진 것은 개념 층이 완벽해도 못 찾는다

F3 이 애초에 fact 를 만들지 않았으면(예: Word 블록 w_b004 미추출) 결과는 missing 입니다. 그건 추출 단계의 문제입니다.

③ 예산이 소진되면 조용히 전 항목이 “대상에 없음”이 된다

max_llm_calls_per_concept(30) × concept_batch_pairs(20) = 600 쌍이 상한입니다. 기준 fact 가 늘어 이 상한을 넘으면 나머지 배치가 전부 unknown → 연결 없음 → missing 이 됩니다. 사용자가 보는 것은 “전부 대상에 없음”뿐이고 원인은 로그에만 남습니다. 그래서 지금은 리포트 맨 위에 경고가 찍힙니다:

⑤ 이름이 같은 두 fact 를 “사실은 다르다”고 선언할 수 없다
