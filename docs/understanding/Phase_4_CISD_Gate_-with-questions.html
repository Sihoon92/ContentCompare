Phase 4 CISD 육안 Gate

차트의 마커는 왜 이렇게 많고, 나는 정확히 무엇을 확인해야 하나 — 처음부터 천천히

이 문서를 읽는 방법 읽다가 궁금한 게 생기면 곳곳에 있는 질문 메모 상자에 바로 적으세요. 적는 즉시 이 브라우저에 자동 저장되고, 맨 아래 [질문 저장] 버튼을 누르면 질문이 박힌 HTML이 다운로드됩니다. 그 파일을 docs/understanding/의 원본 자리에 덮어쓴 뒤 Claude에게 "질문에 답해줘"라고 하면 이 문서 안에 답이 채워집니다.

먼저 결론부터 (급하면 여기만) 차트가 어지러운 건 당신 탓이 아닙니다. 차트는 창(5일치) 안의 모든 사건을 그립니다 — 창 하나에 CISD 판정만 123~178건, 9개 창 합쳐 1,353건입니다. 그런데 판정표는 그중 40행만 뽑아 놨습니다. 화면에 보이는 것의 대부분은 오늘 당신이 볼 대상이 아닙니다.

해결책은 두 줄입니다. ① 차트 오른쪽 범례에서 CISD가 아닌 층을 전부 클릭해서 끄세요. ② 판정표 한 행의 앵커 봉 open (UTC) 시각으로 그 시각만 확대해서 보세요.

1. 배경 ① — 봉, 꼬리, 그리고 "유동성 사냥"

이미 캔들차트와 ICT 개념을 안다면 2번으로 건너뛰세요.

1-1. 봉(캔들) 하나는 "그 시간 동안의 요약"입니다

가격은 1초에도 수십 번 움직입니다. 그걸 전부 그리면 아무것도 안 보이니까, 일정 시간을 한 덩어리로 묶어 막대 하나로 그립니다. 그게 봉입니다.

15분봉 하나에는 딱 4개의 숫자가 들어 있습니다.

왜 "종가"만 유독 중요한가 꼬리는 "한 번 찔러봤다"는 뜻이고, 종가는 "15분이 끝났을 때 시장이 최종적으로 동의한 값"입니다. 꼬리는 큰손 한 명이 잠깐 밀어도 생기지만, 종가는 15분 내내 버텨야 나옵니다. 이 프로젝트의 모든 판정은 종가로만 합니다. 꼬리로 넘은 건 넘은 게 아닙니다. 이 규칙 하나가 오늘 당신이 눈으로 확인할 것의 절반입니다.

1-2. "유동성"은 사람들의 손절 주문이 쌓인 자리입니다

가격이 눈에 띄게 낮았던 자리(전 저점)를 생각해 보세요. 많은 사람이 "여기 밑으로 내려가면 손절한다"고 주문을 걸어 둡니다. 그 자리 바로 아래에 매도 주문 뭉치가 쌓입니다. 이걸 SSL(sell-side liquidity, 매도 쪽 유동성)이라고 부릅니다. 반대로 전 고점 위에는 매수 주문 뭉치가 쌓이고, 그건 BSL입니다.

1-3. "스윕(sweep)"과 "excursion"

큰 자금은 자기 물량을 채우려면 상대방 주문이 필요합니다. 그래서 일부러 전 저점 아래를 잠깐 찔러 손절 주문을 터뜨리고, 그 물량을 받아서 다시 올라갑니다. 이 "잠깐 찌르기"가 스윕입니다.

스윕이 일어나면 이 시스템은 excursion이라는 사건을 하나 엽니다. "어느 선을 언제 얼마나 뚫고 내려갔는가"를 기록하는 서류철이라고 생각하면 됩니다. excursion에는 이름표(ID)가 붙는데, 이게 판정표와 차트를 잇는 열쇠입니다. 

ETHUSDT : EXC : SSL : 1783501200000 : 1732.77
  │        │     │        │              └ 뚫고 내려간 가격
  │        │     │        └ 스윕이 관측된 시각 (epoch 밀리초 = 2026-07-08 09:00 UTC)
  │        │     └ 어느 쪽 유동성인가 (SSL = 아래쪽 / BSL = 위쪽)
  │        └ 이건 excursion 사건이다
  └ 종목
질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

2. 배경 ② — 이 화면은 왜 존재하나

2-1. 전략은 여섯 단계로 나뉘어 있습니다

"유동성을 사냥한 뒤 반대로 간다"는 아이디어를 한 번에 코드로 옮기면, 틀렸을 때 어디가 틀렸는지 알 수 없습니다. 그래서 이 프로젝트는 단계(Phase)를 쪼개고, 단계마다 따로 검증합니다.

2-2. "육안 Gate"가 뭔가요

컴퓨터가 계산한 결과를 사람이 눈으로 채점하는 절차입니다. 왜 필요할까요? 테스트 코드는 "내가 시킨 대로 계산했나"만 확인합니다. "내가 시킨 게 애초에 말이 되나"는 확인하지 못합니다.

실제로 있었던 일 (이 저장소 기록) 382개의 테스트가 전부 초록이었는데, 차트의 시간축이 9시간 어긋나 있었습니다. 숫자끼리는 완벽히 일치했지만, 사람이 화면에서 보고 있던 건 다른 시각의 봉이었습니다. 기계는 서로 어긋난 두 세계가 각자 자기 안에서 완결되어 있으면 절대 눈치채지 못합니다. 그래서 사람 눈이 한 번 들어가야 합니다.

Gate는 세 개의 명령으로 굴러갑니다.

# ① 차트를 만든다 (창 9개 × 표시 타임프레임)
python -m research.analysis.ict_phase4_gate render

# ② 판정표를 만든다 (cisds.csv + worksheet.html)
python -m research.analysis.ict_phase4_gate worksheet

# ③ 판정 서버를 띄운다 (localhost:8770) ← 지금 여기
python -m research.analysis.ict_phase4_gate serve
중요한 안전장치 worksheet는 verdicts.csv(당신이 찍은 판정)를 절대 덮어쓰지 않습니다. 판정은 재생성이 불가능한 자산이니까요. 저장은 serve만 하고, 그것도 기존 판정과 병합합니다.
질문 메모 Phase 구분이나 Gate의 목적에 대해 궁금한 점

3. 핵심 직관 — CISD는 무엇을 묻는가

3-1. 한 문장으로

CISD = Change In State of Delivery (공급 상태의 전환) "가격을 밀어 내리던 힘이, 그 힘이 시작된 첫 발자국까지 되밟혔는가?"

비유로 갑시다. 눈밭에서 누군가 언덕 아래로 내려갔습니다. 발자국이 100m 지점에서 시작해 96m까지 이어져 있어요. "그 사람이 진짜 돌아섰다"고 말하려면 어디까지 올라와야 할까요?

95m? 그건 그냥 미끄러진 걸 수도 있습니다. 발자국이 시작된 100m 지점을 다시 넘어서야 "아, 내려가던 게 끝났구나"라고 말할 수 있습니다.

CISD의 기준선(cisd_level)이 정확히 그 "첫 발자국"입니다. 코드로는 이렇게 정합니다:

  1. 스윕이 일어난 15분봉(bar0)에서 출발한다.
  2. 거기서 과거로 훑으며 첫 번째 반대 봉을 찾는다. (SSL = 아래로 찔렀으니 반대 봉은 음봉)
  3. 그 음봉에서 계속 과거로 이어지는 연속 음봉 덩어리(run)의 맨 첫 봉을 찾는다.
  4. 그 첫 봉의 시가(open) = 기준선. 여기서 얼려버린다(freeze).

3-2. 그림으로 (같은 그림을 계속 재사용합니다)

세 가지 시각을 절대 헷갈리지 마세요
  • bar0 — 스윕이 일어난 15분봉. 기한을 세는 출발점.
  • 앵커 봉 — 기준선을 얼린 봉. 보통 bar0와 같아서 ◇로 표시됩니다. 15분 데이터에 구멍이 나서 bar0가 통째로 없으면 다음 봉이 앵커가 되고, 그때만 ⧗(모래시계)로 표시됩니다.
  • 판정 봉 — 결론이 난 봉. 마커(● 또는 ✕)는 이 봉의 종가 시각에 찍힙니다.

3-3. 실패하는 경우 — 꼬리는 인정하지 않는다

3-5. Reclaim과 CISD는 다른 질문입니다 — 그래서 2×2

Phase 3의 Reclaim은 "뺏긴 그 자리를 되찾았나"를 묻고, Phase 4의 CISD는 "밀던 힘 자체가 꺾였나"를 묻습니다. 비슷해 보이지만 네 조합이 전부 실제로 존재합니다.

4. 차트에 마커가 이렇게 많은 이유

4-1. 원인 ① — 다섯 개의 층이 한 장에 겹쳐 그려집니다

차트는 한 장처럼 보이지만, 사실 투명 필름 다섯 장을 겹친 것입니다. frontend/specs/ict_long_viz.py의 _combined() 함수가 순서대로 다섯 렌더러를 부릅니다.

4-2. 원인 ② — 차트는 전부 그리는데, 판정표는 40행만 뽑습니다

4-3. 해결 — 범례를 클릭해서 층을 끄세요

Plotly 차트의 범례 항목은 클릭하면 그 층 전체가 사라집니다. 코드에서 각 층을 legendgroup으로 묶어 뒀기 때문에 항목 하나를 끄면 같은 그룹의 마커·선이 함께 사라집니다.

차트 x축은 UTC입니다 판정표에는 bar0 (KST) 열도 있지만 흐리게(muted) 처리돼 있습니다. 그 열로 차트를 찾으면 9시간 뒤를 보게 됩니다. 반드시 … (UTC)가 붙은 열을 쓰세요.

chk_*는 왜 믿을 만한가 이 검사들은 detector가 내놓은 값을, detector와 완전히 별개로 다시 만든 15분봉과 대조합니다 (audit_agg = IncrementalTimeframeAggregator("15m")). 같은 계산식에서 나온 값끼리 비교하면 늘 참이 되는 항등식이 되는데, 이 프로젝트는 Phase 3에서 그 함정에 두 번 빠진 적이 있습니다. 현재 40행 모두 True 또는 공란(비교 대상이 없어 검사하지 않음)입니다 — 즉 정의 불일치는 기계 수준에서 이미 0입니다.
질문 메모 특정 열의 의미가 아직 안 잡힌다면 열 이름과 함께 적어주세요

8-2. 판정의 핵심 세 함수

① 기준선 찾기 — 앵커에서 과거로 훑어 run의 첫 봉을 고릅니다.

# coreEngine/analysis/composites/ict_long/cisd_detector.py

def resolve_cisd_level(bars, side, lookback_bars) -> CISDLevel:
    last = len(bars) - 1
    found = -1
    for distance in range(min(lookback_bars, len(bars))):   # 앵커 포함 3봉
        if _is_opposing(bars[last - distance], side):        # 첫 반대봉
            found = last - distance
            break
    if found < 0:
        return CISDLevel(..., reason=NA_NO_OPPOSING_RUN)     # 잴 발자국 없음

    first = found
    while first - 1 >= 0 and _is_opposing(bars[first - 1], side):
        first -= 1                                           # run 시작까지 거슬러
    if first == 0:
        return CISDLevel(..., reason=NA_INSUFFICIENT_HISTORY)  # 버퍼 끝에 닿음

    return CISDLevel(level=bars[first].open_price, ...)      # ★ run 첫 봉의 시가

② 넘었는지 보기 — 엄격 비교입니다. 같은 값은 실패입니다.

@staticmethod
def _beyond(side, close, level) -> bool:
    if side is LiquiditySide.SSL:
        return close > level      # 아래로 찔렀으니 위로 넘어야 성립
    return close < level          # BSL은 반대

③ 퇴화 가드 — 앵커 시점에 이미 참이면 빼버립니다. 여기만 >=라 동가를 포함합니다.

def _degenerate(self, pending) -> bool:
    level, close = pending.level.level, pending.anchor_close
    if pending.side is LiquiditySide.SSL:
        return close >= level     # 이미 넘어 있음 → 관측한 게 없다
    return close <= level

8-3. 그림은 "읽기만" 합니다

렌더 레이어에 계산식이 없다는 게 중요합니다. 예를 들어 판정 마커의 x좌표는 confirm_bar_open_ms + 15분으로 다시 계산하지 않고, 이벤트가 이미 들고 있는 available_at_ms를 그대로 씁니다. 

# frontend/specs/ict_long_cisd_layers.py
mark_x_ms = _as_int(event.available_at_ms)   # 계산하지 말고 읽어라 (마스터 §21)

# 기준선은 run 첫 봉 open → 기한 봉 close 까지
level_x[outcome].extend([_ts(view.level_from_ms),
                         _ts(view.deadline_close_ms), None])   # None = 선 끊기
왜 마커가 봉의 close 시각에 찍히나 그 봉의 종가를 관찰자가 알 수 있게 되는 시점이 봉이 닫힌 뒤이기 때문입니다. 봉 open에 찍으면 15분 먼저 알았던 것처럼 보이는 착시(hindsight)가 생깁니다. 실거래 시뮬레이션의 정직성이 여기서 갈립니다.
None 하나가 성능을 살립니다 Plotly에서 add_shape()를 사건마다 부르면 O(N²)로 느려집니다 — 이 저장소가 5번 물린 규칙입니다. 그래서 선 1,353개를 그리는 대신, outcome 그룹당 trace 하나에 좌표를 몰아넣고 선분 사이를 None으로 끊습니다. CISD 레이어의 trace 수는 사건 수와 무관하게 8개 이하입니다.

9. 퀴즈 5문항

외운 걸 묻는 게 아니라, 이해했는지 확인하는 문제입니다.

Q1. SSL excursion에서 cisd_level은 정확히 어디에서 오나요?
기준선은 "내려가던 발자국이 시작된 자리"입니다. bar0의 시가가 아니라 run 첫 봉의 시가이고, 그래서 차트의 청록 선이 bar0보다 왼쪽에서 시작합니다. 그 시작 위치 자체가 "값이 어디서 왔는지"에 대한 눈으로 확인 가능한 증거입니다.
Q2. 어떤 행의 wick만 돌파가 2이고 판정은 FAILED입니다. 어떻게 해야 할까요?
이 프로젝트의 판정은 종가로만 합니다. wick만 돌파는 "꼬리만 넘은 봉이 몇 개였나"를 세는 진단 열이고, 이 값이 0보다 큰데 FAILED라면 그게 바로 규칙이 제대로 작동한 증거입니다. 사람은 차트에서 몸통이 정말 안 넘었는지만 확인하면 됩니다.
Q3. degenerate_level(퇴화)로 미적용 처리하는 진짜 이유는?
이미 넘어 있는 상태에서 "넘었다"고 선언하면 미래를 예측한 게 아니라 과거를 되풀이한 것입니다. 성공률의 분모에서 빼야 정직한 숫자가 나옵니다. 참고로 ②는 insufficient_history, ③은 no_opposing_run·insufficient_history에 해당하고(퇴화는 레벨이 있어 ▽로 그려집니다), ④는 detector가 서로를 참조하지 않는다는 원칙에 어긋납니다.
Q4. 차트에 마커가 압도적으로 많은 가장 직접적인 이유는?
①은 틀렸습니다 — CISD는 excursion당 정확히 1회만 판정합니다(계약 §4.1). ②는 1m 차트가 더 어지럽긴 하지만 원인이 아니고, 애초에 판정은 15m 차트에서 합니다. ③은 정확히 피하려고 설계한 것이라 add_shape 호출은 0회입니다. 답은 집계 단위의 차이이고, 그래서 해결책도 "범례로 층 끄기 + 시각으로 확대"입니다.
Q5. 어떤 행에서 level−baseline이 거의 0이고, 차트에서 CISD 선과 Reclaim 선이 완전히 겹쳐 보입니다. 어떻게 해야 할까요?
태그는 NG가 아닙니다. NG로 찍으면 멀쩡한 표본이 버려지고 재검토 근거가 사라집니다. 실측상 CISD가 Reclaim보다 엄격한 비율이 99%를 넘는데, 이 태그가 모이면 "둘은 같은 상태의 다른 이름이 아니다"라는 전제를 다시 검토할 유일한 근거가 됩니다. ③도 위험합니다 — 미판정 행이 있으면 gate_pass가 False가 됩니다.
질문 메모 틀린 문제가 있다면 왜 헷갈렸는지 적어두세요 — 그게 다음 설명의 재료가 됩니다
