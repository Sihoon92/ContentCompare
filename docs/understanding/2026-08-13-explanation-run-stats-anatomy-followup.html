1. 배경 — 30초 복습

1.1 처음 보는 분을 위해 (아는 분은 1.2 로)

엑셀 규격표(기준)의 항목들을 워드·PPT(대상)와 대조해 ✅ 일치 / ❌ 불일치 / ⚪ 대상에 없음 / ❓ 판단보류 를 판정하는 시스템입니다. 문서를 통째로 LLM 에 주지 않고, 먼저 fact (항목명 + 값·단위 + 근거 원문 + 좌표)로 정규화한 다음 fact 끼리 비교합니다.

비교는 두 단계이고, 순서가 설계의 핵심입니다.

1.2 "후보"의 정확한 뜻

이 단어가 두 단계에서 다르게 쓰여 혼란을 만듭니다. 이 글에서 말하는 후보는 언제나 뒤쪽, 즉 F5 가 실제로 손에 쥔 것을 말합니다.

recall 후보F5 후보 이 글의 "후보"
만드는 곳FactMatcher (임베딩/BM25)ConceptMatcher.search()
기록되는 곳candidate_pairs.json없음(메모리) — 결과가 comparison_result.json
기준유사도 상위 top_k(기본 5), min_score 0.3 이상 개념 그래프에서 same_as 로 이어진 것만
양거의 항상 5칸이 찬다0건인 경우가 흔하다
⚠️ min_score: 0.3 은 임계값이 아니라 계산량 제한이다 설정 주석에도 "판정 아님 — 계산량 제한"이라고 적혀 있습니다. 한↔영 문서에서는 아무 관계 없는 쌍도 코사인 0.5~0.6 이 나오기 때문에 0.3 으로는 사실상 아무것도 걸러지지 않습니다. recall 이 5칸을 채웠다는 사실은 "관련된 것을 찾았다"는 뜻이 전혀 아닙니다.

2. ① missing 은 후보가 없는 항목인가

거의 그렇습니다. 다만 예외가 하나 있고, 그 예외를 구분하는 방법이 있습니다.

missing 이 나오는 경로는 정확히 두 개입니다.

후보 목록이 비었는가?
= 개념 그래프에 same_as 로 이어진 대상 fact 가 없다
예 →
⚪ missing · decided_by = code · LLM 0회
finalize() 가 첫 줄에서 즉시 반환합니다. 이 실행의 76건이 전부 여기입니다.
아니오 → LLM 이 후보들을 보고…
⚪ missing · decided_by = llm
"후보 중 기준과 같은 대상을 다루는 것이 없다"고 LLM 이 답한 경우. 후보는 있었지만 관련 없다고 본 것입니다.
🔑 decided_by 가 이 둘을 가른다 FactComparator 는 후보가 없으면 LLM 을 부르지 않고 즉시 반환하므로 decided_by 가 code 로 남습니다. 후보가 있는데 LLM 이 "없다"고 답한 경우에만 llm 이 됩니다. 그리고 실패 시 폴백(_fallback)은 missing 을 만들지 않습니다. 그래서 이 구분은 100% 신뢰할 수 있고, 진단 도구 missing_trace.py 의 핵심 판별 신호이기도 합니다.

앞선 실행에서 최종 ⚪ 대상에 없음 은 77건이었습니다 — 후보가 없던 76건 + LLM 이 "없다"고 답한 1건. 리포트의 숫자와 code_missing 76 이 1 차이 나는 이유가 이것입니다.

질문 메모 두 경로 구분에서 궁금한 점을 적어보세요.

3. ② 후보가 있으면 판정은 어떻게 정해지나

짧은 답: 원칙은 "코드가 먼저, 애매하면 LLM"이지만, 이번 실행에서는 사실상 전부 LLM 이 결정했습니다. 왜 그렇게 됐는지가 흥미로운 부분입니다.

3.1 세 갈래 분기

후보가 2건 이상인가? 신규 (2026-08-13)
예 → 코드 판정을 쓰지 않고 무조건 LLM
🤖 종합 판정 + 후보별 findings[]
동명·동개념 fact 는 recall 점수로 갈리지 않아 candidates[0] 축약이 사실상 임의 선택이기 때문입니다
코드가 판정할 수 있는가? (code_result is not None)
공통 속성의 값이 전부 같으면 match, 다르고 단위가 호환되면 mismatch
가능 + uncertain 아님 + 게이트 강제 아님 →
⚙️ 코드 판정 확정 · LLM 0회

🤖 LLM 위임

코드 판정이 있으면 그것으로, 없으면 ❓ unknown 보류
단, 후보 2건 이상이면 코드 판정으로 되돌아가지 않고 무조건 보류입니다

3.2 이번 실행에서는 왜 전부 LLM 으로 갔나

분기의 두 번째 조건 not probe.uncertain 이 한 번도 참이 되지 않았기 때문입니다. low_confidence 가 24/24 였다는 것이 곧 그 뜻입니다. 

if verdict is not None and not probe.uncertain and not force_llm:
    out.result, ... = verdict      # ← 이 줄에 한 번도 도달하지 않았다
    return out
return self._decide_by_llm(...)    # ← 24건 전부 여기로

그리고 uncertain 이 켜진 이유는 pairs_by_code: 0 입니다. 개념 경로에서 needs_review 는 점수 경계가 아니라 "이 연결을 LLM 이 만들었는가"로 재정의돼 있습니다. 한↔영 문서쌍은 이름 완전일치가 원리적으로 불가능하고 온톨로지 승격도 없었으니, 모든 연결이 LLM 산 → 전건 uncertain → 전건 LLM 재판정입니다.

3.3 그럼 LLM 이 마음대로 정하는 건가

아닙니다. 제안은 LLM 이 하지만 검증과 차단은 코드가 합니다. 이 프로젝트를 관통하는 권한 비대칭입니다.

단계🤖 LLM 이 하는 일⚙️ 코드가 하는 일
라벨 선택match|mismatch|missing|unknown 중 하나를 답한다 네 값 밖이면 unknown 으로 강등
후보 지목대응하는 후보를 가리킨다 제시한 후보 목록에 실재하는 id 인지 대조 — 없으면 무시
근거 인용원문을 인용한다 evidence_text 안에 실재하는지 대조 → 실패 시 quote_verified: false
사유한국어로 판단 근거를 쓴다 근거가 불안정하면 "검토 대상입니다" 문구를 자동으로 덧붙인다

프롬프트에도 확신이 없으면 unknown 을 쓰라고, 후보에 없는 내용을 지어내지 말라고 명시돼 있습니다. 틀린 단정보다 보류가 낫다는 것이 이 시스템의 기본값입니다.

🚨 부작용 — 코드 우선 설계의 이득이 이 데이터에서는 0 이다 fact 를 {value, unit} 으로 정규화한 이유가 "값 비교는 코드가 한다"였는데, 연결이 전부 LLM 산이라 코드 판정이 매번 무시되고 있습니다. 버그는 아니지만(설계된 안전장치가 작동한 것) 비용 절감 효과는 사라집니다. 해법은 knowledge/ontology.yaml 에 관계를 승격해 needs_review=False 인 연결을 늘리는 것입니다.
질문 메모 판정 분기나 권한 비대칭에서 궁금한 점을 적어보세요.

4. ③ 76건은 결함인가 — 실측 분석

이것이 이 글의 본론입니다. 76%라는 숫자는 분명 불안하게 보입니다. 하지만 결론부터 말하면, 대부분은 정상이고 일부는 진짜 결함입니다. 둘을 가르는 방법이 있습니다.

4.1 먼저 물어야 할 것 — 상한은 얼마인가

📌 상한(ceiling) 기준 문서에 항목이 20개인데 대상 문서에 10개밖에 없다면, 아무리 검색과 판정이 완벽해도 최소 10건은 반드시 missing 입니다. 이 값이 상한입니다.

비교해야 할 것은 76 이라는 절대값이 아니라, 상한 대비 회수율입니다. 기준은 마스터 규격표이고 대상은 요약 문서인 경우가 많아, 상한이 낮은 것은 결함이 아니라 문서의 성질입니다.

4.2 저장된 실행으로 실제로 재보기

이 저장소의 artifacts/ 에 남아 있는 실행(같은 문서쌍의 작은 판)으로 계산해 봤습니다.

기준 fact자표준문서.xlsx

실제 연결됨same_as 로 이어진 비교

상한 10 중 9 를 회수했습니다 — 90%. missing 11건이라는 숫자만 보면 55% 실패처럼 보이지만, 실제로는 "대상 문서에 없는 항목이 10개였다"가 대부분입니다.

4.4 그래서 76건은? — 같은 방법으로 재세요

100건짜리 실행에도 같은 질문을 던지면 됩니다. 대상 문서들의 fact 총합이 24 근처라면, 76건은 상한 그대로이고 회수율은 100%에 가깝습니다. 

python - <<'PY'
import json, io, glob, sys
sys.stdout.reconfigure(encoding='utf-8')
tot = {}
for p in glob.glob('artifacts/*/facts.json'):
    d = json.load(io.open(p, encoding='utf-8'))
    facts = d['facts'] if isinstance(d, dict) and 'facts' in d else d
    tot[p.split('\\')[-2]] = len(facts)
for k, v in tot.items():
    print(f'{k:40s} fact {v}')
print('\n기준 fact × 대상 문서 수 = 비교 건수(100)와 맞는지,')
print('대상 fact 합계 = 연결 가능한 상한(24?)과 맞는지 보세요.')
PY

세 가지 결과가 나올 수 있고, 각각 뜻이 다릅니다.

관측해석조치
대상 fact 합계 ≈ 24정상. 상한을 거의 다 회수했다 없음 — 대상 문서가 요약본이라 그렇다
대상 fact 합계 ≫ 24 (예: 60)연결 실패. 대상에 있는데 못 이었다 개념 판정 과차단 조사 → rejected_differs_by, 온톨로지 aliases 보강
대상 fact 합계가 문서 내용에 비해 너무 적다추출 결함. F3 가 fact 를 못 뽑았다 facts_by_block.json 의 cited=false 블록 확인

4.5 76건을 네 갈래로 분해하는 진단

missing 의 원인은 여섯 가지로 정의돼 있고 전용 도구가 있습니다. LLM 을 부르지 않아 비용이 0 입니다. 

python scripts/why_missing.py --all        # 전건 원인 분류
python scripts/why_missing.py 최대충전전류    # 항목 하나를 끝까지 추적
갈래 1 — 대상에 진짜 없다 정상
가장 흔합니다. 위 실측에서 11건 중 10건. 조치할 것이 없고, 오히려 리포트가 제 일을 한 것입니다(요약본에 빠진 항목을 드러냈으니까).
갈래 2 — 개념 판정이 정답 쌍을 막았다 과차단
최대충전전류 사례. rejected_evidence(인용 검증 실패)나 rejected_differs_by(모순으로 거부)가 0 이 아니면 여기를 의심합니다. 조치: knowledge/ontology.yaml 에 aliases: 로 승격. 이때 differs_by 목록에 번역어를 직접 나열하면 안 됩니다 — 동의어까지 "다르다"로 선언됩니다.
갈래 3 — F3 가 대상에서 fact 를 못 뽑았다 추출 누락
문서에는 내용이 있는데 fact 가 안 만들어진 경우입니다. 상한 자체가 잘못 계산되므로 가장 교묘합니다. facts_by_block.json 의 cited=false 블록과 줄 단위 커버리지가 이것을 잡습니다.
갈래 4 — recall 이 정답을 못 올렸다 검색 한계
대상 fact 가 많으면 정답이 top_k 5위 밖으로 밀릴 수 있습니다. candidate_pairs.json 의 cut_by 가 top_k 인지 min_score 인지 알려줍니다. 이번 실측에서는 이 갈래가 0 이었습니다.

4.6 그래서 설계가 잘못됐나 — 정직한 평가

"missing 이 많다" 자체는 결함이 아닙니다. 하지만 이 데이터에서 실제 약점 세 가지가 드러납니다.

약점근거성격
1거부권이 정답 쌍을 죽인다 최대충전전류 ↔ Maximum charging current, recall 1위(0.691)인데 차단 진짜 결함 — 다만 "틀린 연결보다 놓친 연결이 낫다"는 의도된 보수성의 부작용
2교차언어에서 코드 확정이 0 pairs_by_code: 0 → low_confidence 24/24 → 코드 판정이 전부 무시됨 구조적 한계 — 이름 완전일치가 원리적으로 불가능. 온톨로지로만 완화된다
3속성 키 어휘가 양쪽에서 갈린다 mean_attribute_coverage 0.1278, code_unknown 22/24 설계 공백 — 기준은 F1 semantic_role 로 정규화되는데 대상은 LLM 자유 추출
⚠️ 1번을 "고치자"고 할 때 주의할 것 거부권을 느슨하게 하면 놓친 연결은 줄지만 틀린 연결이 늘어납니다. 그리고 틀린 연결은 사람을 잘못된 수정으로 유도하는 반면, 놓친 연결은 ⚪ 대상에 없음 으로 검토 목록에 남아 확인됩니다. 두 오류의 비용이 다르기 때문에 설계가 일부러 한쪽으로 기울어 있습니다. 손대기 전에 과차단이 몇 건인지 먼저 세는 것이 순서입니다.
질문 메모 상한 분석이나 네 갈래 분해에서 궁금한 점을 적어보세요.

💡 missing_reason 을 호출자가 주입하는 이유 후보가 왜 없는지는 매칭 전략마다 다릅니다 — 옛 유사도 경로는 "임계 미달", F7 개념 경로는 "개념이 same_as 로 이어지지 않음"입니다. 문구가 틀리면 사용자는 F7 에서 쓰이지도 않는 match_min_score 를 조정하러 갑니다. 그래서 ConceptMatcher.explain_missing() 이 차단한 후보와 축까지 실어 보냅니다: 
개념이 같다고 판정되지 않아 비교하지 않았습니다(개념 그래프에 이 항목과
이어진 대상 fact 가 없습니다). 다른 개념으로 차단된 후보:
'Rated capacity'(측정조건 이(가) 다름) — … / 'Nominal voltage'(물리량 이(가) 다름) — …
이 문장이 리포트의 사유 칸에 그대로 나옵니다. 즉 리포트만 봐도 어느 후보가 무슨 축으로 막혔는지 알 수 있습니다.

7. 요약 한 장

질문답
missing 은 후보가 없는 항목인가? 대체로 그렇다. 단 "후보는 있었지만 LLM 이 없다고 답한" 경우도 있고, decided_by(code vs llm)로 100% 구분된다
후보가 있으면 판정은 누가? 원칙은 코드 우선 → 애매하면 LLM. 그러나 이 실행은 연결이 전부 LLM 산이라 24건 모두 LLM 이 결정했다. LLM 이 라벨을 고르지만 라벨 유효성 · 후보 실재 · 인용 실재는 코드가 검증한다
76건은 결함인가? 대부분 정상. 기준은 마스터 규격표, 대상은 요약본이라 상한이 낮다. 실측에서 missing 11건 중 10건 정당 · 1건 과차단, 상한 대비 회수율 90%. 76건도 같은 방법(대상 fact 수 = 상한)으로 재야 한다
그럼 고칠 것은? ① 과차단(온톨로지 aliases 승격) ② 속성 키 어휘 불일치 (mean_attribute_coverage 0.13) ③ 교차언어에서 pairs_by_code: 0
✅ 한 문장으로 숫자를 볼 때는 분모를 먼저 보고, missing 을 볼 때는 상한을 먼저 보세요. 76 이라는 절대값은 아무것도 말해주지 않지만, "대상 문서에 fact 가 몇 개인가"를 함께 놓는 순간 그 숫자는 정상인지 결함인지를 말하기 시작합니다.
