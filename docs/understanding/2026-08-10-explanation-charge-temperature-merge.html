1배경 — 이 파이프라인이 무엇을 하는가

1.1 깊은 배경 (이미 익숙하면 1.2 로 건너뛰세요)

ContentCompare 가 푸는 문제는 한 문장으로 요약된다. 엑셀 한 장에 정리된 “정답 규격표”가 있고, 그 내용이 Word·PPT 로 흩어진 문서들에 제대로 반영됐는지 확인하고 싶다. 사람이 하면 한 줄씩 눈으로 대조해야 하는 일이다.

이 저장소에는 그 일을 하는 엔진이 두 개 있다.

엔진방식강점 / 약점
rag 대상 문서를 잘게 쪼개(chunk) 색인하고, 기준 항목으로 검색해서 나온 원문 조각을 LLM 에게 통째로 보여 준 뒤 “같냐 다르냐”를 묻는다. 원문을 직접 본다는 게 강점. 대신 검색이 못 찾으면 끝이고, 조각 경계가 의미 단위와 어긋나기 쉽다.
fact 문서를 먼저 fact — {항목명, 속성:{값,단위}, 근거원문} 라는 정형 카드 — 로 바꿔 둔 다음, 카드끼리 비교한다. 숫자·단위가 구조화되면 LLM 없이 코드가 결정적으로 비교할 수 있다. 대신 카드로 바꾸는 순간 카드에 안 담긴 내용은 영영 사라진다.

오늘의 사건은 전적으로 fact 엔진에서 벌어진다. 그리고 그 마지막 문장 — “카드에 안 담긴 내용은 영영 사라진다” — 이 이야기의 전부다.

1.2 이 사건에 필요한 배경 — fact 엔진의 여섯 칸

fact 엔진은 문서 하나를 아래 순서로 통과시킨다. 각 칸 아래 배지는 누가 그 일을 하는가를 나타낸다. 이 색 규약은 프로젝트의 다른 화면(🔬 파이프라인 현미경)과 문서에서 그대로 쓰이므로 눈에 익혀 두면 좋다.

2질문 ① 왜 한 덩어리인가 — 범인은 Word 자신이다

질문은 이랬다. “어떤 로직에 의해 하나로 구성된 것인지 설명해줘. LLM 개입 없이 이게 가능한 것인지 의문이다.”

답은 조금 김빠질 수도 있다. 그것들을 하나로 “묶은” 로직은 존재하지 않는다. Word 파일이 처음부터 그것을 한 덩어리로 저장해 두었고, 우리 코드는 파일에 적힌 구조를 그대로 옮겨 적었을 뿐이다.

2.1 문단의 해부 — <w:p> 와 <w:br/>

.docx 파일은 사실 zip 압축된 XML 묶음이다. 그 안의 word/document.xml 을 열어 보면 문서 본문이 이렇게 생겼다. 여기서 중요한 태그는 딱 둘이다.

태그사람이 하는 동작의미
<w:p>Enter ⏎ 문단(paragraph)의 시작과 끝. Word 가 생각하는 “한 덩어리”의 단위.
<w:br/>Shift + Enter ⇧⏎ 줄바꿈(soft line break). 화면에서는 줄이 바뀌지만 문단은 끝나지 않는다.

그리고 spec_en.docx 의 그 부분은 실제로 이렇게 저장돼 있다 — 진짜 파일에서 꺼낸 구조다.

💡 왜 이게 중요한가

만약 작성자가 Shift+Enter 대신 그냥 Enter 를 눌렀다면 <w:p> 가 다섯 개 생겼을 것이고, 우리 파이프라인은 아무 변경 없이도 이 문제를 겪지 않았을 것이다. 즉 이 사건은 문서 작성 습관 하나에서 시작한다. 그리고 실무 문서에서 Shift+Enter 는 아주 흔하다 — 그래서 이걸 “잘못 쓴 문서”로 치부하고 넘어갈 수 없다.

2.2 코드가 한 일 — 읽고, 옮기고, (한 곳에서) 뭉갠다

추출 코드(contentcompare/raw/word_raw.py)는 세 단계를 거친다. 전부 순수 함수이고 LLM 은 근처에도 없다.

contentcompare/raw/word_raw.py — ① 본문 훑기

def parse_word_xml(xml_str):
    body = _find_body(xml_str)
    for el in list(body):
        if el.tag == _w("p"):        # <w:p> 하나 = 문단 probe 하나
            probes.append(_parse_paragraph(el))
        elif el.tag == _w("tbl"):    # <w:tbl> 하나 = 표 probe 하나
            probes.append(TableProbe(rows=_parse_table(el)))

여기가 “묶임”의 전부다. 반복문이 <w:body> 의 직계 자식만 훑는다. <w:br/> 는 <w:p> 안쪽에 있으므로 이 반복문의 눈에는 아예 보이지 않는다. 문단 하나가 들어오면 probe 하나가 나간다. 판단도, 추론도, 병합도 없다.

contentcompare/raw/word_raw.py — ② 문단 안의 텍스트 잇기

def _runs_text(container):
    for node in container.iter():
        if node.tag == _w("t"):                       # 글자
            parts.append(node.text or "")
        elif node.tag == _w("tab"):                   # 탭은 탭 그대로
            parts.append("\t")
        elif node.tag in (_w("br"), _w("cr")):        # ← 예전엔 " " (공백)
            parts.append("\n")                        #   지금은 "\n" 줄바꿈
    return "".join(parts)

바로 이 두 줄이 커밋 75bfd8e(Phase 3) 에서 바뀐 부분이다. 예전에는 <w:br/> 를 공백으로 바꿔서, 문단 텍스트가 처음부터 한 줄로 뭉개진 채 만들어졌다. 지금은 줄바꿈 문자로 남긴다.

contentcompare/raw/word_raw.py — ③ 블록 만들기

def build_word_doc(file_name, probes):
    for p in probes:
        if isinstance(p, ParaProbe):
            text = " ".join((p.text or "").split())   # ← \n 이 여기서 공백이 된다
            doc.blocks.append(RawWordBlock(
                block_id = block_id,
                type     = "paragraph",
                text     = text,                      # 병합된 한 줄 (예전과 동일)
                lines    = _split_lines(block_id, p.text or ""),  # 원본 \n 기준으로 쪼갠 줄들
            ))

여기서 코드가 양다리를 걸친다. 같은 문단으로부터 두 가지 표현을 동시에 만든다.

필드내용왜 이렇게 뒀나
text "Charge temperature ranges: -5~5℃, 0.1C(4.55V) 5~12℃, …"
줄바꿈이 공백으로 눌린 한 줄		 이 값이 compact_raw 를 타고 F3 LLM 프롬프트에 그대로 실린다. 여기가 바뀌면 fact 추출 결과와 캐시가 통째로 무효화되므로, 예전 그대로를 유지했다 (커밋 메시지의 “compact_raw 출력은 바이트 동일하다”가 이 뜻이다).

2.4 “LLM 개입 없이 이게 가능한가?”

가능한 정도가 아니라, LLM 이 개입할 여지가 원리적으로 없다. 지금까지 나온 동작을 하나씩 세어 보면 이렇다.

동작누가근거
docx 열어서 OpenXML 문자열 얻기⚙️ 코드 win32com 이 Document.Content.WordOpenXML 을 딱 1회 호출
<w:p> / <w:tbl> 세기⚙️ 코드 ElementTree 로 XML 자식 순회
<w:br/> → \n⚙️ 코드 태그 이름 비교 한 줄
줄 쪼개서 l01…l05 매기기⚙️ 코드 text.splitlines()
표 병합(가로/세로) 채우기⚙️ 코드 gridSpan / vMerge 속성 읽기

이것이 raw/ 계층의 설계 원칙이다 — “해석 없이 관찰 가능한 물리 정보만”. 파일을 LLM 에 통째로 던지지 않고, 먼저 코드가 결정적으로 읽을 수 있는 것만 읽어 둔다. 그래야 나중에 LLM 이 헛소리를 했을 때 대조할 원본이 남는다.

✅ 질문 ① 정리

네 조건을 하나로 만든 것은 Word 문서 자신이다(Shift+Enter = <w:br/>). 우리 코드는 “문단 = 블록”이라는 규칙을 기계적으로 적용했을 뿐이고, LLM 은 이 단계에 전혀 관여하지 않는다. 오히려 최근 변경(75bfd8e)은 그 네 줄을 다시 쪼개서 lines[] 에 보존하는 쪽으로 갔다.

질문 메모 Word 파싱 · text 와 lines 의 이중 표현에 대해 궁금한 점을 적어보세요.

3질문 ② 왜 기준 항목과 안 묶이는가 — 다섯 개의 관문

두 번째 질문이 진짜 문제다. “comparison_result.json 을 보면 이 항목은 ‘충전환경온도’로 내용이 묶여야 하는데 전혀 묶이지 않고 있다.”

이걸 제대로 답하려면 먼저 한 가지를 분명히 해야 한다. 여기서 “안 묶인다”는 건 비교가 틀렸다는 뜻이 아니라, 비교 자체가 일어나지 않았다는 뜻이다. 현재 산출물에서 해당 항목은 이렇게 나온다.

{
  "entity_name": "충전환경온도",
  "target_doc": "spec_en.docx",
  "result": "missing",
  "decided_by": "code",          // ← LLM 을 부르지도 않았다
  "match_method": "none",
  "reason": "개념이 같다고 판정되지 않아 비교하지 않았습니다
             (개념 그래프에 이 항목과 이어진 대상 fact 가 없습니다).",
  "target": null                  // ← 후보가 0건
}
🔍 decided_by 가 알려 주는 것

FactComparator.compare 는 후보가 하나도 없으면 LLM 을 호출하지 않고 즉시 반환한다. 그래서 decided_by: "code" + target: null 조합은 “LLM 이 없다고 판단했다”가 아니라 “보여 줄 후보가 애초에 0건이었다”는 뜻이다. 반대로 decided_by: "llm" 인 missing 이라면 후보는 있었는데 LLM 이 아니라고 답한 것이다. 이 구분이 원인 추적의 첫 단추다.

기준 문서에는 온도 항목이 두 종류 있다.

  • 충전환경온도 (17행, −5 / 35 / 85) — 충전할 때의 주변 환경 허용 범위. 상한이 85℃ 인 걸 보면 “이 온도 범위 안에서 보관·동작해도 된다”는 성격이다.
  • 충전온도범위(…) (23~26행, −5~45℃ 를 넷으로 쪼갬) — 온도 구간마다 충전 전류/전압이 달라지는 조건표.

(만약 업무 정의상 두 항목이 같은 개념이라면, 그건 유사도로 풀 문제가 아니라 knowledge/ontology.yaml 에 사람이 적어 줄 문제다 — §5 참고.)

질문 메모 “충전환경온도 vs 충전온도범위” 구분에 이견이 있거나 업무 정의가 다르면 여기에 적어 주세요.

3.2 다섯 개의 관문

기준 항목 하나가 ✅ 일치 까지 가려면 관문 다섯 개를 통과해야 한다. 이 사건에서는 A 에서 이미 다치고, D 에서 최종적으로 멈춘다.

관문 A — compact_raw 경계에서 줄이 사라진다

이것이 단일 최대 원인이다. F3 LLM 이 받는 입력은 compact_raw 인데, compact_word() 는 블록에서 id, type, text, style 만 옮긴다. lines[] 는 옮기지 않는다.

def compact_word(doc):
    for b in doc.blocks:
        if b.type == "paragraph":
            item = {"id": b.block_id, "type": "paragraph", "text": b.text}
            if b.style:
                item["style"] = b.style
        # lines 는 여기 없다 — 의도된 것이다.

그리고 이건 버그가 아니라 의도된 계약이다. 커밋 75bfd8e 는 “compact_raw 출력은 바이트 동일하다” 를 핵심 계약으로 못 박았다. 이유는 캐시다 — F3 는 compact_raw 의 해시를 지문(fingerprint)으로 쓰기 때문에, compact 이 한 글자라도 바뀌면 모든 문서의 fact 추출 캐시가 전부 무효화된다.

🤖 그래서 LLM 이 실제로 보는 것은 이 한 줄이다 
[w_b010] Charge temperature ranges: -5~5℃, 0.1C(4.55V) 5~12℃, 0.3C(4.55V) 12~15℃, 0.7C(4.55V) 15~45℃, 1.2C(4.20V)

사람이 봐도 어디가 구간 경계인지 헷갈린다. 0.1C(4.55V) 와 5~12℃ 사이에 있던 줄바꿈이 다른 공백들과 구분되지 않기 때문이다. Phase 3 가 애써 살려 둔 lines[] 는 바로 이 프롬프트에 닿지 못한다.

질문 메모 관문 A(compact 경계)와 “바이트 동일 계약”에 대해 궁금한 점을 적어보세요.

관문 B — F3 가 만드는 fact 개수가 기준과 어긋난다

F3 프롬프트가 LLM 에게 주는 지시 중에 이런 게 있다.

- 흩어진 서술(본문+스피커노트, 표+설명)이 같은 대상이면 하나의 fact 로 병합합니다.

이 규칙은 원래 “표에 값이 있고 아래 문단에 설명이 있으면 합쳐라”라는 뜻이다. 그런데 지금 상황에서는 정확히 반대로 작동한다. LLM 눈에는 한 블록 안에 “Charge temperature ranges” 라는 하나의 대상이 보이므로, 규칙에 충실하게 fact 1건을 만든다. 심지어 이건 LLM 의 판단 실수도 아니다 — 주어진 입력만 놓고 보면 맞는 판단이다.

관문 C — attributes 맵에 조건표를 담을 수 없다

fact 의 값 부분은 {"속성이름": {"value": …, "unit": …}} 형태다. 이 그릇은 “공칭전압 = 3.85 V” 같은 스칼라를 담기엔 완벽하지만, “−5~5℃ 에서는 0.1C, 5~12℃ 에서는 0.3C, …” 같은 조건별 반복은 담을 자리가 없다.

LLM 이 할 수 있는 선택은 사실상 셋뿐이고, 셋 다 정보를 잃는다.

선택결과이후 어떻게 되나
첫 구간만 담는다 lower_limit: -5, upper_limit: 5 근거 인용도 첫 줄만 → 근거 검증을 통과한다. 나머지 셋이 사라진 걸 아무도 모른다. (설계 §2.1 의 문제 ④)
전체 범위로 뭉갠다 lower_limit: -5, upper_limit: 45 기준 4행 어느 것과도 값이 안 맞아 ❌ 불일치 또는 연결 실패.
문자열로 통째 담는다 value: "-5~5℃ 0.1C, 5~12℃ 0.3C, …" _as_number() 가 숫자로 못 바꾸고, 문자열은 완전히 같을 때만 코드가 단정한다 → 판단 보류 → LLM 위임.

관문 D — 개념 그래프에 same_as 가 생기지 않는다

F7 은 “두 fact 를 비교해도 되는가”만 답하는 단계다. 판정 규칙은 단 하나 — 개념이 same_as 로 이어져 있지 않으면 비교하지 않는다. 그리고 그 연결은 다음 순서로 만들어진다.

구체적으로 concept_assembler.assemble() 안에서 벌어지는 일은 이렇다. same_as 는 union-find 로 병합된다 — 즉 A same_as X 이고 B same_as X 이면 A 와 B 도 같은 개념 덩어리가 된다.

same_edges = [e for e in valid if e.relation == SAME_AS]
for edge in sorted(same_edges, key=lambda e: not e.promoted):
    a, b = find(edge.left.key), find(edge.right.key)
    if a == b: ...
    if blocked(a, b):                    # differs_by 로 이어진 둘이 합쳐지는가?
        _demote(edge, "differs_by")      # → unknown 으로 강등, 연결 무효
        continue
    parent[a] = b                        # 병합

그래서 “대상 fact 1건을 기준 4건 모두에 잇는다”는 해법은 구조적으로 불가능하다. 그렇게 이으면 충전온도범위(-5~5℃) 와 충전온도범위(15~45℃) 가 서로 같은 개념이 돼 버린다. 값이 명백히 다른 두 항목이므로 LLM 이 그 둘 사이에 differs_by 를 하나라도 달아 두면 코드가 즉시 강등한다.

“문제는 LLM 이 Charge temperature ranges 라는 개념을 인식하지 못하는 것이 아니다. 오히려 의미 인식 결과를 다음 단계에서 너무 일찍 축약하고, 최종 비교를 그 축약본에 의존하는 것이 핵심이다.”

4.2 raw/compact.py — 여기가 정보의 절벽 ⚙️ 코드

compact_word() 는 12줄짜리 함수이고, 그중 없는 한 줄이 이 문서의 주인공이다(lines 를 옮기지 않는다). 왜 그대로 뒀는지는 관문 A 에서 설명했다 — F3 캐시 지문이 compact_raw 해시이기 때문이다.

fp = fingerprint_for(json.dumps(compact, ensure_ascii=False), FACT_VERSION)
data = store.cached_or_compute("facts", compute, fingerprint=fp)

즉 compact 에 필드를 하나 더하는 순간, 모든 문서의 fact 를 다시 뽑아야 한다. Phase 3 가 heading_level·list 를 style 이 아니라 새 structure 필드에 담은 것도 같은 이유다 — compact_word 가 style 을 통째로 통과시키므로 거기에 키를 더하면 프롬프트가 바뀐다.

4.3 fact/fact_extractor.py — 추출 + 진단 🤖 LLM ⚙️ 코드

추출 자체는 LLM 이 하지만, 그 옆에 LLM 을 전혀 안 쓰는 진단기가 붙어 있다. 커밋 a173ad5(Phase 4a)가 추가한 줄 단위 인용 커버리지다.

row.update(_line_coverage(lines_map.get(b["id"]), row["fact_ids"], evidence_by_id))

하는 일은 이렇다. physical_raw 의 lines[] 를 가져와, 그 블록을 근거로 든 fact 들의 evidence_text 와 양방향 부분일치로 대조한다. 그러면 어느 줄이 실제로 인용됐는지 역산된다.

지표블록 단위(예전)줄 단위(Phase 4a)
w_b010 판정cited = true 1 / 5 인용 · 4줄 누락

이 숫자는 커밋 메시지에 실측으로 박혀 있다. 블록 단위 계측의 사각지대 — 한 문단에 조건이 넷인데 fact 가 첫 줄만 인용해도 그 블록은 cited=true 로 보이는 문제 — 를 정확히 겨냥한 것이다.

⚠️ Phase 4a 가 못 하는 것

커밋이 스스로 명시한 한계다. 근거는 다 담겼는데 attributes 가 한 조건만 담은 축약은 이 지표로 안 보인다. 그건 evidence 대 attributes 의 문제이고, 앞으로 만들 conditional_series 게이트의 몫이다. 즉 지금은 “어떤 종류의 누락은 보이고, 어떤 종류는 아직 안 보인다” 는 상태를 정확히 알고 있는 셈이다.

FactMatcher F7 에서는 후보 좁히기(recall) 전용. 이름 완전일치 → 임베딩 코사인 → (임베딩 없으면) BM25 폴백. 점수는 판정 근거가 아니다.
ConceptMatcher.search() 개념 그래프에서 same_as 파트너만 꺼낸다. 없으면 [] — 그게 곧 ⚪ 의 근거다.
MatchCandidate.needs_review 개념 경로에서 의미가 재정의된다 — 점수 경계가 아니라 “이 연결을 LLM 이 만들었는가”. 코드/온톨로지 확정이면 False.
verify_evidence() LLM 이 제안한 same_as 만 검사. 인용 토큰의 80% 가 원문에 있어야 한다. 실패하면 버리지 않고 unknown 으로 강등한다.
explain_missing() 후보가 없을 때 사람에게 줄 사유를 만든다 — 그 쌍을 막은 differs_by 가 있으면 축·이유까지 실어 준다.

4.5 fact/fact_comparator.py — 최종 판정 ⚙️ 코드

구조는 compare_code()(LLM 0회) → Acceptance Gate → finalize()(필요할 때만 LLM) 로 나뉘어 있다. 이 사건은 compare_code() 의 첫 if 에서 끝난다 — 후보가 없으니까.

참고로, 만약 후보가 하나라도 만들어졌다면 그다음은 이렇게 흘렀을 것이다.

5.3 지금 당장 할 수 있는 우회 — 온톨로지

만약 업무 정의상 어떤 두 항목이 같은 개념이라면, 그건 유사도로 풀 문제가 아니다. 사람이 knowledge/ontology.yaml 에 적어 주면 LLM 을 건너뛰고 영구 적용되고, recall 과 독립적으로 조회되므로 “유사도가 낮아 후보에도 못 들어오는” 쌍까지 구제된다.

# knowledge/ontology.yaml
aliases:
  # 번역어·약칭은 반드시 여기에. differs_by 에 번역어를 직접 나열하면
  # 동의어까지 '다르다'로 선언돼 버린다.
  - ["충전온도범위", "Charge temperature ranges", "충전 온도 범위"]

same_as:
  - names: ["충전온도범위(5~12℃)", "Charge temperature ranges"]
    reason: "…"
⚠️ 다만 온톨로지로는 이 사건이 완전히 낫지 않는다

연결을 억지로 만들어도, 대상 fact 는 여전히 1건이고 그 안에는 네 구간 중 하나(혹은 뭉갠 값)만 들어 있다. 그러면 ⚪ 가 ❌ 로 바뀔 뿐이다. 근본 해결은 §5.4 다.

5.4 근본 해결 — 이미 설계된 다음 단계

설계 문서가 그리는 방향은 fact 를 더 잘 뽑는 것이 아니라, fact 를 지도로만 쓰고 판정은 원문으로 하는 것이다.

상태단계이 사건에 대한 효과
✅ 완료Phase 3 — lines[] 보존 2차 검사가 읽을 원문을 확보. 단, 아직 판정에는 안 쓰인다
✅ 완료Phase 4a — 줄 단위 인용 커버리지 탐지 가능해짐: “5줄 중 1줄만 인용 · 4줄 누락”
⏳ 예정conditional_series 게이트 조건형 반복 fact 를 2차 검사로 라우팅
⏳ 예정Evidence Bundle 회수 l01~l05 + 상위 heading 을 묶어 LLM 에 원문 그대로 제공
⏳ 예정Entity 별 그룹 배치 기준 4항목이 같은 Bundle 을 공유 → 호출 4회가 1회로
💡 왜 “compact 에 lines 를 그냥 넣어라”가 정답이 아닌가

가장 단순한 해법처럼 보이지만 대가가 크다. ① 모든 문서의 F3 캐시가 무효화되고, ② 프롬프트 토큰이 늘고, ③ fact 를 여러 건으로 쪼개도 관문 D 의 1:N 문제는 그대로다. 설계가 2단계 구조를 택한 이유는, 대부분의 항목(스칼라 값)은 지금 방식이 이미 싸고 정확하기 때문이다. 비싼 처리는 정말 필요한 소수에만 건다.

7한 문단 요약

Word 작성자가 Shift+Enter 를 눌렀다. 그래서 네 개의 충전 온도 조건이 한 문단 안에 들어갔고, 우리 파서는 “문단 = 블록”이라는 규칙대로 그것을 블록 하나로 읽었다 — LLM 은 여기에 아무 관여도 하지 않았다. 최근 변경으로 그 네 줄은 lines[] 에 보존되지만, 그 필드는 캐시 지문을 지키기 위해 compact_raw 에 실리지 않는다. 그래서 F3 LLM 은 여전히 한 줄짜리 문자열만 보고 fact 를 1건 만들고, 기준 엑셀은 같은 내용을 4건으로 갖고 있다. 개념 그래프는 이 1:N 을 이을 방법이 없어(넷 다 이으면 서로 다른 네 항목이 한 개념으로 병합돼 버린다) 연결을 만들지 못하고, F5 는 후보 0건을 받아 LLM 도 부르지 않은 채 ⚪ 대상에 없음 을 적는다. 고칠 자리는 임계값이 아니라 파이프라인의 구조이고, 그 설계는 이미 문서화돼 있다 — fact 는 지도로만 쓰고, 판정은 w_b010:l02 같은 원문 줄로 다시 하는 2단계 재검사다.
