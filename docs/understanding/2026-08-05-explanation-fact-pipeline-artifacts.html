질문 두 개에 답하는 글입니다. “20건 판정 중 LLM 위임 2건”은 왜 그렇게 적은가, 그리고 실행할 때 쏟아지는 그 많은 JSON 파일은 각각 무엇인가. 두 질문은 사실 하나의 답을 공유합니다 — LLM 에게 문서를 통째로 주지 않고, 잘게 나눠서 “LLM 만 할 수 있는 일”에만 쓰기 때문입니다.

이 글을 읽는 법

중간중간 “질문 메모” 상자에 궁금한 점을 적으면 브라우저에 자동 저장되고, 맨 아래 질문 저장 버튼으로 질문이 박힌 사본을 받을 수 있습니다. 그 파일을 docs/understanding/ 에 덮어쓴 뒤 Claude 에게 “질문에 답해줘”라고 하면 됩니다.

선행 글: ContentCompare 는 문서를 어떻게 비교하는가 · 온톨로지 개념 그래프. 이 글의 모든 숫자는 artifacts/ 폴더의 실제 실행 산출물에서 가져왔습니다.

1. 배경 — “파일을 LLM 에 통째로 주지 않는다”

가장 단순한 접근을 먼저 생각해 봅시다. 엑셀과 워드를 통째로 LLM 에 넣고 “다른 데를 찾아줘” 라고 하면 안 될까요? 안 됩니다. 세 가지가 동시에 무너집니다.

❌ 통째로 주면

  • 추적 불가 — 틀렸을 때 어느 단계에서 틀렸는지 알 수 없다. 전부 한 번의 호출 안에서 벌어진다.
  • 재현 불가 — 같은 입력에 매번 다른 답. 고칠 지점이 없다.
  • 검수 불가 — “3.85V 가 다릅니다”가 진짜 문서에 있는 값인지, 지어낸 값인지 확인할 방법이 없다.

✅ 잘게 나누면

  • 단계마다 파일이 남는다 — 어디서 틀렸는지 열어 보면 안다.
  • 값 비교는 코드가 — 3.89 ≠ 3.85 는 파이썬이 100% 재현한다.
  • 근거 좌표가 따라다닌다 — E20:H20 처럼 셀 주소까지 결과에 실린다.

그래서 이 파이프라인은 문서를 여러 단계로 통과시키고, 단계마다 산출물을 파일로 남깁니다. 질문하신 그 많은 JSON 파일들이 바로 이 “단계별 산출물”입니다. 파일이 많은 것은 부작용이 아니라 설계 목적입니다.

질문 메모 “통째로 주면 안 되는 이유”에서 걸리는 게 있나요?

2. 질문 ① — 왜 LLM 이 2건만 판정하는가

LLM 이 불려 나오는 순간 — 같은 값, 세 대상 문서
'왜 2건만?'의 답이 여기 다 들어 있다. 같은 기준 카드인데 대상이 누구냐에 따라 판정 주체가 달라진다. 이름이 똑같으면 코드가 공짜로 끝내고, 그렇지 않을 때만 LLM 이 불려 나온다.
📘 자표준_규격서.docx (한국어 워드)
상대 카드entity_name: "공칭전압"
값 3.85 V
짝 찾기⚙️ 코드 이름이 글자까지 똑같다
norm_name 완전일치 → score 1.0
검문소지나지 않음 — 코드가 이은 연결은 검증 대상이 아니다
값 대조⚙️ 코드 3.89 vs 3.85 · 한쪽만 단위 있음 → 호환으로 봄 → 값이 다름
결과❌ 불일치 decided_by: code
"값이 다릅니다: target_value(기준 3.89 vs 대상 3.85V)"
LLM 을 한 번도 부르지 않았다.
📗 spec_en.docx (영어 워드)
상대 카드entity_name: "Nominal voltage"
값 3.85 V
짝 찾기⚙️ 코드 이름 일치 0건 → 🔢 임베딩
임베딩 0.6589 로 후보에만 오름
개념 판정🤖 LLM → same_as
인용: "3.89" / "The nominal voltage is 3.85V."
검문소🚧 수정 전: 왼쪽 인용이 낱말 1개 < 3 → ⚪ 탈락 → 연결 소멸 → 진짜 오류를 놓쳤다
✅ 수정 후: 원문 전체 인용이라 하한 면제 → 통과
값 대조🤖 LLM 연결을 LLM 이 만들었으므로 needs_review=True → 값도 LLM 이 재확인
결과❌ 불일치 decided_by: llm
"대상은 동일하나 기준 3.89와 후보 3.85가 다릅니다"
📙 자표준_발표.pptx (PPT 스피커노트)
상대 카드entity_name: "충전 규격 상세조건"
속성 2개: 공칭전압 3.89 V, 측정 조건 "0.1C, 4.55V"
짝 찾기⚙️ 코드 이름이 아예 다름 → 🔢 임베딩
임베딩 0.6973

값 대조🤖 LLM 기준은 속성 1개·단위 없음, 대상은 속성 2개 → 코드가 손을 뗌
결과✅ 일치 decided_by: llm
"3.89와 3.89 V는 단위 표기 차이만 있을 뿐 동일"
같은 기준 값인데 판정 주체가 코드 → LLM → LLM 으로 달라진다. 이름이 똑같으면 코드가 공짜로 끝내고, 이름이 다를수록 LLM 이 개입하고 검문소가 걸린다. 영어 문서가 어려운 이유가 여기에 다 들어 있다 — 언어가 다르면 첫 칸(이름 일치)이 절대 성립하지 않아 항상 가장 험한 길로만 간다.

2.1 그 “20건”이 정확히 무엇인가

리포트에 찍히는 그 줄의 정체부터 봅시다.

contentcompare/report/fact_report.py — _overview()
f"- 총 {total}건 판정 — ..."
f"- 판정 주체: 코드 {total - by_llm}건 / LLM {by_llm}건 (LLM 위임률 {by_llm/total:.0%})"

여기서 total 은 기준 fact 개수 × 대상 문서 개수입니다. 엑셀 기준 문서에서 fact 20 개가 나왔고 대상 문서가 워드 하나였으므로 20 × 1 = 20건입니다. 발표자료까지 같이 넣었다면 40건이 됩니다.

핵심

“20건 판정”은 기준 항목 하나하나를 대상 문서와 맞춰 본 횟수입니다. 그리고 그 20번 중에서 LLM 에게 물어본 것이 2번이라는 뜻입니다. 나머지 18번은 파이썬 코드가 결정했습니다.

2.2 세 겹의 체 — 20건이 어떻게 걸러지는가

LLM 까지 도달하려면 후보가 세 개의 체를 통과해야 합니다. 실제 실행(엑셀 ↔ 워드 규격서)의 숫자를 그대로 넣으면 이렇게 됩니다.

세 체를 말로 풀면 이렇습니다.

체 ①
개념 그래프에 연결이 있는가 — 없으면 대상에 없음 으로 끝. 애초에 비교 자체를 하지 않으므로 LLM 을 부를 일이 없습니다. 실측 9건 — deltaOCV·충전방법처럼 워드에 아예 없는 항목 + 온톨로지가 차단한 항목
↓ 통과한 11건
체 ②
코드가 값·단위로 단정할 수 있는가 — 공통 속성이 있고 단위가 호환되면 숫자 비교로 끝. 파이썬이 훨씬 잘하는 일입니다. 실측 9건 — match 8 + mismatch 1(공칭전압 3.89 vs 3.85V)
↓ 남은 2건
체 ③
연결을 사람이나 코드가 확정했는가 — LLM 이 만든 연결이면 값 판정도 한 번 더 보게 합니다. 여기까지 온 것만 LLM 이 판정합니다. 실측 2건
질문 메모 세 개의 체 중 헷갈리는 게 있나요? 체 번호와 함께 적어주세요.

2.3 코드가 판정하는 규칙 (결정 트리)

체 ②가 이 이야기의 핵심입니다. 코드는 언제 “확실하다”고 말하고, 언제 “모르겠다”며 손을 드는 걸까요? fact_comparator.py 의 규칙을 그림으로 옮기면 이렇습니다.

이 설계의 핵심 한 문장

코드는 “다르다”고 말할 자신이 없으면 “모르겠다”고 말합니다. 문자열이 다르다고 곧 불일치는 아닙니다 — “배터리승인규격 ver 4.7 SEC Req. ver.4.7” 과 “SEC Req. ver.4.7” 은 글자가 다르지만 같은 규격입니다. 그래서 문자열은 같을 때만 코드가 단정하고, 다르면 LLM 에 넘깁니다.

2.4 LLM 으로 간 2건의 실제 사유

실행 결과에서 그 2건을 그대로 꺼내면 이렇습니다.

① 고객 표준 버전 — 문자열이 달라서 일치

고객 표준 버전 fact-row-3 · B3:P3 qualitative_spec = "배터리승인규격 ver 4.7\nSEC Req. ver.4.7"
same_as 사람이 승격한 연결
(ontology.yaml)
문서 기준 규격 fact-word-1 참조규격 = 4.7 ver

코드 입장에서 보면: 공통 속성이 없고(qualitative_spec vs 참조규격), 값도 문자열이며 서로 다릅니다. 규칙대로 “모르겠다”가 나옵니다. LLM 이 받아서 판정했습니다: 

"result": "match",  "decided_by": "llm",
"reason": "기준의 '배터리승인규격 ver 4.7'과 후보의 '4.7 ver'은
           표기 순서만 다를 뿐 동일한 버전을 의미하므로 일치합니다."

② 최대충전전류 — 1495 와 1.495 일치

최대충전전류 fact-row-12 target_value = 1495.0 · unit = "" (엑셀 단위 칸이 비었음)
same_as 코드가 이름 완전일치로 확정
최대 충전 전류 fact-word-5 upper_limit = 1.495 A

여기서 코드가 “다르다”고 말하지 않은 것이 중요합니다. 1495 ÷ 1.495 = 1000, 즉 10의 거듭제곱 배수입니다. 이건 mA ↔ A 같은 단위 접두어 차이의 전형적인 흔적이고, 한쪽 단위를 모르는 상태에서 “다르다”고 단정하면 거짓 경보가 됩니다.

contentcompare/fact/fact_comparator.py
def _is_decimal_scaled(a: float, b: float) -> bool:
    """두 값이 10의 거듭제곱 배수 관계인가(1495 ↔ 1.495 = 1000배)."""
    ...

# 값이 다른데 한쪽 단위를 모르고 십진 배수 관계면, 단위 접두어 차이일 수
# 있으므로 코드가 '다르다'고 단정하지 않는다.
if not (a.unit and b.unit) and _is_decimal_scaled(na, nb):
    return None   # ← 모르겠다 → LLM 으로

LLM 은 “단위(A)를 고려했을 때 실질적으로 동일한 값”이라고 판정했습니다. 이것이 LLM 이 정말로 필요한 종류의 일입니다 — 문맥과 단위 상식이 필요한 판단이죠.

그래서 2건인 이유

20건 중 9건은 비교할 상대가 없었고, 9건은 숫자만 비교하면 끝나는 일이었습니다. 진짜로 “사람의 판단력”이 필요한 것은 표기가 다른 같은 버전과 단위가 생략된 배수 관계 — 딱 2건이었습니다.

2.5 같은 20건인데 PPT 는 왜 6건인가

같은 기준 문서를 발표자료와 비교하면 20건 중 LLM 6건이 됩니다. 항목 수도 같고 규칙도 같은데 왜 세 배일까요? 체 ③ 때문입니다.

📘 자표준_규격서.docx📙 자표준_발표.pptx
총 판정2020
⚪ 대상에 없음911
코드 확정93
LLM 위임26
연결을 만든 주체코드(이름 완전일치) 10 · 온톨로지 1코드 3 · LLM 6

워드 규격서는 항목명이 엑셀과 거의 같습니다(공칭용량, 표준환경온도 …). 그래서 연결을 코드가 이름 완전일치로 만들었고, 확정된 연결이므로 값 판정도 코드가 끝냈습니다.

반면 발표자료는 이름이 자유롭습니다 — Standard ambient temperature, 1개월 저장 조건, 충전 전압. 이 연결들은 LLM 이 만들었고, 아직 아무도 확인하지 않았습니다. 그래서 needs_review = True 가 붙고, 확인되지 않은 연결 위에서 코드가 단정하지 않도록 값 판정도 LLM 이 한 번 더 봅니다.

표준환경온도 fact-row-15 21.0 / 25.0 / 29.0
same_as decided_by: llm
→ needs_review = True
Standard ambient temperature fact-ppt-5 21 - 29 degC (target 25 degC)

값은 21/25/29 로 완벽히 같아서 코드만으로도 일치가 나옵니다. 그런데도 LLM 이 다시 봤고, 사유 끝에 “(근거 신뢰도가 낮아 검토 대상입니다.)”가 붙었습니다. 보수적이지만 의도된 비용입니다.

이 비용을 없애는 법

knowledge/ontology.yaml 에 그 쌍을 same_as 로 승격하면 decided_by 가 ontology 가 되어 needs_review 가 사라집니다. 사람이 한 번 확인할 때마다 LLM 위임이 영구히 줄어듭니다.

2.6 가장 흔한 오해 — 이 숫자는 전체 LLM 사용량이 아니다

“LLM 위임 2건”을 보고 “이 실행에서 LLM 을 2번 썼구나”라고 읽으면 완전히 틀립니다. 그 숫자는 마지막 값 대조 단계(F5)의 통계일 뿐입니다. 그 앞에서 LLM 은 이미 여러 번 일했습니다.

LLM
F1 문서 프로파일 — 문서마다 1회 “이 문서는 무엇에 대한 것인가”
LLM
F2 스키마 유도 + 레코드 정규화 — 엑셀만, 표마다 “F열은 하한치, G열은 중심치…”
LLM
F3 fact 추출 — Word·PPT 는 이 단계가 통째로 LLM “이 문장에서 무엇이 주장인가”
LLM
F7-3 개념 관계 유도 — 실측 호출 3회로 48쌍 판정 concept_graph.json 의 llm_calls: 3
LLM
F5 값 대조 — 여기가 “LLM 위임 2건” comparison_result.json 의 decided_by_llm

정리하면 LLM 은 “문서를 이해하는 일”에 집중적으로 쓰이고, “값을 비교하는 일”에서는 거의 빠집니다. 위임률 10% 는 “LLM 을 적게 쓴다”가 아니라 “최종 판정의 90% 를 재현 가능한 코드가 책임진다”는 뜻입니다.

실제 파일에서 확인해 보기

artifacts/자표준문서_xlsx/run_stats.json 을 열면 "llm": {"calls": 0} 으로 보일 수 있습니다. 이건 LLM 을 안 썼다는 뜻이 아니라 캐시가 적중했다는 뜻입니다 ("records": {"cached": true}). 자세한 건 5.5절에서.

3.5 fingerprint — 재실행이 공짜인 이유

폴더에는 .json 말고 .fingerprint 파일도 있습니다(12 bytes 짜리들). 이게 캐시 열쇠입니다.

contentcompare/fact/artifacts.py
def cached_or_compute(self, stage, compute, *, fingerprint=None):
    """캐시가 유효하면 디스크 산출물을 재사용, 아니면 compute() 후 저장."""
    if self.cache and self.exists(stage) and self._fingerprint_ok(stage, fingerprint):
        cached = self.load(stage)
        if cached is not None:
            return cached          # ← LLM 호출 0
    data = compute()               # ← 여기서만 LLM 을 부른다
    self.save(stage, data)
    if fingerprint is not None:
        self._write_fingerprint(stage, fingerprint)
    return data

지문은 입력 + 프롬프트 버전으로 만듭니다. 같은 문서를 다시 돌리면 지문이 일치해 디스크 산출물을 그대로 읽고 LLM 을 한 번도 부르지 않습니다. 반대로 프롬프트를 고치면 버전 상수가 바뀌어 지문이 어긋나고 자동으로 재계산됩니다.

지문을 산출물 안이 아니라 사이드카 파일로 분리한 것도 의도입니다 — 산출물 JSON 은 다운스트림이 그대로 읽는 순수 데이터여야 하고, 캐시 메타데이터가 섞이면 안 되기 때문입니다.

그래서 run_stats 의 llm.calls 가 0 이었다

{"llm": {"calls": 0}, "records": {"cached": true}, "facts": {"cached": true}} — “LLM 을 안 쓰는 문서”가 아니라 “이번 실행에서는 캐시가 다 맞아서 부를 필요가 없었다”는 뜻입니다. 처음 돌렸을 때는 이 문서에서 프로파일·스키마·레코드·fact 를 위해 LLM 을 여러 번 불렀습니다.

질문 메모 캐시가 언제 무효화되는지 등, 더 알고 싶은 게 있나요?

4. 왜 이렇게 하면 비교를 잘하는가

파일이 많고 단계가 많은 것은 분명 복잡합니다. 그 복잡함이 사 오는 것이 무엇인지 다섯 가지로 정리하면 이렇습니다.

① 형식 차이를 초반에 흡수한다

엑셀의 행, 워드의 문장, PPT 의 도형은 서로 비교할 수 없습니다. facts.json 단계에서 셋이 같은 모양이 되고, 그 이후 코드는 “이게 원래 엑셀 이었는지”를 알 필요가 없습니다. 비교 로직이 문서 형식과 분리됩니다.

② 값 비교를 결정적으로 만든다

{value, unit} 으로 정규화했기 때문에 “3.89 vs 3.85”는 파이썬이 판정합니다. 같은 입력이면 언제나 같은 답이 나오고, 틀렸다면 규칙을 고치면 됩니다. LLM 판정은 그렇게 고칠 수 없습니다.

③ LLM 을 “LLM 만 할 수 있는 일”에 남겨 둔다

실측에서 LLM 이 최종 판정을 맡은 것은 40건 중 8건이고, 그 8건은 전부 표기 차이·단위 상식·교차언어 같은 판단이었습니다. 값을 세는 일에 LLM 을 쓰면 비싸고 흔들립니다.

④ 오판을 추적할 수 있다

리포트가 이상하면 파일을 거슬러 올라가면 됩니다. 이건 실제로 쓰는 절차입니다:

  1. comparison_result.json — 판정과 사유, 판정 주체는?
  2. concept_graph.json — 애초에 연결이 있었나? 누가 만들었나?
  3. facts.json — fact 가 제대로 추출됐나? 값이 맞나?
  4. records.json / column_schema.json — 열의 의미를 잘못 잡았나?
  5. compact_raw.json — LLM 이 본 입력이 원본과 같았나?
  6. physical_raw.json — 원본이 실제로 어땠나?

어느 단계에서 틀렸는지 눈으로 확인할 수 있고, 그 단계만 고치면 됩니다. 통짜 LLM 호출에는 이 사다리가 없습니다.

⑤ 사람이 고친 것이 축적된다

knowledge/ontology.yaml(같다/다르다 확정)과 knowledge/*.md(도메인 용어)에 사람의 판단이 쌓입니다. 실행을 거듭할수록 LLM 이 새로 판단할 몫이 줄어들어 결과가 점점 안정됩니다.

정리

이 파이프라인의 목표는 “LLM 을 적게 쓰는 것”이 아닙니다. 판정의 책임을 최대한 코드로 옮기고, 남은 애매함만 LLM 에 맡기며, 그 경계를 파일로 남겨 사람이 검수할 수 있게 하는 것입니다. “LLM 위임 2건”은 그 설계가 의도대로 작동하고 있다는 신호입니다.

질문 메모 이 복잡함이 값어치를 한다고 보시나요? 반론이 있으면 적어주세요.

5. 코드 워크스루

5.1 전체 흐름은 FactPipeline.run() 한 곳에

contentcompare/fact/pipeline.py
def run(self, reference, targets, progress=None):
    docs = [reference, *targets]
    store = FactStore()
    try:
        for i, path in enumerate(docs, start=1):
            summary = self._process_one_safe(path, store, is_reference=(i == 1))
            result.summaries.append(summary)      # ← 문서마다 격리 처리
        self._compare_and_report(store, reference, targets, result)
        return result
    finally:
        close_all_office()                        # ← 열린 COM 문서 정리

_process_one_safe 라는 이름이 설계를 말해 줍니다 — 문서 하나가 실패해도 (COM 오류·LLM 예산 초과·JSON 파싱 실패) 나머지는 계속 처리하고, 그 문서의 summary 에 status="error" 와 사유를 남깁니다.

5.2 판정 분기는 FactComparator.compare() 12줄에

if not candidates:                       # 체 ① — 개념 연결 없음

best = candidates[0]

“20건 중 LLM 2건”의 정체가 이 12줄입니다. verdict is not None and not uncertain 을 통과하지 못한 건수가 곧 위임 건수입니다.

LLM 예산이 끊기거나 응답이 깨져도 코드 판정이 있으면 그것을 쓰고, 없으면 판단보류로 남깁니다. 조용히 사라지는 항목이 없다는 것이 이 파이프라인 전체의 규칙입니다.
