이 파이프라인을 AI 에이전트로 만들 수 있는가

루프 · 그래프 엔지니어링 · 그리고 정말 중요한 것 — 권한 경계

짧은 답: 만들 수 있고, 이미 절반은 만들어져 있다. 그런데 지금 없는 절반은 툴도 프롬프트도 아니다.

이 글은 ContentCompare 의 fact 엔진을 소재로, "고정 파이프라인을 에이전트로 바꾼다"는 것이 구체적으로 무슨 뜻인지 따져 본다. 일반론이 아니라 이 저장소의 실제 코드와 실측 숫자에 붙여서 이야기한다 — 그래야 "그래서 우리는 뭘 하면 되나"가 나온다.

  3. 직관 — 루프를 넣는다는 것의 본질

1. 배경 ① — "에이전트"라는 말이 실제로 가리키는 것

이미 에이전트 아키텍처에 익숙하시다면 2장으로 건너뛰세요.

"AI 에이전트"는 마케팅 용어가 되어 버려서 뜻이 흐려졌다. 기술적으로는 아주 좁은 것을 가리킨다. LLM 을 호출한다고 에이전트가 아니다. 에이전트가 되려면 네 가지가 있어야 한다.

구성요소뜻없으면
루프같은 단계로 되돌아가는 화살표그냥 파이프라인(DAG)이다
상태반복 사이에 누적되는 것 — 지금까지 뭘 했고 뭘 알아냈나매 반복이 처음부터 다시 한다
종료 조건언제 멈출지의 신호무한루프거나, 그냥 N회 반복(=루프가 아님)
행동바깥 세상을 읽거나 바꾸는 수단(툴)생각만 하고 아무것도 못 한다
용어 — credit assignment "결과가 나빴는데, 어느 단계를 고쳐야 하나"를 정하는 문제. 강화학습에서 온 말이지만 에이전트 설계의 핵심이다. 검증(무엇이 잘못됐나)만 있고 이것이 없으면 루프는 그냥 재시도가 된다. 이 글의 7장이 통째로 이 얘기다.
질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

2. 배경 ② — 지금 파이프라인은 어떻게 생겼나

지금 구조는 고정 DAG 다. F1 프로파일 → F2 스키마/레코드 → F3 fact 추출 → F7 개념 그래프 → F5 값 대조 → 리포트. 분기는 있지만 되돌아가는 화살표가 없다. LLM 은 정해진 자리에서 아주 좁은 질문만 받는다 — "이 두 항목이 같은 것인가?" "이 후보들과 기준을 대조하면?"

2.1 이건 미완성이 아니라 선택이었다

코드 곳곳에 그 선택의 흔적이 있다. 네 가지만 꼽으면:

제약어디에무엇을 막는가
단위를 모르면 None 을 돌려주고 물러난다_compare_attribute()코드가 추측으로 등가를 단정하는 것
후보 밖 fact_id 는 드롭한다_parse_findings()LLM 이 없는 대상을 지목하는 것
인용이 원문에 없으면 same_as 를 강등한다verify_evidence()근거 없는 연결이 성립하는 것
예산이 끝나면 코드 판정으로 되돌아가지 않고 보류한다_fallback(multi=True)고치려던 오판이 조용히 남는 것
✅ 먼저 인정하고 시작할 것 이 시스템의 정확도는 LLM 이 뭘 할 수 있느냐가 아니라, 코드가 뭘 못 하게 막느냐에서 나왔다.
실측이 그것을 그대로 보여준다(docs/FACT_F3_5_LIVE_REPORT.md §9.1) — 골든셋 27항목 정확도가 85% → 89% → 93% 로 올라갔는데, 올린 두 변경이 전부 "코드가 언제 단정해도 되는가"의 규칙이었다:
① 양쪽 속성이 하나씩이면 키 이름이 달라도 값으로 판정한다
② 문자열은 같을 때만 단정하고, 다르면 LLM 에 넘긴다

그러니 에이전트로 만든다는 건 이 제약을 푸는 게 아니다. 제약을 그대로 둔 채 되돌아가는 화살표를 추가하는 것이다. 이 문장이 이 글의 나머지 전부를 결정한다.

2.2 그리고 이미 갖춰진 것들

에이전트를 만들 때 보통 제일 귀찮은 것들이 이 저장소엔 이미 있다.

상태 저장 (사실상 checkpointer)

각 단계가 artifacts/<문서>/<단계>.json 에 결과를 남기고, <단계>.fingerprint 사이드카로 캐시 유효성을 판정한다 (ArtifactStore.cached_or_compute). 입력이 같으면 재계산하지 않는다. 재개 가능한 상태 그래프의 핵심 부품이 이미 있다.

평가 데이터

golden/자표준_골든셋.jsonl 27건, golden/spec_en_골든셋.jsonl 104건. 루프를 넣고 나서 좋아졌는지 나빠졌는지를 숫자로 답할 수 있다. 이게 없으면 에이전트 개발은 그냥 느낌으로 하는 일이 된다.

계측

run_stats.json 에 LLM 호출·재시도·파싱 실패·드롭 사유·블록 커버리지가 쌓인다. decided_by 로 판정 주체가, result_changed 로 뒤집힘이 남는다. 루프의 종료 조건 후보가 이미 파일로 존재한다.

원인 분류기

fact/missing_trace.py 가 ⚪ 대상에 없음 의 원인을 6갈래로 가르고 각각의 조치까지 명시한다. LLM 을 안 부르므로 비용 0. 이 표가 곧 루프 정책의 초안이다.

질문 메모 "이미 갖춰진 것" 중 실제로 그런지 의심되는 게 있으면 적어보세요.

3. 직관 — 루프를 넣는다는 것의 본질

루프 하나를 추가한다는 건 세 가지를 정하는 일이다.

  1. 트리거 — 무엇을 보고 되돌아가나? (관측 가능한 신호여야 한다)
  2. 조치 — 되돌아가서 무엇을 다르게 하나? (같은 걸 또 하면 재시도일 뿐)
  3. 종료 — 언제 멈추나? (그리고 멈췄을 때 결과를 어떻게 처리하나)

장난감 예제로 한 바퀴 돌려 보자. 근거 재인용 루프다.

⚠️ 여기서 유혹을 하나 짚고 가자 루프를 넣다 보면 "검증기가 너무 빡빡해서 자꾸 막히네, 임계값을 0.8 에서 0.6 으로 낮추자"는 생각이 든다. 그 순간 루프는 정확도 장치가 아니라 통과율 장치가 된다.
검증기를 고칠 거면 루프와 따로 고치고, 골든셋으로 따로 측정해야 한다. 두 변경을 한 커밋에 넣으면 어느 쪽이 효과를 냈는지 영영 모른다.
질문 메모 그림 2의 루프 한 바퀴에서 헷갈리는 부분을 적어보세요.

4. 루프를 넣을 자리는 이미 정해져 있다

이게 이 저장소를 읽으며 가장 인상적이었던 부분이다. missing_trace.py 가 ⚪ 의 원인을 6갈래로 가르고, 각각 사람이 할 일이 다르다고 표로 적어 놨다. 그 표를 다시 읽으면 — 이건 루프 정책(policy)의 초안이다. 

원인                            사람이 할 일                    →  루프가 할 일
① recall 실패                   임계/후보수 조정 · 온톨로지 승격  →  쿼리를 바꿔 재검색
② LLM 미판정                    예산 증대 · 재실행               →  (예산 문제 — 루프 아님)
③ 근거 게이트 강등              인용 확인 후 승격                →  다시 인용시키기
④ F3 추출 누락                  배치 축소 · 추출 프롬프트 점검    →  미인용 블록만 재추출
⑤ 의도된 차단                   differs_by 재검토                →  (정상 — 건드리지 않음)
⑥ F5 LLM 판정                   판정 근거 확인                   →  (사람 검수 영역)

루프 후보는 ①③④ 셋뿐이다. ②는 설정 문제고, ⑤는 정상 동작이고, ⑥은 사람이 봐야 한다. 셋으로 좁혀지는 것 자체가 좋은 신호다 — 에이전트가 손댈 곳이 명확하다는 뜻이다.

💡 종료 조건이 이미 파일로 존재한다는 것의 의미 루프에서 가장 어려운 게 "언제 멈추나"인데, 이 셋은 전부 기존 산출물에 이미 답이 적혀 있다. 새로 지표를 발명할 필요가 없다. 이건 우연이 아니라, 이 프로젝트가 "오판을 추적할 수 있게 계측을 남긴다"는 원칙을 일관되게 지켜 온 결과다.

4.1 실측이 이미 F4b 의 대상을 특정해 놨다

docs/FACT_F3_5_LIVE_REPORT.md §7 에 "F4b (Repair Loop) — 관측된 실패 모드" 라는 절이 있다. 사변이 아니라 실제 실행에서 본 것들이다:

• 정성 문장에서 fact 미추출(w_b004) — 정량 값이 없는 문장을 LLM 이 건너뛴다.
• entity_name 을 슬라이드/문단 제목으로 대체하고 실제 항목을 attribute 로 흡수 (충전 규격 상세조건.공칭전압). repair 대상: entity 승격.
• JSON 준수도는 양호(parse_failures = 0) → JSON 교정형 repair 는 우선순위가 낮다.

마지막 줄이 특히 좋다. 보통 "LLM 이 JSON 을 잘 못 뱉으니 교정 루프를 만들자"에서 시작하는데, 측정해 보니 그건 문제가 아니었다는 것을 확인하고 우선순위를 내렸다. 이런 판단이 에이전트 개발에서 시간을 가장 많이 아낀다.

그리고 §9.1 의 남은 오답 2건 중 하나도 F4b 대상으로 지목돼 있다 — 최대충전전류 → match(정답 unknown). 프롬프트에 "값이 배수 관계라 단위에 따라 달라지면 unknown" 이라고 명시했는데 LLM 이 따르지 않았다.

⚠️ 그런데 이건 루프로 고칠 수 있는 종류인가? 솔직히 애매하다. "지시를 안 따랐다"를 재시도로 고치려면 같은 지시를 더 크게 말하는 것 외에 할 게 별로 없고, 그건 효과가 불확실하다. 오히려 코드가 사후에 잡는 편이 낫다 — _is_decimal_scaled() 로 십진 배수 관계를 이미 감지하고 있으니, LLM 이 그 상황에서 match 를 냈으면 코드가 unknown 으로 되돌리면 된다.

모든 문제가 루프의 문제는 아니다. 루프 전에 "이건 코드 규칙 하나로 끝나지 않나?"를 먼저 물어야 한다.
질문 메모 세 루프 후보 중 궁금한 것, 혹은 "이것도 루프로 되지 않나?" 하는 아이디어를 적어보세요.

5. "그래프 엔지니어링"의 두 가지 의미

이 말이 두 가지를 가리키는데, 혼동하면 대화가 산으로 간다.

(a) 데이터 그래프

노드 = 개념, 엣지 = fact 쌍의 관계. 이미 하고 있는 것이다. concept_graph.json 이 그거고, LangGraph 같은 프레임워크와는 아무 상관이 없다.

더 밀면 → 문서 3개 이상 통합 · 온톨로지 자동 성장 · 엔티티 단위 배치 판정(상위 설계 Phase 6).

(b) 제어 그래프

노드 = 실행 단계, 엣지 = 조건부 전이, 상태 = 반복 사이에 누적되는 것. "에이전트로 만든다"의 실체는 이쪽이다.

LangGraph · 자체 상태머신 · 그냥 while 루프 — 도구는 아무거나 되고, 중요한 건 전이 조건을 명시적으로 쓰는 것이다.

5.1 (b)로 옮기기에 지금 구조가 아주 유리하다

각 단계가 artifacts/<문서>/<단계>.json 에 상태를 남기고, <단계>.fingerprint 사이드카로 "입력이 같으면 재계산 안 함"을 판정한다: 

def cached_or_compute(self, stage, compute, *, fingerprint=None):
    if self.cache and self.exists(stage) and self._fingerprint_ok(stage, fingerprint):
        cached = self.load(stage)
        if cached is not None:
            return cached          # ← 재계산 없이 디스크 산출물을 그대로
    data = compute()
    if fingerprint is not None:
        self._write_fingerprint(stage, fingerprint)
    ...
✅ 이건 사실상 checkpointer 다 상태 그래프 프레임워크가 제공하는 "중단 지점부터 재개" 기능을, 이 저장소는 이미 자기 방식으로 구현해 뒀다. 제어 그래프로 옮길 때 노드 함수는 지금 함수를 거의 그대로 쓰고, state 는 RunSnapshot(fact/artifact_reader.py)이 된다.
질문 메모 데이터 그래프 / 제어 그래프 구분, 혹은 그림 3의 대응 관계에 대해 적어보세요.

6. 툴을 많이 쥐어주면 되나

아니다. 그리고 이건 취향 문제가 아니라 이 저장소의 코드가 이미 증명한 것이다.

6.1 행동 공간이 커지면 검증 부담은 제곱으로 는다

지금 LLM 이 할 수 있는 행동은 놀랄 만큼 좁다:

  • 개념 판정: same_as / differs_by / unknown 셋 중 하나 + 인용 두 개
  • 값 대조: findings[] 배열 + 종합 result 하나

좁기 때문에 코드가 전수 검증할 수 있다. 관계는 셋 중 하나인지 확인하고, 인용은 원문에 있는지 확인하고, fact_id 는 후보 안에 있는지 확인한다. 툴 10개를 쥐어주면 이 전수 검증이 불가능해진다 — "파일을 읽었다"의 결과가 옳은지 코드가 어떻게 알겠는가.

6.2 좋은 툴의 세 조건

  1. 되돌릴 수 있는가 — 읽기 전용이면 최고다
  2. 결과를 코드가 검증할 수 있는가 — 스키마·범위·실재 여부
  3. 실패가 관측되는가 — 조용히 실패하면 없는 것만 못하다

이 기준으로 보면 저장소에 이미 좋은 툴 후보가 있다. 전부 읽기 전용이고 LLM 비용이 0이다.

툴 후보돌려주는 것에이전트가 쓸 곳
scripts/why_missing.py⚪ 한 건의 원인 6분류 + 근거 포인터어느 루프로 갈지 결정
candidate_pairs.json 조회후보 랭킹 + 탈락 사유(min_score/top_k)recall 재질의가 의미 있는지 판단
facts_by_block.json 조회블록 → fact 매핑, cited 여부재추출할 블록 특정
concept_graph.json 조회엣지의 relation·rejected_by·인용재인용 대상 특정

6.3 절대 주면 안 되는 툴

🚨 knowledge/ontology.yaml 쓰기 사람이 온톨로지에 승격한 관계는 LLM 판정과 근거 검증을 전부 건너뛰고 영구 적용된다 (resolve_known() 이 최우선으로 읽는다). 에이전트에게 여기 쓰기 권한을 주면 게이트를 스스로 우회하는 길을 만드는 셈이다.

이건 가상의 걱정이 아니다. concept_assembler._demote() 의 주석이 정확히 이 시나리오를 경계하고 있다 — 거부된 엣지의 사유를 그대로 두면 사람이 그걸 믿고 승격해서 "게이트를 사람 손으로 우회"시킨다고. 에이전트는 그 사람보다 훨씬 빠르게, 훨씬 많이 그렇게 할 수 있다.

대안: 에이전트는 ontology_suggestions.jsonl 같은 제안 큐에만 쓰고, 사람이 검토해 승격한다. 제안에는 반드시 근거(양쪽 원문 인용)를 달게 한다.
질문 메모 툴 설계나 권한 경계(그림 5)에 대해 궁금한 점을 적어보세요.

7. 검증을 정의하면 되나

절반 맞다. 검증 정의는 필요조건이지만 충분하지 않다.

빠진 절반이 credit assignment — "검증이 실패했을 때 무엇을 바꿀 것인가"다. 이게 없으면 루프는 그냥 재시도가 되고, 재시도는 확신을 만들지 않는다. 표현만 바꾼다.

✅ 그런데 당신은 이걸 이미 갖고 있다 missing_trace 의 "원인 → 사람이 할 일" 표가 정확히 credit assignment 다. 지금은 그 조치를 사람이 하고, 에이전트는 그걸 자동화하는 것뿐이다.
대부분의 팀은 여기서 막힌다 — 검증은 만드는데 "그래서 뭘 고치지?"를 정의하지 못해 재시도 루프에 머문다.
질문 메모 재시도 vs 교정의 구분, credit assignment 에 대해 적어보세요.

8. 구현 로드맵 — 0·1·2·3 단계

기존 시스템을 크게 흔들지 않는 순서다.

0단계 — 리팩터링 없이 상태 그래프로 재기술

노드 = 기존 함수, 상태 = RunSnapshot. 코드는 그대로 두고 오케스트레이션만 갈아끼운다. 

graph = StateGraph(RunState)
graph.add_node("extract",  lambda s: run_f3(s))       # 기존 함수 그대로
graph.add_node("concept",  lambda s: run_f7(s))
graph.add_node("compare",  lambda s: run_f5(s))
graph.add_node("report",   lambda s: render(s))

graph.add_edge("extract", "concept")
graph.add_edge("concept", "compare")
graph.add_edge("compare", "report")
⚠️ 여기서 아무것도 좋아지지 않아야 정상이다 0단계의 목적은 동작이 동일함을 확인하는 것이다. 골든셋 정확도가 그대로여야 하고, run_stats.json 숫자가 그대로여야 한다. 달라졌다면 재기술 과정에서 뭔가를 흘린 것이다 — 루프를 넣기 전에 그것부터 찾아야 한다.

1단계 — 가장 작은 루프 하나: 근거 재인용 (F4b)

graph.add_node("repair_quote", repair_rejected_quotes)

def route_after_concept(state):
    rejected = [e for e in state.graph.edges if e.rejected_by == "evidence"]
    if rejected and state.repair_round < 1:      # ← 종료 조건: 1회
        return "repair_quote"
    return "compare"

graph.add_conditional_edges("concept", route_after_concept)
graph.add_edge("repair_quote", "concept")        # ← 되돌아가는 화살표

이걸 첫 타자로 고른 이유 네 가지:

조건충족 여부
입력이 명확한가✅ rejected_by == "evidence" 엣지. 실측 17건
종료 조건이 명확한가✅ 재시도 1회, 통과 or 그대로 강등
검증기가 이미 있는가✅ verify_evidence() — 새로 만들 것 없음
측정할 정답지가 있는가✅ spec_en_골든셋.jsonl 104건 (교차언어라 이 실패가 집중된다)

이 하나만으로 "루프가 실제로 이득인가"를 숫자로 답할 수 있다. 안 되면 여기서 멈추면 된다 — 그리고 그건 실패가 아니라 싸게 얻은 답이다.

2단계 — recall 재질의

missing_trace 가 ①로 분류한 것만 대상. 쿼리 변형 2~3개를 만들어 재검색한다. 1단계보다 어려운 이유는 "변형을 몇 개까지 시도할 것인가"가 열려 있기 때문이다 — 종료 조건을 설계로 정해야 한다.

3단계 — 전역 루프 (마지막에)

리포트 전체를 보고 자기 비평 → 재실행. 여기가 제일 위험하다: 비용이 문서 크기 × 반복 횟수로 곱해지고, 무엇이 좋아졌는지 귀속시키기가 가장 어렵다. 1·2단계에서 배운 것 없이 여기부터 시작하면 거의 확실히 실패한다.

질문 메모 로드맵 순서나 각 단계 구현에 대해 궁금한 점을 적어보세요.

9. 당신에게 중요한 역량

9.1 이미 갖고 있고, 이게 제일 희소하다

역량이 저장소의 증거
실패를 숫자로 바꾸는 습관 llm_budget_exceeded 를 llm_failures 와 갈라 센 판단 — "파급 범위가 다르니 한 숫자에 섞으면 왜 갑자기 전부 보류인가를 설명할 수 없다". 기존 키의 의미는 유지한 채 부분집합으로 추가한 것도 같은 감각이다.
자기 지표를 의심하는 능력 unsafe_match_rate 0.88 이 실제 순증가 10%(2건)를 3.5배 부풀렸다는 것을 발견하고 enforce_new_llm_count 를 새로 만든 일. 대부분은 자기가 만든 지표를 그대로 믿는다.
LLM 에게 무엇을 묻지 않을지 정하는 능력 F7/F5 분리. "값이 다른 것은 differs_by 의 근거가 아닙니다" 한 문장이 시스템 전체를 구한다. 에이전트 설계에서 가장 자주 실패하는 지점이 바로 "LLM 에게 너무 많은 것을 한꺼번에 묻는 것"이다.
평가 데이터를 직접 만드는 능력 골든셋 27건 + 104건. 특히 후자는 대상 문서와 정답을 한 테이블에서 생성해 드리프트를 구조적으로 막았다. 이게 없으면 에이전트 개발은 느낌으로 하는 일이 된다.
측정 결과에 따라 기능을 안 켜는 결단 Acceptance Gate enforce 를 켜지 않기로 한 결정. 순증가 2건을 열어 보니 둘 다 올바른 match 였고, 잡아낸 오판은 0건이었다. "만들었으니 켜자"를 이겨낸 판단이다.

9.2 앞으로 필요할 것

역량왜 지금은 부족할 수 있나어디서 연습하나
수렴 판단 지금 시스템엔 반복이 없어 "언제 멈추나"를 정할 일이 없었다. 단순 N회 반복은 꼬리를 놓치고, "새로운 게 없을 때까지"는 발산할 수 있다. 1단계에서 재시도 1회 고정으로 시작 — 그리고 "2회로 늘리면 뭐가 더 잡히나"를 숫자로 확인
루프 안에서의 비용 관측 지금도 개념 단계가 120쌍/6호출이다. 문서가 5배 커지고 루프가 2회 돌면 60배. 예산 고갈로 이미 한 번 데였으니 감은 있으실 것이다. 루프마다 별도 예산을 두고, 소진을 llm_budget_exceeded 처럼 따로 센다
반복 단위 실패 격리 문서 단위 격리는 이미 있다. 루프가 들어오면 "3회차에서 터졌을 때 1·2회차 결과를 살릴 것인가"라는 새 질문이 생긴다. 각 반복의 산출물을 <단계>.round-N.json 처럼 따로 남기기
한 줄로 줄이면 에이전트 개발에서 희소한 역량은 프롬프트 작성도 툴 제작도 아니다. ① 문제를 검증 가능한 단위로 쪼개는 것, ② 실패를 숫자로 바꾸는 것, ③ 인간과 기계의 권한 경계를 설계하는 것 — 이 셋이다. 그리고 이 저장소는 셋 다에 대해 이미 증거를 갖고 있다.
질문 메모 역량 진단에 동의하지 않는 부분이나, 더 알고 싶은 것을 적어보세요.

10. 가장 큰 위험 하나

지금 시스템의 미덕은 "확신 없으면 보류" 다. unknown 이 1급 상태이고, 예산이 끝나도 되돌아가지 않고 보류한다.

루프는 이것을 "확신할 때까지 재시도" 로 바꾸려는 압력이다. 그런데 앞에서 봤듯 재시도가 확신을 만드는 게 아니라 표현만 바꿀 때가 많다. 같은 LLM 이 같은 데이터를 보고 다르게 말한 것뿐인데, 두 번째 답이 첫 번째보다 옳다고 볼 근거는 없다.

🚨 루프마다 반드시 함께 세야 하는 두 숫자
  1. 재시도로 뒤집힌 건수 (result_changed 와 같은 패턴)
  2. 그중 정답지 기준 개선 / 악화 건수

이 둘이 갈라져 있지 않으면 루프는 오판을 지우는 게 아니라 오판을 그럴듯하게 만든다.

이건 새로운 교훈이 아니다. 이미 한 번 겪었다. Acceptance Gate enforce 를 검토했을 때, 지표(unsafe_match_rate 0.88)만 보면 켜야 할 것 같았지만 실제 순증가는 2건이었고, 그 2건을 열어 보니 둘 다 올바른 match 였다. 켰다면 정상 판정 2건을 LLM 에 보내 unknown 으로 뒤집을 위험만 만들었을 것이다.

💡 그때 배운 것을 루프에 그대로 적용하면 건수가 늘었다는 사실만으로 좋아졌다고 하지 않는다. 표본을 열어 본다. 루프를 켰을 때 ⚪ 가 76건에서 40건으로 줄었다면, 줄어든 36건 중 몇 건이 정말 맞는 연결이었는지 골든셋으로 확인해야 한다. 36건이 전부 오연결이었다면 루프는 상황을 악화시킨 것이다.
질문 메모 "루프가 오판을 그럴듯하게 만든다"에 대해 궁금하거나 반박하고 싶은 점을 적어보세요.

11. 이해도 점검 퀴즈

다섯 문제다. 답을 고르면 바로 채점되고 해설이 나온다.

Q1. 이 파이프라인을 에이전트로 만들 때 가장 먼저 해야 할 일은?
Q2. "재시도 루프"와 "교정 루프"를 가르는 결정적 차이는?
Q3. 에이전트에게 knowledge/ontology.yaml 쓰기 권한을 주면 안 되는 이유는?
Q4. 근거 재인용 루프(F4b)를 첫 타자로 고른 이유로 가장 약한 것은?
Q5. 루프를 켰더니 ⚪ 대상에 없음 이 76건 → 40건으로 줄었다. 무엇을 확인해야 하나?

12. 한 문단 요약

이 파이프라인은 에이전트로 만들 수 있다. 다만 그 작업의 본질은 툴을 쥐어주는 게 아니라, 이미 만들어 둔 계측을 종료 조건으로 승격시키는 일이다. missing_trace 의 원인 6분류는 그대로 루프 정책이 되고, artifacts/*.fingerprint 는 그대로 체크포인터가 되고, 골든셋 131건은 그대로 평가 하네스가 된다. 새로 만들어야 하는 것은 조건부 엣지 하나뿐이다. 그리고 그 과정에서 지켜야 할 선은 이미 이 저장소가 정해 놨다 — 제안은 LLM, 차단은 코드, 영구 확정은 사람. 루프는 이 비대칭을 푸는 장치가 아니라, 비대칭을 유지한 채 LLM 에게 제대로 답할 기회를 한 번 더 주는 장치여야 한다. 그 구분을 놓치는 순간 루프는 정확도가 아니라 통과율을 올리기 시작하고, 그때부터는 오판이 사라지는 게 아니라 그럴듯해진다.

질문 메모 전체를 읽고 남은 질문, 혹은 "이걸 실제로 시작하려면?" 같은 질문을 적어보세요.
