1. 배경 ①: 아주 기초 — 컴퓨터가 "같은 내용"을 찾기 어려운 이유

회사에는 같은 사실을 여러 문서에 나눠 적는 일이 흔하다. 예를 들어 이 저장소의 샘플 문서 세 개를 보자.

📊 기준.xlsx — 표(엑셀)
제품명 · 연도 · 매출액 · 직원수
A제품 · 2023 · 1,200억원 · 500명
B제품 · 2024 · 800억원 · 320명
C제품 · 2023 · 350억원 · 90명
📄 사업보고서.docx — 글(워드)
A제품의 2023년 매출액은 1,200억원이며, 해당 사업부의 직원수는 500명이다.
B제품은 2024년에 매출 950억원을 기록하였고, 직원은 320명 규모로 운영되었다.
📄 요약.docx — 영어 요약
Executive Summary
Product A employed about 500 people in 2023 and led the company's revenue.

사람은 이 셋을 보고 3초 만에 안다. "B제품 매출이 엑셀은 800억, 보고서는 950억이네. 하나는 틀렸다." 그런데 컴퓨터에게 이건 굉장히 어려운 일이다. 이유는 세 가지다.

  1. 글자가 다르다. 엑셀은 매출액=800억원 이라고 칸에 적혀 있고, 워드는 "매출 950억원을 기록하였고" 라는 문장이다. 글자를 그대로 비교하면 겹치는 게 거의 없다.
  2. 어디에 있는지 모른다. 워드 문서가 300쪽이면, 엑셀 한 줄에 해당하는 문장이 어느 쪽 몇 번째 문단인지 먼저 찾아야 한다.
  3. 말이 달라도 같은 뜻일 수 있다. "500명" 과 "about 500 people", "도씨" 와 "℃" 는 같은 뜻이다. 반대로 "800억" 과 "950억" 은 비슷하게 생겼지만 완전히 다른 사실이다.

세 가지 도구를 먼저 알아두자

이 프로젝트는 이 어려움을 세 가지 도구로 나눠서 푼다. 각각 잘하는 일이 다르다.

① 임베딩 — "뜻이 비슷한 정도"를 숫자로 재는 자

임베딩(embedding)은 문장을 숫자 목록으로 바꾸는 기술이다. 예를 들어 문장 하나가 [0.12, -0.03, 0.88, ...] 같은 1024개짜리 숫자가 된다. 이 숫자 목록을 공간 속의 화살표라고 생각하면, 뜻이 비슷한 문장일수록 화살표가 같은 방향을 가리킨다.

두 화살표가 얼마나 같은 방향인지는 코사인 유사도로 잰다. 완전히 같은 방향이면 1, 아무 상관 없으면 0에 가깝다. 코드에서는 화살표 길이를 1로 맞춰(정규화) 놓고 곱해서 더하기만 하면 된다 — 그게 _dot() 이다.

contentcompare/similarity/hybrid_index.py
def _normalize(vec: list[float]) -> list[float]:
    norm = math.sqrt(sum(v * v for v in vec))
    if norm == 0:
        return vec
    return [v / norm for v in vec]          # 길이를 1로 → 내적 = 코사인유사도

def _dot(a: list[float], b: list[float]) -> float:
    return sum(x * y for x, y in zip(a, b))

임베딩의 강점은 말이 달라도 뜻이 비슷하면 찾아낸다는 것이다. "500명" 과 "about 500 people" 도 같은 방향을 가리킬 수 있다. 약점은 정확한 이름·숫자·코드를 놓칠 때가 있다는 것. "B제품" 과 "D제품"은 뜻이 비슷해서 헷갈린다.

② BM25 — "같은 낱말이 몇 번 나오나"를 세는 검색

BM25 는 옛날부터 쓰이는 검색 방식이다. 원리는 단순하다. 드문 낱말이 겹칠수록 점수를 높게 준다. "제품"처럼 아무 문서에나 나오는 낱말은 점수가 낮고, "B제품", "950" 처럼 드문 낱말이 겹치면 점수가 확 높아진다. 이 프로젝트는 외부 라이브러리 없이 60줄짜리로 직접 구현했다.

contentcompare/similarity/bm25.py
# idf = 그 낱말이 얼마나 '드문가' — 드물수록 큰 값
self._idf = {
    term: math.log(1 + (n - df + 0.5) / (df + 0.5))
    for term, df in self._df.items()
}

BM25 의 강점은 정확한 낱말·숫자에 강하다는 것, 약점은 말이 다르면 아예 못 찾는다는 것이다. 한국어는 "영업이익은", "영업이익이" 처럼 조사가 붙어 낱말이 달라지므로, 이 프로젝트는 한글 3글자 이상을 두 글자씩 잘라 추가로 넣어 준다(bigram).

contentcompare/similarity/tokenize.py
for tok in _WORD_RE.findall(text.lower()):
    tokens.append(tok)
    # 한글 3글자 이상은 bigram 보강(예: "영업이익" → 영업/업이/이익).
    if len(tok) >= 3 and _HANGUL_RE.fullmatch(tok):
        tokens.extend(tok[i : i + 2] for i in range(len(tok) - 1))

2. 배경 ②: 이 프로젝트의 지도

ContentCompare 에는 비교 엔진이 두 개 들어 있다. 이게 이 저장소를 처음 볼 때 제일 헷갈리는 지점이라 먼저 정리한다.

① RAG 엔진 (현행 · 기본값 · 완성)

엑셀 한 줄을 검색어로 삼아, 대상 문서 조각 중 비슷한 걸 10개 찾고, 그 10개를 LLM 에게 보여 주고 판정을 받는다.

pipeline.py, readers/, similarity/, comparison/

실행: contentcompare --engine rag (기본)

② Fact 엔진 (신규 · 만드는 중)

모든 문서를 먼저 사실 카드(fact) 로 바꾼 뒤, 카드끼리 맞대어 본다.

raw/, fact/

실행: contentcompare --engine fact — 현재는 중간 산출물 저장까지만 동작

"RAG" 는 Retrieval-Augmented Generation 의 줄임말로, 먼저 검색(retrieval)해서 찾은 조각을 LLM 프롬프트에 넣어 주는 방식을 말한다. 요즘 챗봇이 사내 문서를 참고할 때 쓰는 그 방식이다.

코드를 읽을 때 이 네 개만 알면 절반은 읽은 것이다. 전부 contentcompare/models.py 에 있다.

핵심 개념: 행은 찾는 단위, 셀은 따지는 단위

엑셀 한 행(RecordItem)은 검색할 때 통째로 쓰인다. "B제품 2024 800억원 320명" 전체를 검색어로 써야 대상 문서에서 그 제품 이야기를 찾을 수 있기 때문이다.
하지만 판정은 셀 단위(FieldClaim)로 따진다. 연도는 맞고 매출액만 틀렸다는 걸 구분해야 하니까.
설정 이름은 excel.granularity: hybrid — 두 방식을 섞었다는 뜻이다.

그리고 ❓ 판단보류(unknown) 가 1급 상태로 있는 게 이 프로젝트의 성격을 보여 준다. LLM 에게 "확신이 안 서면 억지로 고르지 말고 unknown 을 고르고, 왜 어려운지 설명하라" 고 프롬프트에서 명시적으로 지시한다. 틀린 확신보다 정직한 모름이 낫다는 판단이다.

3. 직관: 항목 하나가 판정되기까지

이제 실제로 따라가 보자. 목표는 이 한 줄이다.

📊 기준.xlsx — [실적] 3행
제품명 = B제품
연도 = 2024
매출액 = 800억원
직원수 = 320명

이 한 줄이 사업보고서.docx 와 요약.docx 안에 제대로 반영돼 있는지 확인하고 싶다. 컴퓨터는 다섯 걸음을 밟는다.

1 · 코드 읽기 — 문서를 열어 조각으로 뜯는다.
엑셀은 행마다 RecordItem, 워드는 문단마다 DocItem. 이 예에서 대상 조각은 7개가 나왔다. pipeline._read() → readers/
▼
2 · 임베딩 인덱싱 — 대상 조각 7개를 전부 숫자 화살표로 바꿔 저장하고, 낱말도 세어 둔다(BM25 색인).
한 번 계산한 임베딩은 디스크에 캐시돼 다음 실행 때 재사용된다. chunk_items() → HybridIndex.add()
▼
3 · 코드 검색 — "제품명=B제품 | 연도=2024 | …" 을 검색어로 던져, 7개 중 관련 있어 보이는 순서로 줄 세운다. HybridIndex.search(recall_k=30, top_k=10)
▼
4 · LLM 판정 — 기준 행 + 셀 목록 + 후보 전부를 한 프롬프트에 담아 LLM 에게 주고, JSON 으로 답을 받는다. Comparator.compare_record()
▼
5 · 코드 리포트 — 판정·출처·근거·인용을 표로 렌더링해 report.md 로 저장. report.render_markdown()

3단계에서 실제로 나온 후보 목록

아래는 samples/report.md 에 실제로 기록된, B제품 행에 대한 검색 결과다. 왼쪽 숫자가 점수이고, 초록색 줄이 LLM 이 "이게 근거다" 라고 지목한 후보다.

0.033 B제품은 2024년에 매출 950억원을 기록하였고, 직원은 320명 규모로 운영되었다. 사업보고서.docx > 1페이지 > 3번째 단락 ⟵ 매칭

0.031 신규 라인 D제품은 2025년 출시 예정으로 현재 매출 실적은 집계되지 않았다. 요약.docx > 1페이지 > 3번째 단락
0.031 2024 사업보고서 사업보고서.docx > 1페이지 > 1번째 단락
0.016 Product A employed about 500 people in 2023 and led the company's revenue. 요약.docx > 1페이지 > 2번째 단락
여기서 꼭 짚고 갈 것 — 0.033 은 "3.3% 비슷함" 이 아니다

이 점수는 코사인 유사도가 아니라 RRF 융합 점수다. 계산식이 1/(60+순위) 를 더하는 형태라 값이 원래 작다.
0.033 ≈ 1/61 + 1/61 → 임베딩 순위 1등이자 BM25 순위 1등.
0.016 ≈ 1/64 → 한쪽 목록에서만 4등, 다른 목록엔 아예 없음.
즉 점수의 절대값이 아니라 두 검색기가 모두 위로 올렸는가를 보는 숫자다. 다음 장에서 계산을 직접 따라간다.

질문 메모 후보 점수나 5단계 흐름에서 걸리는 부분을 적어보세요.

4. 코드 워크스루 ①: 현행 RAG 엔진

contentcompare/pipeline.py — 파이프라인 전체 (핵심만 발췌)
def _run(self, reference_path, target_paths, *, progress=None):
    # 1) 문서 읽기
    reference_items = self._read(reference_path)              # 기준(엑셀) 행들
    target_items: list[DocItem] = []
    for path in target_paths:
        target_items.extend(self._read(path))                 # 대상 문서 조각 전부

    # 2) 하이브리드 인덱스 구축 (청킹 후, 임베딩 캐시 적용)
    sim = self.config.similarity
    chunks = chunk_items(target_items, sim.chunk_chars)
    embedder = CachedEmbedder(self.embedder, sim.cache_dir,
                              model_name=self.config.llm.embed_model)
    index = HybridIndex(embedder, fusion=sim.fusion, rrf_k=sim.rrf_k,
                        mmr_lambda=sim.mmr_lambda, per_doc_cap=sim.per_doc_cap,
                        min_score=sim.min_score)
    index.add(chunks)

    # 3~4) 기준 항목 순차 비교
    results = []
    for i, ref in enumerate(reference_items, start=1):
        if ref.is_empty():
            continue
        candidates = index.search(ref.text, recall_k=sim.recall_k, top_k=sim.top_k)
        if isinstance(ref, RecordItem) and ref.fields:
            result = self.comparator.compare_record(ref, candidates)   # 행 종합 판정
        else:
            result = self.comparator.compare(ref, candidates)          # 단순 항목
        results.append(result)
    return results

def add(self, items: list[DocItem], *, batch_size: int = 64) -> None:
    items = [it for it in items if not it.is_empty()]
    for start in range(0, len(items), batch_size):
        batch = items[start : start + batch_size]
        # 본문 청크 → passage 로 임베딩(e5 계열 접두어 분리).
        vectors = self.embedder.embed([it.text for it in batch], kind="passage")
        for it, vec in zip(batch, vectors):
            self._items.append(it)
            self._vectors.append(_normalize(list(vec)))
            self._tokens.append(tokenize(it.text))          # BM25 용 낱말

    fused = reciprocal_rank_fusion([emb_rank, bm_rank], k=self.rrf_k)

5. LLM 은 정확히 어디서 무엇을 하는가

"AI 가 문서를 비교한다" 는 말은 사실 너무 뭉뚱그린 표현이다. 이 프로젝트에서 LLM 이 호출되는 지점은 손에 꼽을 정도로 적고, 하는 일도 명확히 정해져 있다. 정리해 보자.

먼저: 서로 다른 두 종류의 모델이 쓰인다

임베딩 모델 (예: bge-m3, multilingual-e5-large)

문장 → 숫자 화살표. 말을 하지 않는다. 대상 조각마다 1회, 검색어마다 1회 호출. 결과는 .cache/embeddings 에 디스크 캐시되어 두 번째 실행부터는 거의 공짜.

채팅 LLM (예: qwen2.5:14b, gemma)

글을 읽고 JSON 으로 판단을 내놓는다. 비싸고 느린 쪽. 이 프로젝트가 호출 수를 아끼려고 애쓰는 대상.

두 모델의 백엔드는 따로 고를 수 있다(llm.backend / llm.embed_backend). 사내 chat 엔드포인트가 임베딩을 제공하지 않을 때 chat=internal + embed=fastembed 처럼 섞어 쓰기 위한 설계다.

LLM 이 하지 않는 일

  • 문서를 통째로 읽지 않는다. 파일을 LLM 에 던지지 않고, 코드가 뜯어낸 조각 중 관련 있는 10개만 보여 준다.
  • 어디를 볼지 스스로 정하지 않는다. 후보 선정은 임베딩+BM25+MMR 이라는 결정적(deterministic) 코드의 몫이다.
  • 출처 좌표를 만들지 않는다. "사업보고서 3번째 단락" 이라는 라벨은 리더가 붙인 것이고, LLM 은 주어진 id 중에서 고를 뿐이다.
  • 제어 흐름을 정하지 않는다. 다음에 무슨 단계를 할지는 100% 파이썬 코드가 정한다. 에이전트 프레임워크(LangGraph 등)를 쓰지 않기로 한 결정(FACT_PIPELINE_PLAN.md 결정 #7)이 이 원칙을 명문화하고 있다.
한 줄 요약

LLM 의 역할은 "이 후보들 중에 우리 항목과 같은 내용이 있나? 값이 맞나? 왜 그렇게 보나?" 에 JSON 으로 답하는 것, 그 하나다.

6. 현행 RAG 방식의 문제점

지금까지 본 RAG 방식은 잘 동작하고, 빠르고, 싸다. 그런데 이 프로젝트가 새 엔진을 처음부터 다시 설계하기로 한 이유가 있다. docs/FACT_PIPELINE_PLAN.md §1 에 정리된 문제들을, 코드의 어느 줄에서 비롯되는지와 함께 짚어 보자.

문제 1 — 비교하는 두 단위의 모양이 다르다

기준은 표의 한 행이고, 대상은 글의 한 덩어리다. 사과와 문단을 비교하는 셈이다. 한 행에 담긴 4개의 사실을, 자유롭게 쓰인 문장 안에서 LLM 이 매번 다시 찾아내야 한다.

문제 2 — 정보가 흩어져 있으면 조각 하나로는 부족하다

이 저장소의 실제 PPT 샘플을 보자. 한 슬라이드 안에서도 값이 본문과 스피커노트로 쪼개져 있다.

artifacts/발표_pptx/compact_raw.json (실제 파일)
{ "slide_no": 1,
  "shapes": [
    { "id": "p001_s001", "type": "text", "text": "충전환경온도" },
    { "id": "p001_s002", "type": "text", "text": "-5~55℃, 중심치 25℃" }
  ],
  "notes": "0.1C, 4.55V 조건 기준" }

"충전환경온도가 -5~55℃ 인데, 그건 0.1C·4.55V 조건에서다" 라는 하나의 사실이 도형 2개 + 노트 1개에 나뉘어 있다. RAG 엔진은 각각을 별개 조각으로 인덱싱하므로, top-k 후보에 셋이 다 들어오지 않으면 조건이 빠진 채로 판정될 수 있다.

문제 3 — 표현이 다르면 검색에서 아예 빠질 수 있다

앞의 RRF 계산표에서 봤듯, 영어 문장 "Product A employed about 500 people" 은 BM25 목록에 없다. 임베딩이 잡아 주면 다행이지만, 임베딩 순위마저 밀리면 후보 10개 안에 못 들고 조용히 사라진다. 그리고 검색되지 않은 내용은 리포트 어디에도 "놓쳤다" 고 표시되지 않는다 — 그냥 ⚪ 미발견 이 된다. 진짜 없는 것과 못 찾은 것이 구분되지 않는 것이다.

조용한 실패가 가장 위험하다

top_k=10, per_doc_cap=4, chunk_chars=800 은 모두 "여기서 자른다" 는 결정이다. 잘린 뒤에는 그 사실이 결과에 남지 않는다. 리포트를 보는 사람은 10개 후보만 보고 "충분히 찾아봤구나" 라고 믿게 된다.

문제 4 — 단위와 동의어를 처리할 코드가 없다

"도씨" 와 "℃", "1200" 과 "1.2천" 이 같다는 판단은 전부 LLM 의 머릿속과 사람이 knowledge/*.md 에 적어 둔 메모에 의존한다. 코드에는 단위 등가 변환기가 없다. 그래서 같은 문서를 두 번 돌리면 판정이 달라질 수도 있다.

문제 5 — 비교가 한쪽 방향뿐이다

엑셀은 질문하는 쪽, 나머지는 대답하는 쪽으로 고정돼 있다. 그래서 이런 건 절대 발견되지 않는다: "보고서에는 D제품 이야기가 있는데 엑셀에는 그 행이 없다." 실제로 샘플 리포트에도 "신규 라인 D제품…" 문단이 후보로는 계속 등장하지만, 그것이 기준에 없는 내용이라는 지적은 어디에도 없다.

문제 6 — 왜 그런 결과가 나왔는지 되짚기 어렵다

남는 것은 최종 리포트뿐이다. 중간에 무엇이 어떻게 계산됐는지는 로그 파일을 뒤져야 한다. 오판이 났을 때 "검색이 못 찾은 건가, LLM 이 잘못 읽은 건가, 리더가 셀을 잘못 뜯은 건가" 를 가리기가 힘들다.

문제 7 — LLM 산출물을 검증하는 장치가 사실상 없다

있는 것은 ① JSON 파싱 실패 시 1회 재시도, ② 후보 id 교집합 검증, ③ 누락 필드 표시 — 이 세 개뿐이다. 인용문(evidence)이 진짜 원문에 있는 문구인지 확인하는 코드는 없다. 지금은 사람이 리포트를 보며 눈으로 대조해야 한다.

질문 메모 일곱 문제 중 우리 업무에서 제일 아플 것 같은 건 무엇인가요? 왜 그런지도 적어보세요.

핵심 아이디어

7.1 사실 카드(fact) 는 이렇게 생겼다

세 문서가 같은 사실을 이렇게 다르게 적고 있다고 하자(설계 문서 §1.2 의 예시).

📊 Excel

📄 Word
충전환경온도는 -5℃에서 55℃ 범위로 관리하며 중심치는 25℃로 한다.
📽 PPT
충전환경온도: -5~55℃, 중심치 25℃
(스피커노트) 0.1C, 4.55V 조건 기준

세 개를 전부 아래 같은 모양으로 바꾼다.

{

  "fact_type": "quantitative_spec",
  "entity_name": "충전환경온도",
  "entity_path": ["기본사양", "충전환경온도"],
  "attributes": {

def _facts_from_records(records: RecordSet) -> FactSet:

    for rec in records.records:

LLM 이 준 값 중 무엇을 믿는가

믿는다: entity_name, attributes, evidence_text, fact_type — 의미 판단의 결과
안 믿는다: fact_id, source, search_text — 사실 좌표는 전부 코드가 다시 만든다. 근거 id 가 하나도 유효하지 않으면 그 카드는 통째로 버려진다.

7.4 비용을 통제하는 두 장치

단계가 늘면 LLM 호출이 폭증한다. 그래서 두 개의 브레이크가 있다.

① 호출 예산

if self.calls >= self.max_calls:
    raise LlmBudgetExceeded(
        f"LLM 호출 예산 초과(max_calls={self.max_calls})")
self.calls += 1

문서당 기본 50회. 넘으면 예외를 던져 멈춘다. fact/llm_stage.py

② 지문 기반 캐싱

if self.cache and self.exists(stage) \
       and self._fingerprint_ok(stage, fingerprint):
    cached = self.load(stage)
    if cached is not None:
        return cached          # 재계산·재호출 0

입력의 sha1 지문이 그대로면 디스크 산출물을 재사용. fact/artifacts.py

지문은 산출물 JSON 을 더럽히지 않도록 <stage>.fingerprint 라는 별도 파일에 둔다. 실제로 artifacts/기준_xlsx/ 에 document_profile.json 과 document_profile.fingerprint 가 나란히 있다. 덕분에 같은 문서를 다시 돌리면 LLM 호출이 0회가 되고, 산출물 JSON 은 사람이 그대로 읽을 수 있는 깨끗한 데이터로 남는다.

질문 메모 9단계 중 특정 단계가 왜 필요한지, 또는 캐싱·예산 장치에 대해 궁금한 점을 적어보세요.

8. 왜 새 방식이 더 나은가 — 그리고 아직 아닌 부분

앞 장의 문제 7개에 새 방식이 어떻게 답하는지 나란히 놓아 보자.

문제현행 RAG신규 Fact
1. 비교 단위엑셀 행 ↔ 글 조각(모양이 다름)fact ↔ fact (모양이 같음)
2. 흩어진 정보조각 하나로 부족하면 그대로 누락슬라이드 단위로 묶어 하나의 fact 로 병합
3. 표현 차이임베딩이 놓치면 조용히 사라짐entity_name + search_text 로 다중 검색 (F5 예정)
4. 단위·동의어LLM + 사람이 쓴 knowledge/*.md 에 의존{value, unit} 구조 + semantic_role 사전 + 코드 검증
5. 비교 방향엑셀→나머지 한 방향모든 문서가 fact 가 되므로 양방향 가능
6. 추적성출처 라벨 + 로그9종 중간 JSON 전부 디스크 보존
7. 검증JSON 재시도 1회 + id 교집합Rule Validator + Repair Loop (F4 예정)

공짜는 아니다 — 치르는 대가

  • LLM 호출이 크게 늘어난다. RAG 는 "기준 행 수 × 1회" 로 끝나지만, Fact 는 문서마다 profiler → schema → records(배치) → facts(배치) 를 거친다. 그래서 예산·캐싱 장치가 필수다.
  • 느리고 비싸다. 빠른 존재 확인이 목적이라면 RAG 가 여전히 합리적이다.
  • 단계가 많아 실패 지점도 많다. 앞 단계가 틀리면 뒤가 전부 틀어진다(예: 머리글을 잘못 잡으면 전 행의 속성이 어긋난다).
  • 새로운 조용한 실패가 생긴다. 근거 id 없는 fact 를 버리는 안전장치는, 뒤집어 보면 대상 문서의 사실이 통째로 사라지는 통로이기도 하다. 그러면 F5 비교에서 "없다(missing)" 로 오판된다. 설계 문서가 이것을 "침묵하는 recall 손실" 이라 부르며 계측 대상으로 못 박아 둔 이유다.
지금 상태를 정직하게

Fact 엔진은 F0~F3 까지 구현돼 있고, F3.5 이후(라이브 검증·Validator·Repair·Comparator·리포트)는 아직 없다. contentcompare --engine fact 를 실행하면 raw/compact/profile/schema/records/facts 를 artifacts/ 에 저장한 뒤 이렇게 알려 주고 끝난다:

raise NotImplementedError(
    "FactPipeline: Validator~Comparator 는 Phase F4~F6 에서 구현됩니다. "
    "현재(F0~F3)는 raw/compact/profile/schema/records/facts artifacts 저장까지 동작합니다.")

즉 오늘 실제로 문서를 비교해 리포트를 만드는 것은 RAG 엔진뿐이다. "새 방식이 더 낫다" 는 것은 현재로선 설계상의 기대이며, 두 엔진을 같은 입력으로 돌려 실측하는 벤치마크(scripts/compare_engines.py, Phase F6)는 아직 만들어지지 않았다.

그래서 계획 문서는 두 엔진을 공존시키기로 못 박았다. 현행 코드는 한 줄도 바꾸지 않고(🔒), 새 엔진은 별도 패키지(fact/)로 짓고, 사용자가 --engine 으로 고른다. 새 방식이 실제로 더 낫다는 증거가 나온 뒤에 기본값을 바꾸겠다는 순서다.

질문 메모 비용·정확도 트레이드오프나 "언제 어느 엔진을 써야 하나"에 대한 질문을 적어보세요.

9. 전체 프로세스 총정리

마지막으로, 항목 하나가 처음부터 끝까지 어떻게 흐르는지 두 엔진을 나란히 놓고 본다. 같은 입력(기준.xlsx 3행 = B제품)을 준다고 하자.

RAG 엔진 (오늘 동작하는 길)

  1. ExcelReader.read() → 3행이 RecordItem 하나 + FieldClaim 3개
  2. 대상 문서들 → DocItem 7개
  3. chunk_items(800) → 길면 자름
  4. HybridIndex.add() → 7개 임베딩(캐시) + BM25 색인
  5. search(): 임베딩 순위 + BM25 순위 → RRF → MMR(λ=0.5, 문서당 최대 4) → 후보 10개
  6. build_record_prompt() → 기준행 + 필드3 + 후보10 을 한 프롬프트로
  7. LLM 1회 호출 → JSON
  8. 코드 검증: 후보 id 교집합, 누락 필드 채움, 파싱 실패 시 1회 재시도
  9. RecordResult → render_markdown() → report.md

결과: ❌ 다름 + 출처(사업보고서 3번째 단락) + 사유(800 vs 950) + 인용문

Fact 엔진 (설계된 길, F4~ 미구현)

  1. extract_raw() → physical_raw.json (셀 주소·병합·서식)
  2. compact_raw() → compact_raw.json
  3. LLM profile_document() → 문서 목적·구조
  4. LLM induce_schema() → 머리글 위치, row_grain, 열별 semantic_role
  5. LLM normalize_records() → 3행이 Record(entity=B제품, attributes={매출액…})
  6. extract_facts() → Excel 은 코드로 fact 변환(LLM 0회)
  7. 대상 문서도 같은 과정 → 각자 facts.json
  8. (F4a) Validator: 값·단위·인용문 실재 검사 → (F4b) 실패분만 LLM 이 교정
  9. (F5) entity 로 카드를 짝지어 attributes 키별 대조 → match / mismatch(매출액) / missing / unknown
  10. (F6) 양쪽 evidence_text + source 를 나란히 실은 리포트

기대 결과: mismatch_type: "매출액", excel 800억원 / word 950억원, 양쪽 원문·좌표 동시 제시

둘의 차이를 한 문장으로

RAG 는 "비슷해 보이는 글을 찾아서 LLM 에게 읽혀 본다".
Fact 는 "모든 문서를 사실 카드로 바꾼 다음, 카드끼리 맞춰 본다".
앞의 것은 값싸고 빠르지만 글의 모양에 흔들리고, 뒤의 것은 비싸고 느리지만 사실의 구조를 붙잡는다.

질문 메모 전체 흐름 중 아직 흐릿한 단계가 있다면 여기에 적어보세요.
