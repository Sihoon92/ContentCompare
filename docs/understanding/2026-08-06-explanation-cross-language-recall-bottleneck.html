언어가 다르면 왜 비교가 무너지는가

개념 그래프의 recall 경로를 처음부터 끝까지 따라가며, "임베딩이 못 찾는 것"과 "찾았는데 뒤에서 버려지는 것"을 구분한다.

2026-08-06 · 대상 코드: contentcompare/fact/ (F7 개념 그래프 · F5 값 대조)

이 글은 하나의 아주 자연스러운 직관에서 출발한다. "한국어 문서와 영어 문서를 비교하는데 잘 안 된다면, 애초에 임베딩이 짝을 못 찾는 것 아닐까? 그럼 더 좋은 다국어 모델을 써야 하는 것 아닐까?"

합리적인 추측이다. 그리고 틀렸다. 이 프로젝트는 이미 그 가설을 실험했고, 임베딩은 멀쩡했다. 무너진 것은 그 다음 단계였다. 이 글은 그 "다음 단계"가 정확히 어디인지, 왜 그런 일이 벌어지는지, 그리고 진짜 고쳐야 할 곳은 어디인지를 데이터 흐름을 따라가며 짚는다.

덤으로, 그 과정에서 더 근본적인 질문에도 답한다. 지금 쓰고 있는 "개념 그래프"는 온톨로지인가? Graph RAG와는 무엇이 다른가?

1깊은 배경 — 문서를 기계가 비교한다는 것

이 절은 완전 초심자를 위한 것이다. 임베딩·RAG·fact 파이프라인을 이미 안다면 2절로 건너뛰어도 좋다.

사람이 하던 일

엑셀 기준 문서에 "공칭전압 3.85 V" 라는 줄이 있다. 이게 Word 규격서에도, PPT 발표자료에도 똑같이 적혀 있는지 확인해야 한다. 항목이 200개고 대상 문서가 5개면 1000번을 눈으로 대조해야 한다. 지치고, 놓친다.

기계에게 시키려면 두 가지를 풀어야 한다.

  1. 찾기 — 기준의 "공칭전압"에 해당하는 줄이 Word 문서 어디에 있는가?
  2. 판정 — 찾은 줄의 값이 기준과 같은가, 다른가?

찾기: 임베딩이라는 도구

정의 · 임베딩(embedding)

문장을 숫자 벡터(예: 1024개의 실수)로 바꾸는 것. 의미가 비슷한 문장일수록 벡터가 비슷한 방향을 가리키도록 학습되어 있다. 두 벡터의 코사인 유사도(–1 ~ 1)가 클수록 의미가 가깝다고 본다.

핵심은 글자가 달라도 의미가 같으면 가까워진다는 것이다. 그래서 표준환경온도 와 Standard ambient temperature 처럼 공유하는 글자가 하나도 없는 두 문자열도 이어질 수 있다.

비교 대상이 되는 다른 도구가 BM25다. 이건 훨씬 오래된 방식으로, 같은 단어가 몇 번 나오는지를 센다. 단어가 겹쳐야 점수가 나온다. 그래서 한국어 문장과 영어 문장 사이에서는 원리적으로 점수가 0에 가깝다 — 이 사실이 뒤에서 중요해진다.

이 프로젝트의 구조: fact 엔진

ContentCompare 에는 엔진이 둘 있는데, 이 글이 다루는 것은 --engine fact 쪽이다. 문서를 통째로 LLM 에 던지지 않고, 먼저 fact 라는 작은 단위로 잘게 쪼갠 다음 fact 끼리 비교한다.

정의 · fact

문서에서 뽑아낸 주장 하나. 대략 이런 모양이다.

{
  "fact_id": "fact-r003",
  "entity_name": "공칭전압",
  "entity_path": ["기본사양", "전기적특성", "공칭전압"],
  "attributes": { "값": { "value": 3.85, "unit": "V" } },
  "evidence_text": "3.85",
  "search_text": "공칭전압 기본사양 전기적특성 3.85 V"
}

entity_name 은 항목 이름, entity_path 는 문서 안에서의 위치(섹션 계층), search_text 는 검색에 쓰라고 이 모두를 이어붙인 문자열이다. 이 세 개가 이 글 내내 반복해서 등장한다.

2좁은 배경 — F7 개념 그래프의 규칙 하나

fact 를 다 뽑았다고 하자. 이제 기준 문서의 fact 200개와 대상 문서의 fact 180개를 어떻게 짝지을 것인가?

가장 단순한 답은 "유사도가 높은 것끼리 묶는다"이다. 이 프로젝트도 처음엔 그렇게 했다. 그런데 실측에서 이런 표가 나왔다.

기준 항목대상 항목유사도진실
평가환경온도표준환경온도0.6944다른 개념
충전환경온도정격충전전압0.6084다른 개념
공칭용량공칭 용량0.7656같은 개념

여기까지는 임계값 0.7 정도로 가를 수 있을 것 같다. 그런데 더 넓게 재 보니 정답 최저 0.697, 오매칭 최고 0.700 이었다. 두 분포가 완전히 겹친다. 같은 대상 fact 에 대한 두 개의 질의라 원리적으로 점수만으로는 가를 수 없다.

그래서 설계가 뒤집혔다. 점수를 판정에서 완전히 빼 버린 것이다.

F7 의 단 하나의 판정 규칙

두 fact 는 개념이 same_as 로 이어져 있을 때만 비교된다. 이어져 있지 않으면 값이 아무리 비슷해도 비교하지 않는다.

유사도는 판정에서 빠지고 "LLM 에게 검토시킬 후보 쌍을 좁히는 recall 용도" 로만 남았다. 그래서 컷을 0.3 처럼 헐렁하게 잡아도 안전하다 — 틀려도 손해가 작기 때문이다.

그래프의 모양

이 그래프에는 두 종류의 요소가 있다.

권한 비대칭

이 설계에서 가장 영리한 부분이자, 뒤에서 문제의 원인이 되기도 하는 규칙이 하나 더 있다.

권한 비대칭

잇는 것(same_as)은 LLM 이 제안만 할 수 있고, 코드의 근거 검증을 통과해야 성립한다.
막는 것(differs_by)은 코드가 단독으로 집행한다. 검증도 필요 없다.

이유는 단순하다. 잘못 이으면 엉뚱한 걸 비교해서 오답을 낸다. 잘못 막으면 "검토 필요"로 사람에게 간다. 두 실패의 무게가 다르므로 권한도 달라야 한다.

"근거 검증"이란 이것이다. LLM 이 "이 둘은 같은 개념이다"라고 주장할 때, 양쪽 원문을 그대로 인용하게 시킨다. 그리고 코드가 그 인용문이 실제 fact 원문에 존재하는지 대조한다. 없으면 주장을 unknown 으로 강등한다. LLM 이 지어낸 근거로 두 항목을 잇는 것을 막는 장치다.

3직관 — 이건 온톨로지인가, Graph RAG인가

"그래프"라는 말이 나오면 요즘은 자연스럽게 Graph RAG 를 떠올린다. 둘 다 노드와 엣지가 있고 LLM 이 붙어 있으니 비슷해 보인다. 그런데 그래프가 파이프라인에서 하는 일이 정반대다.

세 가지 결정적 차이

Graph RAGF7 개념 그래프
유사도의 지위진입점이자 랭킹 근거. 임계값이 곧 품질후보를 좁히는 recall 전용. recall_score 는 "진단용으로만" 저장
엣지의 레이어인스턴스 사실 (A는 B를 인수했다)메타 수준 동일성 (문서A의 X와 문서B의 Y는 같은 것)
검증보통 검증 없이 색인에 들어감LLM 이 만든 same_as 는 원문 인용 대조 통과 필수
한 줄 요약

Graph RAG는 그래프로 답을 만들고, F7은 그래프로 비교를 허가한다.

그럼 이건 온톨로지인가?

엄밀하게는 아니다. 온톨로지가 갖춰야 할 것들과 대조해 보자.

온톨로지 요건현재 상태
클래스 계층 (is_a)없음 노드는 동치류일 뿐, 상하위 개념이 없다
관계 타입의 형식적 정의없음 same_as / differs_by / unknown 3종 하드코딩
부분 관계 (part_of)없음 entity_path 에 계층이 있는데도 그래프가 안 쓴다
공리와 추론부분 전이적 병합(union-find), "차단이 연결을 이긴다" 정도
통제 어휘없음 axis 가 LLM 자유 문자열
영속·재사용있음 knowledge/ontology.yaml

표준 어휘로 옮기면 지금 있는 것은 대략 SKOS 수준이다. aliases ≈ skos:altLabel, same_as ≈ skos:exactMatch. 포함 관계(broader/narrower)도, 속성 제약도 없다.

그래서 정직한 이름은 "동일성 그래프 + 사람이 관리하는 경량 어휘집" 이다. 다만 이게 결함이라는 뜻은 아니다 — 판정 규칙이 하나뿐이라 오판 추적이 쉽고, axis 를 코드가 해석하지 않으므로 도메인이 바뀌어도 코드가 그대로다. 표현력을 일부러 낮게 유지한 설계다.

질문 메모 Graph RAG 와의 대비, 또는 "온톨로지가 아니다"라는 판단에 대해 궁금한 점

4문제 ①: 엣지는 사실상 1비트다

여기서 자연스러운 관찰이 나온다. "엣지에 '관계가 있다'는 것만 있고 어떤 설명도 없으면, 그건 온톨로지가 아니지 않나?"

절반은 맞다. 데이터 구조를 보면 정보가 꽤 실려 있다.

# contentcompare/fact/concept_models.py:106-127
@dataclass
class ConceptEdge:
    relation: str        # same_as | differs_by | unknown
    left: FactRef
    right: FactRef
    axis: str = ""       # differs_by 일 때 "무엇이" 다른지 (예: "측정조건")
    left_text: str = ""  # 근거 인용 (원문 그대로)
    right_text: str = ""
    reason: str = ""     # 자연어 사유
    decided_by: str = BY_LLM   # code | ontology | llm
    rejected_by: str = ""      # 강등 사유

그런데 조립 모듈의 첫 줄이 스스로 이렇게 못 박는다.

# contentcompare/fact/concept_assembler.py:3-5
**코드가 위상만 보고 집행한다.** ``axis`` 문자열("측정조건"/"산정방식"/…)은 LLM 이 문서
도메인에 맞게 짓는 이름이며 여기서 해석하지 않는다.

실제로 axis 가 런타임에 읽히는 곳은 딱 한 군데다. 리포트 문장을 조립할 때뿐이다.

# contentcompare/fact/fact_matcher.py:221-223 — explain_missing()
axis = f"{edge.axis} 이(가) 다름" if edge.axis else "다른 개념"
detail = f" — {edge.reason}" if edge.reason else ""
blocked.append(f"'{self._label(other)}'({axis}){detail}")

그래서 나온 개선안 두 가지

개선안 A — axis 를 통제 어휘로. 지금은 LLM 이 축 이름을 자유롭게 짓는다(prompts.py:367 이 실제로 "축 이름을 직접 지어"라고 지시한다). 그래서 측정조건 / 측정 조건 / 조건 이 전부 다른 값이 된다. ontology.yaml 에 권장 축 목록을 두고 프롬프트에 제시하면 차단 사유가 집계 가능한 데이터가 된다.

개선안 B — entity_path 를 part_of 엣지로. fact 에는 이미 ["기본사양","충전","충전환경온도"] 같은 계층이 있는데, 그래프가 이걸 전혀 안 쓴다. 구조로 승격하면 두 가지가 가능해진다.

B가 막는 것 — 가장 위험한 무검증 자동 연결

현재 resolve_known() 은 정규화 이름이 같으면 코드가 즉시 same_as 로 확정하고, 조립 단계는 BY_CODE 연결의 근거 검증을 면제한다.

기준 문서: 기본사양 > 충전 > 온도    (entity_name = "온도")
대상 문서: 기본사양 > 방전 > 온도    (entity_name = "온도")
        → BY_CODE 로 same_as 확정, 검증 없음, 로그는 "이름 동일"뿐

충전 온도와 방전 온도가 한 개념으로 병합된다. 게다가 사람이 손으로 막을 수도 없다 — ontology.py:128 의 if a == b: return 때문에 이름이 같은 쌍은 온톨로지에 등록조차 안 된다.

질문 메모 개선안 A/B 의 취지가 잘 와닿지 않는 부분이 있으면 적어보세요.

5문제 ②: 그 개선안은 교차언어를 못 푼다

여기서 이 글의 진짜 주제가 시작된다. A/B 는 그럴듯하다. 그런데 한국어 기준 문서와 영어 대상 문서를 비교하는 상황에서는 어떨까?

먼저 B. entity_path 는 언어 종속 문자열이다.

다행히 실질 피해는 없다. 언어가 다르면 norm_name 완전일치가 애초에 0건이라 BY_CODE 경로 자체를 타지 않기 때문이다. 하지만 B의 이득은 동일언어 문서에서만 나온다는 사실은 분명히 해 둘 필요가 있다.

A 는 어떤가? 축 이름이 언어별로 갈리는 것(측정조건 vs measurement condition)을 막아 주니 약간 도움이 된다. 하지만 그건 차단 사유의 집계 품질이지, 후보를 못 찾는 문제와는 무관하다.

핵심

A 도 B 도 후보 쌍이 이미 만들어진 다음 단계에서 작동한다. candidate_pairs() 가 빈 리스트를 주면 둘 다 실행조차 되지 않는다.

질문 메모 "개선안이 이 상황엔 안 듣는다"는 논리에 대해 궁금한 점

6반전 — 임베딩은 범인이 아니다

여기서 "그럼 임베딩부터 문제인 것 아닌가? 더 좋은 다국어 모델이 필요한 것 아닌가?"라는 결론으로 뛰기 쉽다. 하지만 이 프로젝트는 정확히 그 실험을 이미 했다.

실험 설계

한국어 규격서 samples/자표준_규격서.docx 의 영어판을 만들었다. 중요한 것은 수치와 구조를 원본과 1:1 로 맞추고 언어·표기 관습만 바꿨다는 점이다(°C, 33 to 53 %RH). 즉 정답이 알려진 상태의 통제 실험이다.

그런데 원인은 임베딩이 아니었다

실측 리포트의 진단 (FACT_F3_5_LIVE_REPORT.md §11.2)

"임베딩도 LLM 판단도 멀쩡했다. bge-m3 는 표준환경온도 ↔ Standard ambient temperature 를 0.7492 로 찾았고, LLM 은 12쌍을 정확히 same_as 로 판정했다. 무너진 것은 그 다음이다."

무너진 지점은 근거 검증 게이트였다. 연쇄를 그림으로 보자.

후보 생성 컷은 concept_recall_min: 0.3 이다. 정답 쌍의 유사도가 0.7492 였다. 0.7492 ≫ 0.3 — recall 단계에서 잘릴 이유가 없다.

설계 문서도 같은 말을 한다. "판정에서 빠지므로 임계값을 느슨하게(기본 0.3) 잡아도 안전하다 — 틀려도 손해가 작다."

즉 "더 좋은 다국어 모델"은 측정된 적 없는 문제를 푸는 일이다. spike 실측에서도 임베딩 recall@1 은 100% 였다.

임베딩이 범인이 아니라면 무엇인가? 후보 생성 경로를 코드로 한 줄씩 따라가 보자.

7.0 전체 데이터 흐름

질문 메모 이 4단계 흐름도에서 이해가 안 되는 단계가 있으면 적어보세요.

7.1 구멍 ① — BM25 폴백은 교차언어에서 원리적으로 0인데, 조용히 실패한다

FactMatcher.search() 의 분기를 보자.

# contentcompare/fact/fact_matcher.py:106-130
def search(self, ref: Fact) -> list[MatchCandidate]:
    if not self.targets:
        return []

    key = norm_name(ref.entity_name)
    if key and key in self._by_name:
        return [MatchCandidate(self.targets[self._by_name[key]], 1.0, EXACT)]   # ← 조기 종료

    if self._vectors is not None:                       # 임베더가 있으면
        ranked = self._embed_rank(ref)
        method, cutoff = EMBED, self.min_score
    else:                                               # 없으면 BM25 로 폴백
        ranked = _rank(self._bm25.scores(tokenize(fact_text(ref))), self.top_k)
        method, cutoff = BM25_METHOD, self.bm25_min_score

임베더가 없으면 BM25 로 폴백한다. 그런데 토크나이저를 보자.

# contentcompare/similarity/tokenize.py:12
_WORD_RE = re.compile(r"[0-9]+(?:[.,][0-9]+)*|[a-z]+|[가-힣]+")

한글 덩어리와 영문 덩어리를 각각 뽑는다. 그러니 한국어 fact 와 영어 fact 가 공유하는 토큰은 숫자와 단위밖에 없다.

조용한 실패

fastembed 미설치, 사내 임베딩 엔드포인트 장애, 오프라인 환경 — 어떤 이유로든 임베더가 빠지면 교차언어 비교는 전 항목 ⚪ 대상에 없음 으로 조용히 귀결된다. 경고도, 계측도 없다.

이 프로젝트는 같은 유형의 문제를 이미 한 번 해결한 적이 있다. LLM 호출 예산이 소진되면 역시 전 항목이 missing 이 되는데, 그걸 budget_exhausted_pairs 라는 별도 카운터로 드러냈다. 여기엔 그 장치가 없다.

7.2 구멍 ② — 온톨로지 보강이 교차언어에서 사람 손에 의존한다

recall 이 놓친 쌍을 메우는 유일한 장치가 이것이다.

# contentcompare/fact/concept_builder.py:111-128
def _augment_with_ontology(store, ontology, add) -> int:
    """온톨로지가 아는 (기준 × 대상) 쌍 중 recall 이 빠뜨린 것을 무조건 추가한다."""
    for target in store.targets:
        for ref_fact in ref_doc.facts.facts:
            for tgt_fact in target.facts.facts:
                if ontology.relation_for(ref_fact.entity_name, tgt_fact.entity_name) is None:
                    continue
                if add(target.doc_name, ref_fact, tgt_fact, 0.0, False):
                    added += 1

그런데 relation_for() 의 키는 정규화된 이름이다.

# contentcompare/fact/ontology.py:48-52
def relation_for(self, name_a: str, name_b: str):
    a, b = norm_name(name_a), norm_name(name_b)
    if not a or not b or a == b:
        return None
    return self.pairs.get(frozenset((a, b)))

영어 문서에서는 relation_for('충전환경온도', 'Rated charging voltage') 가 None 이다. 실측 §11.2 의 표현대로 "온톨로지가 통째로 무력화" 된다.

해법으로 aliases 가 도입됐다. 같은 개념의 번역어를 묶으면 관계가 그룹 전체로 확장된다.

# knowledge/ontology.yaml
aliases:
  - ["표준환경온도", "Standard ambient temperature"]
  - ["평가환경습도", "Evaluation ambient humidity"]
  - ["정격충전전압", "Rated charging voltage"]

이 3줄이 pairs_from_ontology 를 0 → 6 으로 만들었다. 효과는 확실하다. 문제는 확장성이다 — 새 문서마다, 새 항목마다 사람이 번역어를 찾아 등록해야 한다.

7.3 구멍 ③ — 값이 유사도를 지배한다 (누락이 아니라 오매칭)

임베딩에 넣는 문자열이 어떻게 만들어지는지 보자.

# contentcompare/fact/fact_extractor.py:130-137
def _build_search_text(entity_name: str, entity_path, attributes: dict) -> str:
    """entity + path + 속성 값/단위를 공백 결합(중복 제거). F5 후보 검색용."""
    tokens = [entity_name, *entity_path]
    for a in attributes.values():
        if a.value is not None:
            tokens.append(str(a.value))
        if a.unit:
            tokens.append(a.unit)

이름·경로·값·단위가 전부 한 문자열에 들어간다. 동일언어에서는 값이 보조 신호로 작동해 도움이 된다. 그런데 교차언어에서는 이름 부분이 임베딩 공간의 먼 자리로 흩어지므로, 상대적으로 숫자와 단위가 유사도를 지배하게 된다.

그래서 구멍 셋의 성격
  • ① 임베더 부재 시 조용한 전면 실패 — 관측 부재의 문제
  • ② 온톨로지 키가 언어 종속 — 사람 노동이 병목
  • ③ search_text 조성이 값에 치우침 — 모델 교체로 안 풀림

셋 중 무엇도 "임베딩 모델의 성능"이 아니다.

질문 메모 구멍 ①②③ 중 더 파고들고 싶은 것을 적어보세요.

8솔루션 — 원리와 예상 효과

(가) 먼저 측정한다 — 이게 선결 조건

지금 missing 하나를 보고 원인 넷 중 무엇인지 구분할 수 없다.

원리: golden/ 에 한↔영 정답 쌍을 두고, candidate_pairs() 결과에 그 쌍이 포함됐는지를 세면 된다. 임베딩을 다시 돌릴 필요도 없다 — 이미 만들어진 후보 목록을 정답과 대조만 하면 된다.

예상 효과: 이 숫자가 100% 에 가깝게 나오면 모델 교체 논의는 그 자리에서 끝난다. 낮게 나오면 그때 비로소 모델을 바꿀 근거가 생긴다. 어느 쪽이든 추측을 사실로 바꾸는 것이 이 작업의 값어치다. 비용은 가장 낮고 정보 이득은 가장 크다.

(나) BM25 폴백의 무력화를 드러낸다

원리: 임베더가 None 이고 기준·대상 문서의 문자 체계가 다르면(한글 vs 라틴), BM25 로는 이름 매칭이 불가능하다는 것을 코드가 미리 안다. 그러니 경고를 띄우고 run_stats.json 에 남기면 된다.

# 개념 스케치 — fact_matcher.py / concept_builder.py 진입부
if embedder is None and _script_of(ref_facts) != _script_of(target_facts):
    logger.warning("[Concept] 임베더 없이 문자 체계가 다른 문서를 비교합니다 "
                   "— BM25 는 교차언어 이름 매칭이 원리적으로 불가능합니다")
    stats["crosslang_without_embedder"] = True

예상 효과: 최악의 실패 모드(전 항목이 이유 없이 ⚪ 대상에 없음)가 진단 가능한 실패로 바뀐다. 리포트를 보는 사람이 "문서가 정말 다르구나"가 아니라 "설정이 잘못됐구나"로 읽게 된다. 구현 비용은 수십 줄이다.

왜 이게 이 프로젝트의 철학과 맞는가

CLAUDE.md 가 명시한다 — "오판·누락 추적이 목적이므로 이 계측을 제거하지 말 것." budget_exhausted_pairs 도 정확히 같은 이유로 존재한다. 조용히 전부 missing 이 되는 경로는 반드시 드러내야 한다는 것이 이미 확립된 원칙이다.

(다) aliases 자동 제안 — 유일하게 상한이 없는 대책

원리: 권한 비대칭을 지킨다. 승인은 여전히 사람이 한다. 다만 "어떤 번역어를 등록해야 하는지 찾아내는" 반복 노동만 자동화한다.

예상 효과: 이게 다른 대책과 결정적으로 다른 점은 상한이 없다는 것이다.

대책효과의 성질상한
더 좋은 임베딩 모델일회성 점프모델 성능이 곧 천장
임계값 튜닝trade-off 이동분포가 겹쳐 원리적 한계
aliases 누적단조 증가없음 — 등록할수록 정확해짐

게다가 승격된 쌍은 _augment_with_ontology() 를 통해 recall 과 무관하게 후보로 들어온다(concept_builder.py:67-74 의 주석이 정확히 이 의도를 설명한다 — "승격이 가장 필요한 쌍이 바로 유사도로는 못 잇는 진짜 동의어다"). 즉 임베딩이 못 찾는 쌍을 사람의 지식이 우회로로 메우는 구조다.

(라) 그리고 search_text 조성 실험 — 모델 교체보다 먼저

구멍 ③에 직접 듣는 저비용 실험이 하나 있다. 임베딩용 문자열에서 값·단위를 빼고 이름·경로만 남겨 보는 것이다.

# 현재
search_text = "공칭용량 기본사양 전기적특성 1150 mAh"
              └── 이름·경로 ──┘ └─ 값·단위 ─┘   ← 교차언어에서 이쪽이 지배

# 실험안: 검색용과 판정용을 분리
search_text  = "공칭용량 기본사양 전기적특성"   # 후보 찾기용 (이름 의미만)
evidence_text = "1150"                          # 값 대조용 (이미 별도 필드로 존재)

원리: 값 대조는 어차피 F5 에서 코드가 attributes 를 보고 한다. 값을 검색 문자열에 넣는 것은 후보를 찾는 데만 쓰이는데, 교차언어에서는 그게 오히려 잡음이다. 예상 효과: "값이 같은 엉뚱한 항목"의 오매칭이 줄어든다. 다만 동일언어에서 값이 보조 신호로 도움이 되던 경우를 잃을 수 있으므로, (가)의 계측이 갖춰진 다음에 A/B 테스트로 확인해야 한다.

우선순위

질문 메모 솔루션의 원리나 우선순위에 대해 궁금한 점을 적어보세요.

9이해 점검 퀴즈

다섯 문항이다. 각 문항은 이 글을 실제로 이해했는지를 확인하도록 설계했다 — 함정 문제는 없다.

Q1. F7 개념 그래프에서 임베딩 유사도 점수의 역할은?
정확하다. 정답 최저 0.697 vs 오매칭 최고 0.700 으로 분포가 겹쳐 원리적으로 점수만으로는 가를 수 없었기 때문에, 점수를 판정에서 완전히 빼고 recall 용도로만 남겼다. 그래서 컷을 0.3 처럼 헐렁하게 잡아도 안전하다.
다시 보자. 실측에서 정답과 오답의 점수 분포가 겹쳐서 점수로는 가를 수 없다는 결론이 났고, 그 결과 점수는 판정에서 빠졌다. recall_score 필드 주석도 "판정에 쓰지 않고 진단용으로만 남긴다"고 못 박는다.
Q2. 영어 대상 문서에서 20건 중 9건이 뒤집힌 직접적 원인은?
맞다. bge-m3 는 0.7492 로 정확히 찾았고 LLM 도 12쌍을 정확히 판정했다. 무너진 곳은 EVIDENCE_MIN_TOKENS = 3 이었다 — 엑셀 단일값 fact 의 원문이 "1150.0" 처럼 토큰 1개라, 원문을 통째로 정확히 인용해도 하한을 넘을 방법이 없었다.
임베딩과 LLM 은 멀쩡했다는 게 이 글의 핵심 반전이다. 거부된 10건을 전수조사한 결과 전부 인용문이 원문과 완전히 일치했고, 토큰 수 하한에만 걸렸다. 한국어에서는 같은 행들이 BY_CODE 로 이어져 검증을 건너뛰었기 때문에 이 결함이 가려져 있었다.
Q3. entity_path 를 part_of 엣지로 승격하는 개선안(B)이 교차언어 비교에 도움이 되지 않는 이유는?
그렇다. ["기본사양","충전",…] vs ["Basic specification","Charging",…] 는 정규화해도 겹치지 않는다. 다만 실질 피해는 없다 — 언어가 다르면 norm_name 완전일치가 0건이라 BY_CODE 경로 자체를 안 타기 때문이다. 요컨대 B 의 이득은 동일언어 문서에서만 나온다.
핵심은 entity_path 가 언어에 종속된 문자열 리스트라는 점이다. 한국어 경로와 영어 경로는 정규화해도 한 마디도 일치하지 않는다. (참고로 비-Excel 문서에서 경로 품질이 낮은 것도 사실이지만, 그건 별개의 제약이다.)
Q4. 임베더 없이 한국어 기준 문서와 영어 대상 문서를 비교하면 어떤 일이 벌어지는가?
맞다. 토크나이저가 [가-힣]+ 와 [a-z]+ 를 각각 뽑으므로 두 언어의 공유 토큰은 숫자·단위뿐이다. BM25 점수는 이름에서 아무 기여도 받지 못한다. 그런데 이 실패는 조용하다 — 리포트만 보면 "문서가 정말 다르구나"로 읽힌다. 그래서 (나) 경고 장치가 필요하다.
BM25 는 단어 겹침을 세는 방식이라 교차언어에서 원리적으로 무력하다(fact_matcher.py 주석도 이를 명시한다). 더 중요한 것은 그 실패가 조용하다는 점 — 오류도, 경고도, 계측도 없이 전 항목이 missing 이 된다.
Q5. aliases 자동 제안이 "더 좋은 임베딩 모델"보다 나은 대책으로 꼽히는 근본 이유는?
정확하다. 모델 교체는 일회성 점프이고 그 모델의 성능이 곧 천장이다. 반면 aliases 는 _augment_with_ontology() 를 통해 유사도와 무관하게 후보를 채워 넣으므로, 등록할수록 단조 증가한다. 실측에서 3줄이 pairs_from_ontology 를 0→6 으로 만들었다. 참고로 승인은 여전히 사람이 한다 — 자동화되는 것은 "후보를 찾아내는 노동"뿐이며, 이는 권한 비대칭 원칙을 지키기 위한 의도적 설계다.
핵심은 효과의 성질이다. 모델 교체는 천장이 있는 일회성 개선이지만, aliases 는 등록할수록 누적된다. 그리고 승격된 쌍은 _augment_with_ontology() 가 recall 과 독립적으로 조회하므로, 유사도가 아무리 낮아도 영원히 이어진다. (덧붙여 이 대책은 완전 자동이 아니다 — 승인은 사람이 하며, 그게 의도된 설계다.)
