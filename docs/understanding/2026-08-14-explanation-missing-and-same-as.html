⚪ 대상에 없음 은 어떻게 정해지는가

개념 연결(same_as)에서 값 대조(findings)까지 — ContentCompare fact 엔진의 판정 경로를 끝까지 따라가 본다.

리포트에 ⚪ 대상에 없음 이 76건 찍혔다고 하자. 이 숫자는 어디서 나왔을까? "대상 문서를 뒤졌는데 없더라"는 뜻일 것 같지만, 실제로는 그렇게 단순하지 않다. 이 시스템에서 missing 은 "찾지 못했다"가 아니라 "비교하지 않았다"에 훨씬 가깝다. 그리고 왜 비교하지 않았는지는 여섯 갈래로 갈린다.

이 글은 세 가지 질문에 답한다. ① missing 건수가 정해지는 원리와 데이터 흐름, ② LLM 이 정한 same_as/differs_by 가 어떻게 missing 으로 번역되고 findings 안에서는 어떻게 match/mismatch 가 갈리는지, ③ same_as 를 판단할 때 정확히 어떤 데이터를 보는지 — 이름만 보는지, 수치도 보는지.

목차
  1. 배경 ① — fact 라는 비교 단위 (익숙하면 건너뛰세요)
  2. 배경 ② — 두 단계로 나눈 이유
  3. missing 은 어떻게 정해지는가
  4. same_as · differs_by · unknown 이 후보로 번역되는 과정
  5. findings 안에서 match 와 mismatch 를 가르는 법
  6. same_as 는 무엇을 보고 판단하는가 (핵심)
  7. 코드 산책
  8. 이해도 점검 퀴즈

📝 읽다가 궁금한 게 생기면 페이지 곳곳의 질문 메모 칸에 바로 적으세요. 타이핑하는 대로 이 브라우저에 자동 저장되고, 맨 아래 질문 저장 버튼을 누르면 질문이 박힌 사본이 같은 파일명으로 내려받아집니다. 그 파일로 원본을 덮어쓴 뒤 Claude 에게 "질문에 답해줘"라고 하면 됩니다.

1. 배경 ① — fact 라는 비교 단위

이미 fact 파이프라인을 아신다면 2장으로 건너뛰세요.

문제는 이렇게 생겼다. 왼쪽에 기준 문서(엑셀 규격서)가 있고, 오른쪽에 대상 문서(워드 규격서, PPT 발표자료, 영문 사양서…)가 여러 개 있다. 기준의 각 항목이 대상에도 같은 내용으로 적혀 있는지 한 줄씩 확인하고 싶다.

그런데 문서를 통째로 LLM 에게 주고 "비교해줘"라고 하면 답이 어디서 왔는지 알 수 없다. 그래서 이 시스템은 문서를 먼저 fact 라는 작은 조각으로 쪼갠다. fact 하나는 "어떤 항목에 대해 이런 값이 이렇게 적혀 있다"는 검증 가능한 주장 하나다.

용어 — fact 비교의 최소 단위. entity_name(무엇에 대한 사실인가) + attributes(값·단위) + evidence_text(문서에 실제로 적힌 원문)로 이루어진다. 원문을 항상 끌고 다니는 이유는 사람이 나중에 할루시네이션을 검수할 수 있어야 하기 때문이다.
질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

2. 배경 ② — 두 단계로 나눈 이유

기준 fact 하나를 대상 문서와 맞춰 보려면 두 가지를 물어야 한다.

  1. "이 둘을 비교해도 되는가?" — 표준환경온도 와 Standard ambient temperature 는 같은 것을 말하고 있는가? 1개월저장온도 와 3개월저장온도 는 다른 항목인가?
  2. "값이 같은가?" — 21/25/29 와 21/25/29 는 같은가? 1495 와 1.495A 는 같은가?

초기 설계는 이 둘을 한꺼번에 물었다. 그러자 치명적인 혼선이 생겼다. LLM 이 "값이 다르니까 다른 항목이겠지" 라고 추론해 버린 것이다. 그러면 우리가 찾으려던 불일치가 "애초에 다른 항목"으로 치환돼 영영 보이지 않는다.

⚠️ 이 시스템의 가장 중요한 분리 F7 개념 그래프는 "비교해도 되는가"만 답하고, F5 값 대조는 "값이 같은가"만 답한다. 개념 판정 프롬프트에는 이 문장이 못 박혀 있다:
"값이 다른 것은 differs_by 의 근거가 아닙니다. … 값의 차이는 우리가 찾으려는 결과이지 판단 재료가 아닙니다."

전체 흐름은 이렇게 생겼다. 색은 저장소의 공용 시각 언어를 그대로 쓴다 — ⚙️ 코드 🤖 LLM 🔢 임베딩 👤 사람.

질문 메모 두 단계 분리가 왜 필요한지, 그림 2의 흐름 중 헷갈리는 곳을 적어보세요.

3. missing 은 어떻게 정해지는가

3.1 한 줄 규칙

놀랄 만큼 단순하다. 후보 리스트가 비어 있으면 missing 이다. 

def compare_code(self, ref, candidates, target, ...):
    if not candidates:                    # ← 이 한 줄이 missing 의 대부분을 만든다
        return ComparisonProbe(
            reference_fact=ref,
            code_result=MISSING,
            code_reason=missing_reason or MISSING_BY_SIMILARITY,
        )

여기서 LLM 은 호출되지 않는다. 대상 문서를 읽지도 않는다. 후보 리스트가 비었다는 사실만으로 바로 결론이 난다. 그래서 이 경로로 나온 missing 은 decided_by = "code" 로 기록된다.

두 번째 경로는 후보가 있는데도 LLM 이 "이 후보들 중에 기준과 같은 대상을 다루는 건 없다"고 답한 경우다. 이때만 decided_by = "llm" 이 된다.

💡 진단의 열쇠 comparison_result.json 에서 result == "missing" 인 항목의 decided_by 한 글자만 보면 후보가 있었는지 없었는지를 알 수 있다. code 면 후보가 0건이었던 것이고, llm 이면 후보는 있었는데 LLM 이 아니라고 답한 것이다. 이 판별에 예외가 없는 이유는 _fallback()(LLM 실패 시 되돌아가는 경로)이 missing 을 절대 만들지 않기 때문이다.

3.2 그럼 후보 리스트는 어디서 오는가

ConceptMatcher.search() 가 만든다. 그리고 이 함수가 하는 일은 유사도 계산이 아니다 — 개념 그래프에서 이웃을 조회할 뿐이다.

class ConceptGraph:
    def partners(self, doc, fact_id, target_doc):
        concept_id = self.node_id_of(doc, fact_id)     # 내가 속한 개념 노드는?
        if concept_id is None:
            return []
        for node in self.nodes:
            if node.concept_id == concept_id:
                return [m for m in node.members if m.doc == target_doc]
        return []

즉 후보가 있다 = 기준 fact 와 대상 fact 가 같은 개념 노드 안에 있다 이고, 같은 노드에 들어가는 유일한 방법은 same_as 로 병합되는 것이다.

🚨 그래서 missing 은 "못 찾았다"가 아니다 개념 경로에서 missing 의 진짜 뜻은 "이 둘을 비교해도 된다고 아무도 확인해 주지 않아서, 값을 대조조차 하지 않았다" 이다. 대상 문서에 그 내용이 버젓이 적혀 있어도 연결이 안 됐으면 missing 이다.

코드가 이 사실을 자백하도록 사유 문구까지 갈아 끼운다: "개념이 같다고 판정되지 않아 비교하지 않았습니다". 유사도 경로의 기본 문구("유사도 임계 미달")를 그대로 두면 사용자가 F7 에서 쓰이지도 않는 match_min_score 를 조정하러 가기 때문이다.

3.3 missing 의 여섯 갈래

그래서 missing 한 건을 보고 "왜?"를 물으면 답이 여섯 개로 갈린다. 조치가 전부 다르다. fact/missing_trace.py 가 산출물만으로 이것을 가려낸다 — LLM 을 부르지 않으므로 비용이 0이다.

원인무슨 일이 있었나사람이 할 일
① recall 실패임베딩 유사도가 낮아 후보 쌍조차 만들어지지 않았다. LLM 은 이 쌍을 본 적도 없다.concept_recall_min 낮추기 · concept_recall_top_k 늘리기 · 온톨로지 승격
② LLM 미판정쌍은 갔는데 unknown 이 돌아왔다(예산 고갈·파싱 실패·응답 누락 포함).max_llm_calls_per_concept 늘리기 · 재실행
③ 근거 게이트 강등LLM 은 same_as 라 했는데 인용이 원문에 없어 코드가 unknown 으로 강등했다.인용을 눈으로 확인 후 온톨로지 승격
④ F3 추출 누락대상 문서에 내용이 있는데 fact 로 뽑히지 않았다. 애초에 후보가 될 수 없었다.배치 축소 · 추출 프롬프트 점검. facts_by_block.json 의 cited=false 블록이 후보
⑤ 의도된 차단LLM/사람이 "다른 개념"이라고 differs_by 를 놓았다. 오판이 아니다.differs_by 가 맞는지만 재검토
⑥ F5 LLM 판정후보는 있었는데 값 대조 LLM 이 "없다"고 답했다.판정 근거(reason) 확인

CLI 로 바로 볼 수 있다: python scripts/why_missing.py [항목명] [대상문서] [--all]

4. same_as · differs_by · unknown 이 후보로 번역되는 과정

LLM 은 쌍마다 세 값 중 하나를 돌려준다. 그런데 이 세 값이 하는 일은 대칭이 아니다.

관계그래프에서 하는 일후보 리스트에 미치는 효과
same_as두 fact 를 같은 노드로 합친다 (union-find)후보가 생긴다
differs_by합치기를 막는다. 다른 same_as 가 이 둘을 이으려 하면 그 엣지를 강등시킨다후보가 안 생긴다 (+ 사유가 리포트에 실린다)
unknown아무것도 안 한다. 합치지도, 막지도 않는다후보가 안 생긴다 (조용히)

핵심은 이것이다 — same_as 가 하나도 성립하지 않으면 기준 fact 는 혼자 노드를 이룬다. 혼자 있는 노드에는 대상 문서 멤버가 없으니 partners() 가 빈 리스트를 돌려주고, 그대로 missing 이다. differs_by 든 unknown 이든 결과는 같다 — 사유 문구만 다르다.

4.1 권한은 비대칭이다 — 연결만 검증받는다

LLM 이 same_as 라고 말했다고 바로 연결되는 게 아니다. 코드가 근거 인용을 검증한다. 반대로 differs_by(차단)는 검증하지 않는다.

설계 원칙 — 비대칭 권한 연결(same_as)은 LLM 이 제안하고 코드가 검증한다. 차단(differs_by)은 코드가 단독으로 한다.
이유: 틀린 연결은 사람을 잘못된 수정으로 유도하지만, 놓친 연결은 검토 목록에 남아 언젠가 확인된다. 손해가 비대칭이므로 권한도 비대칭이다. 
def verify_evidence(edge, left, right):
    for claim, fact in ((edge.left_text, left), (edge.right_text, right)):
        if not claim.strip():
            return False                                   # 인용이 없으면 실격
        source = set(tokenize(f"{fact.evidence_text} {fact.search_text} {fact.entity_name}"))
        if evidence_coverage(claim, source) < 0.8:         # 인용 토큰의 80% 가 원문에 있어야
            return False
        if not _quote_long_enough(claim, fact):            # 한 조각만 떼어낸 인용 차단
            return False
    return True

검증에 실패하면 엣지를 버리지 않고 unknown 으로 강등하고, 사유 앞에 [거부됨: 근거 인용이 원문에 없음] 을 붙인다. LLM 이 쓴 원래 사유를 그대로 두면 리포트에 "이 둘은 같은 항목이다"라는 문장이 실리고, 사람이 그걸 믿고 승격하면 게이트가 막았던 잘못된 연결이 영구화되기 때문이다.

질문 메모 비대칭 권한 · 근거 검증에 대해 궁금한 점을 적어보세요.

5. findings 안에서 match 와 mismatch 를 가르는 법

후보가 생겼다면 이제 값을 본다. 여기서도 코드가 먼저 시도하고, 못 하겠으면 LLM 에 넘긴다.

5.1 코드가 단정하는 경우 (LLM 0회)

@staticmethod
def _decide_by_code(ref, target):
    shared = [k for k in ref.attributes if k in target.attributes]   # 공통 속성 키
    if not shared:
        return _compare_single_attributes(ref, target)               # 양쪽 속성 1개씩일 때만

    same, differ = [], []
    for key in shared:
        state = _compare_attribute(ref.attributes[key], target.attributes[key])
        if state is None:
            return None            # ← 단위 등가를 모름 → 판단 자체를 포기하고 LLM 위임
        (same if state else differ).append(key)

    if not differ:
        return MATCH, [], "공통 속성 ... 의 값이 모두 일치합니다."
    return MISMATCH, differ, "값이 다릅니다: ..."

그리고 _compare_attribute 가 실제 값 비교를 한다. 중요한 건 이 함수가 True/False/None 세 가지를 돌려준다는 점이다 — None 은 "모르겠다"이고, 그러면 코드는 판정 전체를 포기하고 LLM 에 넘긴다.

상황반환왜
둘 다 숫자, 단위 호환, 값 같음True → ✅ 일치—
둘 다 숫자, 단위 호환, 값 다름False → ❌ 불일치—
단위가 사전에 없음 (예: gf/mm)None → 🤖 위임모르는 단위로 등가를 단정하면 안 된다
단위가 양쪽 다 있는데 다름 (mA vs A)None → 🤖 위임값 비교 자체가 의미 없다
한쪽 단위가 비었고 값이 10의 거듭제곱 배 (1495 ↔ 1.495)None → 🤖 위임단위 접두어 차이일 수 있다
문자열이 같음True → ✅ 일치—
문자열이 다름None → 🤖 위임다르다고 곧 불일치가 아니다. "배터리승인규격 ver 4.7 SEC Req. ver.4.7" 과 "SEC Req. ver.4.7" 은 같은 규격을 가리킨다
💡 여기가 설계의 정수 코드는 확실할 때만 단정한다. 조금이라도 애매하면 None 을 돌려주고 물러난다. fact 를 {value, unit} 으로 정규화한 이유가 바로 "값 비교는 코드가 한다"인데, 그 코드가 스스로의 한계를 아는 것이다.

5.2 LLM 이 판정하는 경우 — findings 배열

LLM 으로 넘어가는 조건은 셋이다. (가) 코드가 None 을 돌려줬다, (나) 근거가 불안정하다(uncertain), (다) 후보가 2건 이상이다.

⚠️ 후보 2건 이상이면 무조건 LLM 동명 fact 들은 recall 점수로 갈리지 않는다. 그러니 candidates[0] 하나만 보고 판정하는 것은 사실상 임의 선택이고, 그 위에 쌓은 match/mismatch 는 원리적으로 신뢰할 수 없다. 그래서 finalize() 안에 이 규칙을 박아 두었다 — 게이트 설정과 무관하게 항상 살아 있다.

LLM 에게는 이런 형식을 요구한다. 후보가 1건이어도 findings 는 1건 넣게 해서 파서에 분기가 생기지 않게 했다. 

{
  "result": "match|mismatch|missing|unknown",     ← 종합 판정 하나 (기준 1행 = 리포트 1줄)
  "mismatch_attributes": ["..."],
  "findings": [                                   ← 후보별 내역
    {"fact_id": "<후보로 제시된 id>",
     "result": "match|mismatch|unknown",
     "mismatch_attributes": ["..."],
     "quote": "<이 후보의 근거 원문 인용>",
     "reason": "<한국어 한 문장>"}
  ],
  "reason": "<종합 판단 근거>"
}

프롬프트가 종합 규칙까지 못 박는다:

후보가 여러 건이면 그것들이 함께 하나의 규격을 이룰 수 있습니다(예: 조건 구간별로 나뉜 값). 후보를 각각 기준과 대조해 findings 에 적고, 그 전체를 종합해 result 하나를 내세요. 하나라도 다르면 종합은 mismatch 입니다.

5.3 코드가 LLM 의 답을 검증한다

여기서도 제안은 LLM, 차단은 코드다.

LLM 이 한 일코드가 하는 일왜
후보 목록에 없는 fact_id 를 지목드롭 + dropped_findings 카운트할루시네이션 방지. 드롭은 결과에 안 남으므로 세지 않으면 영영 안 보인다
quote 가 그 fact 의 evidence_text 에 없음드롭하지 않고 quote_verified: false 표시만드롭하면 종합 판정이 통째로 날아간다. 사람이 검수하도록 표시만 남긴다
findings 를 냈는데 전부 드롭됨판정을 ❓ 판단보류 로 강등근거가 하나도 없는 판정이다
findings 를 아예 안 냄그대로 둔다이건 정당한 missing("후보 중 같은 대상이 없다")의 정상 형태다. 위와 합치면 정당한 missing 이 unknown 으로 바뀐다

5.4 대표 1건은 LLM 이 아니라 코드가 고른다

rep = next((f for f in findings if f.result == MISMATCH), findings[0])

순서는 첫 mismatch → 첫 finding → candidates[0]. 리포트에서 대표로 보여줄 것은 문제가 있는 쪽이어야 사람이 먼저 볼 곳을 찾기 때문이다.

질문 메모 코드 판정 표(5.1), findings 검증(5.3), 대표 선정(5.4) 중 궁금한 점을 적어보세요.

6. same_as 는 무엇을 보고 판단하는가

"entity_name 만 가지고 비교하는 건가? 이름이 달라도 적혀 있는 수치의 양식이 비슷하면 비교 대상이 될 수 있을 것 같은데."

좋은 직관이고, 답은 "단계마다 보는 것이 다르다" 이다. same_as 하나가 성립하기까지 fact 는 네 개의 서로 다른 렌즈를 통과한다. 각 렌즈가 fact 의 어느 칸을 보는지가 이 장의 전부다.

6.1 렌즈 1 — recall: 여기서는 수치가 실제로 쓰인다

후보 쌍을 만들 때 임베딩에 넣는 문자열은 entity_name 이 아니라 search_text 다. 그리고 search_text 는 이렇게 만들어진다: 

def _build_search_text(entity_name, entity_path, attributes):
    """entity + path + 속성 값/단위를 공백 결합(중복 제거). F5 후보 검색용."""
    tokens = [entity_name, *entity_path]
    for a in attributes.values():
        if a.value is not None:
            tokens.append(str(a.value))     # ← 값이 들어간다
        if a.unit:
            tokens.append(a.unit)           # ← 단위도 들어간다
    ...

구체적으로 보자.

기준  fact-row-15  search_text = "표준환경온도 기본사양 21 25 29"
대상  fact-word-6  search_text = "Standard ambient temperature 21 29 25 °C"
                                   ↑ 이름은 완전히 다르다        ↑ 숫자가 겹친다
→ 임베딩 코사인 0.86 → 후보로 채택

그러니 "이름이 달라도 수치 양식이 비슷하면 후보가 된다"는 직관은 이미 구현돼 있다. 다만 그건 후보를 만드는 단계이지 판정하는 단계가 아니다.

💡 왜 유사도를 판정에 쓰지 않는가 실측에서 정답의 최저 점수 0.697 vs 오매칭의 최고 점수 0.700 으로 두 분포가 겹쳤다. 같은 대상 fact 에 대한 두 쿼리라 점수로는 원리적으로 가를 수 없다. 그래서 유사도는 "명백히 무관한 것만 자르는 1차 필터"로 강등됐고, concept_recall_min 은 임계값이 아니라 계산량 제한이다.

6.2 렌즈 2 — 코드 확정: 여기만 이름을 본다

def norm_name(name):
    """entity_name 비교용 정규화 — 전각/공백/기호 차이를 없앤다."""
    return _NON_WORD.sub("", unicodedata.normalize("NFKC", name or "").lower())

# resolve_known() 안에서
if pair.exact:                      # norm_name 이 완전히 같으면
    edges.append(ConceptEdge(relation=SAME_AS, ..., decided_by=BY_CODE))

정격충전전압 ↔ 정격 충전 전압 처럼 같은 언어에서 띄어쓰기만 다른 경우를 공짜로 확정한다. 실측에서 같은 언어 문서쌍은 15~50% 가 여기서 해결됐다.

⚠️ 한↔영에서는 이 렌즈가 죽는다 표준환경온도 와 Standard ambient temperature 는 정규화해도 절대 같아지지 않는다. 실제 실행 통계가 그것을 그대로 보여준다 — pairs_by_code: 0, pairs_by_llm: 120. 교차언어 문서에서는 개념 연결이 사실상 전부 LLM 산(産)이다.

6.3 렌즈 3 — LLM: 이름·값·원문을 모두 본다

LLM 이 실제로 받는 프롬프트는 _render_fact() 가 만든다. 쌍마다 이렇게 생겼다: 

[쌍 7]
left_fact_id: fact-row-15 (문서: 자표준문서.xlsx)
  항목: 표준환경온도
  속성: lower_limit=21, target_value=25, upper_limit=29
  근거 원문: 21.0, 25.0, 29.0
right_fact_id: fact-word-6 (문서: spec_en.docx)
  항목: Standard ambient temperature
  속성: lower_limit=21 °C, target_value=25 °C, upper_limit=29 °C
  근거 원문: Standard ambient temperature | 21 ~ 29 (center 25) | °C

여기에 [문서 분야](프로파일), [참고자료 — 도메인 지식](knowledge/*.md), [이미 확정된 관계](온톨로지 요약)가 앞에 붙는다.

그러니까 LLM 은 이름만 보는 게 아니다. 속성값·단위·원문을 다 본다. 사용자가 직관한 "종합적으로 비교해야 한다"는 이미 이 렌즈에서는 이루어지고 있다.

6.4 그런데 여기에 미묘한 비대칭이 있다

프롬프트의 원칙 1은 이렇게 쓰여 있다:

값이 다른 것은 differs_by 의 근거가 아닙니다. "21~29 와 -10~80 은 값이 다르니 다른 항목"이라고 추론하지 마세요. 값의 차이는 우리가 찾으려는 결과이지 판단 재료가 아닙니다. 항목이 무엇에 대한 것인지만 보세요.

잘 읽어 보면 이 문장은 "값이 다르다 → differs_by" 만 금지한다. "값이 같다 → same_as" 는 금지하지 않는다. 이 비대칭이 실제 실행에서 사고를 냈다.

🚨 실측 사고 — 값 하나로 이어진 엉뚱한 연결 artifacts/자표준문서_xlsx/concept_graph.json 에 이런 엣지가 실제로 있다: 
{"relation": "same_as",
 "left":  {"fact_id": "fact-row-3"},    ← 기준: 고객 표준 버전
 "right": {"fact_id": "fact-word-8"},   ← 대상: Nominal capacity
 "left_text":  "배터리승인규격 ver 4.7\nSEC Req. ver.4.7",
 "right_text": "['Nominal capacity', '1150', 'mAh']",
 "reason": "두 항목은 모두 1150이라는 값을 참조하고 있어 같은 내용을 가리킵니다.",
 "decided_by": "llm"}
"모두 1150 이라는 값을 참조하니 같은 항목" — 규격 버전과 공칭용량을 값 하나로 이어 버렸다. 그리고 이 연결은 근거 검증도 통과했다. right_text 가 대상 원문을 통째로 인용했기 때문에 커버리지 100% 였다.

같은 실행에서 정반대 사고도 났다. 맞는 연결이 거부된 것이다. 

{"relation": "unknown",                     ← 원래는 same_as 였다
 "left":  {"fact_id": "fact-row-15"},       ← 기준: 표준충전전류 (한글)
 "right": {"fact_id": "fact-word-10"},      ← 대상: Standard charging current
 "left_text":  "Standard Charging Current", ← LLM 이 기준 쪽 인용을 영어로 썼다!
 "reason": "[거부됨: 근거 인용이 원문에 없음] 거부된 주장: 두 항목은 동일한 값을 나타냅니다.",
 "rejected_by": "evidence"}

기준 fact 의 원문에는 한글밖에 없는데 LLM 이 영어로 인용했으니 커버리지 미달로 거부됐다. 같은 실행에서 rejected_evidence: 17 건이 이렇게 사라졌다.

⚠️ 정리하면 — 근거 게이트는 완벽하지 않다 인용이 실재하는지만 검사하고 적절한지는 검사하지 않는다. 그래서
• 원문을 통째로 베낀 엉뚱한 연결은 통과하고,
• 인용을 번역해 버린 맞는 연결은 거부된다.
이것이 교차언어 문서에서 missing 이 대량으로 나오는 주된 이유 중 하나다(원인 ③).

6.5 사람이 개입하는 우회로 — 온톨로지

그래서 사람이 직접 적는 길이 열려 있다. knowledge/ontology.yaml 에 관계를 쓰면 recall 도, LLM 도, 근거 검증도 전부 건너뛰고 영구히 적용된다. 

- left: 표준환경온도
  right: Standard ambient temperature
  relation: same_as
  aliases: [기준환경온도, Reference ambient temperature]   # 동의어 그룹으로 확장

중요한 점은 온톨로지 쌍이 recall 과 독립적으로 조회된다는 것이다. 유사도가 낮아 후보조차 안 만들어진 쌍은 사람이 same_as 라고 적어도 이어지지 않을 텐데, 승격이 가장 필요한 쌍이 바로 그런 쌍(유사도로는 못 잇는 진짜 동의어)이기 때문이다.

💡 differs_by 목록에 번역어를 직접 나열하지 말 것 그러면 동의어까지 '다르다'로 선언된다. 반드시 aliases: 로 묶어야 관계가 그룹 전체로 확장된다.
질문 메모 네 렌즈 · 값의 비대칭 · 근거 게이트의 한계에 대해 궁금한 점을 적어보세요.

7.1 파이프라인이 이 조각들을 엮는 곳

gate = AcceptanceGate(self.fact.fast_path)
for target in store.targets:
    matcher = self._matcher_for(graph, ref_doc, target)     # 그래프 있으면 ConceptMatcher
    explain = getattr(matcher, "explain_missing", None)
    for ref_fact in ref_doc.facts.facts:
        candidates = matcher.search(ref_fact)               # ← 후보 (비면 missing 확정)
        probe = comparator.compare_code(
            ref_fact, candidates, target,
            ref_low_confidence=ref_doc.is_low_confidence(ref_fact),
            missing_reason=("" if candidates or explain is None else explain(ref_fact)),
        )
        reasons = gate.evaluate(probe)
        unsafe_match = bool(reasons) and probe.code_result == MATCH
        comparison = comparator.finalize(probe, force_llm=gate.enforce and unsafe_match)
        comparison.initial_result = probe.code_result or UNKNOWN   # 코드 판정 보존
        comparison.review_triggers = reasons
        result.comparisons.append(comparison)

initial_result(코드 판정)와 result(최종 판정)를 둘 다 남기는 것이 요점이다. LLM 이 코드 판정을 뒤엎었을 때 그것이 개선인지 새 오판인지 사후에 세려면 둘 다 있어야 한다 (result_changed).

Q5. 한글 기준 문서 ↔ 영문 대상 문서를 비교할 때, 개념 연결(same_as)의 대부분은 누가 만드나? 그리고 그 근거로 무엇을 보나?

9. 한 문단 요약

missing 은 "못 찾았다"가 아니라 "비교하지 않았다"이고, 비교하지 않은 이유는 개념 그래프에서 same_as 로 이어지지 않았기 때문이다. differs_by 든 unknown 이든 근거 게이트 강등이든, 후보 리스트가 비면 결과는 똑같이 ⚪ 이고 — 그래서 원인을 가르는 missing_trace 가 따로 있다. 후보가 생긴 뒤에야 값 대조가 시작되고, 거기서는 코드가 확실한 것만 단정하고 애매하면 None 을 돌려주며 물러나 LLM 에게 findings 를 받는다. 그리고 same_as 를 판단할 때 시스템은 이름만 보지 않는다 — recall 은 값·단위까지 섞은 search_text 를 임베딩하고, LLM 은 이름·속성·원문을 모두 받는다. 다만 값의 차이는 판단 재료로 쓰지 말라고 금지돼 있는 반면 값의 일치는 금지돼 있지 않아, 실제로 "둘 다 1150 이니 같은 항목"이라는 오연결이 관측됐다. 그 비대칭이 지금 이 시스템의 가장 날카로운 모서리다.

질문 메모 전체를 읽고 남은 질문, 혹은 "이건 어떻게 고치면 되나?" 같은 질문을 적어보세요.
