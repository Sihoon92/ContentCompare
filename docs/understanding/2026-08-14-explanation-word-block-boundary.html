규격서 한 줄이 조용히 사라지는 것은 소프트웨어가 저지를 수 있는 가장 고약한 실패에 속한다. 틀린 답을 내면 사람이 알아채지만, 아예 언급하지 않으면 아무도 모른다. 이 글은 그런 사건 하나를 처음부터 끝까지 따라간다 — 무엇이 사라졌는지, 어디서 사라졌는지, 그리고 왜 “LLM 을 더 잘 시키면 된다”가 답이 아닌지를.

📝 이 페이지의 “질문 메모” 사용법

읽다가 막히는 곳마다 질문 메모 상자가 놓여 있다. 거기에 바로 타이핑하면 브라우저(localStorage)에 자동 저장되고, 페이지 맨 아래 고정 바의 질문 저장 버튼을 누르면 질문이 박힌 채로 같은 파일명으로 내려받아진다. 그 파일을 원래 경로에 덮어쓴 뒤 Claude 에게 “이 문서 질문에 답해줘”라고 하면 답이 채워진다.

1.1 깊은 배경 (익숙하면 1.2 로 건너뛰세요)

ContentCompare 가 푸는 문제는 한 문장이다. 엑셀에 정리된 “정답 규격표”가 있고, 그 내용이 워드·PPT 로 흩어진 문서들에 제대로 반영됐는지 확인하고 싶다. 사람이 하면 한 줄씩 눈으로 대조해야 하는 일이다.

이 저장소에는 그 일을 하는 엔진이 둘 있는데, 오늘의 사건은 전적으로 fact 엔진에서 벌어진다. 이 엔진의 발상은 이렇다 — 문서를 먼저 fact 카드로 바꿔 둔 다음, 카드끼리 비교한다.

fact 카드의 칸내용
entity_name무엇에 대한 사실인가 — “충전온도범위”
attributes{이름: {값, 단위}} — {lower_limit: {15, ℃}}
evidence_text원문 인용. 사람이 할루시네이션을 검수하는 자리
source어느 블록에서 나왔나 — w_b245

카드로 바꿔 두면 좋은 점이 있다. 숫자와 단위가 구조화되면 LLM 없이 코드가 결정적으로 비교할 수 있다. 15 와 15 가 같은지는 기계가 판단하면 되지, 언어 모델에게 물어볼 일이 아니다.

그런데 여기 대가가 있다. 카드로 바꾸는 순간, 카드에 안 담긴 내용은 영영 사라진다. 이 문장이 오늘 이야기의 전부다.

1.3 워드는 문단을 어떻게 저장하나 — 이 글의 핵심 지식

.docx 파일은 사실 zip 으로 압축된 XML 묶음이다. 그 안의 word/document.xml 을 열면 본문이 태그로 적혀 있는데, 오늘 필요한 것은 셋뿐이다.

태그사람이 하는 동작의미
<w:p>Enter ⏎ 문단의 시작과 끝. 워드가 생각하는 “한 덩어리”의 단위
<w:br/>Shift + Enter ⇧⏎ 줄바꿈. 화면에서는 줄이 바뀌지만 문단은 끝나지 않는다
<w:ind>Tab 또는 들여쓰기 설정 문단 들여쓰기. 문단 전체를 오른쪽으로 민다

그리고 우리 파서(raw/word_raw.py)가 하는 일은 놀랄 만큼 단순하다.

contentcompare/raw/word_raw.py:190 — parse_word_xml()

for el in list(body):
    if el.tag == _w("p"):        # <w:p> 하나 = 블록 하나
        probes.append(_parse_paragraph(el))
    elif el.tag == _w("tbl"):    # <w:tbl> 하나 = 표 하나
        probes.append(TableProbe(rows=_parse_table(el)))

문단 하나가 들어오면 블록 하나가 나간다. 판단도, 추론도 없다. 그리고 바로 여기에 이 글 전체를 관통하는 문제가 숨어 있다.

🔑 오늘의 핵심 문장

블록 경계는 의미의 경계가 아니라, 작성자가 Enter 를 눌렀는지 Shift+Enter 를 눌렀는지의 기록이다.

같은 표를 두 사람이 쓰면 한 사람은 문단 하나에 줄바꿈으로, 다른 사람은 문단 여러 개로 만든다. 내용은 같은데 우리 눈에는 전혀 다른 구조로 보인다.

2사건 — 무엇이 사라졌나

사용자 규격서(워드)에 이렇게 적혀 있었다. 온도 구간마다 충전 전류와 전압이 다른, 아주 평범한 조건표다.

그런데 우리 파이프라인의 첫 산출물 physical_raw.json 은 이렇게 나왔다.

{ "block_id": "w_b245",
  "text": "12~15도씨, 0.7C(4.55V) 15~45도씨, 1.2C (4.20V)" }

{ "block_id": "w_b246",
  "text": "1.1C(4.28V) 0.8C (4.55V)" }   // ← 주어가 없다

블록이 둘로 갈라졌다. 작성자가 두 번째 줄 끝에서 Enter 를 눌렀기 때문이다. 그리고 w_b246 에는 “무엇에 대한 값인지”가 한 글자도 없다.

결과적으로 fact 카드는 이렇게 만들어졌다.

3원인 추적 — 껍질이 두 겹이었다

처음 보고된 증상은 사실 두 개였다. 그리고 둘은 완전히 다른 층에 있었다. 추적 과정을 그대로 따라가 보자 — 결론보다 어떻게 좁혀 갔는지가 더 쓸모 있다.

3.1 첫 겹 — 후보 목록에서 잘려 나갔다

다른 항목 하나(fact-word-53)가 비교 리포트의 “후보별 내역”에 없었다. 질문은 이랬다. 누가 뺐는가?

이 프로젝트는 판정마다 누가 판단했는지를 남긴다. 그게 첫 단서가 됐다.

{ "entity_name": "충전환경온도",
  "candidate_count": 4,     // ← 비교 단계가 받은 후보 수
  "findings": [ ...4건... ],
  "dropped_findings": 0 }      // ← 버려진 내역 없음

후보가 애초에 4건이었다. 즉 53번은 비교 단계에 도착조차 못 했다. 그러면 범인은 그 앞 — 개념 그래프(F7)다. 그런데 F7 은 한 칸이 아니라 셋이다.

산출물에 각 칸이 흔적을 남기므로, 추적기를 하나 만들어 돌렸다 (scripts/why_findings.py --trace-fact). 답은 ① 이었다.

① recall — 후보 쌍 생성 (🔢 임베딩)
   ❌ 탈락 — cut_by=top_k
      조치: concept_recall_top_k 를 올리세요.

기본값이 5 였다. 그런데 이 문서는 충전 온도 구간만으로 형제 fact 가 다섯이다. 거기에 다른 온도 항목들까지 같은 다섯 자리를 두고 경쟁하니, 정답이 6등으로 밀려 잘렸다. 5는 “형제가 4명 이하”라는 가정이었고, 규격표는 그 가정을 일상적으로 깬다.

✅ 첫 겹은 설정 한 줄로 해결됐다 (커밋 73ad11c)

concept_recall_top_k: 5 → 10. 올려도 위험이 낮은 이유는 이 값이 판정이 아니라 recall 이기 때문이다 — 후보가 늘어도 연결은 여전히 LLM 제안 → 코드 인용 검증 → 차단을 거친다. 그리고 실패 방향이 비대칭이다: 작으면 “대상에 없다”는 확신에 찬 거짓, 크면 검토 목록에 남는 시끄러운 정직.

3.4 반전 — “한꺼번에 보여주기”는 이미 하고 있었다

여기서 자연스러운 제안이 나온다. “블록을 하나씩 보여주니까 못 잇는 거 아닌가? 여러 개를 한꺼번에 주고 LLM 이 알아서 판단하게 하자.”

맞는 방향이다. 그런데 이미 그렇게 하고 있다. F3 는 블록을 20개씩 묶어 한 번에 보낸다(fact_batch_blocks: 20). 그러면 245와 246은 같은 묶음에 들어갔을까? 배치 경계를 계산해 보면 답이 나온다.

# _pack_batches: 블록 1개 = 그룹 1개, 20개씩 순서대로 채운다 (겹침 없음)
배치 경계:  1–20 │ 21–40 │ … │ 241–260 │ 261–280

w_b245 → 241–260 배치
w_b246 → 241–260 배치   ← 같은 배치 = 같은 LLM 호출
⚠️ 그러므로 원인은 “맥락 부족”이 아니다

LLM 은 두 블록을 나란히 보고도 잇지 못했다. 그러니 “더 많이 보여주면 된다”로는 안 낫는다. 진짜 원인은 둘이다 — (가) 프롬프트가 블록을 원자로 못 박고, (나) 판단 근거(들여쓰기)를 우리가 먼저 지웠다.

(가)를 확인해 보자. FACT_SYSTEM 의 구조 관련 규칙은 단 한 줄이고, 방향이 하나뿐이다.

- 흩어진 서술(본문+스피커노트, 표+설명)이 같은 대상이면 하나의 fact 로 병합합니다.

병합만 있고 분해가 없다. “한 블록이 여러 fact 일 수 있다”거나 “레이블 없는 블록이 앞 블록의 레이블을 이어받을 수 있다”는 말은 어디에도 없다. 오히려 첫 문장이 “각 항목 앞의 [id] 가 붙은 블록을 보고” 라고 블록을 단위로 못 박는다.

질문 메모 원인 추적 과정에서 논리가 건너뛴 것 같은 곳이 있으면 적어주세요.

4직관 — 왜 코드가 판별하면 안 되는가

가장 먼저 떠오르는 해법은 이것이다. “선행 공백이 있으면 앞 줄의 레이블을 복사해 채우면 되잖아?” 실제로 이 프로젝트는 표에서 이미 그 일을 하고 있다.

🔑 왜 규칙으로 풀면 안 되는가 — 실패의 비대칭

연속행 판별 규칙을 코드에 넣으면 두 종류의 실수가 가능하다.

  • 놓친다(연속행인데 못 알아봄) → 지금과 같음. 값이 리포트에 안 나온다.
  • 잘못 채운다(각주를 연속행으로 착각) → 없는 규격을 만들어낸다. 게다가 인용 검증도 통과한다 — 그 문자열은 원문에 실재하니까.

둘째가 훨씬 나쁘다. 누락은 언젠가 발견되지만, 그럴듯한 조작은 발견되지 않는다. 그래서 이 프로젝트는 규칙 기반 추측을 기각했다.

5수정 방법 — 네 개의 변경

설계의 뼈대는 한 문장이다. 코드는 판단하지 않는다. 다만 판단에 필요한 원문을 덜 훼손해서 넘긴다. 그리고 판단은 LLM 이 하되, 판단했다는 사실을 남긴다.

결정 0 — compact_raw 는 한 글자도 바꾸지 않는다

초안은 “compact 에 줄 정보를 실어 LLM 에 구조를 보여주자”였다. 조사해 보니 틀린 자리였다.

compact_raw 를 쓰는 곳이 셋이다
  ├ profiler.py:32        ← F1 문서 프로파일러의 캐시 + 프롬프트
  ├ schema_inducer.py:39  ← 엑셀 전용
  └ fact_extractor.py:61  ← 우리가 고치려는 곳

여기 필드를 더하면 고칠 것은 F3 하나인데 F1 프로파일러의 캐시까지 무효화되고 그 프롬프트도 부풀어 오른다. 대신 이미 있는 패턴을 쓴다 — 진단용 함수 build_facts_by_block() 은 원본 데이터를 별도 인자로 받고 있다.

# pipeline.py — 이미 이렇게 쓰고 있다
build_facts_by_block(compact, facts, stats, lines_by_block=raw_obj.to_dict())

# 추출기도 같은 방식으로 받는다 (raw_obj 는 바로 그 스코프에 이미 있다)
facts = extract_facts(compact, ..., lines_by_block=raw_obj.to_dict())
⚠️ 여기 함정이 하나 있다 — 반드시 지문에 반영해야 한다

새 입력이 캐시 지문에 안 들어가면, 같은 compact + 다른 줄 정보인 두 실행이 캐시를 공유해 옛 결과를 그대로 준다. 조용히 틀리는 종류라 설계서에 못 박아 뒀다 — 지문 계산에 줄 정보의 요약을 섞는다.

변경 ① raw 가 들여쓰기를 버리지 않는다

무엇내용

변경 ③ 프롬프트에 반대 방향을 넣는다

마지막으로 1.1C(4.28V) 라는 한 조각이 수정 후 어떻게 흘러 리포트까지 도달하는지 따라가 보자.

① word_raw.py — XML 에서 꺼낸다
   ParaProbe(text='...1.2C (4.20V)\n           1.1C(4.28V)', indent=0)
   → RawLine(raw_text='1.1C(4.28V)', indent=11)

② prompts.py — LLM 에게 보여준다
   [w_b245] 15~45도씨, 1.2C (4.20V)
   [w_b246]            1.1C(4.28V)      ← 정렬이 보인다

③ 🤖 LLM 이 판단한다 (여기가 유일한 판단 지점)
   { "entity_name": "충전온도범위",
     "attributes": {"lower_limit": {"value": 15, "unit": "℃"},
                    "charge_rate": {"value": "1.1C", "unit": ""}},
     "evidence_text": "1.1C(4.28V)",
     "inherited_from": ["w_b245"]       ← 이어받았다고 표시 }

④ F7 개념 그래프 — 기준 엑셀의 행과 이어진다
   충전온도범위(15~45℃) ←same_as→ 이 fact   (top_k 10 이라 후보에 든다)

⑤ F5 값 대조 — 후보가 2건 이상이므로 LLM 종합 판정
   findings: [ 1.2C 건 …, 1.1C 건 …, 0.8C 건 … ]

⑥ 리포트
   기준 1행 = 1줄, 그 아래 "후보별 내역" 3줄
   → 1.1C 가 마침내 사람 눈앞에 놓인다
✅ 눈여겨볼 것 — 판단은 딱 한 곳에서만 일어난다

①②는 ⚙️ 코드가 옮기기만 하고, ④⑤는 기존 장치가 그대로 처리한다. 새로 생긴 판단은 ③ 하나뿐이고, 그것마저 inherited_from 으로 추적 가능하게 남는다. 이것이 “코드는 판단하지 않는다”는 설계 원칙의 실제 모습이다.

8한 문단 요약

워드 작성자가 조건표를 쓰다가 두 번째 줄 끝에서 Enter 를 눌렀다. 그래서 같은 온도 구간에 딸린 두 조건이 별도 문단이 됐고, 우리 파서는 “문단 = 블록” 규칙에 따라 그것을 주어 없는 블록으로 만들었다. 원문에서 그 주어를 알려 주던 것은 글자가 아니라 빈칸의 위치였는데, 우리 코드가 공백을 병합하고 양끝을 다듬으면서 두 번 지웠다. LLM 은 주어 없는 숫자 두 개를 보고, “지어내지 말라”는 규칙에 충실하게 버렸다 — 규칙에 따른 올바른 동작이었고, 그래서 값이 조용히 사라졌다. 고칠 자리는 LLM 도 임계값도 아니고 입력이다. 코드는 들여쓰기를 버리지 않고 옆에 적어 두었다가 원문 모양 그대로 보여주고, “블록 경계는 손버릇일 뿐 의미 경계가 아니다”를 프롬프트에 명시하며, 배치가 의미를 자르지 않게 앞 블록을 맥락으로 붙인다. 그리고 LLM 이 이어받았다면 inherited_from 에 남겨 사람이 그것만 골라 검수할 수 있게 한다. 판단은 내용을 읽는 쪽이 하고, 판단했다는 사실은 데이터로 남는다.
