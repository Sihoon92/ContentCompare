1배경 — 이 호출이 서 있는 자리

아주 처음부터 (이미 아신다면 건너뛰세요)

이 프로그램이 푸는 문제는 한 문장으로 말할 수 있습니다. 엑셀에 적힌 기준 내용이 Word·PPT 같은 다른 문서에도 똑같이 적혀 있는가?

사람이 하면 이렇게 합니다. 엑셀에서 한 행을 읽고, Word 문서를 훑어 그 행이 말하는 대상이 어디에 설명돼 있는지 찾고, 그 자리의 숫자와 표현을 엑셀 값과 하나씩 대조합니다. 찾기와 대조, 두 가지 일이 섞여 있죠.

컴퓨터에게 이 일을 맡길 때 가장 나이브한 방법은 "Word 문서 전체를 LLM 에게 통째로 주고 물어보기"입니다. 그런데 이게 안 됩니다. 문서가 조금만 길어도 LLM 이 한 번에 읽을 수 있는 분량(컨텍스트 창)을 넘고, 넘지 않더라도 수백 페이지 속에서 관련 없는 내용이 판단을 흐립니다. 게다가 기준 항목이 500행이면 500번을 물어야 하니 비용도 500배가 됩니다.

그래서 쓰는 것이 RAG(검색 증강 생성) 라는 패턴입니다. 순서를 뒤집어서, 먼저 기계적으로 후보를 좁힌 뒤 그 좁혀진 것만 LLM 에게 보여 줍니다.

RAG 의 분업

검색은 싸고 빠르지만 "비슷해 보이는 것"까지만 압니다. LLM은 비싸고 느리지만 "같은 뜻인가, 값이 맞는가"를 압니다. 검색으로 수천 개를 10개로 줄이고, 그 10개에 대해서만 LLM 에게 판단을 맡깁니다. 이 페이지가 다루는 것은 뒤쪽 절반, 즉 판단하는 쪽입니다.

질문 메모 RAG 라는 개념 자체에서 걸리는 부분이 있다면 적어 두세요.

ContentCompare 의 다섯 단계

실제 파이프라인(contentcompare/pipeline.py)은 다섯 단계입니다. Langfuse 에서 보고 계신 그 호출은 4단계 한 곳에서만 나옵니다.

왜 하필 모듈 이름이 찍히는가

Langfuse 의 단계 이름은 보통 코드가 명시적으로 붙입니다. fact 엔진은 tracing.stage("F7 개념 판정") 처럼 이름을 지어 주죠. 그런데 RAG 판정만 contentcompare.comparison.comparator — 즉 모듈 경로 그대로 나옵니다.

이유는 설계 원칙에 있습니다. comparison/ 과 readers/ 는 코드 무수정 원칙이 걸린 영역이라 추적 코드를 심을 수 없습니다. 그래서 tracing.current_stage() 가 이름이 지정되지 않았을 때 호출자의 모듈명으로 폴백합니다.

def current_stage(depth: int = 2) -> str:
    explicit = _STAGE.get()
    if explicit:
        return explicit
    frame = sys._getframe(depth)
    module = frame.f_globals.get("__name__", "")
    return module or "(unknown)"

이름 없이 전부 한 덩어리로 뭉치면 trace 를 열어도 어느 단계인지 알 수 없으니, 최소한 어디서 불렀는지는 남기자는 절충입니다.

질문 메모 단계 이름·코드 무수정 원칙에 대해 궁금한 점

2직관 — 왜 한 행을 통째로 물어보는가

보고 계신 trace 에 findings 가 들어 있다는 것은 중요한 단서입니다. 그 필드는 엑셀 행을 판정할 때만 생깁니다. 즉 기준 문서가 엑셀이고 분해 단위가 hybrid(기본값)라는 뜻입니다.

순진한 방법과 그 실패

엑셀 한 행이 이렇다고 합시다.

모델명용량정격전압출시일
BX-2003200mAh3.7V2025-03

가장 단순한 접근은 셀 하나씩 검색해서 판정하는 것입니다. 그런데 "3.7V" 라는 셀 하나만 들고 Word 문서를 검색하면 어떻게 될까요? 전압을 언급하는 모든 문단이 걸립니다. 그중 어느 것이 BX-200 의 전압인지 알 방법이 없습니다. 셀은 자기 행이 무엇에 관한 것인지 모르기 때문입니다.

반대로 행 전체를 한 덩어리 문자열로 만들어 검색하고 판정하면 찾기는 잘 되지만, 결과가 "이 행은 partial 입니다" 한 줄로 뭉개집니다. 네 개 열 중 어느 것이 틀렸는지 사람이 알 수 없죠.

hybrid 분해 — 검색 단위와 판정 단위를 분리한다

행은 검색 단위(RecordItem)이고 셀은 판정 단위(FieldClaim)입니다. 행 전체로 검색해 문맥을 살린 뒤, LLM 에게는 "이 행을 찾아서, 각 열이 맞는지 하나씩 답해라"고 시킵니다. 그래서 응답에 행 전체 판정(verdict)과 열별 내역(findings)이 둘 다 들어 있는 것입니다.

실제로 무엇이 오가는가

위 행에 대해 3단계 검색이 후보 셋을 골라 줬다고 합시다. 이것이 LLM 이 보는 전부입니다 — Word 문서 원본이 아니라, 이 세 조각뿐입니다.

여기서 verdict 가 partial 인 이유가 눈에 보입니다. 세 열 중 둘은 맞고 하나가 틀렸으니 "전부 같음"도 "핵심이 다름"도 아닙니다. 그리고 어느 열이 틀렸는지는 findings 를 봐야 알 수 있습니다. 두 필드는 해상도가 다른 같은 이야기입니다.

질문 메모 이 예시에서 이해가 막히는 지점이 있다면

3구현 — 프롬프트가 조립되고 JSON 이 객체가 되기까지

이제 코드를 따라가 봅시다. 관련 파일은 셋뿐입니다.

파일역할
pipeline.py기준 항목마다 검색 → 어느 판정 함수를 부를지 분기
comparison/prompts.py프롬프트 템플릿과 조립 함수
comparison/comparator.pyLLM 호출 · JSON 파싱 · 결과 객체 생성

3.1 어느 판정 함수가 불리는가

파이프라인의 루프는 이렇게 생겼습니다.

for i, ref in enumerate(reference_items, start=1):
    if ref.is_empty():
        continue
    candidates = index.search(ref.text, recall_k=sim.recall_k, top_k=sim.top_k)
    # 엑셀 hybrid/field: 필드를 가진 RecordItem 이면 필드별 판정.
    if isinstance(ref, RecordItem) and ref.fields:
        result = self.comparator.compare_record(ref, candidates)
    else:
        result = self.comparator.compare(ref, candidates)

분기 조건이 명확합니다. fields 가 있으면 compare_record(), 없으면 compare(). 그리고 두 함수는 서로 다른 시스템 프롬프트를 씁니다.

compare()compare_record()
대상단락·셀·도형 같은 단순 항목엑셀 행
시스템 프롬프트SYSTEM_PROMPTRECORD_SYSTEM_PROMPT
응답 필드verdict · matched_item_ids · reasoning 거기에 findings 추가
결과 객체ComparisonResultRecordResult

findings 가 보인다면 오른쪽 열의 경로입니다.

3.2 user 프롬프트의 조립

build_record_prompt() 이 네 덩어리를 이어 붙입니다.

후보 한 줄의 실제 형식은 이렇습니다. 유사도 점수가 프롬프트에 그대로 들어간다는 점이 눈에 띕니다 — LLM 에게 "이건 0.812 로 가장 가깝다"는 힌트를 주는 셈입니다.

_CANDIDATE_TEMPLATE = "- item_id: {cid} | 유사도: {score:.3f} | 출처: {source}\n  내용: {text}"
_FIELD_TEMPLATE     = "- field_id: {fid} | 항목: {header} | 기준값: {value}"
질문 메모 프롬프트 조립에서 궁금한 점 (예: 지식이 너무 길면? 후보가 너무 길면?)

3.3 시스템 프롬프트가 요구하는 것

RECORD_SYSTEM_PROMPT 에는 판정 규칙 다섯 가지가 박혀 있습니다. 그중 셋이 특히 결과 해석에 중요합니다.

원칙 1값이 같으면 일치, 다르면 다름 — 분명히

단위·표기 차이는 감안합니다. 1,200 과 1200, 1.2천 과 1200 은 같은 것으로 봅니다.

원칙 2확신이 없으면 억지로 고르지 말고 unknown

단위가 불명확하거나(기준 1200 vs 후보 1,200억원), 도메인 지식이 없어 같은 항목인지조차 모르겠으면 unknown 으로 두고 왜 어려운지를 reasoning 에 적으라고 지시합니다. 이 프로젝트에서 unknown 은 실패가 아니라 1급 판정 상태입니다.

원칙 3후보에 없는 내용을 지어내지 말 것

그리고 evidence 는 후보 목록에 실제로 있는 문구만 인용하라고 못박습니다. 사람이 할루시네이션을 검수할 수 있게 하려는 장치입니다.

왜 unknown 을 1급으로 두는가

LLM 에게 "무조건 같다/다르다 중 골라"라고 하면 모르는 것도 고릅니다. 그러면 리포트에 틀린 확신이 섞이고, 사람은 그것을 걸러낼 방법이 없습니다. "모르겠다"를 허용하면 검토해야 할 항목이 스스로 드러납니다.

3.4 호출과 재시도

실제 호출은 _complete_json() 한 곳을 지납니다.

def _complete_json(self, system: str, user: str) -> dict:
    logger.debug("LLM 프롬프트(system):\n%s", system)
    logger.debug("LLM 프롬프트(user):\n%s", user)
    raw = self.llm.complete(system, user)
    logger.debug("LLM 응답(원문):\n%s", raw)
    parsed = self._parse(raw)
    if parsed:
        return parsed
    logger.warning("LLM 응답 JSON 파싱 실패 → 'JSON만 출력' 지시로 재요청")
    retry_user = user + "\n\n위 형식의 JSON 객체만 출력하세요. 다른 텍스트나 코드펜스는 금지합니다."
    raw2 = self.llm.complete(system, retry_user)
    return self._parse(raw2)

파싱에 실패하면 한 번 더 부릅니다. 그래서 Langfuse 에서 같은 항목에 trace 가 연달아 두 건 보인다면 그건 우연이 아니라 첫 응답이 JSON 이 아니었다는 신호입니다. 프롬프트나 모델을 의심할 지점이죠.

파싱 자체도 관대합니다. 순수 json.loads 가 실패하면 본문에서 첫 {...} 블록을 정규식으로 긁어냅니다 — 모델이 코드펜스나 설명을 덧붙이는 흔한 습관에 대한 방어입니다.

3.5 JSON 이 객체가 되는 과정

여기가 마지막이자, 코드가 LLM 을 믿지 않는 지점입니다.

특히 두 번째 게이트가 중요합니다.

valid_cand_ids = {c.item.item_id for c in candidates}
matched = [
    str(x) for x in (parsed.get("matched_item_ids") or []) if str(x) in valid_cand_ids
]

LLM 이 없는 item_id 를 지어내면 조용히 버려집니다. 그래서 Langfuse 의 출력에 있는 id 가 리포트에는 안 보일 수 있습니다 — 버그가 아니라 할루시네이션 방어가 작동한 것입니다.

findings 도 마찬가지로, LLM 의 응답이 아니라 기준 행의 필드 목록을 기준으로 재구성됩니다. LLM 이 한 열을 빼먹으면 그 자리에 "LLM 응답에 항목 내역 누락(검토 필요)" 이 채워집니다. 즉 findings 의 개수는 언제나 엑셀 행의 열 개수와 같습니다.

질문 메모 코드의 검증 단계에 대해 궁금한 점

4네 필드의 정확한 의미

이제 Langfuse 에서 보신 그 네 필드를 정확히 읽을 수 있습니다.

verdict — 행 하나에 대한 최종 한 마디

값뜻읽는 법
same찾았고 핵심 항목이 모두 일치넘어가도 좋다
partial찾았으나 일부만 일치findings 를 봐야 어디가 틀렸는지 안다
different찾았으나 핵심 값이 다름실제 불일치일 가능성이 높다
unknown같은지 다른지 확신 불가사람이 봐야 한다 — 실패가 아니다
not_found이 행에 해당하는 내용을 못 찾음검색 실패일 수도 있다(§5 참고)
파싱 실패 시의 조용한 기본값

LLM 이 스키마에 없는 값을 뱉으면 _to_verdict() 가 different 로 떨어뜨립니다(unknown 이 아닙니다). different 인데 reasoning 이 이상하게 빈약하다면 이 경로를 의심해 보세요.

matched_item_ids — "어디에서 찾았는가"

LLM 이 근거로 삼은 후보의 item_id 목록입니다. 검증을 통과한 것만 남습니다. id 형식이 곧 위치를 말해 줍니다.

형식의미
제품소개.docx#p17Word 의 17번째 단락
카탈로그.pptx#s5_sh2PPT 5번 슬라이드의 2번째 도형
사양.xlsx#Sheet1!12엑셀 Sheet1 의 12행
...#chunk0 접미사긴 항목이 chunk_chars 로 잘린 조각

reasoning — 사람을 위한 서술

"이 행의 내용이 대상의 어디에 있는지, 왜 그렇게 판단했는지"를 한국어로 쓰게 한 필드입니다. unknown 일 때는 왜 어려운지를 반드시 적으라고 프롬프트가 요구합니다 — 그래서 unknown 의 reasoning 이 비어 있으면 그 자체가 이상 신호입니다.

findings — 열별 확인 내역

배열의 각 원소는 엑셀 한 셀에 대응합니다.

키의미주의
field_id어느 셀인가 (파일#시트!C12)코드가 이 값으로 기준 필드와 맞춘다
found대상에서 이 항목을 찾았는가찾았다는 뜻일 뿐, 일치한다는 뜻이 아니다
note일치/다름/불명과 그 근거 한 줄실제 일치 여부는 여기에 서술된다
evidence후보 원문 그대로 인용후보에 없는 문구면 할루시네이션이다
가장 헷갈리는 지점: found ≠ 일치

found: true 는 "대상 문서에서 이 항목에 해당하는 서술을 찾았다"는 뜻입니다. 값이 맞는지는 note 에 적힙니다. 앞의 예에서 출시일은 found: true 이면서 값은 다릅니다(2025-03 vs 2025년 4월). found 만 세어서 "몇 개 일치"라고 읽으면 틀립니다.

이 구조가 그대로 리포트 표가 됩니다 — report/markdown_report.py 가 findings 를 돌며 항목·판단·인용 세 열을 찍습니다.

질문 메모 네 필드 중 해석이 애매한 것이 있다면

5경계와 함정 — trace 를 읽을 때 속지 않으려면

후보가 0개면 trace 자체가 없다

이것이 trace 를 읽을 때 가장 크게 오해하는 지점입니다.

if not candidates:
    return RecordResult(
        record=record,
        verdict=Verdict.NOT_FOUND,
        reasoning="관련 후보가 없어 비교 대상을 찾지 못함.",
        ...
    )

그러니 "대상에 없음"이 많다고 해서 LLM 프롬프트를 고치는 것은 헛수고일 수 있습니다. trace 수가 기준 항목 수보다 훨씬 적다면 손봐야 할 곳은 3단계 검색 (recall_k, top_k, 임베딩 모델, 교차언어 접두어)입니다.

같은 항목의 trace 가 둘이면 재시도다

§3.4 에서 본 대로, 첫 응답이 JSON 으로 파싱되지 않으면 "JSON만 출력하세요"를 덧붙여 한 번 더 부릅니다. 두 번째 trace 의 user 프롬프트 끝에 그 문장이 붙어 있는지 보면 바로 확인됩니다.

임베딩 호출은 기본적으로 trace 에 없다

trace_embeddings 가 기본 false 입니다. 한 번에 20건씩 묶여 오고 출력이 숫자 벡터라 trace 만 지저분해지기 때문입니다. 그래서 Langfuse 에 보이는 것은 사실상 판정 호출뿐입니다.

fact 엔진에는 이 모듈이 관여하지 않는다

--engine fact 로 돌리면 이 경로를 전혀 타지 않습니다. 거기서는 F7 개념 판정 → F5 값 대조 로 이름이 따로 붙고, 값 비교는 LLM 이 아니라 코드가 합니다. 같은 이모지를 써도 라벨의 뜻이 다르니(RAG ✅=같음 / fact ✅=일치) 두 엔진의 결과를 섞어 읽지 않도록 주의하세요.
