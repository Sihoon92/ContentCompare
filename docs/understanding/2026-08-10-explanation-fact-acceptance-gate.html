Acceptance Gate — 코드의 '일치' 판정을 믿어도 되는가

ContentCompare 의 fact 엔진에 게이트를 달았습니다. 코드가 "일치"라고 확정한 판정을 그대로 믿을지, 아니면 더 봐야 할지 채점하는 장치입니다. 이 글은 왜 그게 필요했고, 어떻게 만들었고, 이제 무엇을 확인해야 하는지를 설명합니다.

1. 배경 — ContentCompare 는 무엇을 하는가

1.1 깊은 배경 (이미 아는 분은 1.2 로 건너뛰세요)

배터리 사양서를 떠올려 봅시다. 회사에는 기준이 되는 엑셀 한 장이 있습니다. 한 행에 "공칭전압 3.85V", 다음 행에 "정격용량 1150mAh" 하는 식이죠. 그리고 이 기준을 옮겨 적은 문서가 여기저기 있습니다 — Word 규격서, 고객 제출용 PPT, 협력사가 보낸 엑셀.

사람이 이걸 대조하려면 문서 하나당 수백 줄을 눈으로 훑어야 합니다. ContentCompare 는 그 대조를 자동화합니다. 기준 엑셀의 각 항목에 대해 "이 내용이 대상 문서에 있는가, 있다면 값이 같은가"를 판정하고, 판정 근거가 된 원문을 그대로 인용해서 사람이 검수할 수 있게 합니다.

판정 라벨 4종 결과는 항상 이 넷 중 하나입니다. 이 라벨은 report/fact_report.py 가 단일 출처로 관리합니다.
✅ 일치 ❌ 불일치 ⚪ 대상에 없음 ❓ 판단보류

❓ 판단보류가 1급 상태라는 점이 이 시스템의 성격을 말해줍니다. 확신이 안 서면 억지로 답하지 않고 사람에게 넘깁니다.

중요한 설계 원칙이 하나 있습니다. 문서 파일을 통째로 LLM 에 던지지 않습니다. 대신 문서를 관찰 가능한 조각으로 먼저 분해한 뒤, 그 조각들을 다룹니다. 이렇게 하는 이유는 오판이 났을 때 "어느 단계에서 잘못됐는지" 추적하기 위해서입니다.

1.2 두 개의 엔진

ContentCompare 에는 접근이 다른 엔진이 둘 있습니다.

fact 란? 문서에서 뽑아낸 "하나의 주장"입니다. LLM 이 문서 블록을 읽고 이렇게 만듭니다. 
{
  "entity_name": "공칭전압",          ← 무엇에 대한 얘기인가
  "attributes": {                    ← 값들 (코드가 비교할 대상)
    "nominal": {"value": "3.85", "unit": "V"}
  },
  "evidence_text": "공칭전압 3.85V",  ← 원문 그대로 (사람 검수용)
  "source": {"block_id": "w_b012"}   ← 원문 위치
}
속성을 {value, unit} 으로 정규화한 이유가 "값 비교는 코드가 한다"입니다. 이 한 문장이 이 글 전체의 배경입니다.
질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

2. F5 값 대조가 실제로 하는 일

게이트를 이해하려면 게이트가 붙는 자리를 먼저 봐야 합니다. F5 단계는 기준 fact 하나를 대상 문서 하나와 대조합니다. 작업 전 코드는 이렇게 생겼습니다.

여기서 눈여겨볼 점이 두 가지 있습니다. 이 둘이 나중에 문제가 됩니다.

⚠️ 관찰 1 — 후보가 여럿이어도 첫 번째만 본다 ConceptMatcher 는 같은 개념에 연결된 대상 fact 를 전부 돌려줍니다. 그런데 compare() 는 candidates[0] 하나만 코드 비교에 씁니다. 후보 4건이 왔어도 코드는 1건만 봅니다.
⚠️ 관찰 2 — 코드는 '공통 속성'만 본다 _decide_by_code() 의 첫 줄이 이렇습니다. 
shared = [k for k in ref.attributes if k in target.attributes]
기준과 대상 양쪽에 다 있는 속성만 골라서 비교합니다. 한쪽에만 있는 속성은 조용히 무시됩니다.
질문 메모 위 흐름도나 두 '관찰'에서 걸리는 점이 있으면 적어보세요.

3. 문제 — 조용한 오판

3.1 구멍을 눈으로 보기

관찰 2 가 실제로 어떻게 문제가 되는지 장난감 예제로 봅시다. 기준 엑셀에 "공칭전압" 항목이 있고, 속성이 셋 있습니다. 대상 Word 문서에서 뽑은 fact 는 속성이 하나뿐입니다.

공칭전압기준 (엑셀)
nominal3.85 V
upper4.55 V
lower3.00 V
속성 3개
⟷
공칭전압대상 (Word)
nominal3.85 V
속성 1개

파란색으로 칠한 nominal 만 양쪽에 있습니다. 코드는 이렇게 판단합니다.

shared = ["nominal"]           ← 교집합은 이것뿐
3.85 V == 3.85 V               ← 값도 단위도 같다
→ 판정: match ✅               ← LLM 호출 0회, 즉시 확정
여기가 문제입니다 대상 문서에 상한값도 하한값도 적혀 있지 않은데 시스템은 ✅ 일치라고 답하고 넘어갑니다. 사람이 리포트를 봐도 "확인 완료"로 보입니다. 게다가 이 판정은 LLM 을 거치지 않았으므로 로그에도 흔적이 거의 없습니다. 그래서 조용한 오판입니다.

고쳐야 할 것은 명확합니다. "몇 개나 확인됐는지"를 세야 합니다.

질문 메모 커버리지 계산에서 헷갈리는 점이 있으면 적어보세요.

3.2 더 나쁜 사례 — 조건이 여러 개인 항목

Word 문서에 이런 표가 있다고 합시다. 상위 설계 문서가 대표 사례로 쓰는 실제 패턴입니다.

Charge temperature ranges:
 -5~5℃,  0.1C (4.55V)
  5~12℃, 0.3C (4.55V)
 12~15℃, 0.7C (4.55V)
 15~45℃, 1.2C (4.20V)

사람이 보면 "충전 온도 구간이 네 개고 구간마다 전류가 다르다"는 게 한눈에 보입니다. LLM 도 이 넷이 같은 개념이라는 건 잘 인식합니다. 문제는 그다음입니다.

4. 컨셉 — 2단계로 나누기

4.1 전체 그림

해결책의 뼈대는 이렇습니다. 기존 코드 비교를 버리지 않습니다. 오히려 1차 고속 경로로 그대로 두고, 코드가 자신 없어 하는 소수 항목만 원문을 다시 보는 2차 검사로 보냅니다.

4.2 가장 중요한 원칙 — 게이트는 탐지가 아니라 라우팅이다

🔑 핵심 개념 게이트가 하는 일은 "셀 수 있는 사실"의 확인입니다.
  • 후보가 2건 이상인가? → 세면 됩니다.
  • 커버리지가 1.0 미만인가? → 나누면 됩니다.
  • 근거 원문이 비어 있는가? → 보면 됩니다.
게이트가 하지 않는 일은 이것입니다.
  • "이 4개 후보 중 어느 게 맞는가?" → 이건 원문을 봐야 알 수 있습니다. 2차 검사의 몫입니다.
이 경계를 흐리면 게이트가 또 하나의 축약된 판정기가 되어, 지금 고치려는 문제를 그대로 재생산합니다.

4.3 반직관적인 사실 — 이 작업은 비용을 늘립니다

보통 "게이트를 달아서 빠른 경로를 만든다"고 하면 비용이 줄 것 같습니다. 여기서는 반대입니다. 이유는 단순합니다.

⚠️ 이걸 문서에 명시한 이유 실측에서 LLM 호출이 늘었을 때 회귀(버그)로 오인하지 않기 위해서입니다. 비용 절감은 다음 단계에서 나옵니다 — Phase 2(개념 판정 LLM 을 온톨로지로 대체)와 Phase 6(같은 개념 항목을 묶어 LLM 1회로 처리).

4.4 그래서 기본값은 'shadow'

얼마나 늘어날지 모르는 채로 켜는 것은 위험합니다. 그래서 기본값을 shadow 모드로 두었습니다.

질문 메모 shadow/enforce 구분이나 "비용이 는다"는 부분에 대한 질문을 적어보세요.

5.1 compare() 를 둘로 쪼개기

게이트가 들어갈 자리를 만드는 것이 첫 단계입니다. 핵심은 기존 compare() 의 시그니처와 동작을 100% 보존하는 것입니다.

def compare(self, ref, candidates, target, **kw) -> FactComparison:
    """(호환 래퍼) 코드 판정 → 확정을 한 번에."""
    return self.finalize(self.compare_code(ref, candidates, target, **kw))

def compare_code(...) -> ComparisonProbe:
    """코드 판정까지만 — LLM 을 절대 호출하지 않는다."""

def finalize(self, probe, *, force_llm: bool = False) -> FactComparison:
    """probe → 최종 판정. 필요할 때만 LLM 을 부른다."""
왜 '사후 채점'이 아니라 중간에 끼웠나 판정이 다 끝난 뒤에 결과를 채점하는 방식이 코드는 더 단순합니다. 그런데 _decide_by_llm() 은 LLM 이 지목한 후보로 대상을 교체할 수 있습니다. 그러면 사후 채점은 코드가 실제로 판정할 때 본 것과 다른 후보를 채점하게 됩니다. 지표가 어긋나면 그 지표로 내리는 모든 결정이 어긋납니다.

5.2 ComparisonProbe — 중간 상태

@dataclass
class ComparisonProbe:
    reference_fact: Fact
    target_doc: str
    candidates: list[MatchCandidate]
    code_result: Optional[str]      # match | mismatch | missing | None
    mismatch_attributes: list[str]
    code_reason: str
    attribute_coverage: float
    uncertain: bool
    missing_reason: str
None 과 "unknown" 은 다릅니다
  • code_result = None → 코드가 판단을 포기했다. 단위 등가를 모르겠다든지.
  • code_result = "unknown" → 최종 판정 라벨 ❓ 판단보류.
둘을 합치면 "코드가 못 정한 것"과 "사람이 봐야 하는 것"이 섞여서, 나중에 어느 쪽을 고쳐야 하는지 알 수 없게 됩니다.

5.3 attribute_coverage() — 예외가 하나 있습니다

def attribute_coverage(ref, target, *, confirmed_link: bool) -> float:
    if target is None:
        return 0.0
    if not ref.attributes:
        return 1.0                       # 잴 것이 없으면 논의 무의미
    if confirmed_link and len(ref.attributes) == 1 and len(target.attributes) == 1:
        return 1.0                       # ← 이 예외
    covered = sum(1 for k in ref.attributes if k in target.attributes)
    return covered / len(ref.attributes)

가운데 예외가 왜 필요한지는 실제로 겪은 사례를 봐야 이해됩니다.

정격용량기준 (엑셀)
lower_limit1150 mAh
'하한치' 열에 적혀서 키가 이렇게 됐다
⟷
정격용량대상 (Word)
target_value1150 mAh
같은 값인데 키 이름이 다르다

속성이 하나뿐인 fact 는 사실상 "이 항목의 값은 X 다"라는 뜻이고, 키 이름은 원본 표의 열 위치에서 온 것이라 의미 구분이 아닌 경우가 많습니다. 이 둘의 교집합은 0 이지만 사람은 "같다"고 봅니다.

단, 조건이 붙습니다 — confirmed_link=True 일 때만 이 예외는 개념 연결을 코드나 온톨로지가 확정한 경우에만 적용합니다. LLM 이 만든 연결 위에서는 적용하지 않습니다 — 그 경우는 어차피 low_confidence 사유가 따로 붙습니다.

5.4 AcceptanceGate — 7개 규칙

게이트는 ComparisonProbe 를 보고 검토 사유 목록을 돌려줍니다. 빈 리스트면 안전하게 확정할 수 있다는 뜻입니다.

앞서 본 "공칭전압" 예제를 게이트에 넣으면 이렇게 채점됩니다.

  • ✔code_missing — 후보가 있음
  • ✔code_mismatch — 코드 판정이 match
  • ✔code_unknown — 코드가 확정함
  • ✔low_confidence — 개념 연결이 코드 확정, 저신뢰 표시 없음
  • ✘partial_attribute_coverage — coverage 0.33 < 1.0 ← 여기서 걸린다
  • ✔duplicate_entity_facts — 후보가 1건
  • ✔invalid_evidence — 근거 원문과 위치가 있음

결과: review_triggers = ["partial_attribute_coverage"], safe_to_finalize = False. 앞서 "조용히 확정"되던 항목이 이제 사유와 함께 기록됩니다.

후보가 0건이면 사유는 하나뿐 후보가 없을 때 나머지 규칙을 함께 평가하면, 모든 ⚪ 대상에 없음 판정에 partial_attribute_coverage(커버리지 0.0)와 invalid_evidence(대상 fact 없음)가 덤으로 따라붙습니다. 그러면 사유 통계가 "거의 전부 커버리지 문제"로 보이면서 진짜 원인을 덮습니다. 그래서 후보가 없으면 code_missing 하나만 붙입니다. 
def evaluate(self, probe) -> list[str]:
    if not self.enabled:
        return []
    if not probe.candidates:
        return [CODE_MISSING]          # ← 여기서 조기 반환

    reasons = []
    if probe.code_result == MISMATCH:      reasons.append(CODE_MISMATCH)
    if probe.code_result is None:          reasons.append(CODE_UNKNOWN)
    if probe.uncertain:                    reasons.append(LOW_CONFIDENCE)
    if probe.attribute_coverage < 1.0:     reasons.append(PARTIAL_ATTRIBUTE_COVERAGE)
    if len(probe.candidates) > 1:          reasons.append(DUPLICATE_ENTITY_FACTS)
    if _evidence_invalid(probe):           reasons.append(INVALID_EVIDENCE)
    return reasons

사유는 누적됩니다. 한 비교에 여러 개가 붙을 수 있고, 순서는 REASON_ORDER 로 고정해 실행마다 같은 순서로 재현되게 했습니다.

질문 메모 7개 규칙 중 이해가 안 되는 것이 있으면 적어보세요.

5.5 파이프라인 배선

gate = AcceptanceGate(self.fact.fast_path)
for target in store.targets:
    for ref_fact in ref_doc.facts.facts:
        candidates = matcher.search(ref_fact)
        probe = comparator.compare_code(ref_fact, candidates, target, ...)

        reasons = gate.evaluate(probe)
        unsafe_match = bool(reasons) and probe.code_result == MATCH
        comparison = comparator.finalize(
            probe, force_llm=gate.enforce and unsafe_match
        )

        comparison.initial_result = probe.code_result or UNKNOWN
        comparison.review_triggers = reasons
        comparison.attribute_coverage = probe.attribute_coverage
🔑 shadow 무변경이 보장되는 지점 enforce=False 면 force_llm 이 항상 False 입니다. 그러면 finalize() 가 분리 이전과 완전히 똑같이 동작합니다. 실제로 fact 파이프라인 회귀 테스트 38건이 한 줄도 고치지 않고 통과했습니다.

강등 대상을 code_result == MATCH 로 제한한 것도 이유가 있습니다. ❌ 불일치와 ❓ 판단보류는 finalize() 가 이미 LLM 으로 보냅니다. 여기서 또 밀면 같은 항목에 LLM 이 두 번 갑니다.

5.6 판정 이력 — 1차를 덮지 않는다

FactComparison 에 필드 3개를 추가만 했습니다. 기존 키는 그대로여서 missing_trace.py, artifact_reader.py, ui/micro_world.py, why_missing.py 가 무수정으로 동작합니다.

질문 메모 배선 코드나 이력 필드에 대한 질문을 적어보세요.

7. 아직 안 한 것

상위 설계는 Phase 0~7 로 되어 있고, 이번에 끝낸 것은 Phase 1 하나입니다.

계획에서 의도적으로 뺀 것 하나

상위 설계에는 conditional_series 라는 여덟 번째 규칙이 있었습니다. "조건이 여러 개인 fact 가 하나로 축약된 것 같다"는 휴리스틱 신호입니다. 이번에는 넣지 않았습니다.

왜 뺐나 — 게이트를 빠져나가는 경로를 따져보면
대상 fact 상태코드 판정2차로 가는가
엉뚱한 구간이 후보 → 값 다름❌✔ 자동
개념 연결 없음⚪✔ 자동
단위 등가 미상None✔ 자동
fact 가 4건으로 쪼개짐 (3.2 경우 A)✅✔ duplicate_entity_facts
fact 1건에 뭉침 + 값 일치 (경우 B)✅✘ 이것만 남음

마지막 한 줄만 conditional_series 가 필요합니다. 그런데 그 경우는 F3 추출 단계에서 이미 정보를 잃은 상태라, Phase 3(원문 무손실 보존) 없이는 2차로 보내봐야 그래프가 볼 원문이 없습니다. 지금 넣으면 오탐 위험만 지고 효과는 0 입니다.

질문 메모 로드맵이나 conditional_series 를 뺀 판단에 대해 질문을 적어보세요.

8. 퀴즈

다섯 문제입니다. 답을 고르면 즉시 채점되고 해설이 나옵니다.

Q1. 게이트를 켜면(enforce: true) LLM 호출 수는 어떻게 되고, 그 이유는?
Q2. 게이트를 "판정이 끝난 뒤에 결과를 채점하는" 방식으로 만들지 않은 이유는?
Q3. 기준 fact 에 속성이 3개, 대상 fact 에 1개 있고 그 하나의 값이 같습니다. 게이트 도입 전에는 어떻게 됐나요?
Q4. 후보가 0건일 때 게이트가 code_missing 하나만 붙이는 이유는?
Q5. conditional_series(조건형 축약 탐지) 규칙을 이번에 넣지 않은 핵심 이유는?
질문 메모 퀴즈에서 헷갈렸던 부분이나, 글 전체에 대한 마지막 질문을 적어보세요.

요약 한 장

  • 문제 — 코드가 ✅ 일치로 확정하는데, 그 판단이 기준 속성의 일부만 확인한 것일 수 있다. LLM 을 안 거치므로 흔적도 거의 없다 (조용한 오판).
  • 컨셉 — 코드 비교를 1차 고속 경로로 유지하고, 자신 없는 항목만 2차로 보낸다. 게이트는 어느 후보가 맞는지가 아니라 더 봐야 하는지만 판단한다 (탐지 아닌 라우팅).
  • 구현 — compare() 를 compare_code()(LLM 0회) + finalize() 로 쪼개고 그 사이에 AcceptanceGate(7규칙)를 넣었다. compare() 는 래퍼로 남아 기존 경로가 무변경.
  • 기본값 — shadow. 채점만 하고 분기는 그대로여서 판정도 LLM 호출도 안 변한다. fact 회귀 38건이 무수정 통과했다.
  • 다음 — 실제 문서로 돌려 unsafe_match_rate 를 잰다. 그 숫자가 enforce 전환 여부와 Phase 2/3 중 어디로 갈지를 정한다.
