붕어빵 틀과 JSON

pydantic 으로 LLM 출력을 고정한 이야기 — 왜 “검사”가 아니라 “틀”이었나

어느 날 프로그램이 멈췄습니다. 엑셀 100줄을 처리하다가 7번째 묶음에서 죽었어요. 로그에는 딱 한 줄, JSON 파싱 실패.

이 글은 그 사건을 고친 이야기입니다. 고치는 방법으로 pydantic 이라는 도구를 썼는데, 많은 사람이 “pydantic = 결과를 검사하는 도구”라고 생각합니다. 이 글에서 가장 중요한 한 문장은 이겁니다: 우리는 pydantic 을 검사에 쓰지 않았습니다. 붕어빵 틀을 만드는 데 썼습니다.

1. 배경 — 무슨 일이 있었나

1-1. 아주 처음부터 알면 건너뛰기

이 프로그램(ContentCompare)이 뭘 하는지 이미 안다면 1-2 로 건너뛰세요.

회사에는 기준 문서가 하나 있습니다. 보통 엑셀이고, “충전환경온도는 −5도에서 55도” 같은 규격이 수백 줄 적혀 있어요. 그리고 그 내용을 옮겨 적은 다른 문서들이 있습니다. 워드 설명서, 발표용 PPT, 영문 사양서…

문제는 이겁니다. 다들 같은 말을 하고 있을까? 엑셀엔 55도라고 썼는데 PPT엔 50도라고 썼다면 큰일이죠. 그런데 문서가 수십 개면 사람이 눈으로 대조하기 어렵습니다.

그래서 이 프로그램은 문서를 읽어서 “사실 조각(fact)” 으로 잘게 쪼갠 다음, 조각끼리 맞춰 봅니다. 쪼개는 일은 사람이 못 하니까 🤖 LLM(챗지피티 같은 AI)에게 시킵니다.

1-2. “JSON 으로 답해줘”라는 부탁

LLM 은 글로 답합니다. 그런데 프로그램은 글을 못 읽어요. 프로그램이 읽을 수 있는 건 JSON 이라는, 규칙이 아주 엄격한 글쓰기 형식입니다.

📖 JSON 이 뭐예요? 이름표와 값을 짝지어 적는 방법입니다. 규칙이 딱 정해져 있어요 — 따옴표는 반드시 쌍으로, 항목 사이엔 쉼표, 마지막 항목 뒤엔 쉼표 금지, 중괄호는 열면 반드시 닫기. 하나라도 어기면 프로그램은 전체를 못 읽습니다. 한 글자만 틀려도요. 
{ "이름": "충전환경온도", "하한": -5, "상한": 55 }   ← 올바름
{ "이름": "충전환경온도", "하한": -5, "상한": 55, }  ← 쉼표 하나 더 있음 → 전체 실패
{ "이름": "충전환경온도", "하한": -5 "상한": 55 }   ← 쉼표 하나 빠짐 → 전체 실패

그래서 지금까지 우리는 LLM 에게 이렇게 부탁했습니다: 

반드시 아래 JSON 만 출력하세요(설명·마크다운 금지):
{
  "records": [ ... ]
}

부탁은 대부분 잘 통합니다. 문제는 “대부분” 이라는 말입니다.

질문 메모 JSON 이나 “왜 프로그램이 글을 못 읽는지”가 아직 애매하면 여기 적어보세요.

1-3. 그날의 사건: 배치 7/13

엑셀 100줄을 한 번에 주면 LLM 이 힘들어하니까, 우리는 30줄씩 잘라서 여러 번 물어봅니다. 100줄이면 13번쯤 되겠죠. 이걸 “배치”라고 부릅니다.

그날 7번째 배치에서 LLM 이 답을 줬는데, JSON 문법이 살짝 틀렸습니다. 프로그램은 “다시 해줘”라고 한 번 더 물었고, 또 틀렸습니다. 그리고 포기했어요. 문서 전체가 죽었습니다.

🔍 재시도가 왜 소용없었나 프로그램은 “다시 해줘”라고 할 때 같은 질문에 “JSON 만 출력하세요”라는 문장 하나를 덧붙일 뿐 이었습니다. 게다가 LLM 설정이 temperature=0(=매번 똑같이 답하기)이라, 같은 질문에는 거의 같은 답이 나옵니다. 처음에 틀렸으면 두 번째도 틀립니다. 주사위를 굴리는 게 아니라 복사기를 두 번 돌린 셈이에요.
질문 메모 “그럼 재시도를 늘리거나 temperature 를 올리면 되지 않나?” 같은 생각이 들었다면 적어두세요.

2. 직관 — 붕어빵 틀

2-1. 부탁 vs 틀

붕어빵을 만든다고 해봅시다. 두 가지 방법이 있어요.

방법 A — 부탁하기

반죽을 철판에 붓고 이렇게 말합니다.
“붕어 모양으로 예쁘게 퍼져줘!”

대부분은 붕어 비슷하게 됩니다. 그런데 가끔 꼬리가 뭉개지고, 가끔 지느러미가 안 생겨요. 망가진 건 버려야 합니다.

방법 B — 틀에 붓기

붕어 모양 틀에 반죽을 붓습니다.

반죽이 아무리 이상하게 흘러도 틀 밖으로 나갈 수가 없습니다. 꼬리가 뭉개진 붕어빵은 만들어질 수 없어요.

지금까지 우리는 방법 A 였습니다. 프롬프트에 “JSON 만 출력하세요”라고 부탁했죠. 이번에 바꾼 것이 방법 B 입니다.

📖 틀의 정체 — “강제 디코딩” LLM 은 글자를 한 글자씩 만들어냅니다. 다음 글자로 뭘 쓸지 매번 고르는 거예요. 우리가 서버에 “이 모양의 JSON 만 받겠다”고 미리 알려주면, 서버는 규칙을 어기게 될 글자를 후보에서 아예 지워버립니다.

예를 들어 마지막 항목을 쓰고 나서 , 를 찍으면 규칙 위반이 되는 자리라면, 그 순간 , 라는 글자가 선택지에서 사라집니다. 모델이 실수하고 싶어도 실수할 방법이 없습니다.
질문 메모 “글자를 선택지에서 지운다”는 게 잘 안 그려지면 여기에 적어보세요.

2-2. pydantic 이 붙는 자리 이 글에서 제일 중요

자, 그럼 그 “틀”은 누가 만들까요? pydantic 입니다.

많은 사람이 pydantic 을 “받은 데이터가 올바른지 검사하는 도구” 로 압니다. 맞는 말이지만, 우리는 그 용도로 쓰지 않았습니다. 왜냐하면 검사는 이 문제를 못 고치거든요 — JSON 문법이 깨져 있으면 pydantic 도 못 읽습니다. 못 읽는 건 매한가지예요.

대신 우리는 pydantic 에게 이렇게 말합니다: “내가 원하는 모양을 파이썬으로 적어둘게. 너는 그걸 보고 설계도를 뽑아줘.” 그 설계도를 서버에 보내면 서버가 틀로 씁니다.

💡 이 그림이 답하는 질문 “pydantic 을 도입하면 기존 코드를 다 뜯어고쳐야 하지 않나요?”
아니요. pydantic 이 요청 쪽에만 붙기 때문에, 응답을 받아 처리하는 코드 (parse_json_object → from_llm → 기존 dataclass)는 그대로입니다. 실제로 이 작업에서 도메인 모델 파일은 한 줄도 안 고쳤습니다.
질문 메모 위 그림에서 “왜 굳이 pydantic 이어야 하나? 설계도를 손으로 써도 되지 않나?” 같은 의문이 들면 적어두세요.

2-3. 무엇이 보장되고, 무엇이 안 되나

여기서 오해하면 위험합니다. 틀은 모양을 보장하지 내용을 보장하지 않습니다. 붕어빵 틀은 붕어 모양을 보장하지만, 안에 팥이 들었는지 슈크림이 들었는지는 모릅니다.

질문 메모 “그럼 값이 틀리는 건 어떻게 막나요?” 같은 질문을 여기 남겨두면 좋습니다.

3. 코드 — 어디가 어떻게 달라졌나

3-1. 파일 5개 지도

바뀐 곳은 크게 다섯 군데입니다. 아래 그림의 순서가 곧 데이터가 흐르는 순서입니다.

질문 메모 지도에서 역할이 헷갈리는 파일이 있으면 여기 적어두세요.

3-2. ① 틀 설계도 — fact/wire_models.py (신규)

“원하는 모양”을 파이썬 클래스로 적습니다. 이게 전부예요. 

# contentcompare/fact/wire_models.py
class WireAttribute(BaseModel):
    name: str
    value: CellValue        # 글자 | 숫자 | 참거짓 | 없음
    unit: str

class WireRecord(BaseModel):
    record_id: str
    entity: WireEntity
    attributes: list[WireAttribute]
    metadata: list[WireNamedText]
    source: WireRecordSource
    evidence_text: str
    confidence: float

class RecordsResponse(BaseModel):
    records: list[WireRecord]

그런데 여기서 중요한 결정이 하나 있었습니다. 우리에겐 이미 Record 라는 거의 똑같이 생긴 클래스가 있거든요. “중복이잖아, 하나로 합치자”가 자연스러운 생각인데, 그러면 안 됩니다.

⚠️ 왜 기존 모델과 따로 만들었나

Fact 에는 fact_id, source, search_text 라는 칸이 있습니다. 그런데 이 셋은 LLM 이 채우면 안 되는 칸이에요 — 코드가 직접 채웁니다. (LLM 이 “이 내용은 3번 문단에서 왔어요”라고 지어내면 안 되니까요.)

문제는 틀에는 “선택 사항”이라는 개념이 없다는 것입니다. 틀에 칸이 있으면 반드시 채워야 합니다. 그러니 이 칸들을 틀에 남겨두면, LLM 에게 “지어내라”고 강제하는 셈이 됩니다. 지어내기를 막으려고 만든 규칙을 틀이 정반대로 되돌리는 거예요.

그리고 이 결정을 미래의 누군가가 되돌리지 못하도록 테스트로 못을 박았습니다:

3-3. ② 틀 다듬기 — llm/structured.py (신규)

pydantic 에게 “설계도 뽑아줘”라고 하면 model_json_schema() 가 하나 나옵니다. 그런데 그대로 보내면 서버가 거절해요. 서버의 엄격 모드(strict) 규칙이 더 까다롭거든요.

pydantic 이 주는 것서버가 요구하는 것우리가 하는 일
additionalProperties 없음모든 칸 묶음에 false넣어준다
기본값 있는 칸은 “선택”모든 칸이 “필수”required 에 전부 넣는다
"default", "maxLength" …이런 건 안 받음지운다
클래스 독스트링을 description 으로(받긴 함)지운다 — 아래 참고
🧹 곁가지 발견 — 설계도가 31% 뚱뚱했다 pydantic 은 클래스에 적어둔 설명글(독스트링)을 설계도에 그대로 실어 보냅니다. 그런데 우리 설명글은 “record_normalizer 가 채운다” 같은 우리끼리 하는 메모였어요. LLM 에게 보낼 말이 아닙니다. 걷어내니 설계도 6개 합계가 9,654자 → 6,630자 로 줄었습니다. F2 는 배치마다 보내니까, 13배로 아껴진 셈입니다.

가장 자주 실수하는 곳도 여기 있습니다. 설계도 안에는 공용 부품 보관함($defs)이 있어요. 여러 곳에서 WireAttribute 를 쓰니까 한 번만 정의하고 참조하는 거죠.

그리고 이 파일의 진짜 값어치는 “일찍 죽이는 것” 에 있습니다. 

# 표현할 수 없는 모양이면 여기서 즉시 실패
_FREE_KEY_MSG = (
    "strict 스키마는 키 이름을 미리 모르는 object 를 표현할 수 없습니다 (경로: {path}). "
    "dict[str, X] 대신 list[{{name, value}}] 로 바꾸고, map 으로 되돌리는 것은 parse_* "
    "함수 한 곳에서 하세요 (예: record_models.parse_attributes)."
)
💡 왜 이게 좋은가 이 검사가 없으면 어떻게 될까요? 잘못된 설계도가 그대로 서버에 가고, 서버는 파이프라인 한복판에서, 문서 몇 개를 이미 처리한 뒤에 Invalid schema 한 줄을 던집니다.
검사가 있으면 같은 문제가 단위 테스트 실패로 바뀝니다. 커밋도 하기 전에요. 게다가 메시지가 어디가 문제고 어떻게 고치는지까지 알려줍니다.
질문 메모 $defs·$ref 나 “왜 평탄화하지 않았나”가 궁금하면 적어두세요.

3-4. ③ 문지기 — schemas.py & llm_stage.py

문지기 하나: pydantic 이 없는 컴퓨터도 있다

이 프로젝트를 돌리는 파이썬 환경이 두 개 였습니다. 하나엔 pydantic 이 있고, 하나엔 없어요. 그런데 테스트는 양쪽에서 다 돕니다.

파이썬은 파일 맨 위에서 import pydantic 을 만나면 없을 때 그 자리에서 죽습니다. 그러면 pydantic 없는 쪽에서 테스트가 수집조차 안 돼요. 그래서 schemas.py 라는 얇은 문을 하나 뒀습니다. 

# contentcompare/fact/schemas.py
@lru_cache(maxsize=None)
def schema_for(stage: str) -> Optional[dict]:
    try:
        from . import wire_models     # ← 함수 "안"에서 import
    except ImportError as exc:
        logger.info("pydantic 이 없어 구조화 출력을 끕니다: %s", exc)
        return None                    # ← 없으면 그냥 None
    ...
💡 예상 밖의 이득 None 은 “틀 없이 예전 방식으로”라는 뜻입니다. 그러니 pydantic 없는 환경에서는 예전 코드 경로가 매일 자동으로 테스트됩니다. 되돌림 경로가 몰래 썩는 걸 막는 가장 싼 방법이에요. 우회책처럼 보이지만 사실 더 좋은 성질입니다.

문지기 둘: 가짜 chat 37개를 어떻게 안 깨뜨렸나

여기가 이 작업에서 가장 까다로웠던 부분입니다. 테스트 코드 안에는 가짜 LLM 이 37개 있습니다. 진짜 서버 없이 테스트하려고 만든 흉내쟁이들이죠. 그런데 전부 이렇게 생겼습니다: 

def complete(self, system, user, *, temperature=0.0):
    return '{"ok": true}'

여기에 schema= 라는 새 인자를 무조건 넘기면? 37개가 동시에 터집니다. TypeError: complete() got an unexpected keyword argument 'schema'

해법은 “받는 쪽에게 물어보기” 였습니다. 백엔드가 스스로 “나 이거 받을 수 있어요”라고 손을 들면 그때만 넘깁니다. 

# contentcompare/fact/llm_stage.py
def _call_kwargs(self, schema):
    kwargs = {"temperature": self.temperature}
    if schema and getattr(self.chat, "supports_structured_output", False):
        kwargs["schema"] = schema          # ← 손 든 애한테만
        self.structured_calls += 1
    return kwargs

raw = self.chat.complete(system, prompt, **self._call_kwargs(schema))

가짜들은 supports_structured_output 을 선언하지 않았으니 getattr 이 False 를 돌려주고, 인자는 아예 안 넘어갑니다. 37개 전부 무사합니다.

그런데 백엔드는 세 겹으로 싸여 있다

실제 코드에서 self.chat 은 진짜 백엔드가 아닙니다. 양파처럼 싸여 있어요.

⚠️ 같은 기능이 여기선 해법, 저기선 함정 이 프로젝트의 다른 문서에는 __getattr__ 위임을 조심하라고 적혀 있습니다. 백엔드에 새 메서드를 추가하면 위임 때문에 기록·대기 기능을 조용히 건너뛰기 때문이에요.

그런데 플래그(그냥 값)일 때는 정반대입니다. 위임이 값을 위로 전달해주는 정확히 필요한 동작이 됩니다. 그래서 우리는 새 메서드가 아니라 기존 complete() 의 선택 인자로 갔습니다.
🚫 절대 하면 안 되는 최적화 “getattr 을 매번 부르는 건 낭비니까 __init__ 에서 한 번만 읽자” — 안 됩니다. 서버가 틀을 거절하면 백엔드가 실행 중에 스스로 손을 내리는데, 값을 캐시해두면 그 변화가 반영이 안 돼서 남은 수백 번이 전부 같은 오류에 부딪힙니다. 이 리팩터링을 막으려고 테스트를 하나 붙여뒀습니다 (test_the_flag_is_read_per_call_so_a_mid_run_downgrade_takes_effect).
질문 메모 “그냥 가짜 37개를 다 고치면 되지 않나?” 같은 생각이 들었다면 적어보세요.

3-5. ④ 실제로 보내기 — llm/langchain_backend.py

드디어 서버로 보냅니다. 딱 한 줄 차이예요. 

# 이전
resp = chat.bind(temperature=temperature).invoke(messages)

# 이후
bound = {"temperature": temperature}
if fmt is not None:
    bound["response_format"] = fmt      # ← 틀을 함께 실어 보낸다
resp = chat.bind(**bound).invoke(messages)
🔎 왜 fmt=None 일 때 키를 아예 안 넣나 response_format=None 을 넣으면 그걸 그대로 서버에 실어 보내는 SDK 버전이 있습니다. 그러면 “끔”이 “끔이라고 명시함”으로 바뀌어서 예전과 다른 요청이 돼요. “바이트 단위로 같은 요청”을 지키려면 키 자체가 없어야 합니다.

왜 with_structured_output() 을 안 썼나

LangChain 에는 with_structured_output() 이라는 더 유명한 함수가 있습니다. 안 쓴 이유가 있는데, 흔히 말하는 이유(반환 타입이 달라짐)가 아니었습니다.

이유는 이 밖에도 셋 더 있습니다. 정리하면:

#잃는 것왜 문제인가
1-> str 계약래퍼 3겹 전부에 파급된다
2토큰 사용량“우리 잘못”이 “서버 잘못”으로 기록된다 결정타
3모델 원문 기록“무엇을 받았나” 보려고 만든 추적이 무력해진다
4parse_failures 계측“모델의 JSON 준수도” 통계가 사라진다

서버가 거절하면?

사내 서버가 나중에 바뀌어서 틀을 거절할 수도 있습니다. 그때 프로그램이 죽으면 안 되겠죠.

⚠️ 거절 판정은 일부러 좁게 “400 이면 무조건 틀 문제”라고 넓게 잡으면 어떻게 될까요? 인증 실패(401)나 프롬프트 초과에도 “틀 빼고 다시”를 시도하게 됩니다. 그러면 모든 실패의 비용이 두 배가 돼요. 그래서 상태코드(400/422)와 본문 단어를 둘 다 확인합니다.
(참고: 요청 한도 판정은 반대로 넓게 잡습니다. 그쪽은 놓치면 60초를 못 기다려 손해지만, 이쪽은 잘못 잡으면 돈을 두 배 씁니다.)
질문 메모 강등 정책이나 with_structured_output 기각 이유에 대해 궁금한 점을 적어보세요.

3-6. ⑤ 이름표가 자유로운 칸 문제

마지막 걸림돌입니다. 우리 attributes 는 이렇게 생겼어요: 

"attributes": {
  "lower_limit": {"value": -5, "unit": "℃"},
  "upper_limit": {"value": 55, "unit": "℃"},
  "정격전압":     {"value": 3.7, "unit": "V"}   ← 이름이 엑셀 헤더에서 온다!
}

문제가 보이시나요? 이름표를 미리 알 수가 없습니다. 엑셀 열 제목이 뭐냐에 따라 달라지니까요. 그런데 틀은 “있을 수 있는 칸”을 전부 미리 적어야 합니다. 미리 모르는 이름은 틀로 표현할 방법이 없어요.

해법은 모양을 바꾸는 것이었습니다. 다만 주고받을 때만 바꿉니다. 

# contentcompare/fact/record_models.py
def parse_attributes(raw):
    if isinstance(raw, list):                       # ← 새로 추가된 3줄
        raw = _named_items_to_map(raw, keep=("value", "unit"))
    if not isinstance(raw, dict):
        return {}
    ...                                             # 나머지는 그대로
🤔 “같은 이름이 두 번 오면?” 목록에는 {"name": "a", ...} 가 두 번 들어갈 수 있습니다(map 에서는 불가능했죠). 우리는 뒤에 온 것이 이긴다로 정했습니다 — JSON 파서가 중복 키를 다루는 방식과 똑같이요. 두 모양의 결과가 같아야 캐시에서 읽은 것과 새로 받은 것이 갈라지지 않습니다.
그리고 이름이 빈 항목은 버립니다. "" 같은 대체 이름을 만들면 두 번째 무명 항목이 첫 번째를 조용히 덮어써요. 보이지 않는 손실이 제일 나쁩니다.
질문 메모 map ↔ 배열 변환이나 “왜 저장 형식은 그대로 두었나”가 궁금하면 적어보세요.
