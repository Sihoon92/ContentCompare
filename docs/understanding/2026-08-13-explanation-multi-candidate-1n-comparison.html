1. 배경 — 이 시스템은 무엇을 하는가

1.1 아주 깊은 배경 (이미 아는 분은 1.2 로 건너뛰세요)

회사에는 같은 내용을 서로 다른 양식으로 적은 문서가 여럿 있습니다. 엑셀로 정리된 표준 규격표가 하나 있고, 같은 규격을 문장으로 풀어쓴 워드 규격서가 있고, 고객에게 보여줄 PPT가 또 있습니다. 문제는 이들이 시간이 지나면서 서로 어긋난다는 것입니다. 엑셀에서는 상한이 55℃인데 PPT 에서는 50℃로 남아 있는 식이죠.

ContentCompare 는 이 대조를 자동화합니다. 엑셀을 기준으로 두고, 워드·PPT 를 대상으로 두어 항목마다 "같음 / 다름 / 대상에 없음 / 판단보류"를 판정합니다. 핵심 요구는 정확도만이 아닙니다 — 사람이 원문으로 재확인할 수 있어야 합니다. 그래서 모든 판정에는 양쪽 원문 인용과 좌표(시트·행·슬라이드·문단 번호)가 함께 실립니다.

엔진은 둘입니다. 옛 방식(--engine rag)은 임베딩으로 비슷한 문장을 찾아 LLM 에게 "이 둘이 같냐"고 묻습니다. 새 방식(--engine fact)은 다릅니다. 문서를 LLM 에게 통째로 주는 대신, 코드가 먼저 문서를 물리 구조로 읽어내고, LLM 은 그것을 보고 fact 라는 공통 형태로 정규화합니다.

📌 fact 란 문서에서 뽑아낸 하나의 주장을, 문서 종류와 무관한 공통 모양으로 정규화한 것입니다. 
{
  "fact_id":      "w_f012",
  "entity_name":  "charge temperature range",     ← 무엇에 대한 주장인가
  "attributes":   { "upper_limit": {"value": 45, "unit": "℃"} },   ← 값 + 단위
  "evidence_text":"15~45℃, 1.2C(4.20V)",          ← 실제 원문 (지어내기 금지)
  "source":       { "block_id": "w_b010", "line": "l05" }          ← 어디서 왔나
}
값을 {value, unit} 으로 쪼개 둔 이유가 중요합니다. 값 비교는 LLM 이 아니라 코드가 하기 위해서입니다. 55 와 50 이 다르다는 것을 확률적 모델에게 물어볼 이유가 없죠.
질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

1.2 이 사건에 필요한 배경 — 비교는 두 단계다

fact 끼리 비교할 때 던져야 할 질문은 사실 둘입니다. 이 둘을 섞으면 시스템이 망가집니다.

  1. 이 둘을 비교해도 되는가? — 엑셀의 "충전환경온도"와 워드의 "charge temperature range"가 같은 것을 가리키는가? (언어가 다르고 표기가 달라도)
  2. 값이 같은가? — 그렇다면 45 와 45 가 같은가, 45 와 50 이 다른가?

1번이 F7 개념 그래프, 2번이 F5 값 대조입니다. 판정 규칙은 하나뿐입니다 — 개념이 same_as 로 이어져 있지 않으면 아예 비교하지 않습니다. 유사도 점수(임베딩·BM25)는 판정에 쓰이지 않고 후보를 좁히는 recall 용도로만 남았습니다. 코사인 유사도 0.7 은 "관계 있음"도 "무관함"도 뜻하지 못한다는 것이 실측의 결론이었기 때문입니다.

fact 엔진의 비교 경로 (오늘)

🔢 후보 검색임베딩 + BM25 로 후보만 좁힌다 (판정 아님)
→
🤖 F7 개념 판정same_as / differs_by. 인용 없으면 무효
→
⚙️ F5 코드 대조값·단위를 결정적으로 비교
→
🤖 F5 LLM 위임애매한 것만 (실측 30%)
→
📄 리포트양측 원문 + 좌표

F5 안쪽은 최근에 한 번 더 쪼개졌습니다. 예전에는 compare() 하나가 "코드 판정"과 "최종 확정"을 한꺼번에 했는데, 그 사이에 Acceptance Gate(수용 게이트)가 들어갈 자리를 만들려고 갈랐습니다.

  • compare_code() — 코드 판정까지만. LLM 을 절대 부르지 않습니다(테스트로 고정). 결과는 ComparisonProbe 라는 중간 상태입니다.
  • AcceptanceGate.evaluate(probe) — 그 중간 상태를 채점해 검토 사유를 붙입니다. 게이트는 판단하지 않습니다. "후보가 2건 이상이다", "커버리지가 1.0 미만이다" 같은 셀 수 있는 사실만 확인합니다.
  • finalize(probe, force_llm=…) — 최종 판정을 만듭니다. 필요할 때만 LLM 을 부릅니다.
⚠️ 게이트는 지금 구경만 하고 있다 (shadow 모드) 기본 설정은 fast_path.enforce: false 입니다. 즉 게이트는 사유를 붙이고 통계를 남기지만 판정을 바꾸지는 않습니다. 켜면 지금까지 조용히 확정되던 판정들이 LLM 으로 넘어가 비용이 늘어나기 때문에, 얼마나 늘지를 unsafe_match_rate 로 먼저 재보는 중입니다. 이 사실이 뒤에서 결정적으로 중요해집니다.
질문 메모 게이트 · probe · finalize 분리가 헷갈린다면 여기에 적어두세요.

2. 문제 — 한 문단, 네 개의 조건

실제 문서에는 이런 문단이 있습니다. 충전 온도를 구간별로 나눠 각 구간의 충전율(C-rate)을 다르게 정한 것입니다. 배터리에서는 아주 흔한 표기입니다. 

Charge temperature ranges:
-5~5℃,   0.1C(4.55V)
5~12℃,   0.3C(4.55V)
12~15℃,  0.7C(4.55V)
15~45℃,  1.2C(4.20V)

눈으로 보면 다섯 줄이지만, 워드 파일 안에서 이것은 문단 하나입니다. 줄바꿈이 문단 나눔(<w:p>)이 아니라 문단 안의 줄바꿈(<w:br/>)이기 때문입니다. 이 형태가 바로 설계가 문제 삼는 모양이고, 그래서 샘플 문서에도 일부러 이 형태로 넣었습니다.

기준 엑셀 쪽에는 같은 내용이 한 행(항목명 충전환경온도)으로 들어 있습니다. 그러니까 이것은 1 대 N 대응입니다. 기준 1건 ↔ 대상 4건.

2.1 검색은 성공한다

가장 먼저 의심할 곳은 검색입니다. 4건 중 3건을 못 찾은 게 아닐까? 아닙니다. 진단 산출물 candidate_pairs.json 을 열어 보면 네 건이 전부 후보로 들어와 있습니다. 개념 그래프도 정상 동작해서 넷 다 같은 개념 노드에 same_as 로 이어져 있습니다.

그런데 판정 단계에서 세 건이 사라집니다.

2.2 왜 candidates[0] 은 믿을 수 없는가

후보 목록은 recall 점수 순으로 정렬돼 있습니다. 보통은 1등이 가장 그럴듯한 후보죠. 그런데 이 경우는 다릅니다 — 네 후보의 entity_name 이 전부 같습니다 (charge temperature range). 이름이 같으니 임베딩 벡터도 거의 같고, BM25 점수도 거의 같습니다.

즉 1등이 1등인 이유가 없습니다. 정렬 순서는 사실상 임의입니다. 실측 리포트가 표현했듯이 "두 분포가 겹칩니다". 그 위에서 내린 match / mismatch 는 원리적으로 신뢰할 수 없습니다.

질문 메모 "동명 후보는 점수로 안 갈린다"가 왜 결정적인지 헷갈리면 적어두세요.

3. 원인 — 1:1 이 세 층에 박혀 있다

버그를 한 줄로 지목하고 싶지만, 이 문제는 한 줄이 아닙니다. "기준 하나 ↔ 대상 하나"라는 가정이 서로 다른 세 곳에 각각 박혀 있습니다. 하나만 고치면 다른 둘이 되돌립니다.

① 후보 선택
코드
fact_comparator.py:226 과 :260 
best = candidates[0]        # compare_code
best = probe.candidates[0]  # finalize
후보가 몇 건이든 첫 번째만 꺼내 씁니다. 나머지는 probe.candidates 에 남아는 있지만 아무도 읽지 않습니다.
② LLM 프롬프트
지시문
prompts.py COMPARE_SYSTEM 원칙 4번 
4. target_fact_id 는 후보로 제시된 id 중 하나만 쓰세요.
LLM 에게는 후보를 전부 보여주면서(build_compare_user 는 이미 4건을 다 넣습니다), 정작 답은 하나만 고르라고 금지하고 있습니다. 설령 LLM 이 "넷이 함께 하나의 규격"임을 알아채도 표현할 방법이 없습니다.
③ 결과 스키마
데이터 모델
FactComparison.target_fact: Optional[Fact]
단수 필드입니다. 4건을 담을 그릇 자체가 없습니다. 리포트도, 진단 도구도, 현미경 UI 도 전부 이 단수 필드를 전제로 만들어져 있습니다.
🔍 그래서 이건 무엇의 문제가 아닌가
  • recall 문제가 아니다 — 후보 4건이 전부 들어왔습니다.
  • 개념 그래프(F7) 문제가 아니다 — 넷 다 올바르게 연결됐습니다.
  • 추출(F3) 문제가 아니다 — 워드에서 fact 4건이 제대로 뽑혔습니다.
F5 값 대조의 계약이 1:1 로 고정된 것이 원인입니다. 원인을 잘못 짚으면 concept_recall_min 같은 무관한 손잡이를 돌리며 시간을 낭비하게 됩니다.

3.1 게이트는 이미 알고 있었다

재미있는 사실이 있습니다. Acceptance Gate 에는 duplicate_entity_facts 라는 사유가 이미 있습니다(review_router.py:71). 

if len(probe.candidates) > 1:
    reasons.append(DUPLICATE_ENTITY_FACTS)

게이트는 "후보가 2건 이상이다"라는 사실을 정확히 탐지하고 있었습니다. 그런데 아무 일도 일어나지 않았습니다. 기본이 shadow(enforce: false)라서 사유만 통계에 쌓이고 판정은 그대로 나갔기 때문입니다. 강제 조건은 이것뿐입니다(pipeline.py:205): 

unsafe_match = bool(reasons) and probe.code_result == MATCH
comparison = comparator.finalize(
    probe, force_llm=gate.enforce and unsafe_match      # ← enforce=false 면 항상 False
)

탐지와 조치 사이에 스위치가 하나 끼어 있었고, 그 스위치가 꺼져 있었던 것입니다. 이 관찰이 해법의 모양을 결정합니다.

질문 메모 세 층 중 하나만 고치면 왜 안 되는지 등, 궁금한 점을 적어보세요.

4. 직관 — 네 명을 한 법정에 세운다

해법의 핵심은 한 문장입니다.

💡 한 줄 요약 후보가 2건 이상이면 하나를 고르지 말고 넷을 한꺼번에 LLM 에 넣어, 종합 판정 하나와 후보별 내역 넷을 받는다. 그리고 그 내역이 원문에 실재하는지는 코드가 검증한다.

법정에 비유하면 이렇습니다. 지금은 증인 넷 중 아무나 한 명만 불러 세우고 판결을 내립니다. 바뀐 방식은 넷을 모두 세워 각자 진술을 받고(findings), 그 진술을 종합해 하나의 판결 (result)을 내립니다. 그리고 각 증인의 진술이 실제 문서에 있는 말인지는 서기(코드)가 대조합니다.

✅ 12~15℃ 0.7C
✅ 15~45℃ 1.2C
📌 권한 비대칭 — 제안은 LLM, 차단은 코드 이 프로젝트 전체를 관통하는 규칙입니다. F7 개념 판정에서도 연결을 제안하는 것은 LLM 이지만, 근거 인용이 원문에 없으면 연결을 무효화하는 것은 코드입니다. 1:N 판정에도 같은 규칙을 적용합니다 — 후보별 판단은 LLM 이 하지만, 존재하지 않는 fact_id 를 지어냈거나 원문에 없는 문장을 인용했는지는 코드가 단독으로 확인합니다.
질문 메모 종합 판정 + 후보별 내역 구조에 대해 궁금한 점을 적어보세요.

5. 설계 결정 다섯 가지와 그 이유

여기서부터가 이 설계의 알맹이입니다. 각 결정에는 "그럴듯한데 채택하지 않은 대안"이 하나씩 붙어 있고, 그 대안을 왜 버렸는지가 이유를 설명합니다.

결정 1 — N≥2 에서도 코드 판정을 지우지 않는다

후보가 넷일 때 candidates[0] 기준 코드 판정은 의미가 없습니다. 그러니 code_result = None(판단 포기)로 두는 게 깔끔해 보입니다. 채택하지 않았습니다.

이유가 둘입니다. 첫째, None 은 게이트에서 code_unknown 사유가 됩니다. 그러면 "단위 등가를 몰라 포기했다"와 "후보가 여럿이라 포기했다"가 같은 사유로 뭉쳐 통계가 흐려집니다. 둘째, 그리고 이게 더 중요한데 — 코드 판정을 남겨 두면 _code_overridden() 이 "1:1 축약이 만들던 오판 건수"를 그대로 드러냅니다. 이 변경의 효과 측정치가 공짜로 생기는 셈입니다. 

# review_router.py — 이미 있는 함수. 이 케이스에 정확히 들어맞는다.
def _code_overridden(c):
    """코드가 의견을 냈는데 최종 판정이 그것과 다른가."""
    return c.initial_result in (MATCH, MISMATCH) and c.result != c.initial_result

결정 2 — 강제는 게이트가 아니라 finalize 호출부에 붙인다

가장 쉬운 구현은 게이트 안에 "후보 2건 이상이면 강제" 규칙을 넣는 것입니다. 하지만 fast_path.enabled: false(게이트 자체를 끔)로 두면 그 규칙이 함께 죽습니다.

⚠️ 게이트는 실험이고, 이건 정확성 버그 수정이다 게이트는 "얼마나 더 엄격하게 볼까"를 재보는 실험 장치라 언제든 꺼질 수 있습니다. 반면 1:N 라우팅은 틀린 답을 막는 수정이라 항상 살아 있어야 합니다. 수명이 다른 두 기능을 한 스위치에 묶으면 안 됩니다.

따라서 조건은 게이트 상태가 아니라 probe.candidates 를 직접 봅니다.

force_llm = (gate.enforce and unsafe_match) or len(probe.candidates) >= 2

덤으로, 롤백 경로(use_concept_graph: false 의 옛 유사도 매칭)도 match_top_k 만큼 후보를 주므로 같은 규칙에 그대로 걸립니다. 분기를 따로 만들 필요가 없습니다.

결정 3 — 인용 검증 실패는 드롭이 아니라 표시다

LLM 이 후보별 근거를 인용하면, 코드가 그 인용이 해당 fact 의 evidence_text 안에 실제로 있는지 대조합니다(공백 병합 후 부분일치 — fact_extractor._norm 과 같은 규약). 없으면?

검사실패 시 처리왜
fact_id 가 실제 후보 목록에 있나 그 finding 드롭 + 계측 존재하지 않는 것을 가리키는 진술은 근거가 될 수 없다 (기존 할루시네이션 방지 규칙과 동일)
quote 가 그 fact 의 원문에 있나 quote_verified: false 로 표시, 판정은 유지, 리포트에 ⚠️ 드롭하면 종합 판정이 통째로 날아가 사용성이 무너진다. 사람이 확인하도록 깃발만 세운다

단, LLM 이 finding 을 냈는데 그것이 전부 드롭되면 근거가 하나도 없는 판정이므로 unknown 으로 강등합니다. 여기에 함정이 하나 있습니다.

🚨 놓치기 쉬운 구분 — "전부 드롭" ≠ "애초에 없음" findings: [](LLM 이 애초에 아무 내역도 안 냄)는 result: "missing" — "후보 중 기준과 같은 대상이 없다" — 의 정상적인 형태입니다. 이 둘을 합쳐서 처리하면 정당한 ⚪ 대상에 없음 이 전부 ❓ 판단보류 로 바뀌어 버립니다. "비어 있음"과 "비워졌음"은 다릅니다.

결정 4 — 실패해도 1:1 로 되돌아가지 않는다

LLM 이 꺼져 있거나(compare_use_llm: false), 호출 예산이 끝났거나 (LlmBudgetExceeded), JSON 파싱이 실패하면(ValueError) 어떻게 할까요? 현재 코드에는 _fallback() 이 있어 코드 판정으로 되돌아갑니다.

상황후보 1건후보 N≥2
LLM 꺼짐기존 _fallback(코드 판정 복귀)❓ unknown 보류
예산 초과기존 _fallback❓ unknown 보류
JSON 파싱 실패기존 _fallback❓ unknown 보류

N≥2 에서 _fallback 으로 돌아간다는 것은 임의의 candidates[0] 축약으로 돌아간다는 뜻입니다. 지금 고치려는 바로 그 오판이 조용히 그대로 남습니다. 확신이 없으면 보류한다는 unknown 원칙의 정확한 적용 대상입니다.

결정 5 — "조건 계열"로 묶는 코드 휴리스틱은 넣지 않는다

"-5~5, 5~12, 12~15, 15~45 는 연속된 구간이니 한 계열로 묶자" 같은 규칙을 코드에 넣고 싶은 유혹이 있습니다. 넣지 않습니다. 두 가지 이유입니다.

  • 원칙 충돌 — 게이트(와 그 주변 코드)는 셀 수 있는 사실만 확인하고 "어느 후보가 맞는가"는 판단하지 않습니다. 구간 계열 판별은 명백히 판단입니다. 이 경계를 흐리면 게이트가 또 하나의 축약된 판정기가 되어 지금 고치려는 문제를 재생산합니다.
  • 불필요 — "후보 2건 이상"이라는 단순한 규칙만으로 이 케이스가 이미 잡힙니다. 복잡한 규칙을 추가해서 얻을 것이 없습니다(YAGNI).
질문 메모 다섯 결정 중 납득이 안 되는 것이 있으면 여기에 적어보세요.

6. 구현 — 무엇이 어떻게 바뀌는가

설계는 승인됐고 코드는 아직 손대지 않았습니다. 아래는 확정된 변경 계획입니다. 파일 다섯 개, 그중 넷은 이미 존재하는 파일입니다.

6.1 데이터 모델 — 필드를 추가한다 (기존 필드는 그대로)

@dataclass
class FactComparison:
    ...
    target_fact:  Optional[Fact] = None       # 유지 — 대표 1건
    target_facts: list[Fact] = field(default_factory=list)        # 신규
    findings:     list[FactFinding] = field(default_factory=list) # 신규

@dataclass
class FactFinding:
    fact_id: str
    result: str                     # match | mismatch | unknown
    mismatch_attributes: list[str]
    quote: str                      # 🤖 LLM 이 인용한 대상 원문
    quote_verified: bool            # ⚙️ 코드가 evidence_text 와 대조한 결과
    reason: str

기존 target_fact 를 지우지 않는 것이 핵심입니다. 후보가 1건이면 target_facts/findings 도 1건이므로, 기존 소비자 (report/fact_report.py, fact/missing_trace.py, 현미경 UI)는 무변경입니다. 회귀 위험을 이 설계로 사 놓은 셈입니다.

🎯 대표 1건은 코드가 결정론적으로 고른다 프롬프트에서 target_fact_id 를 없앴으므로 LLM 이 대표를 고르지 않습니다. 규칙은 "첫 mismatch finding → 없으면 첫 finding → findings 가 비면 candidates[0]" 입니다. 리포트에서 대표로 보여줄 것은 문제가 있는 쪽이어야 사람이 먼저 볼 곳을 바로 찾습니다.

6.2 프롬프트 — 금지를 허가로 바꾼다

- 4. target_fact_id 는 후보로 제시된 id 중 하나만 쓰세요.
+ 4. 후보가 여러 건이면 그것들이 함께 하나의 규격을 이룰 수 있습니다(예: 조건 구간별로
+    나뉜 값). 후보를 각각 기준과 대조해 findings 에 적고, 그 전체를 종합해 result
+    하나를 내세요. 하나라도 다르면 종합은 mismatch 입니다.

출력 JSON 은 이렇게 바뀝니다.

{
  "result": "match|mismatch|missing|unknown",
  "mismatch_attributes": ["<어긋난 속성 이름>"],
  "findings": [
    { "fact_id": "<후보로 제시된 id>",
      "result": "match|mismatch|unknown",
      "mismatch_attributes": ["..."],
      "quote":  "<이 후보의 근거 원문 인용>",
      "reason": "<한국어 한 문장>" }
  ],
  "reason": "<종합 판단 근거 한두 문장>"
}

스키마는 후보 수와 무관하게 항상 같습니다 — 후보가 1건이면 findings 가 1건일 뿐입니다. 파서에 분기를 만들지 않기 위한 결정입니다. 분기가 없으면 "후보 1건일 때만 나는 버그"도 없습니다.

한편 build_compare_user() 는 변경하지 않습니다. 이미 후보 전부를 [id] 와 함께 프롬프트에 넣고 있기 때문입니다 — 입력은 처음부터 옳았고, 출력 계약만 1:1 이었던 것입니다.

6.3 파이프라인 — 라우팅 한 줄과 계측 셋

# pipeline.py — force_llm 조건
comparison = comparator.finalize(
    probe,
    force_llm=(gate.enforce and unsafe_match) or len(probe.candidates) >= 2,
)
계측 키의미
multi_candidate_comparisons후보 2건 이상이었던 비교 수
multi_candidate_overridden그중 코드 1:1 판정과 최종 판정이 갈린 수 — 이 작업의 성과 지표
quote_unverified인용 검증에 실패한 finding 수

multi_candidate_overridden 이 0 이면 어떨까요? 실패가 아닙니다 — "1:1 축약이 애초에 오판을 만들지 않았다"는 뜻이고, 그것 자체가 유효한 정보입니다. 측정 가능한 실패 조건을 미리 정해 두는 것이 이 프로젝트의 습관입니다.
