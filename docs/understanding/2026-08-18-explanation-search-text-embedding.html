검색 문자열은 원문이 아니다

재조립된 search_text 가 숫자를 잃을 때 — 그리고 그것을 재느라 발견한 세 겹의 착각

어떤 항목이 대상 문서에 분명히 있는데 시스템은 ⚪ 대상에 없음 이라고 답했다. 원인을 쫓아 들어가니 임베딩에 들어가는 문자열에서 숫자가 통째로 빠져 있었다. 숫자를 넣어 보니 순위가 16위에서 1위로 뛰었다. 여기까지는 깔끔한 성공담이다.

그런데 그 성공을 검증하려고 측정 도구를 만들면서 세 가지가 차례로 뒤집혔다. 정답이라 믿던 fact 가 정답이 아니었고, 기존 채점 도구의 정답 판별이 새고 있었고, 마지막엔 기준 문서 자체가 틀려 있었다. 이 글은 그 과정 전체의 기록이다.

1. 배경 — 문서 두 개를 어떻게 견주는가

아주 처음부터 (이미 아신다면 건너뛰세요)

이 시스템이 하는 일은 한 문장으로 말할 수 있다. 기준 문서(엑셀 규격서) 한 개와 대상 문서(워드·PPT) N개를 받아, 기준의 각 항목이 대상에도 같은 내용으로 적혀 있는지 한 줄씩 판정한다. 결과는 네 가지다 — ✅ 일치, ❌ 불일치, ⚪ 대상에 없음, ❓ 판단보류.

문제는 문서를 통째로 LLM 에 던질 수 없다는 것이다. 규격서는 길고, 항목은 수백 개이고, LLM 은 한 번에 볼 수 있는 양이 정해져 있다. 그래서 파이프라인은 문서를 잘게 부수어 fact 라는 단위로 만든다. fact 하나는 대략 "무엇에 대해, 값이 얼마다" 한 조각이다.

질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

이 글에 필요한 좁은 배경

위 그림에서 recall 단계를 확대해 보자. 기준 fact 하나를 들고 대상 문서의 fact 수십~수백 개 중에서 닮은 것 10개를 골라내는 일이다. 이때 "닮았다"를 재는 방법이 임베딩이다. 문장을 숫자 벡터로 바꾸고, 두 벡터가 이루는 각도로 비슷함을 잰다.

임베딩(embedding)이란 문장을 고차원 숫자 배열로 바꾸는 것. 뜻이 비슷한 문장은 비슷한 방향의 벡터가 되도록 학습돼 있어서, 한국어 "충전온도범위"와 영어 "Charge Temperature Ranges"가 가깝게 나온다. 이 프로젝트가 한↔영 문서를 견줄 수 있는 근거가 이것이다.

여기서 이 글의 핵심 질문이 나온다. 그래서, 정확히 어떤 문자열을 임베딩하는가?

직관적으로는 "문서 원문"일 것 같다. 그런데 아니다. 파이프라인은 fact 마다 search_text 라는 별도의 검색용 문자열을 따로 조립해 두고 그것을 임베딩한다. 그리고 바로 이 조립 과정에서 사고가 났다.

recall 이 실패하면 조용하다 후보에 못 들면 F7·F5 는 실행조차 되지 않는다. 리포트에는 ⚪ 대상에 없음 이 찍히는데, 이건 "못 찾았다"가 아니라 "없다"는 단언으로 읽힌다. 실패 방향이 비대칭이라 recall 은 넉넉한 쪽이 안전하다 — 이 설계 원칙이 뒤에서 여러 번 다시 등장한다.
질문 메모 "왜 원문을 그대로 안 쓰지?" 같은 의문이 들었다면 적어두세요.

2. 직관 — 세 개의 문자열

문제를 발견한 실제 fact 로 보자. 영문 사양서에 이런 문장이 있다. 

Charge temperature ranges: -5~5℃, 0.1C(4.55V) 5~12℃, 0.3C(4.55V)
                           12~15℃, 0.7C(4.55V) 15~45℃, 1.2C(4.20V)

F3 가 이걸 fact 하나로 뽑았다. 이름은 Charge Temperature Ranges and C-rates, 속성은 네 구간이다. 그런데 속성 값이 전부 null 이었다. 칸은 만들었는데 숫자를 안 채운 것이다.

그 결과, 임베딩에 실제로 들어간 문자열은 이랬다.

off — 현재 동작
Charge Temperature Ranges and C-rates Charge temperature ranges ℃

숫자가 하나도 없다. 이름을 두 번 되풀이하고 단위 ℃ 하나가 붙어 있을 뿐이다. 반면 이 fact 가 겨뤄야 하는 기준 쪽 질의는 이랬다.

기준(질의) — 충전온도범위(-5~5℃)
충전온도범위(-5~5℃) 기본사양 -5.0 ℃ 5.0

질의에는 -5.0, 5.0 이 들어 있는데 상대에는 맞댈 숫자가 없다. 교차언어 검색에서 숫자는 언어를 타지 않는 가장 강한 신호인데, 그 신호가 한쪽에서만 사라진 것이다.

불공정한 경쟁 같은 문서의 옆 항목 Standard Ambient Temperature Range 는 속성 값이 ['21','29','25'] 로 채워져 있어서 … Range Key Specification Table 21 °C 29 25 처럼 숫자가 들어갔다. 숫자가 똑같이 닮은 두 항목인데 한쪽만 그 신호를 못 쓴다. 순위 경쟁이 조용히 기울어져 있었다.

그래서 넣어 보기로 했다 — 두 가지 방법

숫자가 없는 게 문제라면 넣으면 된다. 그런데 어떻게 넣느냐에 두 갈래가 있었고, 이 갈래가 결과를 갈랐다.

numbers — 근거에서 숫자만 뽑아 덧붙임
Charge Temperature Ranges and C-rates Charge temperature ranges ℃ -5 5 0.1 4.55 5 12 0.3 4.55 12 15 0.7 4.55 15 45 1.2 4.20
full — 근거 원문을 통째로 덧붙임
Charge Temperature Ranges and C-rates Charge temperature ranges ℃ Charge temperature ranges: -5~5℃, 0.1C(4.55V) 5~12℃, 0.3C(4.55V) 12~15℃, 0.7C(4.55V) 15~45℃, 1.2C(4.20V)

실측 결과, full 에서 이 fact 는 16위에서 1위로 올라갔다. 왜 이렇게까지 차이가 났을까? 두 문자열을 질의와 나란히 놓으면 보인다.

이번 실험이 진짜 말한 것 "숫자를 넣어라"가 아니라 "원문 형태를 보존하라"에 가깝다. numbers 는 -5~5℃ 를 -5 와 5 로 분해해 그 형태를 깨뜨린다. 값과 단위가 붙어 있고 0.1C(4.55V) 같은 묶음이 살아 있는 쪽이 이겼다.
질문 메모 "그럼 그냥 항상 full 로 하면 되는 것 아닌가?" — 그 의문은 4장에서 다룹니다.

3. 코드 — 무엇이 버려지는가

이제 search_text 가 어떻게 만들어지는지 실제 코드를 보자. contentcompare/fact/fact_extractor.py:136 이다. 

def _build_search_text(entity_name: str, entity_path, attributes: dict) -> str:
    """entity + path + 속성 값/단위를 공백 결합(중복 제거). F5 후보 검색용."""
    tokens = [entity_name, *entity_path]
    for a in attributes.values():
        if a.value is not None:
            tokens.append(str(a.value))   # 값
        if a.unit:
            tokens.append(a.unit)          # 단위
    seen: list[str] = []
    for t in tokens:
        t = str(t).strip()
        if t and t not in seen:   # 중복 제거
            seen.append(t)
    return " ".join(seen)

짧은 함수인데, 여기서 다섯 가지가 빠진다.

빠지는 것왜이 fact 에서 구체적으로
속성 이름(key) 루프가 attributes.values() 만 돈다. key 는 쳐다보지도 않는다. charge_temp_range_1~4 — 이름 자체가 "충전 온도 범위"인데 통째로 버려짐
값이 null 인 속성 if a.value is not None 에서 걸러진다. 네 구간 값이 전부 null → 숫자 0개
값·단위의 결합 값과 단위를 따로 append 한다. -5~5℃ 가 "-5.0", "℃", "5.0" 으로 분해
반복 seen 중복 제거. 네 번 나오는 ℃ 가 1개로 접힘
어순·문장 구조 토큰 나열이라 원문의 배치가 사라진다. 0.1C(4.55V) 같은 묶음이 소실
질문 메모 이 다이어그램에서 막히는 부분이 있으면 적어주세요.

폴백은 왜 작동하지 않았나

사실 코드에는 원문으로 되돌아가는 안전장치가 이미 있다. fact_matcher.py:50 이다. 

def fact_text(fact: Fact) -> str:
    """검색에 쓰는 문자열 — ``search_text`` 가 비면 근거 원문으로 폴백."""
    return fact.search_text or fact.evidence_text or fact.entity_name

그런데 이 폴백은 search_text 가 완전히 빈 문자열일 때만 걸린다. 우리 fact 의 search_text 는 "…and C-rates …ranges ℃" 로 비어 있지 않다. 빈약할 뿐이다. 파이썬의 or 는 "쓸모없음"을 모른다.

이미 이 상황을 잡는 검사가 있었다 validator.py:197 의 numeric_coverage 는 "근거에는 숫자가 여럿인데 속성에 수치가 하나도 없는가"를 센다. 우리 fact 에 돌려보니 정확히 걸렸다 — 근거에 숫자가 11개인데 속성에 수치가 없음(축약 의심). 진단은 이미 작동하고 있었고, 그 경고가 recall 로 연결돼 있지 않았을 뿐이다.

이름은 왜 중요한가

search_text 의 첫 성분이 entity_name 이다. 그래서 F3 가 같은 블록에 매번 다른 이름을 붙이면 검색 결과가 흔들린다. 실제로 그랬다 — 같은 코드·같은 문서인데 한 실행은 Charge Temperature Ranges and C-rates, 다른 실행은 Charge Temperature Protocol 로 나왔다. 한국어 "충전온도범위"와 맞물리던 "Ranges" 가 "Protocol" 로 바뀌면 그 대응이 끊긴다.

이름이 recall 에 관여하는 지점이 하나 더 있다. fact_matcher.py:124 의 이름 완전일치 조기 종료다. 정규화한 이름이 딱 맞으면 후보를 1건만 돌려주고 임베딩 계산을 아예 건너뛴다. 한↔영 문서쌍에서는 걸릴 일이 없지만, 같은 언어 문서끼리는 이것 때문에 후보가 1건으로 접힌다.

4. 실험 — 고치기 전에 재기

"16위 → 1위"를 보고 곧장 _build_search_text 를 고치고 싶어진다. 그런데 이 저장소에는 그러지 말아야 할 이유가 실측으로 남아 있다.

전례 — 형식만 먹은 개정 F7 차단 축을 4종으로 고정하는 프롬프트 개정을 한 적이 있다. 결과는 축 형식 준수율 98.5% 인데 실제 차단은 35건만 줄었다. LLM 이 같은 값을 양쪽에 적어 형식만 채운 것이다. 그럴듯한 변경이 실제로 먹었는지는 재봐야 안다.

그래서 추출기를 건드리기 전에, 산출물만 읽어 순위를 다시 계산하는 실험 장치를 만들었다. recall 은 임베딩만 쓰므로 facts.json 과 임베더만 있으면 재현된다 — chat LLM 은 한 번도 부르지 않는다.

세 모드

모드무엇을 하나왜 이 갈래인가
off현행 그대로대조군. 비교 기준이 없으면 개선을 말할 수 없다
numbers수치가 하나도 없는 fact 에만 근거의 숫자만 덧붙임제안 정책. 구멍만 좁게 메운다
full전 fact 에 근거 전문을 덧붙임상한 대조군. 긴 문장이 임베딩을 희석해 더 나빠질 수도 있다

numbers 와 full 을 굳이 나눈 이유가 있다. 둘의 결과가 갈리면 처방 범위가 정해지기 때문이다.

한 항목이 좋아진 것 ≠ 정책이 좋은 것 full 은 기준·대상 전 fact 의 검색 문자열을 바꾼다. 우리 항목이 1위가 된 만큼 다른 항목의 정답이 밀려났을 수 있다. 지금 본 건 100여 개 중 하나다. 그래서 골든셋 전체로 재는 두 번째 도구가 필요했고 — 그걸 만들다가 반전이 시작된다.

5. 세 번의 반전

전체를 재려면 "골든셋이 말하는 정답 fact"를 알아야 한다. 그런데 골든셋은 target_text(대상 문서의 원문 문장)만 주고 fact 의 id 를 주지 않는다. 그래서 토큰이 겹치는 fact 를 정답으로 간주하는 휴리스틱을 쓴다. 여기서부터 하나씩 무너졌다.

반전 ① — 채점 도구의 정답 판별이 새고 있었다

기존 score_golden.py 의 토큰화 규칙은 [a-z0-9]+ 다. 이 규칙으로 0.1C(4.55V) 를 자르면 이렇게 된다. 

['0', '1c', '4', '55v']     # 소수점이 토큰을 쪼갠다

그러자 Charging Voltage 라는 엉뚱한 fact 가 '4', '55v' 두 조각만 공유하고 "정답"으로 판정됐다. 겹침 하한이 2였기 때문이다.

1.겹침5Operating Protocol in different Temperatures ★정답판정
2.겹침2Charging Voltage ★정답판정 ← 오탐
3.겹침3Charge Voltage (Standard Charge) ★정답판정 ← 오탐
4.겹침5Charge Temperature Ranges and C-rates

이 규칙으로 재면 recall@10 = 74/76 이라는 훌륭한 숫자가 나온다. 허수다. 소수를 통째로 두고(\d+(?:\.\d+)?) 골든 토큰 대비 비율로 다시 재니 57/76 이었고, 판별 자체가 안 되는 17건이 분리됐다.

파급 같은 규칙이 실측 보고서 §14 의 "정답 상대가 후보에 있었음 39/49건" 을 만들었다. 그 수치가 "F7 이 병목이고 recall 은 범인이 아니다" 라는 결론의 근거다. 판별이 헐거우면 그 결론도 흔들린다 — 아직 재검토하지 않은 숙제로 남아 있다.

반전 ② — 쫓던 fact 가 정답이 아니었다

정답 판별을 고치고 나서 출력을 눈으로 확인하니, 이 문서에 비슷한 블록이 둘 있었다.

즉 "충전온도범위가 후보에 안 든다"는 문제의식 자체가 부분적으로 헛짚은 것이었다. 골든이 원하는 fact 는 처음부터 1위에 있었다.

질문 메모 두 블록이 왜 다른 값을 갖는지 등, 이 대목의 의문을 적어주세요.

반전 ③ — 기준 문서가 틀려 있었다

여기서 사람이 개입했다. 실제 규격서를 아는 사람이 기준 엑셀이 실제와 다르다고 지적한 것이다. 확인해 보니 정말 그랬다.

게다가 실제 문서는 구간을 별도 행으로 나누지 않는다. 정성규격 한 칸에 다섯 줄이 같이 들어 있다. 샘플 엑셀에만 존재하던 구간별 4개 행은 실재하지 않는 형제 fact 로서 top_k 자리를 차지하며 경쟁을 왜곡하고 있었다.

그래서 지금까지의 mismatch 판정은 대상 문서(w_b014)가 실제 값과 맞았고 기준 쪽이 틀려 있었다. 시스템은 성실하게 "다르다"고 말했지만, 다른 이유가 우리가 생각한 것과 정반대였다.

엑셀을 고치고 나면 골든셋도 따라 움직여야 한다. 골든은 물리 행번호를 조인 키로 쓰기 때문이다. 행 4개를 지우자 뒤의 80건이 4칸씩 어긋났다. 이건 판정을 바꾸는 일이 아니라 포인터를 다시 맞추는 기계적 작업이므로, 행번호만 옮기고 expected 는 한 건도 건드리지 않았다. 검증은 간단했다 — 100건 전부에 대해 "골든의 항목명 == 그 행의 엑셀 항목명"을 확인했다.

교훈 — 측정 도구를 먼저 의심하라 세 반전 중 둘(①②)은 측정 도구를 만들면서 드러났다. 도구가 없었다면 "full 로 바꾸니 좋아졌다"에서 멈추고, 실재하지 않는 행과 틀린 기준값 위에 _build_search_text 를 고쳤을 것이다. 고치기 전에 재려는 습관이 코드 변경 자체보다 많은 것을 건졌다.
질문 메모 세 반전 중 더 파고들고 싶은 것이 있으면 적어주세요.

6. 남은 것 — 도구 세 개

이 과정에서 만들어진 도구들이다. 셋 다 chat LLM 을 부르지 않아 예산과 무관하고, 산출물(artifacts/)만 읽는다.

도구답하는 질문비용
show_search_text.py 무엇이 임베딩되는가? 세 모드의 문자열을 나란히 출력. 버려지는 속성 이름과 "값이 null 이라 숫자가 없음" 경고를 함께 표시 0 (임베더도 안 부름)
rank_candidates.py 그래서 몇 위인가? candidate_pairs.json 은 상위 top_k+5 만 남겨 "16위인지 60위인지" 구분이 안 된다. 전체 순위를 재계산 임베딩만
sweep_recall.py 정책으로 삼을 만한가? 골든 전체에 대해 모드별 recall@k 와 항목별 개선·악화. --show-answers 로 정답 판별을 눈으로 확인 임베딩만 
# 무엇이 임베딩되는지 보기
python scripts/show_search_text.py --grep "charge temperature" --doc target

# 전체 순위 — --augment 로 세 모드 비교
python scripts/rank_candidates.py "충전온도범위(-5~5" --limit 30 \
    --grep "charge temperature" --augment full

# 정책 판단 — 반드시 --show-answers 로 정답 판별부터 확인
python scripts/sweep_recall.py --show-answers
python scripts/sweep_recall.py --modes off,numbers,full --detail
아직 결정되지 않은 것 이 글은 문제 규명까지의 기록이다. _build_search_text 를 실제로 고칠지, 고친다면 numbers 쪽인지 full 쪽인지는 정해지지 않았다. 기준 엑셀이 바뀌어 형제 fact 4개가 사라졌으므로, 이전 측정값은 그대로 쓸 수 없고 재실행 후 sweep_recall 로 다시 재야 한다.
그리고 recall 은 필요조건일 뿐이다 후보에 들어가도 F7 이 차단하면 여전히 ⚪ 대상에 없음 이다. 실제로 이 fact 는 4위로 recall 을 통과하고도 differs_by("온도 범위와 온도 범위 및 C-rate는 서로 다른 정보")로 막혔다. 그 다음 관문은 온톨로지 승격이 열어야 한다.
질문 메모 도구 사용법이나 다음 단계에 대한 질문을 적어주세요.
